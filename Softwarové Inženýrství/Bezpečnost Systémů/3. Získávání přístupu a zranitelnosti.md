- **[[3. Získávání přístupu a zranitelnosti#Od informace k přístupu|Od informace k přístupu]]:** jak se výsledek průzkumu mění v útok.
- **[[3. Získávání přístupu a zranitelnosti#Zranitelnost není jen chyba v kódu|Zranitelnost není jen chyba v kódu]]:** software, konfigurace, identita, procesy a lidé.
- **[[3. Získávání přístupu a zranitelnosti#Sociální inženýrství|Sociální inženýrství]]:** phishing, pretexting a proč je člověk součást systému.

Získání přístupu je bod, kde se z mapy cíle stane reálný průnik. V předchozí fázi víme, jaké služby běží, jaké verze používají, jaké weby existují a kde jsou vstupní body. Teď se ptáme: _který z těchto vstupů dovolí změnit pravidla hry?_

Důležité je, že přístup nemusí znamenat rovnou root shell. Přístup může být platný účet, session cookie, API token, možnost nahrát soubor, možnost spustit SQL dotaz, nebo jen možnost přimět server zavolat interní službu. Bezpečnostní dopad se neměří efektností exploitu, ale tím, co lze s dosaženým oprávněním udělat.

# Od informace k přístupu

Typický útočný řetězec začíná informací. Na serveru běží stará verze CMS. Admin rozhraní je vystavené do internetu. Git repozitář obsahuje starý token. Webová aplikace vrací detailní stack trace. Každá taková informace sama o sobě nemusí být kritická, ale skládá se do cesty.

**Exploit** je konkrétní postup, který zranitelnost využije. Někdy je to binární payload, jindy jen správně tvarovaný HTTP požadavek. Exploit má preconditions: musí sedět verze, konfigurace, architektura, oprávnění a často i síťová dostupnost. Proto veřejný CVE záznam neznamená automaticky kompromitaci. Znamená potenciál, který musí útočník zasadit do konkrétního prostředí.

Z inženýrského pohledu je exploitace zneužití předpokladu, který si vývojář nebo administrátor udělal. Vývojář předpokládal, že parametr bude číslo. Útočník pošle SQL. Administrátor předpokládal, že služba bude přístupná jen interně. Cloud security group ji otevře do internetu. Aplikace předpokládala, že uživatel v UI neuvidí cizí ID. Útočník změní ID v URL.

# Zranitelnost není jen chyba v kódu

Nejviditelnější jsou chyby v kódu: buffer overflow, SQL injection, XSS, path traversal nebo insecure deserialization. Jenže v produkci jsou často stejně ničivé chyby konfigurační.

Krátce k pojmům: **buffer overflow** je zápis mimo vyhrazenou paměť. **SQL injection** je vložení vstupu tak, že změní databázový dotaz. **XSS** je spuštění útočníkova JavaScriptu v prohlížeči oběti. **Path traversal** je obcházení očekávané cesty k souboru, typicky přes `../`, aby aplikace četla něco mimo povolený adresář. **Insecure deserialization** nastane, když aplikace obnoví objekt z nedůvěryhodných dat a tím spustí nečekané chování nebo kód.

Server může mít defaultní heslo. Databáze může poslouchat na veřejné IP. S3 bucket může být public. Debug endpoint může vracet secrets. CI logy mohou obsahovat tokeny. Kubernetes dashboard může běžet bez autentizace. Tohle nejsou sofistikované exploit chainy, ale v praxi jsou extrémně účinné.

**S3 bucket** je cloudové objektové úložiště; chyba bývá v tom, že kontejner s daty je veřejně čitelný. **Debug endpoint** je pomocná adresa pro diagnostiku, která může omylem ukazovat konfiguraci, proměnné prostředí nebo stack trace. **CI logy** jsou výstupy automatického buildu a testů; pokud build vypíše secret, únik se uloží do historie. **Kubernetes dashboard** je webové administrační UI pro cluster a bez autentizace dává útočníkovi přímý pohled do infrastruktury.

Další třída jsou chyby v identitě a oprávněních. Pokud API ověří, že uživatel je přihlášený, ale už neověří, že smí číst konkrétní objekt, vzniká IDOR. Pokud role `support` může měnit e-mail libovolnému uživateli, může si nepřímo převzít účty. Pokud backend věří hlavičce `X-User-Id` od klienta, zaměňuje autentizaci za důvěru ve vstup.

# Hesla, tokeny a identita

Slabé heslo je pořád jedna z nejlevnějších cest do systému. Brute force zkouší mnoho hesel proti jednomu účtu nebo mnoho účtů proti jednomu heslu. Credential stuffing používá hesla uniklá z jiných služeb. Password spraying zkouší jedno běžné heslo proti mnoha účtům, aby se vyhnul lockoutu.

Obrana není jen „delší hesla“. Potřebujeme MFA, detekci anomálního přihlašování, rate limiting, blokování známých uniklých hesel, bezpečné ukládání hashů a správnou správu tokenů. Hesla se nemají ukládat šifrovaně, ale hashovat pomalou funkcí typu Argon2, bcrypt nebo scrypt se solí.

**Token** je často praktičtější cíl než heslo. Když útočník získá session cookie nebo API token, může se vydávat za uživatele bez znalosti hesla. Proto mají tokeny mít omezenou životnost, scope, možnost revokace a bezpečné uložení.

# Sociální inženýrství

Sociální inženýrství není „netechnická část bezpečnosti“. Je to útok na lidské rozhraní systému. Uživatelé, helpdesk, administrátoři a vývojáři jsou součást architektury stejně jako API endpointy.

**Phishing** se snaží přimět oběť k zadání hesla, otevření přílohy nebo schválení MFA push notifikace. Dobrý phishing nevyhrává špatnou gramatikou, ale kontextem. Když přijde zpráva ve správný čas, z domény podobné firemnímu systému a tlačí na urgentní reakci, mnoho lidí klikne.

**Pretexting** znamená vytvoření příběhu. Útočník se vydává za technika, kolegu, banku nebo dodavatele. Neprodává exploit, prodává důvěryhodnou situaci. **Baiting** používá návnadu: USB disk, falešný dokument, nabídku práce nebo slevu.

Obrana je kombinace školení, technických kontrol a procesů. MFA pomáhá, ale push fatigue útoky ukazují, že ani MFA není kouzelný štít. Pomáhá phishing-resistant MFA, například FIDO2/WebAuthn, kde autentizace váže odpověď na konkrétní doménu.

# Responsible disclosure

Pokud zranitelnost najde bezpečnostní výzkumník, měl by postupovat odpovědně. Ověřit dopad jen v nezbytném rozsahu, neexfiltrovat data, nezpůsobit výpadek, kontaktovat vlastníka a dát čas na opravu. V profesionálním prostředí se pracuje s pravidly engagementu, právním rámcem a dokumentací kroků.

Ke státnicím je dobré umět vysvětlit, že bezpečnostní testování bez souhlasu není automaticky legitimní jen proto, že „jsem to myslel dobře“. Bezpečnostní dovednosti jsou dvojího užití. Stejná technika může být pentest i útok podle kontextu, oprávnění a dopadu.

# Co říct u státnic

Získávání přístupu je využití zranitelnosti, slabé identity, chybné konfigurace nebo lidského faktoru k získání nějaké kontroly nad systémem. Nejde jen o remote code execution. Platná cookie, špatně nastavené oprávnění nebo SSRF do interní metadata služby mohou být stejně kritické. Robustní obrana stojí na patch managementu, bezpečné konfiguraci, least privilege, MFA, bezpečném ukládání secretů, monitoringu a procesech pro reakci na incident.
