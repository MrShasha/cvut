Web je obrovská útočná plocha, protože spojuje mnoho technologií: prohlížeč, JavaScript, HTML, cookies, HTTP, load balancery, cache, API, backend, databázi a často i třetí služby. Každý požadavek je malá cesta přes mnoho komponent. Chyba v jedné z nich může otevřít celý systém.

# Web jako systém systémů

Když uživatel klikne na stránku, prohlížeč pošle HTTP požadavek. Server odpoví HTML, JavaScriptem, CSS a daty. Prohlížeč následně spouští JavaScript v bezpečnostním modelu originů. Cookie často nese session identitu. Backend volá databázi nebo interní API. Mezi tím může být CDN, reverse proxy, WAF, cache a TLS terminace.

**Origin** je kombinace schématu, domény a portu, například `https://example.com:443`. Prohlížeč podle originu rozhoduje, co si skripty smějí navzájem číst. **Reverse proxy** sedí před aplikací a přeposílá požadavky na backend. **Cache** ukládá odpovědi pro rychlejší obsluhu dalších požadavků. **TLS terminace** znamená, že šifrované spojení končí na proxy nebo load balanceru a dál do interní sítě může jít jiný spoj.

Útoky často vznikají na hranici, kde se míchají kontexty. Uživatelův text se vloží do HTML jako kód. Vstup z formuláře se vloží do SQL jako část dotazu. URL od uživatele se použije jako adresa pro serverový request. ID z URL se vezme jako autorizační rozhodnutí. Všechny tyto chyby jsou ve skutečnosti stejný typ problému: nedůvěryhodná data dostala význam, který mít neměla.

# Recon webové aplikace

Webový průzkum hledá endpointy, parametry, formuláře, API, technologie, verze, chybové hlášky a soubory, které neměly být veřejné. Google dorking používá vyhledávače k nalezení indexovaných adresářů, config souborů, logů nebo starých PDF s metadaty.

**Endpoint** je konkrétní adresa nebo route aplikace, která něco dělá, například `/api/users/123`. **Parametr** je vstup v URL, těle požadavku nebo hlavičce. **Google dorking** používá speciální vyhledávací operátory, třeba `site:` nebo `filetype:`, aby našel omylem indexované citlivé stránky.

Directory listing, staré backupy, `.git` adresáře, debug endpointy, Swagger UI bez autentizace nebo verbose stack trace jsou typické nálezy. Nejde o exotiku. V produkci se takto často najdou connection stringy a tokeny.

**Directory listing** je výpis souborů v adresáři web serveru. **Backup** soubor může obsahovat starou konfiguraci nebo zdrojáky. **Swagger UI** je dokumentace a testovací rozhraní pro API; bez autentizace může prozradit endpointy nebo je rovnou volat. **Verbose stack trace** je detailní chybový výpis s cestami, knihovnami a někdy i secrety.

# XSS

**Cross-Site Scripting (XSS)** nastane, když útočník dostane svůj JavaScript do stránky, kterou si zobrazí jiný uživatel. Prohlížeč pak kód spustí v kontextu důvěryhodného webu. To je kritické, protože JavaScript v tomto kontextu může číst DOM, posílat požadavky jménem uživatele a někdy krást data.

**Reflected XSS** se odrazí v odpovědi okamžitě. Útočník pošle oběti odkaz s payloadem v URL a server ho bez escapování vrátí ve stránce. **Stored XSS** se uloží na serveru, například do komentáře, a spustí se každému, kdo stránku zobrazí. **DOM XSS** vzniká v prohlížeči, když JavaScript vezme data z URL nebo jiné části DOM a vloží je nebezpečně do stránky.

Kořen problému je kontextové escapování. Jinak se escapuje text v HTML, jinak atribut, jinak JavaScript string, jinak URL. Univerzální „odstraníme špičaté závorky“ není robustní obrana. Správná obrana používá frameworky s auto-escapingem, bezpečné API pro práci s DOM, Content Security Policy, HttpOnly cookies a validaci vstupů podle očekávaného formátu.

# SQL injection

**SQL injection** nastane, když aplikace skládá SQL dotaz jako string a vloží do něj nedůvěryhodný vstup. Útočníkův vstup se pak nestane hodnotou, ale strukturou dotazu.

Naivní dotaz může vypadat takto:

```sql
SELECT * FROM users WHERE email = '$email' AND password = '$password'
```

Pokud útočník do e-mailu vloží text, který ukončí string a přidá vlastní podmínku, změní dotaz. Problém není konkrétní payload. Problém je smíchání dat a kódu.

Robustní řešení jsou **prepared statements**. SQL struktura je předána databázi odděleně od hodnot. Hodnota už nemůže změnit tvar dotazu, i kdyby obsahovala uvozovky nebo SQL klíčová slova.

SQLi může číst data, obcházet login, měnit data, mazat tabulky nebo v některých konfiguracích spouštět příkazy na serveru. Dopad závisí na právech databázového účtu. Proto nestačí parametrizace. Databázový účet aplikace má mít jen nezbytná práva.

# WAF a bezpečnostní hlavičky

**WAF (Web Application Firewall)** filtruje HTTP provoz a hledá útoky jako SQLi nebo XSS. Je to užitečná vrstva, ale ne náhrada bezpečného kódu. WAF může zablokovat známý payload, ale útočník může najít obcházení nebo zranitelnost na jiném endpointu.

Bezpečnostní hlavičky snižují dopad. `Content-Security-Policy` omezuje, odkud se smí spouštět skripty. `HttpOnly` brání JavaScriptu číst cookie. `SameSite` omezuje posílání cookie v cross-site požadavcích. `Secure` posílá cookie jen přes HTTPS.

**Cross-site požadavek** je požadavek vyvolaný z jiné domény, než je cílová aplikace. `SameSite=Lax` nebo `Strict` pomáhá proti CSRF, protože prohlížeč cookie v některých cross-site situacích nepošle. **CSP** XSS chybu neopraví přímo, ale omezuje, odkud může stránka načítat skripty, takže snižuje dopad chyby.

# Co říct u státnic

Webové útoky často vznikají tím, že nedůvěryhodný vstup dostane syntaktický význam. XSS spustí útočníkův kód v prohlížeči oběti. SQL injection spustí útočníkem ovlivněný dotaz v databázi. Obrana je kontextové escapování, bezpečné frameworky, parametrizované dotazy, validace vstupu, minimální práva a bezpečnostní hlavičky. WAF je doplňková vrstva, ne oprava chyby.
