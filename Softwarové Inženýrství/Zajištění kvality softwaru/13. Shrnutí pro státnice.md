# 1. Jádro ZKS na jednu stránku

→ Detaily: [[1. Základy testování softwaru]]

**Testování a základní pojmy:** software testing hledá informace o kvalitě systému a odhaluje defekty. **Error** je lidská chyba nebo omyl, **defect** je chyba v artefaktu a **failure** je pozorované selhání systému za běhu. Test basis je zdroj, ze kterého navrhujeme testy: požadavky, specifikace, model, kód, rizika nebo business pravidla. Test case má vstupy, předpoklady, kroky a očekávaný výsledek; test scenario je uživatelsky nebo procesně orientovaný průchod; test suite je sada testů.

→ Detaily: [[2. V-model, W-model a static testing]]

**V-model, W-model a static testing:** V-model páruje vývojové fáze s odpovídajícími testovacími úrovněmi. W-model posouvá testování doleva: už požadavky, návrh a kód se kontrolují staticky. Static testing se provádí bez spuštění softwaru. Patří sem requirements review, design review, code review, walkthrough, inspection, static code analysis a quality gates. U státnic zdůrazni ekonomiku: chyba v požadavku je levnější odhalená review než až E2E testem nebo produkcí.

→ Detaily: [[3. Model-Based Testing (MBT)]], [[7. Path-based testing, coverage criteria a prioritizace]]

**MBT a modely systému:** Model-Based Testing převádí test basis na model SUT a z něj generuje test requirements, test cases nebo test scenarios. Model může být state machine, workflow graph, UML activity/state diagram, BPMN model, control-flow graph nebo API model. Path-based testing bere test case jako cestu grafem. Minimum jsou node/edge coverage, silnější jsou edge-pair, TDL, prime-path coverage a all-paths coverage. Coverage level je manažerské a rizikové rozhodnutí, ne automatická honba za maximem.

→ Detaily: [[4. Test automation - princip, ekonomika, úrovně a technologie]], [[9. End-to-end testing, Selenium, POM, BDD a Screenplay]]

**Automatizace testů:** automatizace se vyplatí u opakovaných, stabilních, jasně vyhodnotitelných testů. Důležitý je ROI: investice do skriptů, údržby a infrastruktury se musí vracet opakovaným spouštěním. Test automation pyramid doporučuje hodně unit testů, méně integračních/API testů a málo UI/E2E testů. E2E testy ověřují celý tok, ale bývají drahé a flaky. Selenium automatizuje prohlížeč, POM odděluje stránkové objekty od testů, BDD popisuje chování jazykem scénářů a Screenplay modeluje aktéry, schopnosti, úkoly a otázky.

→ Detaily: [[5. Equivalence classes a boundary value analysis]]

**Black-box návrh testů:** equivalence partitioning rozděluje vstupy na třídy, u kterých očekáváme podobné chování. Z každé třídy vybereme reprezentanty. Boundary Value Analysis testuje hodnoty na hranicích a těsně kolem nich, protože právě tam často vznikají off-by-one chyby, špatné nerovnosti nebo špatně pochopené limity. Rozlišuj validní, technicky nevalidní a businessově nevalidní třídy.

→ Detaily: [[6. Combinatorial Interaction Testing, pairwise a N-way]]

**Optimalizace kombinací:** exhaustive testing vstupních kombinací rychle exploduje. CIT testuje interakce určité síly. Pairwise/2-way pokryje každou dvojici hodnot každých dvou parametrů alespoň jednou. N-way zobecňuje na trojice, čtveřice atd. Uniform strength používá stejnou sílu pro všechny parametry, mixed-strength posiluje coverage jen pro rizikové skupiny. Constraints vyřazují nemožné kombinace nebo slouží jako základ negativních testů.

Historické otázky mluví také o **ortogonálních polích** a **latinských čtvercích**. Ortogonální pole je tabulka testů, kde se kombinace hodnot mezi vybranými sloupci vyskytují rovnoměrně. Latinský čtverec je uspořádání symbolů do čtverce tak, že každý symbol je právě jednou v každém řádku a sloupci. V testování jsou to konstrukce pro systematické a vyvážené pokrytí kombinací faktorů.

→ Detaily: [[8. Exploratory testing, MCDC a Elementary Comparison Test]]

**Exploratory testing, MC/DC a ECT:** exploratory testing kombinuje učení, návrh testů, provádění a vyhodnocování během jedné aktivity. Hodí se u slabé dokumentace, nového systému nebo UI, ale hůř dokazuje coverage. MC/DC vyžaduje, aby každá jednoduchá podmínka nezávisle ovlivnila výsledek decision. Pro `n` podmínek se často snažíme o přibližně `n + 1` testů místo `2^n`. ECT skládá lokální test situations pro decision points do celkových cest workflowem.

→ Detaily: [[10. Static code analysis a quality gates]], [[12. Symbolic a concolic execution (doplňkově)]]

**Static analysis a formálnější techniky:** static code analysis pracuje nad zdrojovým kódem nebo binárkou bez běhu programu. Používá AST, CFG a data-flow analysis k hledání chyb, bezpečnostních problémů, dead code, špatných vzorů nebo metrik. Quality gate je automatická podmínka v CI/CD, například maximální počet kritických findings nebo minimální coverage. Symbolic execution pracuje se symbolickými vstupy, sbírá path conditions a solverem generuje vstupy pro nové cesty. Concolic testing kombinuje konkrétní běh a symbolickou analýzu.

→ Detaily: [[11. QA, defect management a širší pohled na kvalitu]]

**QA, defect management a kvalita:** QA je širší procesní rámec než testování. Testing hledá informace o produktu, QA nastavuje procesy, standardy, reviews, metriky a průběžné zlepšování. Defect management zajišťuje, že se nalezená chyba neztratí: New → Analyzed → Assigned → Fixed → Retest → Closed. Kvalita má funkční i strukturální stránku a zahrnuje reliability, performance, usability, security, maintainability, compatibility i quality in use.

# 3. Odpovědi na historické otázky

## [ZKS/TVS] [Bureš/Herout/Průša] — Kategorizace softwarových chyb

**Padalo:** definice SW chyby, kategorizace, rozdíl error/defect/failure, praktické příklady.

**Odpověď:** začni řetězcem **error → defect → failure**. Error je lidský omyl, defect je chyba ve specifikaci, návrhu, kódu, konfiguraci nebo datech a failure je pozorované selhání při běhu. Kategorizovat lze podle původu: requirements defects, design defects, coding defects, interface defects, data defects, configuration defects, performance defects, security defects, usability defects. Lze kategorizovat i podle závažnosti, priority, reprodukovatelnosti a fáze vzniku. Důležité je neuvíznout jen u „bug v kódu“; požadavkový defekt může být horší než syntaktická chyba.

→ Látka: [[1. Základy testování softwaru#Error, defect, failure|Error, defect, failure]], [[11. QA, defect management a širší pohled na kvalitu#Defect management|Defect management]], [[11. QA, defect management a širší pohled na kvalitu#Software quality|Software quality]]

## [TVS] [Průša] — Black-box a white-box testing

**Padalo:** testování bílé a černé schránky, příklad na merge sort, u white-boxu zaměření na invariant po sloučení.

**Odpověď:** **black-box testing** navrhuje testy z požadavků a rozhraní bez znalosti interní implementace. Typické techniky jsou equivalence partitioning, boundary value analysis, decision tables, state transition testing a use-case/scenario testing. **White-box testing** používá znalost kódu nebo struktury: statement, branch/decision, condition, MC/DC, path coverage, data-flow testing. U merge sortu může white-box test cílit na invariant merge kroku: výstupní prefix je seřazený a obsahuje přesně prvky z odpovídajících prefixů vstupních částí.

→ Látka: [[5. Equivalence classes a boundary value analysis]], [[7. Path-based testing, coverage criteria a prioritizace]], [[8. Exploratory testing, MCDC a Elementary Comparison Test#MC/DC|MC/DC]]

## [TVS] [Herout] — Test oracle, boundary values, pozitivní a negativní testy

**Padalo:** co je orákulum, testování hraničních podmínek, pozitivní a negativní testy.

**Odpověď:** **Test oracle** je mechanismus, který rozhodne, zda test prošel nebo selhal. Může to být explicitní expected result, specifikace, referenční implementace, metamorfní relace, databázový stav nebo ruční posouzení. Boundary Value Analysis vybírá hodnoty na hranici tříd a těsně kolem ní. Pozitivní test ověřuje validní scénář, negativní test ověřuje, že systém bezpečně a správně odmítne nevalidní vstup. U negativních testů řekni, zda jde o technicky nevalidní vstup, businessově zakázanou kombinaci nebo bezpečnostní zneužití.

## [ZKS/TVS] [Bureš/Herout] — Optimalizace testovacích sad, pairwise, ortogonální pole a latinské čtverce

**Padalo:** optimalizace testů, faktory a úrovně, pairwise testing, ortogonální pole, latinské čtverce, párově ortogonální latinské čtverce.

**Odpověď:** nejprve vysvětli problém: pokud má systém mnoho parametrů a každý několik hodnot, exhaustive testing má součin počtů hodnot a rychle se stane nepraktickým. Parametr se v experimentálním návrhu často nazývá **faktor** a jeho možné hodnoty **úrovně**. **Pairwise testing** vybírá testy tak, aby každá dvojice hodnot každých dvou faktorů byla pokryta alespoň jednou. **Ortogonální pole** je tabulka, kde jsou kombinace hodnot mezi vybranými sloupci vyvážené. **Latinský čtverec** pomáhá systematicky rozložit hodnoty tak, aby se každý symbol objevil jednou v každém řádku a sloupci; párově ortogonální latinské čtverce dávají vyvážené dvojice. Expected result obvykle není další běžný faktor, který by se volně kombinoval; je to orákulum odvozené z konkrétní kombinace vstupů.

## [ZKS] [Bureš] — Generování testů z modelu, coverage levels a MC/DC

**Padalo:** model aplikace jako graf, kombinace vstupních dat, úrovně testovacího pokrytí, pairwise testing, MCC, MC/DC, CC a DC.

**Odpověď:** model aplikace může být graf: uzly jsou stavy, akce nebo decision points, hrany jsou přechody. Test case odpovídá cestě od startu do konce. Coverage levels určují, jak silně model pokrýváme: node coverage, edge coverage, edge-pair/TDL=2, prime-path coverage a all-paths coverage. U rozhodovací logiky rozliš **CC (Condition Coverage)**, kdy každá jednoduchá podmínka nabude true/false, **DC (Decision Coverage)**, kdy celé rozhodnutí nabude true/false, **MCC (Multiple Condition Coverage)**, kdy se testují všechny kombinace podmínek, a **MC/DC**, kdy každá podmínka nezávisle ovlivní výsledek. Pairwise řeší kombinace vstupních dat napříč faktory.

## [TVS] [Rogalewicz] — Statická vs. dynamická analýza a data-flow

**Padalo:** statická a dynamická analýza, analýza datových cest.

**Odpověď:** **statická analýza** zkoumá artefakt bez spuštění programu. Může analyzovat AST, control-flow graph a data-flow. **Dynamická analýza** sleduje chování při běhu: test execution, profiling, runtime monitoring, sanitizery nebo instrumentace. Data-flow analysis sleduje, kde se hodnota definuje, kudy teče a kde se používá. Typické otázky: definice-use páry, nepoužitá proměnná, použití neinicializované hodnoty, null dereference, tainted input. U státnic řekni trade-off: statická analýza může najít chyby dřív a levněji, ale má false positives; dynamická analýza dává konkrétní běhový důkaz, ale pokrývá jen provedené cesty.

## [TVS] [Rogalewicz] — Formální specifikace, automatické dokazování a model checking

**Padalo:** formální specifikace programu, verifikace automatickým dokazováním, model checking, CTL* a běhové formule.

**Odpověď:** formální specifikace přesně popisuje požadované vlastnosti systému matematickým jazykem, například invarianty, pre/postconditions nebo temporální formule. **Automatické dokazování** převádí ověření vlastnosti na logický důkaz nebo satisfiability problém. **Model checking** prochází stavový prostor modelu a ověřuje, zda splňuje vlastnost vyjádřenou temporální logikou. CTL* je temporální logika kombinující větvení času a lineární vlastnosti cest. Prakticky zmiň riziko state explosion a vztah k symbolickému/concolic testování: solver umí generovat vstupy pro cesty, ale úplná verifikace většího systému je náročná.

# 4. Tipy z historických zkušeností

- **Začni definicemi.** U ZKS se často doptávali na přesné pojmy: faktor, úroveň, oracle, defect, coverage, model, rozhodnutí.
- **Kombinační testování si připrav na příkladě.** Nejrychlejší odpověď je malá tabulka parametrů a vysvětlení, proč exhaustive testing exploduje a pairwise ji zmenší.
- **Bureš chtěl formálnější definice.** U MBT a coverage si připrav větu s grafem `G = (N, E)`, cestou a coverage itemy.
- **Herout chtěl profesionální formulace.** Nestačí „ono to nějak vyjde“; u oracle, boundary a negativních testů mluv přesně.
- **Rogalewicz může jít mimo běžné testování do verifikace.** Připrav si rozdíl static/dynamic, data-flow, symbolic execution, solver, model checking a state explosion.
- **Latinské čtverce a ortogonální pole ber jako historickou specialitu.** Současné zápisky víc používají CIT/pairwise/N-way, ale starší komise se ptaly právě na tyto konstrukce.
- **Black-box a white-box propojuj s příklady.** Black-box: EC/BVA/oracle. White-box: coverage, invariants, control/data-flow.
- **U každé techniky řekni náklady a rizika.** ZKS není jen seznam metod; jde o rozhodnutí, kdy se metoda ekonomicky a rizikově vyplatí.
