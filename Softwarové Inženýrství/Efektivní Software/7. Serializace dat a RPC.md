# Co je serializace

**Serializace** převádí objekt nebo strukturu v paměti na sekvenci bajtů.

**Deserializace** převádí bajty zpět na objekt nebo strukturu.

```text
object in memory
    -> serialize
bytes
    -> transport / file / broker
bytes
    -> deserialize
object in another process
```

Serializace je potřeba vždy, když data opouštějí aktuální proces:

- síťová komunikace;
- REST API;
- gRPC;
- message broker;
- ukládání do souboru;
- databáze;
- IPC;
- logování;
- cache snapshoty;
- komunikace mezi různými jazyky.

## Data v paměti nejsou totéž co data na síti

Objekt v paměti může obsahovat:

- pointery;
- padding kvůli zarovnání;
- object header;
- runtime metadata;
- reference na jiné objekty;
- interní reprezentaci stringů;
- endianitu a velikost typů závislou na platformě.

Tohle nemůžeš jen tak poslat přes síť. Síť potřebuje stabilní formát bajtů, kterému rozumí obě strany.

# Proč serializace ovlivňuje výkon

Výkon serializace není jen "jak rychle knihovna převede objekt na JSON".

## CPU cost

Textové formáty musí parsovat znaky:

```json
{ "age": 12345 }
```

Číslo `12345` je v JSONu text. Parser musí znaky načíst, validovat a převést na integer.

Binární formát může uložit číslo rovnou jako varint nebo fixed-width hodnotu. To často znamená méně CPU práce.

## Memory allocation

Deserializace často vytváří mnoho objektů:

- stringy;
- pole;
- mapy;
- wrapper objekty;
- dočasné buffery;
- DOM strom u XML/JSON parserů.

Alokace znamenají tlak na allocator a u managed jazyků i na GC.

## Payload size

Menší zpráva znamená:

- méně bajtů přes síť;
- menší tlak na bandwidth;
- menší počet packetů;
- rychlejší kopírování bufferů;
- lepší cache locality při parsování.

Velikost payloadu ale není jediné kritérium. Někdy je menší formát dražší na CPU kvůli kompresi nebo složitému dekódování.

## Compatibility

Formát musí přežít změny:

- přidání pole;
- odebrání pole;
- nový enum value;
- starý klient proti novému serveru;
- nový klient proti starému serveru.

Bez compatibility pravidel se distribuovaný systém rozbije při každém rolling deployi.

# Textové vs binární formáty

| Vlastnost | Textové formáty | Binární formáty |
|---|---|---|
| Příklady | JSON, XML, CSV | Protobuf, Avro, MessagePack, FlatBuffers |
| Čitelnost pro člověka | vysoká | nízká |
| Velikost zprávy | větší | menší |
| Parsing CPU cost | vyšší | nižší |
| Typy | často omezené | přesnější |
| Schema | volitelné nebo externí | často povinné |
| Debug | jednoduchý | potřebuje nástroj/schema |
| Public API | často vhodné | někdy horší ergonomie |
| Internal RPC | často zbytečně drahé | často vhodné |

Textový formát není automaticky špatný. JSON je výborný pro veřejné API, konfiguraci a debug. Binární formát není automaticky dobrý. Pokud nemáš schema disciplínu, nástroje a kompatibilitu, můžeš si jen vyrobit rychlejší chaos.

# JSON a XML

## JSON

JSON je jednoduchý textový formát:

```json
{
  "id": 12345,
  "name": "Jan Novak",
  "active": true
}
```

Výhody:

- čitelný pro člověka;
- obrovský ekosystém;
- přirozený pro web;
- dobrý pro REST API;
- snadný debug přes logy a curl;
- podporovaný prakticky všude.

Nevýhody:

- čísla a datumy se musí parsovat z textu;
- klíče se opakují v každém objektu;
- nemá nativní `datetime`, `decimal`, binary blob;
- velký payload proti binárním formátům;
- parsing často alokuje;
- schema není povinné.

Performance problém JSONu:

```json
[
  { "id": 1, "name": "A" },
  { "id": 2, "name": "B" },
  { "id": 3, "name": "C" }
]
```

Stringy `"id"` a `"name"` se opakují pro každý záznam. Binární schema formát pošle field numbers místo názvů polí.

## Streaming JSON parsing

JSON nemusíš vždy načíst celý do DOM stromu. Streaming parser čte tokeny postupně:

```text
START_OBJECT
FIELD_NAME "id"
VALUE_NUMBER 123
FIELD_NAME "name"
VALUE_STRING "Jan"
END_OBJECT
```

To snižuje memory overhead, ale API je složitější. Hodí se pro velké soubory a streamy.

## XML

XML je textový formát se značkami:

```xml
<person id="12345">
  <name>Jan Novak</name>
  <active>true</active>
</person>
```

Výhody:

- XSD schema a validace;
- namespaces;
- atributy;
- mixed content;
- historicky silný v enterprise integracích;
- dobrý pro dokumentové formáty.

Nevýhody:

- velmi verbose;
- tagy se opakují;
- DOM parsing může vytvořit velký objektový strom;
- složitější bezpečnostní povrch;
- většinou horší volba pro high-throughput RPC.

## XML security poznámka

U XML parserů je nutné hlídat:

- XXE útoky;
- entity expansion;
- načítání externích entit;
- obří dokumenty;
- hlubokou rekurzi.

Bezpečné defaulty parseru jsou důležitější než elegance formátu.

# Binární formáty

## Protocol Buffers

Protocol Buffers používá schema:

```protobuf
message Person {
  int64 id = 1;
  string name = 2;
  bool active = 3;
}
```

Field numbers jsou součást binárního formátu. Neodesílá se string `"name"`, ale číslo pole `2`.

Výhody:

- malý payload;
- rychlé parsování;
- generovaný kód;
- dobrá podpora jazyků;
- dobrá schema evolution;
- standardní volba pro gRPC.

Nevýhody:

- není čitelný bez schema;
- potřebuje code generation;
- změny field numbers jsou nebezpečné;
- není ideální pro ad-hoc dotazy a ruční debug.

## Field numbers

Ve Protobufu je důležité číslo pole, ne jeho název.

```protobuf
string name = 2;
```

Přejmenování `name` v kódu může být kompatibilní, pokud zůstane field number `2`.

Změna field number je breaking change, protože stará strana bude data číst jako jiné pole.

## Varint

Malá čísla se ukládají do méně bajtů.

```text
1        -> 1 byte
127      -> 1 byte
128      -> 2 bytes
large int -> more bytes
```

To snižuje payload u běžných malých hodnot, ale dekódování varintů stojí nějaký CPU čas.

## Reserved fields

Když pole odstraníš, jeho number už nepoužívej znovu.

```protobuf
message Person {
  reserved 4, 7;
  reserved "old_name";
}
```

Jinak staré zprávy mohou být novým kódem interpretovány jako úplně jiné pole.

## Avro

Avro je silný hlavně ve streamingu a data platformách.

Vlastnosti:

- schema je JSON dokument;
- data jsou binární;
- schema může být přiloženo nebo uloženo ve schema registry;
- často se používá s Kafka, Hadoop, Spark;
- dobře řeší schema evolution v event streamingu.

Avro dává smysl, když:

- máš eventy v Kafka;
- chceš schema registry;
- data čtou různé systémy;
- nechceš všude generovat stejný kód jako u Protobufu.

## MessagePack

MessagePack je binární formát podobný JSON modelu.

Výhody:

- menší než JSON;
- nepotřebuje pevné schema;
- jednoduchý model dat.

Nevýhody:

- bez schema má slabší compatibility disciplínu;
- méně explicitní kontrakt;
- pro RPC často prohraje s Protobuf/gRPC toolingem.

## FlatBuffers a Cap'n Proto

FlatBuffers a Cap'n Proto jsou navržené tak, aby šlo číst data přímo z bufferu bez plné materializace objektů.

Motivace:

- nízká latency;
- méně alokací;
- čtení jen části zprávy;
- IPC a game/real-time systémy.

Výhody:

- lazy access;
- méně kopírování;
- dobré pro read-heavy zprávy;
- mohou omezit deserializační overhead.

Nevýhody:

- složitější API;
- přísnější layout;
- horší ergonomie než JSON/Protobuf;
- zero-copy neznamená nulový cost pro validaci, bounds checks a cache misses.

# Schema evolution a compatibility

Distribuovaný systém se nenasazuje najednou. Nějakou dobu běží starý klient s novým serverem nebo nový klient se starým serverem.

## Backward compatibility

Nový reader umí přečíst stará data.

```text
old writer -> new reader
```

Příklad: přidáš nové volitelné pole a nový reader stále chápe staré zprávy, kde pole chybí.

## Forward compatibility

Starý reader umí přečíst nová data.

```text
new writer -> old reader
```

Příklad: starý klient ignoruje unknown fields, která přidal nový server.

## Full compatibility

Backward i forward zároveň.

To je důležité u event streamů, dlouho uložených dat a rolling deployů.

## Breaking changes

Typické breaking changes:

- změna významu existujícího pole;
- změna field number v Protobufu;
- změna typu pole nekompatibilním způsobem;
- odstranění pole, které někdo považuje za povinné;
- přejmenování hodnot enumu bez kompatibilní mapy;
- použití starého field number pro nové pole;
- změna jednotek bez nového pole, například ms -> seconds.

## Optional vs required fields

Required fields jsou nebezpečné v distribuovaných systémech. Jakmile pole vyžaduješ, starší producenti zpráv mohou začít padat.

Lepší pattern:

- pole přidávej jako optional;
- definuj default hodnotu;
- validuj na hranici systému;
- required invariant drž v business logice, ne v wire formátu.

## Unknown fields a enum evolution

Parser by měl umět:

- ignorovat unknown fields;
- zachovat unknown fields, pokud formát podporuje round-trip;
- přežít unknown enum value;
- logovat nečekané hodnoty bez pádu celého systému.

# RPC

RPC znamená Remote Procedure Call: voláš funkci, která běží v jiném procesu nebo na jiném stroji.

```text
client stub
    -> serialize request
    -> network
    -> server handler
    -> serialize response
    -> network
    -> client
```

## Transparentnost je nebezpečná

RPC vypadá jako lokální volání:

```cpp
user = userService.getUser(id);
```

Ale chová se jako distribuovaný systém:

- síť může selhat;
- request může timeoutnout;
- server může odpovědět dvakrát;
- odpověď může přijít pozdě;
- retry může vytvořit duplicitu;
- latency je o řády vyšší než lokální volání;
- payload se musí serializovat a deserializovat.

Nikdy neber RPC jako obyčejné volání funkce. Je to síťová operace s chybami, timeouty a verzemi protokolu.

## CORBA jako historická poznámka

CORBA se snažila dělat distribuované objekty transparentní a jazykově nezávislé. Problém byl v komplexitě, vendor lock-inu, těžkém toolingu a složitém debugování.

Poučení pro moderní systémy: transparentní remote object abstraction často skrývá nejdůležitější věc, tedy že volání jde přes síť.

# REST a gRPC

## REST/JSON

REST v praxi často znamená HTTP endpointy a JSON payload.

Výhody:

- jednoduchý debug;
- funguje s browserem;
- curl/Postman/logy stačí na mnoho problémů;
- dobré pro public API;
- široký ekosystém;
- HTTP caching, status codes, proxies.

Nevýhody:

- textový payload;
- větší zprávy;
- často over-fetching nebo under-fetching;
- slabší kontrakt, pokud se nepoužívá OpenAPI/JSON Schema;
- těžší streaming;
- N+1 request pattern.

## gRPC

gRPC typicky používá Protobuf a HTTP/2.

Výhody:

- striktní schema;
- generované klienty a servery;
- menší payload;
- rychlé interní RPC;
- streaming;
- deadline/timeout model;
- dobré pro polyglot microservices.

Nevýhody:

- horší ruční debug než JSON;
- potřebuje tooling;
- browser podpora je složitější;
- schema změny vyžadují disciplínu;
- load balancery/proxy musí dobře podporovat HTTP/2.

## Typy gRPC komunikace

- **Unary**: jeden request, jedna response.
- **Server streaming**: jeden request, stream odpovědí.
- **Client streaming**: stream requestů, jedna response.
- **Bidirectional streaming**: stream na obou stranách.

Streaming je užitečný, když nechceš držet obří payload v paměti nebo chceš průběžné výsledky.

## HTTP/1.1 vs HTTP/2 intuition

HTTP/1.1:

- request/response model;
- omezený počet paralelních spojení;
- head-of-line blocking na úrovni requestů přes jedno spojení;
- typicky horší pro mnoho malých RPC.

HTTP/2:

- multiplexing více streamů přes jedno TCP spojení;
- binární framing;
- header compression;
- vhodnější pro gRPC.

Pozor: HTTP/2 řeší aplikační multiplexing, ale pořád běží často nad TCP. TCP head-of-line blocking na transportní vrstvě může stále existovat při packet loss.

# Payload size, compression a fetching

## Co ovlivňuje velikost payloadu

- názvy polí;
- opakování metadat;
- textové vs binární kódování;
- počet objektů;
- nested struktury;
- optional fields;
- null hodnoty;
- binary data v base64;
- komprese.

## Base64 overhead

Base64 zvětší binární data zhruba o 33 %.

```text
3 bytes binary -> 4 bytes base64 text
```

Pokud posíláš obrázky, soubory nebo velké binární bloky uvnitř JSONu, platíš větší payload a další CPU za encoding/decoding.

## Over-fetching

Over-fetching znamená, že server pošle víc dat, než klient potřebuje.

```text
client potřebuje: id, name
server posílá: id, name, profile, settings, history, permissions
```

Problém:

- větší payload;
- více parsing CPU;
- více alokací;
- horší cache locality.

## Under-fetching

Under-fetching znamená, že klient musí udělat více requestů, protože jeden endpoint nevrací dost dat.

```text
GET /users/1
GET /users/1/orders
GET /orders/10/items
GET /items/99
```

To zvyšuje latency přes N+1 RPC pattern.

## Compression

Komprese pomáhá, když:

- payload je velký;
- data jsou opakující se;
- síť je bottleneck;
- latency navíc za CPU je menší než úspora přenosu.

Komprese škodí, když:

- payload je malý;
- CPU je bottleneck;
- data už jsou komprimovaná;
- přidá tail latency;
- komprimuješ každý malý RPC zvlášť.

Běžné algoritmy:

| Algoritmus | Vlastnost |
|---|---|
| gzip | dobrá kompatibilita, pomalejší |
| zstd | dobrý poměr rychlost/komprese |
| lz4 | velmi rychlý, menší kompresní poměr |
| brotli | často dobrý pro web assets |

# Allocation overhead a generated serializers

## Object materialization

Object materialization znamená, že parser vytvoří plný objektový model zprávy.

To je pohodlné:

```cpp
Person p = parse(buffer);
use(p.name);
```

Ale může to být drahé, pokud potřebuješ jen jedno pole z velké zprávy.

Náklady:

- alokace objektů;
- kopírování stringů;
- dočasné buffery;
- GC pressure;
- cache misses při procházení objektového grafu.

## Reflection-based serialization

Reflection-based serializer zjišťuje strukturu objektu za runtime.

Výhody:

- jednoduché použití;
- méně generovaného kódu;
- flexibilita.

Nevýhody:

- pomalejší lookup polí;
- více runtime metadat;
- horší optimalizace;
- často více alokací.

## Generated serializers

Generated serializer vznikne ze schema nebo z build-time analýzy.

Výhody:

- rychlejší přístup k polím;
- méně reflection;
- lepší typová kontrola;
- méně alokací;
- jasný kontrakt.

Nevýhody:

- build krok navíc;
- generované soubory;
- potřeba řešit verze schema.

## Pooling

Pooling bufferů může snížit alokace, ale není automatická výhra.

Rizika:

- složitější ownership;
- únik starých dat;
- contention na poolu;
- držení velkých bufferů v paměti;
- bugy při reuse po předání jinému vláknu.

Pooling používej tam, kde měření ukáže alokační bottleneck.

# Zero-copy a buffer-oriented parsing

Zero-copy znamená, že data zbytečně nekopíruješ do nových objektů.

## Buffer-oriented parsing

Místo vytvoření plného objektu můžeš číst přímo z bufferu:

```text
buffer bytes
    -> read field offset
    -> return view/slice
    -> parse only what is needed
```

To snižuje:

- alokace;
- kopírování;
- práci na nepotřebných polích.

## Lazy / partial parsing

Lazy parsing znamená, že pole se parsuje až ve chvíli, kdy ho opravdu potřebuješ.

Hodí se pro:

- velké zprávy;
- read-mostly přístup;
- filtrování podle několika polí;
- systémy, kde většinu payloadu jen přeposíláš.

## Limity zero-copy

Zero-copy má limity:

- buffer musí žít dost dlouho;
- data musí být zarovnaná nebo čitelná bezpečně;
- musíš řešit endianitu;
- parser musí validovat hranice;
- přímé čtení může mít horší locality než materializovaný hot objekt;
- u síťových stacků stejně často existují nějaké kopie mezi kernel/user space.

Zero-copy není magická nula. Je to snaha odstranit zbytečné kopírování a materializaci.

# Batching, streaming a backpressure

## Batching

Batching spojí více malých operací do jedné větší zprávy.

```text
1000x RPC po 1 položce
    -> 1x RPC s 1000 položkami
```

Výhody:

- méně round tripů;
- méně per-request overheadu;
- lepší throughput;
- lepší komprese.

Nevýhody:

- větší jednotlivý payload;
- vyšší latency pro první položku;
- složitější error handling;
- riziko velkých alokací.

## Streaming

Streaming posílá data postupně.

Hodí se, když:

- payload je velký;
- výsledky vznikají postupně;
- nechceš držet celou odpověď v paměti;
- potřebuješ flow control.

## Backpressure

Backpressure znamená, že příjemce umí zpomalit producenta.

Bez backpressure:

```text
producer posílá rychleji, než consumer parsuje
fronta roste
paměť roste
latency roste
systém padá
```

Řešení:

- bounded queues;
- flow control;
- request credits;
- streaming s potvrzováním;
- limity velikosti zpráv;
- timeouty a cancellation.

# Security considerations

Deserializace je bezpečnostně citlivá hranice. Parser čte data, která mohou přijít od útočníka.

## Deserialization attacks

Nebezpečné jsou hlavně formáty, které umí rekonstruovat libovolné objekty a spouštět kód přes konstruktory, hooks nebo gadget chains.

Rizikové příklady:

- Java native serialization (`ObjectInputStream`);
- Python `pickle`;
- starý .NET `BinaryFormatter`;
- formáty, které dovolují načíst libovolný typ podle jména z payloadu.

Pravidlo: nedeserializuj nedůvěryhodná data nativní objektovou serializací.

## Resource limits

Parser musí mít limity:

- maximální velikost zprávy;
- maximální hloubka nesting;
- maximální počet polí/prvků;
- timeout;
- limit alokací;
- limit délky stringů;
- limit počtu unknown fields.

Bez limitů stačí útočníkovi poslat payload, který způsobí obří alokaci, dlouhý parse time nebo stack overflow.

## Validate on boundary

Validuj data na hranici systému:

- schema;
- povinné business invarianty;
- rozsahy hodnot;
- enum values;
- délky stringů;
- počet položek;
- oprávnění volajícího.

Schema validace není totéž co business validace. Schema řekne, že pole je integer. Business validace říká, že věk nemůže být `-50`.

# Praktická volba formátu

| Situace | Dobrá volba | Proč |
|---|---|---|
| Public HTTP API | JSON + OpenAPI | jednoduchý debug, široká kompatibilita |
| Browser client | JSON | nativní podpora ve webu |
| Internal high-throughput RPC | gRPC + Protobuf | schema, menší payload, generated code |
| Kafka/event streaming | Avro/Protobuf + schema registry | evolution a centrální kontrola schema |
| Ultra-low latency IPC | FlatBuffers/Cap'n Proto | lazy/zero-copy přístup |
| Konfigurace | JSON/YAML/TOML | čitelnost pro lidi |
| Dokumenty a legacy enterprise | XML | XSD, namespaces, dokumentový model |
| Ad-hoc binární JSON-like data | MessagePack | menší než JSON bez pevného schema |

Praktické pravidlo:

1. Public API optimalizuj na stabilitu, čitelnost a kompatibilitu.
2. Internal hot path optimalizuj na schema, payload, alokace a p99 latency.
3. Event stream optimalizuj na schema evolution a dlouhou životnost dat.
4. Nikdy nevybírej formát jen podle microbenchmarku.

# Serialization performance checklist

Měř:

- serialization time;
- deserialization time;
- payload size;
- počet alokací;
- GC pressure;
- p50/p95/p99 latency;
- throughput;
- CPU usage;
- compression ratio;
- error rate;
- compatibility při rolling deployi.

Optimalizuj:

- zmenšení payloadu;
- odstranění opakovaných klíčů;
- generated serializers;
- streaming parsing;
- batching;
- snížení object materialization;
- limity parseru;
- compression jen tam, kde se vyplatí.

# Časté chyby

- vybrat JSON pro interní high-throughput RPC bez měření;
- posílat velké binární soubory jako base64 v JSONu;
- nemít limity parseru;
- používat native object serialization pro nedůvěryhodná data;
- změnit Protobuf field number;
- recyklovat odstraněný field number;
- ignorovat unknown enum values;
- dělat N+1 RPC;
- komprimovat každý malý payload;
- používat reflection serializer v hot path bez měření;
- materializovat celý objekt, když potřebuješ jen jedno pole;
- zapomenout, že retry u RPC může operaci provést dvakrát.

# Zkouškové minimum

**Serializace:** převod objektu/struktury na bajty. Deserializace je převod bajtů zpět na objekt.

**Proč ovlivňuje výkon:** stojí CPU, alokace, velikost payloadu, cache locality, síťovou latency a compatibility.

**Textový vs binární formát:** textový je čitelný a snadno debugovatelný, ale větší a dražší na parsing. Binární je menší a rychlejší, ale potřebuje schema/tooling.

**JSON:** dobrý pro REST/public API a debug, horší pro high-throughput kvůli textovému parsingu, opakování klíčů a slabším typům.

**XML:** silný v dokumentech, XSD a legacy enterprise, ale verbose a drahý na parsing.

**Protobuf:** binární schema formát s field numbers, generated code a dobrou schema evolution. Standardní volba pro gRPC.

**Avro:** schema-oriented binární formát často používaný v Kafka/data platformách se schema registry.

**FlatBuffers/Cap'n Proto:** formáty pro lazy/zero-copy čtení z bufferu.

**Backward compatibility:** nový reader umí číst stará data.

**Forward compatibility:** starý reader umí přežít nová data, typicky ignoruje unknown fields.

**RPC:** vzdálené volání přes síť. Není to lokální funkce: řeší timeouty, retry, serializaci, kompatibilitu a partial failures.

**REST vs gRPC:** REST/JSON je jednodušší a vhodný pro public API. gRPC/Protobuf je vhodné pro interní RPC s vyšším výkonem a striktním kontraktem.

**Batching:** spojení více operací do jedné zprávy kvůli snížení round tripů a overheadu.

**Backpressure:** mechanismus, kterým příjemce zpomalí producenta, aby nerostly fronty a paměť.

**Deserialization security:** nikdy nedeserializuj nedůvěryhodná data nativní objektovou serializací; nastav resource limits.

# Mini tahák

```text
serialization:
    object -> bytes

deserialization:
    bytes -> object

JSON:
    readable, public API, bigger, parse CPU

XML:
    schema/docs/legacy, verbose, security pitfalls

Protobuf:
    binary, field numbers, generated code, gRPC

Avro:
    schema registry, Kafka, data pipelines

MessagePack:
    binary JSON-like format

FlatBuffers / Cap'n Proto:
    lazy / zero-copy style reading

compatibility:
    backward = new reads old
    forward  = old survives new

RPC:
    network call, not local call

performance:
    CPU + allocations + payload + p99 + compatibility
```

# Jak navazuje další téma

Další kapitola jde do JVM internals. Serializace s JVM přímo souvisí: parsing vytváří objekty, objekty zatěžují heap, alokace zatěžují TLAB/GC a hot serializační kód ovlivňuje JIT. Bez pochopení JVM paměti a JIT optimalizací nejde dobře vysvětlit, proč některé serializační knihovny v Javě škálují lépe než jiné.
