# Networking mental model

## Co měříme

U síťového výkonu se typicky sleduje:

| Metrika | Co znamená | Typická otázka |
|---|---|---|
| **Latency** | čas od requestu po response | Jak rychle odpovíme jednomu klientovi? |
| **Throughput** | množství dat/requestů za čas | Kolik requestů/s nebo MB/s zvládneme? |
| **Concurrent connections** | počet současně otevřených spojení | Kolik klientů může čekat najednou? |
| **Tail latency** | p95/p99/p999 latency | Jak špatné jsou nejpomalejší requesty? |
| **Utilization** | CPU, memory, network, disk, backend | Co je bottleneck? |

Síťový server bývá často **I/O-bound**: CPU by mohl pracovat, ale request čeká na socket, databázi, disk, remote service nebo timeout.

## Latency vs throughput

Nízká latency neznamená automaticky vysoký throughput.

```text
latency:    jeden request trvá 20 ms
throughput: kolik requestů/s zvládne celý server
```

Když server čeká 20 ms na databázi, jedno vlákno většinu času nic nepočítá. Pro vysoký throughput musíš umět obsloužit mnoho čekajících requestů současně, aniž bys vytvořil neomezený počet drahých OS vláken.

## Sockety, file descriptors a buffery

Socket je endpoint síťové komunikace. V OS je reprezentovaný jako **file descriptor**.

TCP spojení je identifikováno 4-tuple:

```text
source IP, source port, destination IP, destination port
```

U každého spojení typicky existují:

- kernel receive buffer;
- kernel send buffer;
- aplikační input/output buffer;
- stav TCP spojení;
- metadata socketu/file descriptoru;
- případně Java objekty a NIO struktury.

Proto "10 000 spojení" není jen číslo v `for` cyklu. Je to paměť, kernel state, file descriptor limit, timeouty, fronty, buffery a scheduler.

# OSI model a TCP/IP stack

## OSI přehled

OSI model je učebnicový model vrstev. Pro výkon serveru jsou nejdůležitější hlavně vrstvy 4 a 7.

| Vrstva | Příklad | Co řeší |
|---|---|---|
| 7 Application | HTTP, gRPC, WebSocket | request/response, framing, headers, aplikační protokol |
| 6 Presentation | TLS, serializace | šifrování, komprese, formát dat |
| 5 Session | session state | správa relace |
| 4 Transport | TCP, UDP | porty, spolehlivost, pořadí, flow/congestion control |
| 3 Network | IP | adresace a routing |
| 2 Data link | Ethernet, Wi-Fi | rámce, MAC, lokální síť |
| 1 Physical | kabel, rádio, optika | fyzický přenos signálu |

Praktický TCP/IP model je jednodušší:

```text
Application: HTTP/gRPC/TLS
Transport:   TCP/UDP/QUIC
Internet:    IP
Link:        Ethernet/Wi-Fi
```

## TCP vs UDP

| Vlastnost | TCP | UDP |
|---|---|---|
| Spojení | connection-oriented | connectionless |
| Doručení | spolehlivé, potvrzované | bez záruky |
| Pořadí | zachovává pořadí streamu | pořadí negarantuje |
| Řízení toku | ano | ne |
| Congestion control | ano | aplikace si musí řešit sama nebo přes vyšší protokol |
| Typické použití | HTTP/1.1, HTTP/2, databáze, SSH | DNS, realtime audio/video, hry, QUIC jako vyšší protokol |

TCP poskytuje spolehlivý byte stream. To je pohodlné, ale má cenu: handshake, ACK, retransmise, congestion control a head-of-line blocking.

UDP je jednodušší datagramový protokol. Nezaručuje doručení ani pořadí, takže se hodí tam, kde aplikace nebo vyšší protokol umí ztráty řešit.

## TCP performance intuice

TCP spojení typicky začíná 3-way handshake:

```text
SYN -> SYN/ACK -> ACK
```

U TLS se přidává další handshake. U krátkých requestů může být setup významná část latency, proto existuje keep-alive a connection pooling.

TCP head-of-line blocking znamená: pokud se ztratí část byte streamu, pozdější data nemohou být předána aplikaci, dokud se mezera nedoplní.

HTTP/2 multiplexuje více streamů nad jedním TCP spojením, ale pořád sedí nad jedním TCP streamem. HTTP/3 používá QUIC nad UDP, aby část těchto problémů řešil jinak.

# Blocking I/O a C10K problém

## Blocking I/O

Blocking read:

```c
int n = read(fd, buffer, size);
```

Pokud nejsou data připravena, vlákno stojí. CPU může běžet jiné vlákno, ale tohle konkrétní vlákno drží stack, runtime stav a scheduler s ním musí počítat.

V Javě klasický blocking server vypadá jednoduše:

```java
ServerSocket server = new ServerSocket(8080);

while (true) {
    Socket socket = server.accept(); // blocks
    new Thread(() -> handle(socket)).start();
}
```

To je čitelné, ale škáluje špatně, pokud počet spojení roste.

## Thread-per-connection

Thread-per-connection:

```text
connection 1 -> thread 1
connection 2 -> thread 2
...
connection N -> thread N
```

Výhoda:

- jednoduchý kód;
- přirozený call stack;
- snadné debugování;
- blocking API se dobře čte.

Nevýhody:

- každé OS vlákno má stack;
- context switching roste s počtem vláken;
- scheduler má víc práce;
- mnoho vláken většinu času jen čeká;
- tail latency roste při oversubscription;
- limity OS a JVM se projeví dřív než CPU výkon.

## Thread-per-request a thread pool

Thread pool zlepší situaci tím, že nevytváří nové vlákno pro každý request:

```java
ExecutorService pool = Executors.newFixedThreadPool(200);

while (true) {
    Socket socket = server.accept();
    pool.submit(() -> handle(socket));
}
```

Ale pořád platí: pokud worker čeká na I/O, zabírá OS thread z poolu. Když všechny workery čekají, nové requesty stojí ve frontě.

Thread pool musí být **bounded**:

- omezený počet vláken;
- omezená fronta;
- jasná politika při přetížení;
- timeouty;
- metriky queue length a saturation.

Neomezená fronta pouze schová overload a později vytvoří obrovskou latency nebo OOM.

## C10K problém

**C10K problem** znamená: jak obsloužit 10 000 současných klientů na jednom serveru.

Historicky C10K odhalil, že problém není jen CPU:

- mnoho OS vláken má velký memory overhead;
- context switching je drahý;
- `select()`/`poll()` špatně škálují;
- kernel a file descriptor limity musí být nastavené;
- každé spojení potřebuje buffery;
- backend databáze/služby mohou být bottleneck dřív než web server.

Dnes 10 000 spojení není extrémní číslo, ale princip zůstává. Moderní problém je spíš C100K/C1M, tail latency, backpressure a správné chování při overloadu.

# Non-blocking I/O a readiness notification

## Non-blocking socket

Non-blocking I/O znamená, že operace nečeká, dokud se dá dokončit.

```c
fcntl(fd, F_SETFL, O_NONBLOCK);

int n = read(fd, buffer, size);
if (n == -1 && errno == EAGAIN) {
    // žádná data teď nejsou připravena
}
```

To samo o sobě nestačí. Potřebuješ vědět, kdy má smysl zkusit `read()` nebo `write()` znovu. To řeší **readiness notification**.

## Readiness vs completion

Readiness-based model:

```text
OS říká: fd je pravděpodobně připravený pro read/write
aplikace potom sama zavolá read/write
```

Completion-based model:

```text
aplikace zadá operaci
OS později oznámí: operace je hotová
```

Linux `epoll` je typicky readiness model. Windows IOCP je completion model.

## select

`select()` čeká na aktivitu na sadě file descriptorů.

Nevýhody:

- historický limit velikosti `fd_set` bývá 1024;
- při každém volání se předává sada FD;
- po návratu musí aplikace scanovat FD;
- pro mnoho spojení je to O(n) práce.

## poll

`poll()` odstranil pevný limit `fd_set`, ale pořád musí projít pole sledovaných FD.

```text
10 000 spojení, aktivních 20
poll pořád musí projít velký seznam
```

## epoll

`epoll` drží sledované FD v kernelu:

```c
int epfd = epoll_create1(0);
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event);

while (true) {
    int n = epoll_wait(epfd, events, MAX_EVENTS, timeout);
    for (int i = 0; i < n; i++) {
        handle(events[i]);
    }
}
```

Přesnější formulace než "epoll je O(1)": registrace a interní práce mají svoje náklady, ale `epoll_wait()` vrací hlavně připravené eventy. Aplikace nemusí při každém probuzení scanovat všech 10 000 spojení. Práce v event loopu je typicky úměrná počtu aktivních eventů.

Ekvivalenty:

- Linux: `epoll`;
- BSD/macOS: `kqueue`;
- Windows: IOCP;
- Solaris: event ports.

## Level-triggered vs edge-triggered

| Režim | Jak notifikuje | Výhoda | Riziko |
|---|---|---|---|
| Level-triggered | dokud je FD ready, event se vrací opakovaně | jednodušší, bezpečnější | více notifikací |
| Edge-triggered | event přijde při změně stavu | méně notifikací | musíš číst/psát až do `EAGAIN` |

U edge-triggered režimu je typická chyba přečíst jen část dat. Pokud nepřečteš socket až do `EAGAIN`, další event už nemusí přijít a spojení se zasekne.

# Event-driven server a Reactor pattern

## Event loop

Event loop je smyčka, která čeká na I/O eventy a rychle je zpracuje:

```text
while running:
    events = wait_for_io_events()
    for event in events:
        handle(event)
```

Pravidlo:

```text
event-loop handler nesmí dlouho blokovat
```

Pokud v event loopu zavoláš blocking DB query, blocking HTTP call nebo dlouhý CPU výpočet, stojí všechna spojení obsluhovaná tímto loopem.

## Reactor pattern

Reactor pattern rozděluje server na:

- demultiplexer (`epoll_wait`, `Selector.select`);
- event loop;
- handlery pro accept/read/write;
- případně worker pool pro CPU/blocking práci.

```text
socket ready -> event loop -> handler -> krátká práce
                                |
                                +-> worker pool pro blocking/CPU task
```

![[Assets/ESW/java-nio-selector.svg]]

## Threading architektury

| Model | Jak funguje | Výhoda | Nevýhoda |
|---|---|---|---|
| Thread per connection | každé spojení má OS thread | jednoduchý kód | memory + context switch overhead |
| Thread pool per request | omezený počet workerů | kontrola resources | fronty, starvation při blocking I/O |
| Single event loop | jedno vlákno obsluhuje mnoho spojení | nízký overhead | žádné blocking handlery |
| Multi-reactor | více event loopů, často per-core | škálování na více jader | složitější ownership a load balancing |
| Event loop + worker pool | I/O v loopu, práce ve workerech | běžný praktický kompromis | backpressure mezi loopem a workery |
| Virtual threads | mnoho levných JVM threadů | jednoduchý blocking styl | pořád potřebuje limity, neřeší CPU bottleneck |

## Backpressure

Backpressure znamená: když downstream nestíhá, upstream musí zpomalit.

Bez backpressure:

```text
klienti posílají data
server ukládá do front
backend nestíhá
fronty rostou
latence roste
nakonec OOM nebo timeout storm
```

V event loopu se backpressure projevuje hlavně u zápisu. Socket nemusí přijmout všechna data najednou:

```text
write() zapíše jen část response
zbytek musíš uložit do per-connection output bufferu
OP_WRITE registruj jen tehdy, když máš co dopisovat
```

Typická chyba v Java NIO: registrovat `OP_WRITE` pořád. Socket je skoro pořád writable, takže selector se budí v tight loopu a pálí CPU.

# Java IO a Java NIO

## Klasické Java IO

Klasické API:

- `ServerSocket`;
- `Socket`;
- `InputStream`;
- `OutputStream`.

Je blocking a stream-oriented.

```java
try (Socket socket = server.accept()) {
    InputStream in = socket.getInputStream();
    OutputStream out = socket.getOutputStream();
    handle(in, out);
}
```

Výhoda:

- jednoduchý kód;
- přirozený call stack;
- dobré pro malý počet spojení nebo virtual threads.

Nevýhoda:

- platform thread blokuje na I/O;
- pro mnoho spojení potřebuješ mnoho vláken nebo jiný model.

## Java NIO

Java NIO používá:

- **Channel** — zdroj/cíl dat, například `SocketChannel`, `ServerSocketChannel`, `FileChannel`;
- **Buffer** — paměťový prostor pro data, typicky `ByteBuffer`;
- **Selector** — multiplexing mnoha channelů v jednom vlákně;
- **SelectionKey** — registrace channelu v selectoru + interest ops + attachment.

Server skeleton:

```java
Selector selector = Selector.open();

ServerSocketChannel server = ServerSocketChannel.open();
server.configureBlocking(false);
server.bind(new InetSocketAddress(8080));
server.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();
    Iterator<SelectionKey> it = selector.selectedKeys().iterator();

    while (it.hasNext()) {
        SelectionKey key = it.next();
        it.remove();

        if (!key.isValid()) continue;

        if (key.isAcceptable()) {
            accept(selector, server);
        } else if (key.isReadable()) {
            read(key);
        } else if (key.isWritable()) {
            write(key);
        }
    }
}
```

Accept:

```java
static void accept(Selector selector, ServerSocketChannel server) throws IOException {
    SocketChannel client = server.accept();
    client.configureBlocking(false);
    client.register(selector, SelectionKey.OP_READ, new ConnectionState());
}
```

NIO je výkonné, ale ručně psané NIO je chybové. V praxi se často používá Netty, Vert.x, Akka HTTP nebo framework nad NIO.

## SelectionKey

`SelectionKey` obsahuje:

- channel;
- selector;
- interest ops: co chceš sledovat (`OP_ACCEPT`, `OP_READ`, `OP_WRITE`, `OP_CONNECT`);
- ready ops: co je teď připravené;
- attachment: vlastní stav spojení.

Connection state je nutný, protože TCP je stream. Request nemusí přijít celý v jednom `read()`.

# ByteBuffer, direct buffers a zero-copy

## ByteBuffer state

`ByteBuffer` má hlavně:

- capacity;
- position;
- limit;
- mark.

Write mode:

```text
position ukazuje, kam se bude zapisovat
limit = capacity
```

Po zápisu dat zavoláš:

```java
buffer.flip();
```

Read mode:

```text
position = začátek dat
limit = konec zapsaných dat
```

Po přečtení:

- `clear()` — připraví buffer na nový zápis, data nepřemaže, jen resetuje pozice;
- `compact()` — ponechá nepřečtená data a posune je na začátek.

Častá chyba: zapomenout `flip()` nebo použít `clear()` tam, kde ještě zůstala nepřečtená data.

## Heap vs direct ByteBuffer

| Buffer | Kde leží | Výhoda | Nevýhoda |
|---|---|---|---|
| Heap buffer | JVM heap | levná alokace, GC ho vidí přímo | pro native I/O může vyžadovat kopii/pinning |
| Direct buffer | native memory mimo Java heap | vhodný pro OS I/O, méně kopírování | drahá alokace, mimo heap, potřeba pooling |

Direct buffer není automaticky "zadarmo". Pro hot path je špatně:

```java
ByteBuffer.allocateDirect(8192); // v každém requestu
```

Lepší je buffer pooling nebo framework, který pooling řeší.

## Copying a zero-copy

Kopírování dat stojí:

- CPU cykly;
- memory bandwidth;
- cache pollution;
- alokace;
- GC pressure.

Zero-copy intuice: data se nepřelévají přes user-space buffer, pokud to není nutné.

V Javě:

```java
FileChannel file = FileChannel.open(path);
file.transferTo(0, file.size(), socketChannel);
```

`transferTo()` může použít OS mechanismy typu `sendfile`, takže kernel pošle data ze souboru do socketu bez kopírování do Java heapu. Není to univerzální magie: záleží na OS, TLS, typu channelu a konkrétní cestě dat.

# Thread pools a virtual threads

## Thread pools

Thread pool je pořád dobrý nástroj, ale musí mít limity.

Sleduj:

- velikost poolu;
- délku fronty;
- rejection policy;
- průměrný a p99 čas ve frontě;
- počet aktivních workerů;
- timeouty downstream služeb.

Špatně:

```java
Executors.newCachedThreadPool(); // neomezený růst threadů
```

Lépe:

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    50, 200,
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

Konkrétní čísla nejsou univerzální. Musí odpovídat CPU, I/O čekání, backend kapacitě a SLO.

## Virtual threads

Virtual threads jsou lightweight thready spravované JVM. Finálně byly zavedené v Java 21. JVM plánuje mnoho virtual threads na menší počet platform/carrier threads.

Model:

```text
virtual thread běží na carrier threadu
blocking I/O -> virtual thread se unmountne
carrier thread může běžet jiný virtual thread
I/O dokončeno -> virtual thread se znovu naplánuje
```

Kód může vypadat blocking:

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> handleRequest(request));
}
```

Výhody:

- jednoduchý thread-per-request styl;
- dobré stack traces;
- méně callback/reactive complexity;
- vysoká škálovatelnost pro I/O-bound workloads;
- existující blocking API se často používá beze změn.

Limity:

- virtual threads nezrychlí CPU-bound práci;
- pořád potřebuješ limity na počet requestů, DB connections a downstream calls;
- neomezený fan-out může zabít backend;
- thread-local hodnoty mohou vytvořit velký memory footprint;
- native/FFM blokování může pořád pinovat carrier thread;
- u starších JDK před změnami v Java 24 mohl dlouhý blocking uvnitř `synchronized` pinovat carrier thread.

Praktická formulace pro rok 2026: virtual threads jsou výborné pro jednoduchý I/O-bound server, ale nejsou náhrada za backpressure, timeouts, connection pooling a měření.

## Virtual threads vs NIO

| Kritérium | NIO/event loop | Virtual threads |
|---|---|---|
| Styl kódu | callback/state machine | běžný blocking call stack |
| Škálování čekání | velmi dobré | velmi dobré pro podporované blocking I/O |
| CPU-bound práce | musí pryč z event loopu | omezená počtem carrier/CPU |
| Debugging | složitější async stack | přirozenější stack |
| Backpressure | explicitní | pořád nutná |
| Nejlepší použití | high-performance networking framework | aplikační servery s blocking stylem |

# Performance bottlenecks síťových serverů

## CPU bottlenecks

CPU může pálit:

- TLS handshake a šifrování;
- parsing HTTP/JSON;
- serializaci/deserializaci;
- kompresi;
- kopírování bufferů;
- logging;
- business logiku;
- garbage collection.

## Memory bottlenecks

Paměť může mizet v:

- per-connection bufferech;
- request/response objektech;
- frontách;
- thread stacks;
- direct bufferech;
- TLS state;
- cache a session datech.

Počet spojení krát velikost bufferu je nebezpečné násobení:

```text
100 000 connections * 64 KB buffer = 6.4 GB
```

Proto buffer management rozhoduje.

## Kernel/network bottlenecks

Sleduj:

- file descriptor limit;
- accept backlog;
- SYN backlog;
- socket receive/send buffers;
- packet drops;
- retransmissions;
- network interface saturation;
- ephemeral port exhaustion u klientské strany;
- `TIME_WAIT` chování;
- load balancer timeouty.

## Backend bottlenecks

Web server může zvládnout 100 000 spojení, ale databáze nemusí zvládnout 100 000 paralelních dotazů.

Omezení:

- DB connection pool;
- rate limiting;
- bulkheads;
- bounded queues;
- circuit breakers;
- timeouts;
- retry budget.

Retry bez limitu zhoršuje outage:

```text
backend zpomalí
klienti retryují
load se násobí
backend padá víc
tail latency exploduje
```

## Monitoring

Měř:

- active connections;
- requests/s;
- p50/p95/p99 latency;
- error rate;
- timeout rate;

# Framework intuition

## Classic Servlet model

Klasický servlet container historicky používal thread pool: request dostane worker thread, ten běží přes servlet/filter chain a typicky blokuje na I/O.

To je jednoduché, ale pool musí být správně dimenzovaný a bounded.

## Netty

Netty je event-driven networking framework nad NIO/native transports.

Typický model:

- boss event loop přijímá spojení;
- worker event loops obsluhují read/write;
- pipeline handlerů zpracovává data;
- blocking práci musíš přesunout mimo event loop.

Netty je rychlý, ale vyžaduje disciplínu: nesmíš blokovat event loop a musíš správně pracovat s buffery/backpressure.

## Reactive frameworks

Reactive model explicitně reprezentuje asynchronní tok dat a backpressure. Hodí se pro hodně I/O a streaming, ale zvyšuje složitost kódu.

Virtual threads část této složitosti snižují: pro mnoho aplikací je jednodušší vrátit se k čitelnému blocking stylu a nechat JVM organizovat čekání.

# Časté chyby

- **Blocking call v event loopu.** Jeden pomalý handler zastaví mnoho spojení.
- **Neomezená fronta.** Overload se schová, latency naroste a systém spadne později.
- **Příliš mnoho platform threadů.** Stack memory a context switching zabijí throughput.
- **`OP_WRITE` registrovaný pořád.** Selector se budí neustále a CPU jede naprázdno.
- **Zapomenutý `flip()` u ByteBufferu.** Čteš/zapisuješ špatnou část bufferu.
- **`allocateDirect()` v hot path.** Direct buffer alokace je drahá, používej pooling.
- **Ignorování partial read/write.** TCP je stream, ne message protocol.
- **Žádné timeouts.** Čekající requesty drží resources donekonečna.
- **Retry storm.** Retry bez limitu násobí load při incidentu.
- **Žádná backpressure.** Fronty a buffery rostou bez kontroly.
- **Měřit jen průměr.** Síťové servery se hodnotí přes p95/p99 a overload chování.

# Jak vybrat model

| Situace | Dobrá volba |
|---|---|
| Malý počet spojení, jednoduchá aplikace | blocking IO + bounded thread pool |
| Hodně idle spojení, websockety, gateway | event loop / NIO / Netty |
| Aplikační server s hodně blocking I/O | virtual threads |
| CPU-bound workload | pevný CPU-sized pool, paralelizace podle jader |
| Streaming s backpressure | reactive/Netty/Flow API |
| Static file serving | zero-copy/sendfile, kernel caching |
| Backend s malou kapacitou | bulkhead, rate limit, bounded queue |

# Zkouškové minimum

**C10K:** problém obsloužit 10 000 současných spojení. Thread-per-connection selhává kvůli paměti thread stacků, context switchingu, scheduler overheadu a blocking I/O.

**Blocking I/O:** vlákno čeká v `read/accept/write`, dokud operace nejde dokončit. Jednoduché, ale při mnoha spojení potřebuje mnoho vláken.

**Non-blocking I/O:** operace se vrací hned, pokud není připravena. Aplikace používá readiness notification (`select/poll/epoll/kqueue`) a zpracovává jen ready sockety.

**epoll:** Linux mechanismus pro efektivní čekání na I/O eventy. Sledované FD zůstávají v kernelu a `epoll_wait` vrací aktivní eventy.

**Event loop:** jedno nebo několik vláken čeká na I/O eventy a rychle volá handlery. Handler nesmí blokovat.

**Reactor:** pattern: demultiplexer eventů + event loop + handlery + případně worker pool.

**Java NIO:** `Channel`, `Buffer`, `Selector`, `SelectionKey`. Umožňuje obsluhovat mnoho socketů jedním vláknem.

**ByteBuffer:** má `position`, `limit`, `capacity`. `flip()` přepíná ze zápisu do čtení, `clear()` připraví nový zápis, `compact()` zachová nepřečtená data.

**Direct buffer:** native memory mimo Java heap, vhodná pro I/O, ale drahá na alokaci a musí se poolovat.

**Backpressure:** mechanismus, kterým se systém brání tomu, aby rychlý producer zahltil pomalý consumer.

**Virtual threads:** lightweight JVM thready, finální v Java 21. Umožňují thread-per-request styl pro I/O-bound aplikace bez tisíců platform threadů, ale nenahrazují limity, backpressure ani CPU paralelismus.

# Mini tahák

```text
latency        = čas jednoho requestu
throughput     = requesty nebo bajty za sekundu
concurrency    = kolik spojení/requestů běží současně

TCP            = spolehlivý byte stream, pořadí, ACK, congestion control
UDP            = datagramy bez záruky, nízký overhead

blocking IO    = thread čeká v read/write/accept
non-blocking   = read/write vrátí EAGAIN, když není ready

select         = historické, limit/scan
poll           = bez fd_set limitu, pořád scan
epoll          = Linux readiness events pro mnoho FD
kqueue         = BSD/macOS alternativa
IOCP           = Windows completion model

event loop     = wait events -> handle quickly
reactor        = demultiplexer + handlers

Java NIO:
  ServerSocketChannel
  SocketChannel
  Selector
  SelectionKey
  ByteBuffer

ByteBuffer:
  write -> flip -> read -> clear/compact

OP_WRITE:
  registruj jen když máš pending output

direct buffer:
  native memory, useful for IO, pool it

zero-copy:
  FileChannel.transferTo / sendfile when possible

virtual threads:
  blocking style, cheap waiting, not infinite backend capacity
```

# Jak navazuje další téma

Další lekce řeší paměť JVM, objekty, boxing a kolekce. To přímo navazuje na síťové servery: každý request vytváří objekty, buffery, kolekce, mapy headerů a response data. Pokud má server vysoký throughput, špatný memory layout a zbytečné alokace rychle vytvoří GC pressure a p99 latency problém.
