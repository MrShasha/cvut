# JVM alokace objektů a TLAB

## Kde vznikají objekty

Většina běžných Java objektů vzniká na heapu, typicky v Young generation, konkrétně v Eden space.

Zjednodušeně:

```text
new Object()
-> rezervuj místo v Eden/TLAB
-> vynuluj paměť
-> nastav object header
-> spusť constructor
-> reference se vrátí programu
```

Alokace není totéž co constructor. Alokace je získání paměti, constructor je inicializační kód třídy.

## Bump-the-pointer

Pokud má JVM souvislý volný blok paměti, alokace může být jen posunutí pointeru.

```text
[ used objects ][ free space ................ ]
                ^
                allocation pointer

new Point()

[ used objects ][ Point ][ free space ....... ]
                         ^
                         pointer moved
```

Tomu se říká **bump-the-pointer allocation**.

Proč je rychlá:

- není potřeba hledat volný blok jako u obecného `malloc`;
- není potřeba složitá práce s freelisty;
- většina krátkodobých objektů se alokuje v Eden;
- po GC/compaction vznikají souvislé volné oblasti.

Pointa: alokace v JVM může být velmi levná. Drahé začne být hlavně to, že mnoho objektů musí později projít GC, zhorší cache locality nebo přežije do Old generation.

## TLAB

**TLAB (Thread-Local Allocation Buffer)** je malý privátní kus Eden space, který dostane konkrétní vlákno.

Problém bez TLAB:

```text
všechna vlákna alokují
-> všechna by musela atomicky posouvat jeden globální heap pointer
-> contention
```

Řešení:

```text
Thread A -> TLAB A -> bump pointer bez locku
Thread B -> TLAB B -> bump pointer bez locku
Thread C -> TLAB C -> bump pointer bez locku
```

Výhody:

- běžná alokace nepotřebuje lock;
- minimální synchronizace;
- dobrá krátkodobá locality objektů vytvořených stejným vláknem;
- TLAB velikost JVM adaptivně upravuje podle alokačního chování vlákna.

## TLAB refill a slow path

Když se objekt vejde do TLAB:

```text
fast path:
    zkontroluj volné místo
    posuň pointer
    inicializuj objekt
```

Když se nevejde:

```text
slow path:
    požádej JVM o nový TLAB
    případně alokuj mimo TLAB
    může vzniknout synchronizace nebo GC pressure
```

TLAB může mít i **waste**: na konci TLAB zůstane malý kousek, do kterého se další objekt nevejde. JVM balancuje velikost TLAB tak, aby nebylo moc refillů ani moc odpadu.

## Proč object pooling často nepomáhá

V Javě je malý krátkodobý objekt často levnější alokovat a nechat zemřít v Young generation, než ho ručně recyklovat v poolu.

Object pooling malých objektů může škodit:

- objekty žijí déle a přesunou se do Old generation;
- pool potřebuje synchronizaci;
- zhorší locality;
- drží paměť i ve chvíli, kdy není potřeba;
- komplikuje kód.

Pooling dává smysl hlavně pro opravdu drahé resources: connections, threads, velké direct buffers, native handles.

# Object initialization a velké objekty

## Inicializace objektu

Po rezervaci paměti JVM typicky:

- vynuluje fieldy;
- nastaví object header;
- nastaví klass pointer;
- spustí constructor;
- vrátí referenci.

```java
Point p = new Point(1, 2);
```

Neznamená jen "vezmi paměť". Znamená i bezpečně vytvořit validní Java objekt.

## Safe publication

Objekt může být správně vytvořený v jednom vlákně, ale špatně publikovaný do druhého.

```java
// špatně bez synchronizace
shared = new Config(...);
```

Pokud objekt čte jiné vlákno, použij bezpečnou publikaci:

- `volatile` reference;
- `synchronized`;
- thread-safe kolekce;
- final fields + správná konstrukce;
- publikace před `Thread.start()`.

Toto navazuje na lekci 9 o JMM.

## Velké objekty a humongous allocation

Velké objekty, typicky velké `byte[]`, `char[]`, `int[]` nebo buffery, mají speciální dopad na GC.

U G1 jsou objekty větší než přibližně polovina regionu alokované jako **humongous objects** do humongous regionů.

Proč to může bolet:

- velký objekt zabere celé regiony;
- hůř se přesouvá/kompaktuje;
- může přispět k fragmentaci;
- často souvisí s JSON/XML payloady, velkými response buffery nebo neomezeným čtením do paměti.

Detailní GC fáze jsou v lekci **[[13. Garbage Collectors v JVM]]**. Tady stačí pointa: velké dočasné arrays mohou být výrazný latency problém.

# Escape analysis a scalar replacement

## Escape analysis

**Escape analysis** je JIT analýza, která zjišťuje, jestli objekt unikne z metody nebo vlákna.

Typické kategorie:

| Kategorie | Význam | Co může JIT udělat |
|---|---|---|
| **NoEscape** | objekt zůstane uvnitř metody | odstranit alokaci |
| **ArgEscape** | objekt se předá dál, ale neunikne globálně | některé optimalizace možné |
| **GlobalEscape** | objekt se uloží do fieldu, statiky, kolekce nebo se vrátí | alokace musí zůstat |

NoEscape příklad:

```java
int distance(int x, int y) {
    Point p = new Point(x, y);
    return p.x * p.x + p.y * p.y;
}
```

Pokud `p` nikam neunikne, JIT nemusí vytvořit heap objekt.

GlobalEscape příklad:

```java
List<Point> points = new ArrayList<>();
points.add(new Point(x, y));
```

Tady objekt uniká do kolekce, takže musí existovat na heapu.

## Scalar replacement

**Scalar replacement** znamená, že JIT rozloží objekt na jeho fieldy.

Místo:

```java
Point p = new Point(x, y);
return p.x + p.y;
```

může mít interně:

```text
int p_x = x
int p_y = y
return p_x + p_y
```

Výsledek:

- žádný heap objekt;
- žádná práce pro GC;
- hodnoty mohou být v registrech CPU;
- mikrobenchmark může vypadat "magicky rychle", protože objekt nikdy nevznikl.

## Allocation elimination a lock elimination

Pokud JIT prokáže, že objekt není potřeba jako objekt, může odstranit celou alokaci.

Pokud JIT prokáže, že objekt nemůže sdílet více vláken, může odstranit i lock:

```java
void f() {
    Object lock = new Object();
    synchronized (lock) {
        work();
    }
}
```

`lock` neuniká z metody, takže synchronizace nemá význam pro jiné vlákno. JIT ji může odstranit.

Související optimalizace:

- **lock elimination** — odstraní zbytečný lock;
- **lock coarsening** — spojí více sousedních lock/unlock operací do jedné větší kritické sekce;
- **scalar replacement** — nahradí objekt fieldy.

## Stack allocation nedorozumění

Často se říká "JVM alokuje objekt na stacku". Přesnější je:

```text
JIT může alokaci úplně odstranit
a fieldy objektu držet ve stack slots nebo registrech
```

Není to garantované pravidlo jazyka. Je to optimalizace konkrétního JITu v konkrétním runtime profilu.

# Data locality a NUMA

## Data locality

Data locality znamená, že CPU pracuje s daty, která jsou blízko sebe v paměti a často se znovu používají.

- **Spatial locality** — když čtu jednu adresu, brzy budu číst sousední adresy.
- **Temporal locality** — když čtu hodnotu teď, brzy ji budu číst znovu.

Bump-the-pointer alokace často vytvoří dobrou krátkodobou locality pro objekty vytvořené po sobě.

Problém: dlouhodobě může locality zhoršit:

- pointer chasing;
- object graph;
- GC přesuny;
- objekty různých životností;
- rozptýlení objektů po heapu.

## Compact representation

Špatně pro locality:

```java
List<Point> points; // reference na mnoho objektů
```

Lépe pro numerický hot path:

```java
int[] xs;
int[] ys;
```

Nebo jedna kompaktní struktura:

```java
long[] points; // packed x/y
```

To navazuje na lekci 6 o cache a lekci 11 o kolekcích.

## NUMA

**NUMA (Non-Uniform Memory Access)** znamená, že přístup do RAM není stejně drahý ze všech CPU socketů.

```text
CPU socket 0 -> lokální RAM: rychlejší
CPU socket 0 -> RAM socketu 1: pomalejší
```

Prakticky řeš NUMA hlavně u:

- multi-socket serverů;
- velkých heapů;
- nízkolatenčních systémů;
- aplikací s vysokým memory bandwidth;
- serverů, kde thread migration a remote memory access pálí výkon.

Nástroje a přístupy:

- CPU affinity;
- `numactl`;
- měření remote/local memory access;
- JVM flags jako `-XX:+UseNUMA` podle JDK/collector/workloadu;
- opatrné ladění, protože ruční pinning může i uškodit.

Pravidlo: NUMA neřeš naslepo na notebooku. Řeš ho, když máš multi-socket stroj a profil ukazuje memory/latency problém.

# Bloom filter

![[Assets/ESW/bloom-filter-references.svg]]

## Proč existuje

Membership test znamená otázku:

```text
Je prvek X v množině?
```

Přesná struktura:

```text
HashSet -> přesná odpověď, ale drží všechny prvky
```

Bloom filter:

```text
velmi málo paměti
rychlý dotaz
ale občas false positive
```

Bloom filter odpovídá:

- **určitě ne**;
- **možná ano**.

Nikdy neříká "určitě ano".

## Struktura

Bloom filter obsahuje:

- bitové pole délky `m`;
- `k` hash funkcí;
- očekávaný počet prvků `n`;
- cílovou false positive rate `p`.

Insert:

```text
insert(x):
    for each hash_i:
        bit[hash_i(x) % m] = 1
```

Query:

```text
contains(x):
    for each hash_i:
        if bit[hash_i(x) % m] == 0:
            return "definitely not"
    return "maybe yes"
```

## False positive a false negative

**False positive**:

```text
Bloom filter řekne "maybe yes",
ale prvek ve skutečnosti v množině není.
```

Vzniká proto, že všechny bity pro dotazovaný prvek mohly nastavit jiné prvky.

**False negative** standardní Bloom filter nemá, pokud:

- nemažeš prvky;
- hash funkce jsou stejné při insert/query;
- bitové pole není poškozené;
- nepřekročíš chybně implementované limity.

Když Bloom filter řekne "definitely not", prvek tam opravdu nebyl vložen.

## Parametry m, n, k

Symboly:

| Symbol | Význam |
|---|---|
| `m` | počet bitů |
| `n` | počet vložených prvků |
| `k` | počet hash funkcí |
| `p` | false positive probability |

Přibližná false positive probability:

```text
p ≈ (1 - e^(-k*n/m))^k
```

Optimální počet hash funkcí:

```text
k ≈ (m / n) * ln(2)
```

Prakticky:

- větší `m` -> méně false positives, víc paměti;
- větší `n` -> více nastavených bitů, více false positives;
- příliš malé `k` -> málo informací;
- příliš velké `k` -> víc CPU a rychlejší saturace bitů.

## Saturation

Bloom filter má pevnou kapacitu. Když do něj vložíš víc prvků, než pro kolik byl navržený, bitové pole se zaplní.

Pak se stane:

```text
většina bitů = 1
contains(x) skoro vždy vrací "maybe yes"
filter přestává být užitečný
```

Proto musíš znát očekávané `n` nebo použít variantu, která umí růst.

## Kdy použít Bloom filter

Bloom filter se hodí, když:

- přesná množina by byla moc velká;
- false positive je přijatelné;
- false negative by byl problém;
- chceš ušetřit drahý lookup;
- dotazy "určitě ne" jsou časté.

Typické použití:

- databáze / LSM trees: RocksDB, Cassandra, HBase;
- před dotazem na disk;
- cache penetration protection;
- deduplikace ve streamu s tolerancí false positives;
- síťové/security filtry.

Příklad:

```text
dotaz na key
-> Bloom filter říká "definitely not"
-> nechoď na disk

dotaz na key
-> Bloom filter říká "maybe yes"
-> ověř v přesné struktuře/disku
```

Kdy ho nepoužít:

- potřebuješ přesnou odpověď "ano";
- false positive je nepřijatelný;
- potřebuješ běžně mazat prvky;
- počet prvků je malý a `HashSet` stačí;
- hash výpočty jsou dražší než ušetřený lookup.

# Bloom filter varianty

## Counting Bloom filter

Standardní Bloom filter neumí bezpečně mazat, protože jeden bit může sdílet více prvků.

Counting Bloom filter místo bitů používá čítače:

```text
insert -> increment counters
delete -> decrement counters
query  -> check counters > 0
```

Výhoda:

- podporuje delete.

Nevýhoda:

- mnohem větší paměť;
- riziko counter overflow/underflow;
- složitější implementace.

## Scalable Bloom filter

Scalable Bloom filter řeší problém pevné kapacity.

Když se starý filtr blíží saturaci, přidá se další filtr:

```text
BF1 + BF2 + BF3 ...
```

Dotaz kontroluje více filtrů. Výhoda je růst bez přesného odhadu `n`, nevýhoda je víc CPU a složitější kontrola false positive rate.

## Blocked Bloom filter

Blocked Bloom filter zlepšuje cache locality.

Místo nastavování bitů po celém velkém poli vybere hash nejdřív blok a další hashe pracují uvnitř tohoto bloku.

Výhoda:

- méně cache misses;
- lepší výkon pro velké filtry.

Nevýhoda:

- trochu horší false positive rate při stejné velikosti, podle návrhu.

## Stable Bloom filter a Cuckoo filter

**Stable Bloom filter** se hodí pro streamy, kde chceš držet přibližně poslední prvky. Staré informace postupně mizí, takže může mít false negatives.

**Cuckoo filter** je alternativa, která ukládá fingerprints a často podporuje delete lépe než Bloom filter. Má jiné trade-offy a složitější insert.

# Java reference types

## Reachability levels

Java nemá jen jednu úroveň "objekt je dosažitelný". Pro GC existují různé úrovně dosažitelnosti.

| Typ dosažitelnosti | Co znamená |
|---|---|
| **Strongly reachable** | existuje běžná silná reference |
| **Softly reachable** | nejsou strong reference, ale existuje `SoftReference` |
| **Weakly reachable** | nejsou strong/soft reference, ale existuje `WeakReference` |
| **Phantom reachable** | objekt už není dostupný přes `get()`, čeká se na cleanup notifikaci |
| **Unreachable** | žádná relevantní reference, objekt může být uvolněn |

Standardní reference v Javě je strong reference:

```java
User user = new User();
```

Dokud existuje strong reference, GC objekt neuvolní.

## SoftReference

`SoftReference<T>` drží objekt slaběji než strong reference.

```java
SoftReference<byte[]> ref = new SoftReference<>(loadData());
byte[] data = ref.get();
```

GC může soft reference vyčistit při memory pressure. Není to přesný cache eviction mechanismus.

Použití:

- paměťově citlivé cache;
- data, která lze znovu načíst.

Nevýhody:

- chování závisí na JVM a memory pressure;
- těžko garantuje latency;
- moderní aplikace často preferují explicitní cache typu Caffeine s jasným limitem.

Prakticky: **SoftReference nepoužívej jako hlavní cache systém, pokud potřebuješ predikovatelné chování**.

## WeakReference

`WeakReference<T>` nebrání GC uvolnit objekt. Pokud objekt nemá strong/soft reference, může být při příští GC odstraněn.

```java
WeakReference<User> ref = new WeakReference<>(user);
User u = ref.get(); // může být null
```

Použití:

- metadata k objektům, které nechceš držet při životě;
- canonicalization;
- `WeakHashMap`;
- listenery s opatrností.

`WeakHashMap` má slabé **klíče**, ne hodnoty:

```java
Map<Key, Value> map = new WeakHashMap<>();
```

Záznam zmizí, když key už není silně dosažitelný odjinud.

Typická chyba:

```java
map.put(key, value);
// value drží strong reference zpět na key
```

Pak key může zůstat dosažitelný přes value a záznam nezmizí podle očekávání.

## PhantomReference

`PhantomReference<T>` slouží pro cleanup po tom, co objekt už není běžně dosažitelný.

Důležité:

- `phantomRef.get()` vždy vrací `null`;
- používá se s `ReferenceQueue`;
- hodí se pro cleanup nativních resources;
- je bezpečnější náhrada historických finalizerů.

```java
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> ref = new PhantomReference<>(obj, queue);
```

Když GC zjistí, že objekt je phantom reachable, reference se dostane do fronty. Cleanup kód může uvolnit související native handle.

## ReferenceQueue

`ReferenceQueue` je fronta, do které GC zařadí reference, jejichž referent změnil stav dosažitelnosti.

Pattern:

```java
ReferenceQueue<Resource> queue = new ReferenceQueue<>();
PhantomReference<Resource> ref = new PhantomReference<>(resource, queue);

Reference<? extends Resource> cleared = queue.remove();
// cleanup metadata spojených s ref
```

Samotná reference neví, jaký native handle má uvolnit, protože `get()` u phantom reference vrací `null`. Metadata musíš držet bokem.

## Cleaner

`Cleaner` je modernější API pro cleanup, když uživatel zapomene zavolat `close()`.

```java
class NativeResource implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    NativeResource() {
        this.cleanable = CLEANER.register(this, this::cleanup);
    }

    public void close() {
        cleanable.clean();
    }

    private void cleanup() {
        // release native resource
    }
}
```

Cleaner je safety net, ne hlavní lifecycle mechanismus. Správný základ je pořád `try-with-resources` a explicitní `close()`.

## Přehled referencí

| Typ | Brání GC? | `get()` | Typické použití | Pozor |
|---|---:|---|---|---|
| Strong | ano | objekt | běžné reference | drží objekt při životě |
| Soft | slabě, do memory pressure | objekt nebo `null` | dočasná cache | nepredikovatelné eviction |
| Weak | ne | objekt nebo `null` | WeakHashMap, metadata | může zmizet při další GC |
| Phantom | ne | vždy `null` | cleanup native resources | potřebuje ReferenceQueue |

# Časté chyby

- **Myslet si, že `new` je vždy drahé.** Běžná TLAB alokace je rychlá; problém je často allocation rate a GC pressure.
- **Ručně poolovat malé objekty.** Často zhorší GC a kód.
- **Ignorovat escape analysis v benchmarku.** JIT může odstranit alokaci a benchmark pak neměří to, co si myslíš.
- **Tvrdit, že objekt je "na stacku" jako jazykové pravidlo.** Přesnější je allocation elimination/scalar replacement.
- **Přidávat do Bloom filteru bez kapacitního plánu.** Saturace zničí false positive rate.
- **Používat Bloom filter jako přesnou množinu.** "Maybe yes" musíš ověřit jinde.
- **Mazat ze standardního Bloom filteru.** Bez counting varianty tím vytvoříš false negatives.
- **SoftReference jako hlavní cache.** Použij explicitní cache s limitem, pokud potřebuješ předvídatelnost.
- **Nechápat WeakHashMap.** Slabé jsou klíče, ne hodnoty.
- **PhantomReference bez ReferenceQueue/metadat.** Sama o sobě cleanup neudělá.
- **Spoléhat na Cleaner místo `close()`.** Cleaner je fallback, ne deterministické uvolnění.

# Zkouškové minimum

**Bump-the-pointer:** rychlá alokace posunutím pointeru v souvislém volném bloku.

**TLAB:** per-thread část Eden space. Vlákno v ní alokuje bez locku; refill/slow path se řeší až po zaplnění.

**Escape analysis:** JIT zjišťuje, jestli objekt uniká. Pokud ne, může odstranit alokaci.

**Scalar replacement:** objekt se nahradí jeho fieldy v registrech/stack slots.

**Lock elimination:** pokud lock objekt neuniká mezi vlákna, JIT může synchronizaci odstranit.

**Data locality:** blízká data se lépe využívají v cache. Object graph a pointer chasing locality zhoršují.

**NUMA:** na multi-socket serveru není přístup do každé RAM stejně drahý. Řeší se až podle měření.

**Bloom filter:** kompaktní pravděpodobnostní struktura pro membership test. Odpovídá "určitě ne" nebo "možná ano".

**False positive:** Bloom řekne "možná ano", ale prvek tam není. False negative standardně nemá.

**Counting Bloom filter:** varianta s čítači, která podporuje delete za cenu větší paměti.

**SoftReference:** objekt může GC uvolnit při memory pressure.

**WeakReference:** nebrání GC; objekt může zmizet při další GC, pokud nemá strong/soft reference.

**PhantomReference:** cleanup notifikace přes `ReferenceQueue`, `get()` vždy vrací `null`.

# Mini tahák

```text
allocation:
  new -> TLAB fast path -> bump pointer
  TLAB full -> refill / slow path

bump-the-pointer:
  allocation = posun pointeru

TLAB:
  thread-local Eden chunk
  no lock on common path

escape analysis:
  NoEscape -> allocation elimination possible
  GlobalEscape -> heap allocation needed

scalar replacement:
  object -> fields in registers/stack slots

lock elimination:
  synchronized on non-escaping object can disappear

large objects:
  big arrays/buffers can hurt GC, especially G1 humongous regions

Bloom filter:
  bit array + k hashes
  query -> definitely not / maybe yes
  no false negatives in standard variant
  false positives depend on m, n, k

reference types:
  strong  -> keeps alive
  soft    -> cleared under memory pressure
  weak    -> cleared when weakly reachable
  phantom -> cleanup notification, get() null

Cleaner:
  fallback cleanup, not replacement for close()
```

# Jak navazuje další téma

Další lekce jde do garbage collectorů. Tady jsme řešili, jak objekty vznikají, kdy vůbec nemusí vzniknout a jak lze s GC spolupracovat přes reference. GC lekce vysvětlí, jak JVM rozhoduje, co je živé, jak sbírá Young/Old generation a proč vznikají stop-the-world pauzy.
