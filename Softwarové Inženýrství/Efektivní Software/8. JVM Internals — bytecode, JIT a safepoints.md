# JVM jako managed runtime

## Co JVM dělá

JVM je specifikace virtuálního stroje a zároveň prakticky runtime, který ji implementuje. Nejčastější implementace je **HotSpot** v OpenJDK.

JVM řeší:

- **class loading** — načítá `.class` soubory z classpath/module path;
- **bytecode verification** — ověřuje, že bytecode neporušuje typovou bezpečnost a strukturu JVM;
- **execution** — spouští bytecode interpretací nebo JIT-kompilovaným nativním kódem;
- **memory management** — alokace objektů na heapu a garbage collection;
- **threading** — Java vlákna, synchronizace, safepoints, interakce s OS;
- **runtime services** — reflection, class metadata, exceptions, native calls přes JNI;
- **observability** — JFR, GC logs, safepoint logs, thread dumps, heap dumps.

## Proč bytecode

Klasický nativní program:

```text
C/C++ source -> compiler -> x86-64/ARM machine code -> CPU
```

Java model:

```text
Java source -> javac -> JVM bytecode -> JVM -> native machine code za běhu
```

Bytecode oddělí jazyk od konkrétního CPU. `.class` soubor je stejný pro Windows/Linux/macOS a JVM až za běhu rozhodne, jak ho spustit na konkrétní architektuře.

## Výhody a nevýhody

| Vlastnost | Co to znamená pro výkon |
|---|---|
| Platformová nezávislost | Stejný bytecode běží na různých OS/CPU. |
| JIT optimalizace podle profilu | JVM zná runtime data: typy objektů, horké větve, chování smyček. |
| Automatická správa paměti | Programátor nevolá `free`, ale platí za GC a objektový overhead. |
| Warm-up | První běh metody nemusí reprezentovat stabilní výkon. |
| Safepoints a GC pauzy | Latence může mít špičky, které v nativním mikrobenchmarku neuvidíš. |
| Méně low-level kontroly | Layout objektů a alokace řídí runtime, ne přímo programátor. |

> [!info] Krátká pointa
> JVM kupuje portabilitu, bezpečnost, GC a runtime optimalizace za cenu warm-upu, runtime overheadu a složitější interpretace benchmarků.

# JVM memory layout

JVM paměť není jeden velký blok. Některé části patří konkrétnímu vláknu, jiné sdílí celá aplikace.

![[Assets/ESW/jvm-memory-layout.svg]]

## Per-thread části

- **Program Counter (PC)** — ukazuje na aktuální bytecode instrukci daného vlákna. Každé Java vlákno má vlastní PC.
- **JVM stack** — zásobník volání metod. Každé volání metody vytvoří nový frame.
- **Native method stack** — zásobník pro JNI/native metody napsané například v C/C++.

Per-thread paměť se používá pro řízení běhu vlákna. Když vlákno skončí, jeho stack a PC zmizí.

## Sdílené části

- **Heap** — hlavní prostor pro Java objekty a pole. Sdílí ho všechna vlákna a spravuje ho GC.
- **Metaspace** — metadata tříd: názvy tříd, metody, fieldy, constant pool, class metadata. Od Java 8 je mimo klasický Java heap.
- **Code cache** — nativní kód vyrobený JIT kompilátorem. Když C1/C2 zkompiluje horkou metodu, výsledek žije právě tady.

## Stack vs heap

| Místo       | Co tam typicky je                                | Životnost                  | Správa                   |
| ----------- | ------------------------------------------------ | -------------------------- | ------------------------ |
| Stack frame | lokální proměnné, operand stack, návrat z metody | do návratu z metody        | automaticky podle volání |
| Heap        | objekty, pole, instance tříd                     | dokud jsou dosažitelné     | GC                       |
| Metaspace   | metadata tříd                                    | dokud je class loader živý | JVM                      |
| Code cache  | JIT-kompilovaný kód                              | dokud ho JVM nezahodí      | JVM/JIT                  |

Pozor: lokální proměnná typu reference může být na stacku, ale objekt, na který ukazuje, je na heapu.

```java
User u = new User("A");
```

- proměnná `u` je reference v lokálním frame;
- objekt `User` je na heapu;
- string `"A"` je také objekt, typicky dosažitelný přes string pool.

## JVM frame

Frame je záznam jednoho volání metody. Interpreted frame obsahuje hlavně:

- **local variables array** — lokální proměnné a parametry; u instance metody je index `0` obvykle `this`;
- **operand stack** — pracovní zásobník pro bytecode instrukce;
- **constant pool reference** — odkaz na constant pool aktuální třídy;
- **return information** — kam se vrátit po dokončení metody.

U JIT-kompilovaného kódu už to nemusí fyzicky vypadat jako čistý zásobníkový frame. Hodnoty mohou být v registrech CPU, některé objekty mohou být rozloženy na skalární hodnoty a část kódu může být úplně odstraněna. JVM si ale musí umět v safepointu rekonstruovat stav programu.

# JVM bytecode

## `.class` soubor

`javac` nepřekládá Javu rovnou do x86-64 nebo ARM instrukcí. Vytvoří `.class` soubor.

Zjednodušeně obsahuje:

- **magic + version** — identifikace class file formátu a verze Javy;
- **constant pool** — tabulka stringů, tříd, metod, fieldů a symbolických referencí;
- **fields** — popis fieldů třídy;
- **methods** — bytecode metod;
- **attributes** — debug info, annotations, generics metadata, stack maps atd.

`constant pool` je důležitý: bytecode často neobsahuje přímo plné názvy metod/tříd, ale indexy do constant poolu.

## Stack-oriented model

JVM bytecode je zásobníkový. Instrukce pracují s operand stackem, ne přímo s CPU registry.

Java:

```java
static int add(int a, int b) {
    return a + b;
}
```

Bytecode:

```text
0: iload_0
1: iload_1
2: iadd
3: ireturn
```

Co se děje:

```text
iload_0  -> push a
iload_1  -> push b
iadd     -> pop a, pop b, push (a + b)
ireturn  -> pop výsledek a vrať ho volajícímu
```

Bytecode je zásobníkový, ale CPU je registrový. JIT později převede zásobníkové operace na registry a instrukce konkrétního procesoru.

## Typové prefixy instrukcí

Bytecode instrukce často nesou typ v názvu:

| Prefix | Typ | Příklad |
|---|---|---|
| `i` | `int` | `iload`, `iadd`, `ireturn` |
| `l` | `long` | `lload`, `ladd`, `lreturn` |
| `f` | `float` | `fload`, `fadd` |
| `d` | `double` | `dload`, `dadd` |
| `a` | reference | `aload`, `astore`, `areturn` |

## Důležité skupiny bytecode instrukcí

| Skupina | Instrukce | Co dělají |
|---|---|---|
| Load/store | `iload`, `istore`, `aload`, `astore` | přesun mezi lokálními proměnnými a operand stackem |
| Aritmetika | `iadd`, `isub`, `imul`, `idiv` | výpočty nad hodnotami na operand stacku |
| Řízení toku | `ifeq`, `if_icmpge`, `goto`, `tableswitch` | podmínky, skoky, switch |
| Volání metod | `invokevirtual`, `invokespecial`, `invokestatic`, `invokeinterface`, `invokedynamic` | dispatch metod |
| Objekty | `new`, `getfield`, `putfield`, `checkcast`, `instanceof` | alokace a práce s objekty |
| Pole | `iaload`, `iastore`, `aaload`, `arraylength` | práce s Java arrays |

`invokedynamic` je speciální instrukce zavedená pro dynamické jazyky na JVM a později použitá i pro lambdy a string concatenation.

## Disassembler vs decompiler

- **Disassembler** ukáže skutečný bytecode: `javap -c -v MyClass.class`.
- **Decompiler** se pokusí z bytecode zrekonstruovat Java kód: IntelliJ, CFR, Procyon.

Decompiler není pravda o zdrojovém kódu. Je to jen čitelná rekonstrukce. Pro výkon a JVM internals je přesnější `javap`.

# Object layout, OOP a compressed OOP

## OOP

**OOP** v HotSpot kontextu znamená **ordinary object pointer**: reference na objekt v heapu. Java reference není objekt samotný. Je to ukazatel nebo komprimovaný ukazatel na místo v heapu.

Objekt v HotSpot JVM typicky obsahuje:

- **mark word** — informace pro hash code, lock state, GC metadata;
- **klass pointer** — odkaz na metadata třídy;
- **array length** — jen u polí;
- **instance fields** — skutečná data objektu;
- **padding** — zarovnání objektu, často na 8 bytů.

Příklad dopadu:

```java
class Point {
    int x;
    int y;
}
```

Data jsou jen 8 B (`x`, `y`), ale objekt má ještě header a zarovnání. Proto objekt není jen součet svých fieldů.

## Compressed OOP

Na 64bit JVM by reference normálně zabírala 8 B. **Compressed OOPs** ukládají reference jako 32bit offsety, typicky při heapu do přibližně 32 GB při 8bytovém zarovnání.

Výhody:

- reference mají 4 B místo 8 B;
- menší objekty a menší pole referencí;
- lepší cache locality;
- menší tlak na paměťovou propustnost a GC.

Nevýhoda: JVM musí offset při použití dekódovat na skutečnou adresu. V praxi se to většinou vyplatí, protože menší paměťový footprint často rozhoduje víc než pár instrukcí navíc.

> [!warning] Typická chyba
> `ArrayList<Integer>` není kompaktní pole `int`. Je to pole referencí na objekty `Integer`. `int[]` drží čísla přímo za sebou, `ArrayList<Integer>` drží pointery a objekty jsou zvlášť na heapu.

# JIT, tiered compilation a optimalizace

## Proč JVM nekompiluje všechno hned

Kdyby JVM zkompilovala celý program před startem, platila by vysokou startovací cenu za kód, který se možná nikdy nespustí. Navíc by neměla runtime profil.

JVM proto používá adaptivní model:

```text
bytecode -> interpreter -> C1 -> C2 -> native code v code cache
```

Interpreter začne okamžitě. Sbírá profily a counters. Horké metody přejdou do C1 a nejdůležitější části do C2.

## Tiered compilation

HotSpot běžně používá více úrovní:

| Úroveň | Co běží | Smysl |
|---|---|---|
| 0 | interpreter | okamžitý start, sběr základního profilu |
| 1-3 | C1 compiler | rychlá kompilace, lehčí optimalizace, profiling |
| 4 | C2 compiler | agresivní optimalizace pro peak throughput |

Přechod mezi úrovněmi řídí hlavně:

- **invocation counter** — kolikrát se metoda zavolala;
- **backedge counter** — kolikrát se provedl skok zpět ve smyčce;
- **profil typů** — jaké reálné třídy chodí do virtuálních volání;
- **profil větví** — které větve jsou hot/cold;
- **compile budget a code cache** — kompilace také stojí CPU a místo.

Konkrétní thresholdy nejsou univerzální konstanta. JVM je upravuje podle konfigurace, zatížení a kompilátorové fronty.

## Co C1 a C2 dělají

- **C1** rychle vyrábí slušný nativní kód, aby program nemusel dlouho běžet interpretovaně.
- **C2** je pomalejší kompilátor, ale dělá výrazně agresivnější optimalizace.

Nejdůležitější JIT optimalizace:

- **inlining** — vložení těla volané metody do volající metody; otevírá cestu dalším optimalizacím;
- **devirtualization** — virtuální volání se změní na přímé, pokud profil ukazuje stabilní cílový typ;
- **escape analysis** — JVM zjistí, že objekt neuniká z metody nebo vlákna;
- **scalar replacement** — neunikající objekt se vůbec nemusí alokovat, jeho fieldy se drží jako obyčejné hodnoty;
- **lock elimination** — pokud objekt neuniká mezi vlákna, zámek může být odstraněn;
- **range check elimination** — odstranění opakovaných kontrol indexu v hot smyčce;
- **null check elimination** — odstranění redundantních null checků;
- **loop optimizations** — unrolling, hoisting invariantů, případně vectorization.

## Escape analysis příklad

```java
static int dist(int x, int y) {
    Point p = new Point(x, y);
    return p.x * p.x + p.y * p.y;
}
```

Pokud `p` neunikne ven, JIT může udělat něco jako:

```text
p.x -> scalar int
p.y -> scalar int
žádný objekt Point na heapu
žádná GC práce pro Point
```

To neznamená, že Java automaticky alokuje běžné objekty na stacku. Znamená to, že JIT může konkrétní alokaci odstranit, pokud to prokáže.

## OSR

**On-Stack Replacement (OSR)** řeší horké smyčky.

Problém:

```java
while (running) {
    work();
}
```

Metoda se zavolá jednou, takže invocation counter moc nepomůže. Ale backedge counter vidí, že smyčka běží pořád. JVM zkompiluje OSR verzi metody a přeskočí z interpretovaného běhu do kompilované smyčky bez čekání na návrat z metody.

## Speculative optimization a deoptimization

C2 optimalizuje spekulativně: využívá to, co JVM zatím viděla za běhu.

Příklad:

```java
interface Sink { void write(String s); }
```

Profil ukazuje, že `sink.write(x)` vždy volá `FileSink.write`. JIT může virtuální volání nahradit přímým voláním a dál inlinovat. Pokud se později objeví `NetworkSink`, předpoklad přestane platit.

**Deoptimization** = JVM zahodí nebo obejde příliš optimistický nativní kód a vrátí běh do bezpečnější verze: interpreter/C1/nově zkompilovaný C2. Aby to šlo, musí mít JVM u safepointů dost informací k rekonstrukci Java stavu.

# Safepoints

## Co je safepoint

**Safepoint** je místo, kde JVM ví, v jakém stavu je vlákno, kde jsou reference na objekty a jak lze bezpečně pozastavit nebo rekonstruovat běh.

Safepoint není "libovolná instrukce". JVM je typicky vkládá na místa jako:

- návraty a volání metod;
- backedge ve smyčce;
- místa, kde může být potřeba GC nebo deoptimization;
- poll instrukce v JIT-kompilovaném kódu.

## OopMap

Krátce: **OopMap je mapa pro GC, která říká, kde přesně jsou v daném okamžiku uložené reference na Java objekty**. Neříká "co je v heapu". Říká: "když se program zastaví v tomto safepointu, reference jsou tady: v těchto registrech CPU a na těchto místech stacku".

Bez OopMap by GC při běhu JIT kódu nevěděl, které hodnoty jsou pointery na objekty a které jsou jen obyčejná čísla. A kdyby si spletl číslo s pointerem nebo pointer s číslem, mohl by buď držet mrtvý objekt zbytečně při životě, nebo naopak uvolnit živý objekt.

Pro přesný GC musí JVM vědět, co je reference a co je obyčejné číslo.

V nativním JIT kódu mohou být hodnoty:

- v registrech CPU;
- na stacku;
- optimalizované pryč;
- rozložené ze struktury objektu na skalární hodnoty.

**OopMap** říká pro konkrétní safepoint: "tady v registru `r12` je reference, tady na stack offsetu `+24` je reference, tohle je integer". Bez toho by GC nemohl spolehlivě najít live objekty.

## Global safepoint

Globální safepoint znamená, že JVM potřebuje, aby všechna Java vlákna došla do bezpečného stavu.

Použití:

- stop-the-world fáze GC;
- některé deoptimalizace;
- class unloading;
- thread dump / stack inspection;
- některé VM operace.

Průběh:

```text
JVM požádá o safepoint
-> běžící vlákna kontrolují safepoint poll
-> každé vlákno dojde do bezpečného bodu
-> JVM provede VM operaci
-> vlákna pokračují
```

## Time to Safepoint

**TTSP (time to safepoint)** je čas od požadavku na safepoint do chvíle, kdy všechna vlákna opravdu stojí v bezpečném stavu.

GC pauza tedy může mít dvě části:

```text
celková pauza = čekání na safepoint + samotná VM/GC práce
```

Když log ukazuje dlouhou pauzu, nemusí být celý čas strávený v GC algoritmu. Část může být čekání na vlákno, které dlouho nedošlo k safepoint pollu.

Příčiny velkého TTSP:

- dlouhá smyčka bez safepoint pollu;
- dlouhý native/JNI úsek;
- vlákno blokované v místě, kde JVM nemůže okamžitě provést potřebnou operaci;
- extrémní CPU starvation.

## Thread-local handshakes

Moderní HotSpot umí pro některé operace použít **thread-local handshake**: není nutné zastavit celý svět, stačí domluvit bezpečný bod s konkrétním vláknem.

To snižuje potřebu globálních safepointů, ale neodstraňuje je. GC a některé VM operace pořád mohou potřebovat stop-the-world fázi.

# Automatic memory management v přehledu

GC se v této lekci řeší jen jako součást JVM execution modelu. Detailní algoritmy jsou v lekci **[[13. Garbage Collectors v JVM]]**.

Tady je potřeba chápat minimum:

- objekt je živý, pokud je dosažitelný z **GC roots**;
- GC roots jsou například stack references, static fields, JNI references a aktivní monitory;
- Java memory leak znamená, že objekt je stále dosažitelný, i když ho aplikace logicky už nepotřebuje;
- většina Java GC využívá **generational hypothesis**: většina objektů umírá mladá;
- časté alokace nejsou automaticky katastrofa, ale vysoký allocation rate zvyšuje GC pressure;
- GC potřebuje safepoints a OopMaps, aby přesně našel reference.

Krátká orientace:

| Pojem | Co znamená |
|---|---|
| Young generation | nové objekty, časté a relativně levné kolekce |
| Old generation | dlouho žijící objekty, dražší kolekce |
| Minor/Young GC | sběr mladé generace |
| Full GC | drahá kolekce větší části heapu, často latency problém |
| G1/ZGC/Shenandoah | modernější collectory s jinými trade-offy throughput vs. latency |

# Profiling JVM aplikací

## Typy profilování

**Profiling** znamená měření běžící aplikace s cílem najít bottleneck. Výstup se často nazývá **profil**: flame graph, heap dump, JFR recording, allocation profile, thread dump nebo GC log.

Nejdřív si ujasni, jaký problém hledáš:

| Typ profilování | Na co odpovídá | Typické nástroje |
|---|---|---|
| **CPU profiling** | Kde program tráví CPU čas? | async-profiler, JFR, Java Mission Control |
| **Allocation profiling** | Kdo vytváří nejvíc objektů a jaký je allocation rate? | JFR allocation events, async-profiler `alloc` |
| **Heap / memory profiling** | Co zůstává v paměti a kdo to drží při životě? | heap dump, Eclipse MAT, VisualVM |
| **GC profiling** | Kolik času tráví JVM v GC a proč vznikají pauzy? | `-Xlog:gc*`, JFR, GCViewer |
| **Lock / thread profiling** | Kde vlákna čekají, blokují se nebo soutěží o lock? | JFR lock events, thread dump, async-profiler `lock` |
| **I/O profiling** | Čeká aplikace na síť, disk, databázi nebo remote service? | JFR socket/file events, APM, framework metrics |
| **JIT profiling/logging** | Co JVM zkompilovala, inlinovala nebo deoptimalizovala? | `-XX:+PrintCompilation`, JITWatch, JFR |

`Sampling` a `tracing/instrumentation` nejsou samostatné oblasti problému. Jsou to **metody sběru dat**:

- **sampling** — profiler periodicky vzorkuje stack; nízký overhead, výsledek je statistický;
- **tracing/instrumentation** — profiler zaznamenává konkrétní vstupy/výstupy metod; přesnější počty, ale výrazně větší overhead.

Praktické pravidlo: když nevíš, kde začít, vezmi JFR nebo async-profiler CPU flame graph. Pokud flame graph ukáže hodně alokací/GC/locků/I/O čekání, přepni na konkrétnější profil.

## CPU profiling

CPU profiler odpovídá na otázku: **kde program tráví CPU čas**.

| Přístup | Jak funguje | Výhoda | Nevýhoda |
|---|---|---|---|
| Sampling | periodicky odebírá stack trace | nízký overhead, vhodné pro produkční diagnózu | statistický výsledek |
| Tracing/instrumentation | zapisuje vstup/výstup metod | přesné počty volání | vysoký overhead, mění chování programu |

Pro JVM je důležité vyhnout se safepoint bias. Profiler, který vzorkuje jen v safepointech, může ukázat zkreslený obraz. **async-profiler** a **Java Flight Recorder** jsou proto praktičtější než jednoduché instrumentační profilery.

## Memory profiling

Memory profiling řeší jiné otázky:

- kdo alokuje nejvíc objektů;
- jaký je allocation rate;
- co drží objekty při životě;
- kolik je shallow size vs. retained size;
- jestli roste old generation;
- jestli GC tráví příliš mnoho času.

Nástroje:

- `jcmd <pid> GC.class_histogram`;
- heap dump + Eclipse MAT / VisualVM / IntelliJ profiler;
- JFR allocation events;
- async-profiler v allocation režimu.

## Warm-up a JMH

JVM benchmark bez warm-upu skoro vždy měří něco jiného, než si myslíš.

V jednom běhu se může stát:

```text
1. interpreter
2. C1 kompilace
3. C2 kompilace
4. deoptimization
5. GC
6. stabilní hot path
```

Proto se pro Java microbenchmarky používá **JMH**:

- oddělí warm-up a measurement;
- opakuje fork procesy;
- brání dead-code elimination;
- poskytuje statistiku;
- umí pracovat s JVM parametry.

Ruční `for` smyčka se `System.nanoTime()` je pro JVM často špatný benchmark.

## Praktické příkazy

```bash
# bytecode
javap -c -v MyClass.class

# JIT kompilace
java -XX:+PrintCompilation App
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining App

# GC a safepoints
java -Xlog:gc* App
java -Xlog:safepoint App

# běžící proces
jcmd <pid> VM.flags
jcmd <pid> Compiler.codecache
jcmd <pid> Thread.print
jcmd <pid> GC.heap_info
jcmd <pid> JFR.start name=profile duration=60s filename=profile.jfr
```

`jstack`, `jmap`, `jcmd`, JFR, JMC, async-profiler a JITWatch jsou základní praktické nástroje kolem JVM výkonu.

# Jak to souvisí s předchozími tématy

- Z lekce o kompilátorech: JVM má taky frontend-like část (`javac`), IR-like interní reprezentace v JITu a backend generující machine code.
- Z cache lekce: Java objekty, reference, autoboxing a pointer chasing mají přímý dopad na cache locality.
- Z benchmarkingu: warm-up, JIT, GC a safepoints jsou zdroje šumu, které musíš kontrolovat.
- Ze synchronizace: `synchronized`, atomics a `volatile` se v JVM optimalizují přes JIT, memory barriers a runtime locking. To navazuje v další lekci.

# Časté chyby

- **Měřit první běh Java kódu jako stabilní výkon.** První běh často měří interpreter, class loading nebo C1.
- **Brát decompiler jako skutečný zdroják.** Pro bytecode analýzu používej `javap`.
- **Myslet si, že Java objekt = jen jeho fieldy.** Objekt má header, alignment a často reference na další objekty.
- **Tvrdit, že každá alokace je drahá jako `malloc`.** JVM alokace přes TLAB může být velmi levná; drahý je allocation rate, GC pressure a přežívající objekty.
- **Vinit GC z celé pauzy bez safepoint logu.** Dlouhá pauza může být TTSP, ne samotný GC.
- **Ignorovat code cache.** Když je code cache plná nebo JVM nestíhá kompilovat, výkon může spadnout.
- **Předpokládat, že JIT optimalizace je garantovaná.** Escape analysis, inlining a vectorization závisí na konkrétním kódu a runtime profilu.

# Zkouškové minimum

JVM spouští `.class` bytecode přes interpreter a JIT. HotSpot používá tiered compilation: interpreter sbírá profil, C1 rychle kompiluje, C2 dělá agresivní optimalizace. Bytecode je zásobníkový, ale JIT ho překládá na registrový machine code. JVM paměť se dělí na per-thread části (PC, JVM stack, native stack) a sdílené části (heap, metaspace, code cache). Java objekt má header, fieldy a padding; compressed OOP zmenšuje reference. Safepoint je bezpečný bod, kde JVM zná reference přes OopMap a může provést GC/deoptimization/VM operaci. TTSP je čekání, než všechna vlákna dojdou do safepointu. JVM profiling musí počítat s warm-upem, JITem, GC a safepoint bias.

# Mini tahák

```text
JVM = class loading + bytecode verification + interpreter + JIT + GC + runtime services

Java source
  -> javac
  -> .class bytecode
  -> interpreter/C1/C2
  -> native code v code cache

Per-thread:
  PC, JVM stack, native stack

Shared:
  heap, metaspace, code cache

Frame:
  local variables + operand stack + constant pool ref + return info

JIT:
  interpreter -> C1 -> C2
  invocation counter + backedge counter + type profile
  inlining, devirtualization, escape analysis, scalar replacement, OSR

Safepoint:
  bezpečný bod + OopMap
  global STW nebo thread-local handshake
  TTSP = čekání na dosažení safepointu

Profiling:
  CPU: on-CPU hot methods
  allocation: kdo vytváří objekty
  heap: co zůstává v paměti
  GC: pauzy a allocation pressure
  lock/thread: contention a blocking
  I/O: čekání na síť/disk/databázi
  benchmark: JMH + warm-up + forks
```
