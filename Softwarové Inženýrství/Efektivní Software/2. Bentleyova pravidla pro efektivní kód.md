- **[[2. Bentleyova pravidla pro efektivní kód#Základní pravidlo měř a redukuj práci|Základní pravidlo měř a redukuj práci]]:** proč optimalizace začíná měřením a proč největší efekt mívá odstranění práce.
- **[[2. Bentleyova pravidla pro efektivní kód#Optimalizace datových struktur|Optimalizace datových struktur]]:** jak vybírat a navrhovat datové struktury tak, aby šetřily cache a paměť (Reduce Bits, Augmentation, Precomputation, Sparsity).
- **[[2. Bentleyova pravidla pro efektivní kód#Optimalizace logiky|Optimalizace logiky]]:** přeskupení podmínek, short-circuit evaluation a eliminace zbytečné práce.
- **[[2. Bentleyova pravidla pro efektivní kód#Optimalizace smyček|Optimalizace smyček]]:** loop unrolling, loop fusion, tiling/blocking — kde smyčky ztrácejí výkon.
- **[[2. Bentleyova pravidla pro efektivní kód#Optimalizace funkcí|Optimalizace funkcí]]:** inlining, coarsening a tail call — overhead volání funkce a jak ho eliminovat.

Jon Bentley je autor knihy *Programming Pearls* a guru low-level optimalizace. Jeho pravidla jsou praktický toolbox, který funguje nezávisle na jazyce a architektuře. Nejsou to fancy triky — jsou to systematické zásady, jak vyplýtvat co nejméně cyklů a bajtů. Tato kapitola tě naučí myslet jako překladač a odhalovat plýtvání, které překladač sám nedokáže eliminovat.

# Základní pravidlo měř a redukuj práci

## Proč je tahle lekce tak brzy

V chronologii předmětu je Bentley praktický checklist. Některé termíny z této kapitoly se vysvětlí hlouběji později: cache, branch prediction, compiler optimalizace, GC, synchronizace a I/O. Teď stačí znát mentální model: nejdřív najdi plýtvání, potom vyber nejjednodušší změnu, která ho odstraní.

Tahle kapitola tedy není licence k náhodnému micro-tuningu. Je to mapa typických míst, kde programy zbytečně platí za práci.

## Optimalizace musí začít měřením

Nejprve potřebuješ vědět:

- kde program tráví čas;
- kolik alokuje;
- jestli čeká na CPU, paměť, lock, disk, síť nebo GC;
- jestli problém leží v hot path, nebo v kódu, který se spustí jednou.

Bez toho často optimalizuješ část, která tvoří jen malé procento běhu. To je Amdahlova intuice: 10× zrychlení kódu, který tvoří 1 % běhu, skoro nic nezmění.

## Reduce work

Nejsilnější optimalizace je nedělat práci vůbec:

- **Early exit:** skonči hned, jak znáš výsledek.
- **Filter before expensive transform:** nejdřív levně odfiltruj data, potom dělej drahé parsování, validaci nebo výpočty.
- **Avoid repeated work:** nepočítej ve smyčce něco, co je pro všechny iterace stejné.
- **Batching:** spoj mnoho malých operací do jedné větší, pokud je overhead volání, I/O nebo synchronizace vysoký.

Příklad:

```java
// Špatně: drahá validace běží i pro očividně neplatné vstupy.
for (String item : items) {
    if (expensiveValidation(item) && item.length() <= maxLen) {
        process(item);
    }
}

// Lépe: levný filtr jde první.
for (String item : items) {
    if (item.length() <= maxLen && expensiveValidation(item)) {
        process(item);
    }
}
```

# Optimalizace datových struktur

## Čtyři základní strategie

Datová struktura je víc než "kde jsou data uložena" — je to **kontrakt mezi algoritmem a hardwarem** o tom, jak data přistupovat. Špatná volba struktury může způsobit 10–100× zpomalení bez jediného špatného algoritmu.

### 1. Reduce Bits (Packing) — šetři místo

**Princip:** Zmenši data tak, aby se jich vešlo více do jedné cache line (64 B).

- **Encoding:** Data zapiš s méně bity (datum jako `int32` místo `string`).
- **Packing:** Ulož více malých hodnot do jednoho strojového slova (bit fields, packed structs).

**Fyzikální analogie:** Cache line je kontejner. Pokud má každý balík půl kontejneru volného prostoru, můžeš vozit dvojnásobek balíků najednou, nebo platit za poloprázdné kontejnery.

**Kdy použít:** Read-heavy workload, velká pole dat, network packet processing.

**Kdy ne:** Write-heavy workload, kde packing přidává overhead extrakce bitů.

### 2. Spend Memory (Augmentation) — přidej redundanci

**Princip:** Přidej redundantní data, aby byly běžné operace rychlejší.

**Příklad:** Linked list bez pole `size` → počítání délky je O(N). Přidej `size` pole → O(1). Zaplatíš 4–8 B navíc, ušetříš traversal.

**Další příklady:**
- Skip list — víceúrovňové propojení pro rychlejší search.
- B-tree vs. binary tree — víc klíčů v uzlu = méně úrovní = méně cache miss.
- Denormalizace v databázi — duplikovaná data pro rychlejší čtení.

**Fyzikální analogie:** Navigační mapa s vyznačenými dálnicemi — redundantní informace (cesty jsou i v detailní mapě), ale orientace je rychlejší.

### 3. Spend Time (Precomputation) — předpočítej výsledky

**Princip:** Spočítej výsledky dopředu a ulož je — lookup table místo výpočtu za běhu.

**Příklady:**
- Lookup table pro sinus/cosinus (přesné hodnoty ve stupních).
- Počítání bitů (popcount) — lookup table pro každý bajt, kombinuj pro 64-bit číslo.
- Prefix sum array — předpočítané kumulativní součty pro O(1) range queries.

**Trade-off:** Startup čas + paměť vs. runtime výkon. Kritické u real-time systémů, kde latence spuštění nezáleží, ale latence odpovědi ano.

### 4. Avoid Work (Sparsity/Caching) — nepočítej zbytečně

**Princip:** Neskladuj co tam není, nepočítej co už znáš.

- **Sparsity:** Compressed Row Storage (CSR) pro řídké matice — místo 1000×1000 matice s 1 % nenulových prvků ulož jen nenulové.
- **Caching/Memoization:** Ulož výsledky drahých výpočtů (LRU cache, memoize rekurzivní funkce).
- **Lazy evaluation:** Proveď výpočet jen pokud je výsledek skutečně potřeba.

### Cache a memoization nejsou zdarma

Cache se vyplatí jen tehdy, když se stejné vstupy opakují a výpočet je dražší než lookup. Jinak přidáš paměťový overhead, složitější invalidaci a někdy i synchronizaci.

Typické otázky:

- Jak velká cache může být?
- Kdy záznam vyhodit?
- Může být výsledek zastaralý?
- Nezpůsobí cache větší GC tlak než původní výpočet?

## Volba konkrétní struktury

Někdy je hlavní optimalizace prostě správná datová struktura:

- `ArrayList` je dobrý pro sekvenční průchod a random access, protože data leží blízko sebe.
- `LinkedList` je často špatná volba pro výkon: pointer chasing, mnoho objektů, špatná cache locality.
- `HashMap` dává očekávané O(1) lookupy, ale platí za hashování, resize a paměťový overhead.
- `TreeMap` dává O(log n), ale udržuje seřazení a umí range queries.
- `BitSet` nebo bitmapa je výborná pro velké množiny boolean hodnot.
- Primitive/type-specific kolekce se hodí, když boxing (`Integer`, `Long`) vytváří moc objektů.

Tohle je space-time trade-off: často přidáš paměť nebo redundanci, aby běžná operace byla rychlejší.

> [!note] Ke státnicím
> Čtyři strategie: Packing (méně bitů, víc do cache line), Augmentation (redundantní data pro rychlejší operace), Precomputation (lookup tables), Sparsity/Caching (nepočítej zbytečně). Vždy trade-off paměť vs. čas.

# Optimalizace logiky

## Early exit

Pokud už znáš výsledek, nepokračuj ve výpočtu.

```java
boolean containsNegative(int[] xs) {
    for (int x : xs) {
        if (x < 0) {
            return true;
        }
    }
    return false;
}
```

Bez early exit by program prošel celé pole i tehdy, když je odpověď jasná po prvním prvku.

## Short-circuit evaluation

V `if (A && B)` se B nevyhodnotí, pokud A je false. Pokud je A levný test a B drahý výpočet → dej A na první místo.

**Pravidlo:** Levné podmínky (integer comparison) dávej před drahé (volání funkce, přístup do paměti).

## Reordering conditions

Pokud máš sérii nezávislých podmínek, přeuspořádej je podle kombinace:
- **Pravděpodobnosti selekce** — podmínky, které nejčastěji selžou, dávej první (short-circuit).
- **Ceny vyhodnocení** — levné podmínky dávej první.

**Příklad:** Validace vstupu — nejdřív ověř, zda je číslo v rozsahu (levné), pak teprve zda prvočíslo (drahé).

## Loop unswitching

Místo:
```c
for (int i = 0; i < N; i++) {
    if (condition) { /* jedna větev */ }
    else { /* druhá větev */ }
}
```
Přepiš na:
```c
if (condition) {
    for (int i = 0; i < N; i++) { /* jedna větev */ }
} else {
    for (int i = 0; i < N; i++) { /* druhá větev */ }
}
```
**Proč:** Podmínka se vyhodnocuje N-krát místo 1×. Branch predictor nemusí hádat. LLVM to někdy udělá automaticky, ale ne vždy.

## Avoid repeated work

Nevytahuj opakovaně stejné hodnoty, pokud se mezi iteracemi nemění.

```java
// Špatně: pattern se kompiluje v každé iteraci.
for (String line : lines) {
    if (Pattern.compile("[0-9]+").matcher(line).find()) {
        count++;
    }
}

// Lépe: invariant je mimo smyčku.
Pattern digits = Pattern.compile("[0-9]+");
for (String line : lines) {
    if (digits.matcher(line).find()) {
        count++;
    }
}
```

Tohle je ruční varianta myšlenky, kterou kompilátory znají jako loop invariant code motion. Překladač ale neumí bezpečně přesunout všechno, hlavně pokud je ve hře alokace, I/O, výjimky nebo volání cizí knihovny.

## Fast path / slow path

Častý případ dej do jednoduché a rychlé větve. Složitý nebo vzácný případ odsuň do slow path.

```java
if (input.isAscii()) {
    return parseAsciiFast(input);
}
return parseUnicodeSlow(input);
```

Smysl není psát dvě verze všeho. Smysl je nezatěžovat běžný případ kontrolami a abstrakcemi, které jsou potřeba jen pro výjimky.

# Optimalizace smyček

## Loop invariant extraction

Když výraz ve smyčce nezávisí na `i`, vytáhni ho ven.

```c
// Před:
for (int i = 0; i < n; i++) {
    out[i] = in[i] * expensive_scale(config);
}

// Po:
double scale = expensive_scale(config);
for (int i = 0; i < n; i++) {
    out[i] = in[i] * scale;
}
```

## Loop unrolling

Místo:
```c
for (int i = 0; i < N; i++) { a[i] += b[i]; }
```
Přepiš na:
```c
for (int i = 0; i < N; i += 4) {
    a[i]   += b[i];
    a[i+1] += b[i+1];
    a[i+2] += b[i+2];
    a[i+3] += b[i+3];
}
```

**Proč pomáhá:**
- Méně testů podmínky smyčky a méně inkrementací (`i++`).
- Větší instrukční okno pro out-of-order execution → lepší ILP.
- Překladač (LLVM) toto dělá automaticky (`-O2`, `-O3`). Manuální unrolling je jen pro případy, kde překladač selhá.

## Loop fusion

Spoj dvě smyčky přes stejná data do jedné:

```c
// Před (2 průchody přes pole):
for (int i = 0; i < N; i++) { a[i] = f(i); }
for (int i = 0; i < N; i++) { b[i] = g(a[i]); }

// Po (1 průchod):
for (int i = 0; i < N; i++) { a[i] = f(i); b[i] = g(a[i]); }
```

**Proč:** Data zůstanou v cache mezi výpočty `f` a `g`. Jinak druhá smyčka znovu načte celé pole z DRAM (eviction).

## Loop fission

Opak fusion je fission: jednu složitou smyčku rozdělíš na dvě jednodušší. Pomůže, když jedna smyčka dělá příliš mnoho nezávislých věcí najednou, zvyšuje register pressure, kazí vectorizaci nebo míchá hot a cold větve.

```c
// Někdy špatně: jedna smyčka míchá dvě nezávislé práce.
for (int i = 0; i < n; i++) {
    a[i] = f(x[i]);
    if (rare_condition(i)) {
        log_slow_case(i);
    }
}

// Někdy lépe: hot výpočet zůstane čistý.
for (int i = 0; i < n; i++) {
    a[i] = f(x[i]);
}
for (int i = 0; i < n; i++) {
    if (rare_condition(i)) {
        log_slow_case(i);
    }
}
```

Fusion není vždy lepší. Vždy záleží na cache, větvení a tom, co opravdu měří profiler.

Proč to může zrychlit:
Hot smyčka zůstane jednodušší: má méně větvení, menší register pressure a kompilátor ji snáze vectorizuje. Rare/slow část se přesune mimo hlavní výpočet, takže běžný případ neplatí cenu za výjimečný případ.
## Strength reduction

Nahraď drahou operaci levnější, pokud tím nezměníš význam programu.

```c
// Před:
for (int i = 0; i < n; i++) {
    offset = i * stride;
    use(base + offset);
}

// Po:
int offset = 0;
for (int i = 0; i < n; i++) {
    use(base + offset);
    offset += stride;
}
```

Moderní překladač to často udělá sám. Ručně má smysl hlavně tehdy, když výraz schovává abstrakce, volání funkcí nebo složitější indexaci.

## Loop tiling / blocking

Pro 2D operace (matice, obrázky) rozděl smyčku na bloky, které se vejdou do cache:

```c
// Klasicky (špatné pro cache):
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        for (int k = 0; k < N; k++)
            C[i][j] += A[i][k] * B[k][j];

// Tiled (cache-friendly):
for (int ii = 0; ii < N; ii += BLOCK)
  for (int jj = 0; jj < N; jj += BLOCK)
    for (int kk = 0; kk < N; kk += BLOCK)
      for (int i = ii; i < ii+BLOCK; i++)
        for (int j = jj; j < jj+BLOCK; j++)
          for (int k = kk; k < kk+BLOCK; k++)
            C[i][j] += A[i][k] * B[k][j];
```

**Detaily** jsou v kapitole o cache → [[6. Cache, paměť a cache-efektivní algoritmy#Příklad: násobení matic|Příklad: násobení matic]].

# Optimalizace funkcí

## Function inlining

Volání funkce má overhead: uložení registrů, skok na adresu, nastavení stack frame, návrat. Pro malé funkce může být overhead větší než samotný kód.

**Inlining** = překladač zkopíruje tělo funkce přímo na místo volání. Eliminuje overhead + umožňuje další optimalizace (constant folding, dead code elimination v kontextu volání).

```c
// Překladač může inlinovat:
inline int max(int a, int b) { return a > b ? a : b; }
```

**Kdy je inlining nebezpečný:** Velké funkce volané na mnoha místech → code bloat → větší binárka → instrukční cache miss.

**LTO (Link-Time Optimization):** Moderní překladače inlinují přes hranice kompilačních jednotek díky LTO.

## Tail call optimization

Rekurzivní volání na konci funkce (tail call) lze přeložit jako skok místo nového stack frame → O(N) stack → O(1) stack.

```c
// Tail recursive factorial (překladač optimalizuje):
int fact(int n, int acc) {
    if (n == 0) return acc;
    return fact(n - 1, n * acc); // tail call
}
```

## Coarsening (granularity)

Rozděl práci na hrubší granuly — méně volání funkcí, méně synchronizace (v paralelním kontextu). Příklad: místo rekurzivního mergesort do hloubky 1 přepni na insertion sort pro malá pole.

## Avoid allocation in hot path

Alokace je v moderních runtimes často rychlá, ale není zdarma. V Javě navíc zvyšuje allocation rate a tím i GC pressure.

Typické zdroje zbytečných alokací:

- vytváření dočasných kolekcí v každé iteraci;
- `String` concatenation ve smyčce místo `StringBuilder`;
- `Pattern.compile(...)` v hot path;
- boxing primitiv (`int` → `Integer`) ve velkých kolekcích;
- stream pipeline v kódu, který běží milionkrát za sekundu.

Neznamená to "nikdy nealokuj". Znamená to: v hot path sleduj allocation rate a alokace odstraňuj, když profiler ukáže problém.

## Specialization

Obecný kód je pohodlný, ale někdy platí za flexibilitu. Pokud existuje velmi častý jednoduchý případ, specializovaná větev může být rychlejší.

Příklady:

- parser má rychlou cestu pro ASCII a pomalou pro Unicode;
- kolekce má specializovanou implementaci pro primitivní typy;
- algoritmus používá insertion sort pro malá pole a jiný sort pro velká pole;
- server má samostatnou cestu pro cache hit a cache miss.

# Praktické optimalizace mimo CPU

## Batching a buffering

Batching spojuje mnoho malých operací do jedné větší. Pomáhá tam, kde má každá operace fixní overhead.

Příklady:

- poslat 100 záznamů v jednom SQL batchi místo 100 samostatných insertů;
- zapisovat přes buffer místo mnoha malých zápisů na disk;
- serializovat větší blok dat najednou;
- zpracovat zprávy po dávkách místo jedné po druhé.

Nevýhoda: batching často zvyšuje latenci jednotlivé položky, protože čeká na naplnění dávky. Je to throughput vs. latency trade-off.

## Reduce round trips

U databází, sítě a RPC často nedominuje CPU, ale počet cest tam a zpět.

Typický problém je N+1 query:

```text
1 dotaz načte seznam objednávek
N dalších dotazů načte položky pro každou objednávku
```

Lepší bývá join, batch load, cache nebo změna API tak, aby jeden request vrátil data pohromadě.

## Reduce shared state

V paralelním kódu často není problém samotný výpočet, ale sdílení:

- jeden globální lock;
- jeden sdílený counter;
- jedna fronta pro všechna vlákna;
- jedna cache s hrubým zámkem.

Praktické strategie:

- per-thread data;
- sharding;
- lock striping;
- batching zápisů;
- redukce sdíleného mutable stavu.

Detaily synchronizace budou později, tady stačí intuice: čím méně vláken bojuje o stejný objekt, tím lépe se systém škáluje.

# Anti-patterny a checklist

## Anti-patterny

- **Premature optimization:** optimalizuješ předtím, než víš, kde je problém.
- **Micro-optimization bez profilu:** zrychlíš řádek kódu, který netvoří hot path.
- **Ignorování memory footprintu:** CPU vypadá dobře, ale program zabíjí cache nebo GC.
- **Komplexita bez důvodu:** kód je rychlejší v benchmarku, ale dražší na údržbu a rizikovější.
- **Víra v překladač nebo JIT bez ověření:** compiler dělá hodně, ale neví všechno o workloadu.

## Checklist

Před změnou:

- Mám benchmark nebo produkčně podobné měření?
- Vím, jestli jde o CPU, paměť, alokace, lock, I/O nebo síť?
- Je optimalizovaná část skutečně hot path?

Při změně:

- Měním jednu věc najednou?
- Nezhoršuji správnost, čitelnost nebo bezpečnost?
- Je trade-off explicitní: čas vs. paměť, throughput vs. latency, obecnost vs. specializace?

Po změně:

- Ověřil jsem zlepšení stejným benchmarkem?
- Nezhoršila se p95/p99 latency, paměť nebo GC?
- Nezavedl jsem regresi v jiném workloadu?

> Ke státnicím: Bentleyova pravidla = systematický toolbox. Nejprve měř a redukuj práci. Datové struktury: pack, augment, precompute, avoid work. Smyčky: invariant extraction, unroll, fuse/fission, strength reduction, tile. Funkce: inline, tail call, coarsening, specialization. Prakticky: batching, méně round trips, méně alokací v hot path, méně sdíleného stavu. Vždy měř — překladač dělá hodně automaticky, ale nezná celý workload.
