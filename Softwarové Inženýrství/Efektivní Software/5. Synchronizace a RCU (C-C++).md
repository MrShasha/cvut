# Proč synchronizace existuje

Synchronizace typicky řeší pět problémů:

- **atomicita** — operace se musí provést jako jeden nedělitelný krok;
- **mutual exclusion** — do kritické sekce smí vstoupit jen jedno vlákno;
- **visibility** — zápis jednoho vlákna musí být viditelný pro jiné vlákno;
- **ordering** — instrukce se nesmí přeuspořádat tak, že jiné vlákno uvidí neplatný stav;
- **coordination** — jedno vlákno musí počkat, až jiné vlákno něco dokončí.

## Race condition

Race condition nastane, když výsledek závisí na pořadí přístupů ke sdíleným datům.

```cpp
int counter = 0;

void worker() {
    counter++;
}
```

`counter++` nevypadá nebezpečně, ale na úrovni CPU je to přibližně:

```text
load counter
add 1
store counter
```

Když dvě vlákna načtou stejnou starou hodnotu, obě přičtou 1 a obě zapíšou stejný výsledek. Jedna inkrementace se ztratí.

## Kritická sekce

Kritická sekce je část kódu, která pracuje se sdíleným stavem a nesmí běžet souběžně bez ochrany.

```cpp
std::mutex m;
int counter = 0;

void worker() {
    std::lock_guard<std::mutex> lock(m);
    counter++;
}
```

Tady mutex zajišťuje, že `counter++` provádí vždy jen jedno vlákno.

## Busy waiting jako naivní zámek

```cpp
bool locked = false;

void worker() {
    while (locked) {
        // busy wait
    }

    locked = true;
    critical_section();
    locked = false;
}
```

Tohle je špatně ze dvou důvodů:

- test `while (locked)` a zápis `locked = true` nejsou jedna atomická operace;
- čekající vlákno pálí CPU cykly a nedělá užitečnou práci.

Správný spinlock musí být postavený na atomické operaci. Obyčejná proměnná nestačí.

# Atomic operations a memory ordering

Atomická operace je operace, kterou ostatní vlákna neuvidí "napůl". V C++ se používá `std::atomic`.

```cpp
std::atomic<int> counter{0};

void worker() {
    counter.fetch_add(1, std::memory_order_relaxed);
}
```

Tady se inkrementace neztratí, protože `fetch_add` je atomická read-modify-write operace.

## Compare-and-swap

CAS, tedy compare-and-swap nebo compare-exchange, je základ mnoha lock-free algoritmů.

```cpp
std::atomic<int> value{10};
int expected = 10;

bool ok = value.compare_exchange_strong(expected, 20);
```

Význam:

- pokud `value == expected`, nastav `value = 20` a vrať `true`;
- pokud už někdo hodnotu změnil, operace selže a do `expected` se zapíše aktuální hodnota.

CAS je silný nástroj, ale není zadarmo. Při contention může mnoho vláken opakovaně selhávat a zatěžovat cache coherency.

## ABA problém

ABA problém vznikne, když vlákno vidí hodnotu `A`, jiné vlákno ji změní na `B` a pak zpět na `A`.

```text
T1 přečte pointer A
T2 změní A -> B -> A
T1 vidí A a myslí si, že se nic nezměnilo
```

Pro jednoduché čítače to často nevadí. U lock-free datových struktur to může být zásadní problém, protože objekt na adrese `A` už nemusí být stejný logický objekt.

Řešení bývá version counter, tagged pointer, hazard pointers, epoch-based reclamation nebo RCU.

## Memory ordering

Atomická operace řeší atomicitu. Memory ordering řeší, v jakém pořadí smí vlákna vidět zápisy.

| Order | Co garantuje | Typické použití |
|---|---|---|
| `memory_order_relaxed` | Pouze atomicitu, ne pořadí | statistiky, čítače bez vazby na data |
| `memory_order_acquire` | Následující čtení/zápisy se nepřesunou před load | čtení publikovaného stavu |
| `memory_order_release` | Předchozí čtení/zápisy se nepřesunou za store | publikace hotových dat |
| `memory_order_acq_rel` | acquire + release pro read-modify-write | CAS, exchange, fetch_add se synchronizací |
| `memory_order_seq_cst` | nejsilnější globální pořadí | default, nejjednodušší pro korektnost |

Typický producer-consumer vzor:

```cpp
int data = 0;
std::atomic<bool> ready{false};

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
    }

    use(data); // garantovaně vidí data = 42
}
```

`release` říká: "všechno před tímto store musí být viditelné, než je viditelný flag".

`acquire` říká: "když uvidím flag, musím vidět i zápisy, které byly před release".

# Mutex a RAII

Mutex zajišťuje vzájemné vyloučení. V jednu chvíli ho vlastní nejvýše jedno vlákno.

Důležité: mutex není jedna speciální "mutex instrukce" v CPU. Je to synchronizační abstrakce z runtime/knihovny/OS, postavená typicky nad:

- atomickou instrukcí pro rychlé získání locku;
- paměťovými bariérami pro správnou viditelnost dat;
- schedulerem operačního systému, pokud musí vlákno čekat;
- kernelovou wait queue nebo podobným mechanismem při contention.

Proto má mutex dvě tváře: bez sporu může být velmi levný userspace fast path, při sporu se z něj stane OS-level čekání s context switchi a probouzením vláken.

```cpp
std::mutex m;
std::vector<int> values;

void add(int x) {
    std::lock_guard<std::mutex> lock(m);
    values.push_back(x);
}
```

Co mutex řeší:

- chrání invariant sdílené datové struktury;
- zajišťuje, že kritickou sekci vykonává jen jedno vlákno;
- poskytuje synchronizační hranici: `lock()` funguje jako acquire operace a `unlock()` jako release operace.

Acquire/release význam mutexu:

```cpp
std::mutex m;
std::vector<int> values;

// Thread A
m.lock();
values.push_back(1);
m.unlock(); // release: změny před unlockem se publikují

// Thread B
m.lock();   // acquire: po úspěšném locku vidí změny publikované unlockem
auto x = values.back();
m.unlock();
```

Smysl: změny provedené v kritické sekci před `unlock()` budou korektně viditelné jinému vláknu po úspěšném `lock()` stejného mutexu.

## Co se děje při locku

Moderní mutex obvykle nemá syscall při každém `lock()`. Má rychlou cestu a pomalou cestu.

```text
std::mutex::lock()
    |
    |-- fast path: lock je volný
    |       -> atomická operace v userspace
    |       -> žádný syscall
    |       -> vlákno hned pokračuje
    |
    |-- krátký contention
    |       -> runtime může chvíli spinovat v userspace
    |       -> vlákno pořád běží na CPU
    |       -> čeká se, že lock bude rychle uvolněn
    |
    |-- dlouhý contention
            -> runtime zavolá kernel
            -> vlákno se uspí
            -> CPU může běžet jiné vlákno
            -> po unlocku kernel čekající vlákno probudí
```

Rozdíl mezi čekáním:

| Typ čekání | Kde se děje | Co dělá vlákno | Výhoda | Nevýhoda |
|---|---|---|---|---|
| **Userspace atomic fast path** | userspace | nečeká, jen atomicky získá lock | nejrychlejší případ | funguje jen když je lock volný |
| **Userspace spinning** | userspace | aktivně točí smyčku a pálí CPU | dobré pro velmi krátké čekání | plýtvá CPU při delším čekání |
| **Kernel blocking wait** | kernel | vlákno spí ve wait queue | neplýtvá CPU | syscall, context switch, wakeup latency |

Proto je mutex kompromis:

- když lock skoro nikdo nesdílí, je levný;
- když je lock krátce obsazený, může být levnější chvíli spinovat než hned uspat vlákno;
- když je lock obsazený dlouho, je lepší uspat vlákno, protože aktivní čekání by jen pálilo CPU.

Na Linuxu je typický mechanismus **futex**: fast userspace mutex. Rychlá cesta je v userspace, kernel se použije hlavně při contention.

## RAII v C++

Ruční `lock()` a `unlock()` je chybové:

```cpp
m.lock();
do_work();
m.unlock(); // neproběhne, pokud do_work() vyhodí výjimku
```

Používej RAII:

```cpp
{
    std::lock_guard<std::mutex> lock(m);
    do_work();
} // unlock automaticky v destruktoru
```

`std::lock_guard` je jednoduchý vlastník zámku.

`std::unique_lock` je flexibilnější:

- umí odložené zamčení;
- umí `unlock()` před koncem scope;
- jde přesunout;
- používá se s `std::condition_variable`.

```cpp
std::unique_lock<std::mutex> lock(m);
cv.wait(lock, [] { return ready; });
```

# Deadlock, priority inversion a convoy effect

## Deadlock

Deadlock nastane, když vlákna čekají navzájem na zdroje a žádné nemůže pokračovat.

```text
T1 drží mutex A a čeká na mutex B
T2 drží mutex B a čeká na mutex A
```

Čtyři Coffmanovy podmínky:

- **mutual exclusion** — zdroj může vlastnit jen jedno vlákno;
- **hold and wait** — vlákno drží jeden zdroj a čeká na další;
- **no preemption** — zdroj nelze vláknu násilně odebrat;
- **circular wait** — existuje cyklus čekání.

Praktická prevence:

- zamykej mutexy vždy ve stejném globálním pořadí;
- drž zámky co nejkratší dobu;
- nevolej cizí callbacky pod lockem;
- pro více mutexů použij `std::scoped_lock`.

```cpp
std::mutex a;
std::mutex b;

void f() {
    std::scoped_lock lock(a, b);
    work_with_both();
}
```

## Priority inversion

Priority inversion nastane, když high-priority vlákno čeká na zámek držený low-priority vláknem, ale low-priority vlákno nedostane CPU, protože běží medium-priority vlákno.

Výsledek: high-priority práce stojí kvůli vláknu se střední prioritou.

Typické řešení je **priority inheritance**: vlákno držící mutex dočasně zdědí vyšší prioritu čekajícího vlákna, rychle doběhne a zámek uvolní.

## Convoy effect

Convoy effect vznikne, když jedno pomalé vlákno drží lock a ostatní vlákna se řadí za ním. Po uvolnění locku se probudí více vláken, znovu soutěží o stejný lock a systém tráví čas přepínáním a čekáním.

Časté příčiny:

- I/O uvnitř kritické sekce;
- dlouhý výpočet pod lockem;
- page fault pod lockem;
- příliš hrubý lock chrání moc velkou část systému.

Řešení:

- zmenšit kritickou sekci;
- přesunout I/O mimo lock;
- rozdělit jeden globální lock na jemnější zámky;
- změnit datovou strukturu nebo použít batching.

# Condition variable a semaphore

Mutex chrání sdílený stav. Condition variable slouží k čekání na změnu stavu.

```cpp
std::mutex m;
std::condition_variable cv;
std::queue<Job> queue;

void producer(Job job) {
    {
        std::lock_guard<std::mutex> lock(m);
        queue.push(std::move(job));
    }
    cv.notify_one();
}

void consumer() {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [] { return !queue.empty(); });

    Job job = std::move(queue.front());
    queue.pop();
    lock.unlock();

    process(job);
}
```

Důležité pravidlo:

- `wait()` musí být v loopu nebo s predikátem;
- vlákno při čekání atomicky uvolní mutex;
- po probuzení mutex znovu drží;
- probuzení neznamená automaticky, že podmínka pořád platí.

## Semaphore

Semaphore je čítač dostupných povolení.

```text
acquire() -- sníží čítač; pokud je 0, čeká
release() -- zvýší čítač; případně probudí čekající vlákno
```

Použití:

- connection pool;
- omezení počtu paralelních requestů;
- bounded queue;
- řízení přístupu k N identickým zdrojům.

Rozdíl proti mutexu:

- mutex chrání vlastnictví jedné kritické sekce;
- semaphore počítá kapacitu;
- mutex má typicky jasného vlastníka, který ho musí odemknout;
- semaphore může signalizovat i jiné vlákno.

# Read-write lock

Read-write lock rozlišuje čtenáře a zapisovatele.

```cpp
std::shared_mutex m;
std::unordered_map<std::string, Value> cache;

Value get(const std::string& key) {
    std::shared_lock lock(m);
    return cache.at(key);
}

void put(std::string key, Value value) {
    std::unique_lock lock(m);
    cache[std::move(key)] = std::move(value);
}
```

Vlastnosti:

- více readerů může číst současně;
- writer musí být exkluzivní;
- writer čeká, dokud odejdou existující readery;
- reader často čeká, pokud už čeká writer, aby nedošlo ke starvation.

Rw-lock se hodí, když:

- čtení výrazně převažuje nad zápisy;
- kritická sekce při čtení není úplně triviální;
- data nejde jednoduše kopírovat nebo verzovat;
- potřebuješ konzistentní pohled na aktuální stav.

Rw-lock nemusí být rychlejší než mutex, když:

- čtení je extrémně krátké;
- readerů je mnoho a všichni mění interní počítadlo readerů;
- zápisy jsou častější, než čekáš;
- implementace preferuje writery a tím blokuje nové readery;
- bottleneck je cache line s metadaty locku.

Pointa: rw-lock není "lepší mutex". Je to mechanismus pro konkrétní read-heavy workload.

# Spinlock a futex

## Spinlock

Spinlock aktivně čeká v cyklu, místo aby vlákno uspal.

```cpp
class SpinLock {
    std::atomic_flag flag = ATOMIC_FLAG_INIT;

public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire)) {
            // spin
        }
    }

    void unlock() {
        flag.clear(std::memory_order_release);
    }
};
```

Spinlock dává smysl, když:

- kritická sekce je velmi krátká;
- čekání bude kratší než context switch;
- systém má více CPU jader;
- lock drží vlákno, které skutečně běží na jiném jádře.

Spinlock škodí, když:

- kritická sekce může trvat mikrosekundy až milisekundy;
- vlákno pod lockem může usnout;
- systém je oversubscribed;
- lock chrání I/O;
- běžíš na jednom jádře.

Lepší implementace často používají `pause/yield` instrukci a backoff, aby zbytečně nesaturovaly cache coherency a execution pipeline.

## Futex

Futex znamená **fast userspace mutex**. Není to totéž co `std::mutex`, ale nízkoúrovňový Linux mechanismus, ze kterého se mutexy často staví.

Mentální model:

- `std::mutex` je API v C++ knihovně;
- `pthread_mutex_t` je POSIX mutex v runtime/knihovně;
- `futex` je Linux syscall/mechanismus pro uspání a probuzení vláken podle hodnoty v paměti;
- CPU atomická instrukce řeší rychlé získání locku v userspace.

Futex kombinuje rychlou userspace cestu a kernelové čekání. Kernel se nepoužívá, dokud není důvod opravdu čekat.

Zjednodušeně:

```text
lock volný:
    atomic compare/exchange v userspace
    žádný syscall
    žádný context switch

lock obsazený:
    zkus atomicky získat lock
    pokud to nejde, zavolej futex_wait
    kernel ověří, že hodnota locku je pořád obsazená
    kernel uspí vlákno do wait queue

unlock s čekajícími vlákny:
    vlastník lock uvolní v userspace
    zavolá futex_wake
    kernel probudí jedno nebo více čekajících vláken
```

Proč kernel při `futex_wait` znovu kontroluje hodnotu? Aby se neztratil wakeup. Může se stát, že lock se uvolní mezi userspace kontrolou a uspáním vlákna. Kernel proto uspí vlákno jen tehdy, pokud hodnota v paměti pořád odpovídá očekávanému "lock je obsazený".

## Userspace čekání vs kernelové čekání

Userspace čekání znamená, že vlákno pořád běží na CPU:

```text
while (lock_is_busy()) {
    pause();
}
```

To má smysl jen tehdy, když čekání bude extrémně krátké. Jinak vlákno spotřebuje celý svůj CPU slice a nedělá užitečnou práci.

Kernelové čekání znamená, že vlákno přestane běžet:

```text
futex_wait(&lock_word, expected_value)
```

Kernel ho dá do wait queue a scheduler pustí na CPU jiné vlákno. To je lepší pro delší čekání, ale má cenu:

- syscall user -> kernel;
- context switch;
- pozdější wakeup;
- návrat z kernelu do userspace;
- možné zhoršení cache locality.

Proto běžný mutex není automaticky "drahý syscall". Drahý je hlavně **contended mutex**: lock, o který bojuje více vláken, takže vzniká uspávání, probouzení, context switch a cache invalidace.

# Read-Copy-Update (RCU)

RCU je technika pro read-mostly workload: čtení je extrémně časté, zápis vzácný.

Typické příklady:

- routing tabulky;
- konfigurace;
- seznamy handlerů;
- kernelové datové struktury;
- feature flags;
- data, která se čtou na každém requestu a mění jednou za čas.

## Myšlenka

RCU znamená **Read-Copy-Update**:

- **Read** — reader vezme aktuální pointer a čte;
- **Copy** — writer vytvoří novou verzi dat;
- **Update** — writer atomicky publikuje pointer na novou verzi;
- **Grace period** — stará verze se uvolní až tehdy, když ji nemůže držet žádný starý reader.

```text
old version:  A  <- starší readery mohou pořád číst
new version:  B  <- nové readery dostanou nový pointer

global pointer se přepne z A na B
A se smaže až po grace period
```

## RCU read path

V kernelovém stylu:

```c
rcu_read_lock();
struct config *cfg = rcu_dereference(global_cfg);
use(cfg);
rcu_read_unlock();
```

Read path je velmi levná, ale není přesné říkat, že je vždy úplně nulová. Podle implementace může obsahovat compiler barrier, memory barrier, preemption tracking nebo bookkeeping kvůli detekci grace period.

Hlavní pointa je jiná: reader nemusí brát sdílený mutex ani inkrementovat jedno globální počítadlo readerů.

## RCU write path

```c
mutex_lock(&writer_lock);

struct config *old = rcu_dereference_protected(global_cfg, true);
struct config *new_cfg = copy_config(old);
new_cfg->value = new_value;

rcu_assign_pointer(global_cfg, new_cfg);

mutex_unlock(&writer_lock);

synchronize_rcu();
free_config(old);
```

Writer bývá dražší:

- alokuje novou verzi;
- kopíruje nebo rekonstruuje data;
- musí publikovat pointer se správným orderingem;
- musí počkat na grace period před uvolněním staré verze.

To je dobrý trade-off jen tehdy, když je zápis opravdu vzácný.

## Grace period

Grace period je interval, po kterém je bezpečné uvolnit starou verzi.

RCU potřebuje vědět, že všechna vlákna, která mohla vidět starý pointer, už opustila read-side critical section.

V kernelu se to řeší přes quiescent states, plánování vláken, preemption model a RCU infrastrukturu. V userspace existují knihovny typu `liburcu`.

## RCU vs copy-on-write vs GC jazyky

RCU je blízké copy-on-write, ale není to jen kopírování.

RCU navíc řeší:

- jak bezpečně publikovat novou verzi;
- jak zabránit readerům vidět napůl inicializovaná data;
- kdy je bezpečné uvolnit starou verzi;
- jak to celé udělat s minimální režií na read path.

V jazycích s GC můžeš často použít podobný pattern:

```java
volatile Config config;

Config read() {
    return config;
}

void update(Config oldConfig) {
    Config newConfig = oldConfig.withNewValue(...);
    config = newConfig;
}
```

GC pomůže s uvolněním staré verze, protože objekt zůstane živý, dokud na něj existují reference. To ale není totéž jako plnohodnotné RCU. Pořád musíš řešit bezpečnou publikaci, immutable data, ordering, konzistenci a cenu kopírování.

# Copy-on-write

Copy-on-write znamená, že při čtení sdílíš existující data a při zápisu vytvoříš novou kopii.

```text
reader -> čte starý snapshot
writer -> vytvoří novou verzi
publish -> nové readery dostanou novou verzi
```

Výhody:

- readery nemusí blokovat writera;
- reader může mít stabilní snapshot;
- dobře se kombinuje s immutable objekty;
- jednoduchý mentální model pro konfigurace a lookup tabulky.

Nevýhody:

- zápis může být drahý kvůli alokaci a kopírování;
- chvíli existuje více verzí dat;
- u velkých struktur může výrazně růst paměťová spotřeba;
- u častých zápisů je to špatný trade-off.

Rozdíl proti RCU:

- copy-on-write je obecný pattern;
- RCU je synchronizační technika, která navíc řeší read-side critical sections, grace period a bezpečné uvolnění starých verzí;
- v GC jazycích je copy-on-write často jednodušší, protože staré verze uklidí GC;
- v C/C++ musíš explicitně vyřešit memory reclamation, jinak riskuješ use-after-free.

# Read-mostly workload

Read-mostly workload znamená, že čtení výrazně převažuje nad zápisem.

Příklad:

```text
99.99 % operací: čtení konfigurace
0.01 % operací: změna konfigurace
```

V takové situaci může být globální mutex špatný, protože serializuje i čtení, které by se jinak navzájem nerušilo.

Možnosti:

| Mechanismus        |                  Čtení |           Zápis | Kdy dává smysl                                |
| ------------------ | ---------------------: | --------------: | --------------------------------------------- |
| Mutex              |          serializované |      jednoduché | málo vláken, jednoduchý kód                   |
| Rw-lock            |      paralelní readery | blokuje readery | read-heavy, ale zápisy nejsou extrémně vzácné |
| RCU                |            velmi levné |           drahé | masivně read-mostly, zápis vzácný             |
| Immutable snapshot |            velmi levné |      kopírování | konfigurace, lookup tabulky, feature flags    |
| Sharding           | paralelní podle shardu |    lokální lock | mapy, cache, per-key state                    |

# Jak vybrat synchronizační mechanismus

| Situace | Dobrá volba | Proč |
|---|---|---|
| Jednoduchá sdílená struktura | `std::mutex` | korektnost, čitelnost, nízké riziko |
| Čekání na událost | `condition_variable` | neplýtvá CPU a čeká na změnu stavu |
| Omezený počet zdrojů | semaphore | přirozený model kapacity |
| Hodně čtení, občas zápis | `std::shared_mutex` | paralelní readery |
| Extrémně krátká kritická sekce | spinlock | vyhne se context switchi |
| Extrémně read-mostly data | RCU/snapshot | minimalizuje read path |
| Čítač/statistika | `std::atomic` | lock by byl zbytečný |
| Per-thread akumulace | thread-local + merge | odstraní sdílený hot spot |

Praktické pravidlo:

1. Začni s nejjednodušším korektním mechanismem.
2. Změř contention, latenci a škálování.
3. Optimalizuj jen konkrétní bottleneck.
4. Pokud lock pálí výkon, nejdřív zkrať kritickou sekci nebo změň granularitu.
5. Lock-free/RCU používej až tehdy, když umíš obhájit složitost.

# Performance bottlenecks synchronizace

Synchronizace zpomaluje různými způsoby:

- **contention** — více vláken chce stejný lock;
- **context switch** — vlákno usne a kernel naplánuje jiné;
- **cache line bouncing** — jádra si přehazují vlastnictví cache line s lockem nebo čítačem;
- **false sharing** — nezávislá data sdílí jednu cache line;
- **NUMA penalty** — vlákna sahají na vzdálenou paměť nebo lock na jiném NUMA uzlu;
- **scheduler latency** — držitel locku zrovna neběží;
- **oversubscription** — vláken je víc než CPU jader;
- **long critical section** — lock chrání příliš mnoho práce.

## False sharing

False sharing nastane, když dvě nezávislé proměnné leží ve stejné cache line a různá jádra do nich zapisují.

```cpp
struct Counters {
    std::atomic<long> a;
    std::atomic<long> b;
};
```

Pokud `a` aktualizuje jedno vlákno a `b` druhé vlákno, může cache line pořád migrovat mezi jádry, i když proměnné logicky nesdílí data.

Řešení:

- oddělit často zapisované hodnoty do různých cache lines;
- použít padding nebo `alignas(64)`;
- agregovat per-thread a sloučit až na konci;
- měřit, protože padding bez bottlenecku jen zvětšuje paměť.

## NUMA

NUMA znamená, že přístup k paměti není stejně drahý ze všech CPU socketů. Vlákno může běžet na jednom socketu a sahat na paměť alokovanou na jiném socketu.

U synchronizace to bolí hlavně tehdy, když:

- jeden globální lock používají vlákna z více socketů;
- atomický čítač leží na vzdáleném NUMA uzlu;
- data chráněná lockem migrují mezi sockety;
- scheduler přesouvá vlákna mezi sockety.

Praktická řešení:

- držet data blízko vláken, která je používají;
- shardovat stav podle NUMA uzlu nebo workeru;
- omezit jeden globální hot lock;
- u serverů sledovat placement vláken a paměti.

Příklad špatného patternu:

```cpp
std::mutex m;

void handle_request(Request r) {
    std::lock_guard<std::mutex> lock(m);
    auto data = read_from_disk(r.path); // I/O pod lockem
    update_global_state(data);
}
```

Lepší:

```cpp
void handle_request(Request r) {
    auto data = read_from_disk(r.path);

    {
        std::lock_guard<std::mutex> lock(m);
        update_global_state(data);
    }
}
```

# Benchmarking synchronizace

U synchronizace nestačí měřit jen průměrný čas operace.

Měř:

- throughput při 1, 2, 4, 8, 16, ... vláknech;
- p50/p95/p99 latenci;
- CPU usage;
- počet context switchů;
- počet lock contention eventů;
- cache misses a cache coherency signály, pokud máš perf/hardware counters;
- chování při různém poměru čtení a zápisů.

Důležité je měřit reprezentativní kritickou sekci. Benchmark prázdného lock/unlock často neodpovídá reálnému systému.

# Časté chyby

- používat obyčejnou proměnnou jako lock;
- předpokládat, že `volatile` v C++ řeší synchronizaci;
- držet mutex během I/O;
- zamykat více mutexů v různém pořadí;
- používat spinlock pro dlouhou kritickou sekci;
- čekat na condition variable bez predikátu;
- používat rw-lock jen proto, že "hodně čteme", bez měření;
- tvrdit, že atomics jsou vždy rychlejší než mutex;
- zapomenout na memory ordering při publikaci dat;
- u RCU uvolnit starou verzi dřív, než doběhla grace period;
- kopírovat v RCU obrovská data při každém zápisu bez odhadu nákladů.

# Zkouškové minimum

**Race condition:** výsledek programu závisí na nedeterministickém pořadí přístupů ke sdíleným datům.

**Mutex:** zaručuje, že kritickou sekci vykonává jen jedno vlákno. Není to jedna CPU instrukce, ale abstrakce runtime/OS nad atomics, memory barriers a čekáním vláken. V C++ se má používat přes RAII (`lock_guard`, `unique_lock`, `scoped_lock`).

**Atomic operation:** nedělitelná operace nad sdílenou hodnotou. Řeší atomicitu, ale memory ordering musíš chápat zvlášť.

**Acquire/release:** běžný model publikace dat mezi vlákny. Writer zapíše data a potom release-store flag/pointer. Reader acquire-load flag/pointer a potom bezpečně čte data.

**Condition variable:** slouží k čekání na změnu stavu. `wait()` musí být s predikátem nebo v loopu.

**Semaphore:** čítač povolení. Hodí se pro omezený počet identických zdrojů.

**Rw-lock:** umožňuje více readerů současně, writer je exkluzivní. Pomáhá u read-heavy workloadu, ale může mít overhead na metadatech a starvation problémy.

**Spinlock:** aktivně čeká. Hodí se jen pro velmi krátké kritické sekce na multicore systému.

**Futex:** rychlá userspace cesta pro uncontended lock, kernelové čekání při contention.

**RCU:** read-mostly technika. Reader čte aktuální verzi s minimální režií, writer vytvoří kopii, publikuje nový pointer a starou verzi uvolní až po grace period.

# Mini tahák

```text
mutex        = jeden dovnitř, ostatní čekají
semaphore    = N povolení pro N paralelních vstupů
condvar      = čekání na změnu stavu
rw-lock      = více readerů, jeden writer
spinlock     = čekání pálením CPU
futex        = rychlý userspace lock + kernel sleep při contention
atomic       = nedělitelná operace, ne automaticky celý protokol
RCU          = read-copy-update, dražší zápis za velmi levné čtení
deadlock     = cyklus čekání na locky
convoy       = fronta vláken za pomalým držitelem locku
```

# Jak navazuje další téma

Synchronizace nejde pochopit bez paměťové hierarchie. Mutex, atomic counter, rw-lock i spinlock často naráží na stejný fyzický problém: více jader sahá na stejnou cache line. Další kapitola proto řeší cache, locality, false sharing, NUMA a cache-efektivní algoritmy.
