# Proč potřebujeme compiler mental model

## Zdrojový kód není to, co vykonává CPU

Programátor píše C/C++/Rust/Java/C#, ale procesor vykonává strojové instrukce konkrétní architektury: x86-64, ARM64, RISC-V atd.

Překladač nebo runtime proto musí udělat několik věcí:

```text
source code
    ↓
parse and check meaning
    ↓
represent program internally
    ↓
optimize
    ↓
generate machine code
    ↓
CPU executes instructions
```

Z performance pohledu je důležité, že mezi zdrojovým kódem a CPU je velká optimalizační vrstva. Někdy odstraní práci, kterou jsi napsal. Někdy ale optimalizaci odmítne, protože by nebyla bezpečná.

## Compiler není magie

Compiler může změnit program jen tehdy, když zachová jeho pozorovatelné chování.

Může například:

- spočítat konstanty během kompilace;
- odstranit nedosažitelný kód;
- vložit malou funkci přímo na místo volání;
- přesunout invariantní výpočet ze smyčky;
- vektorizovat nezávislé iterace smyčky;
- vybrat lepší instrukce a registry.

Nemůže bezpečně:

- ignorovat side effects;
- předpokládat, že dva pointery neukazují na stejnou paměť, pokud to nedokáže;
- měnit pořadí volatile/atomic operací;
- odhadnout produkční workload bez profilovacích dat;
- inlinovat přes hranice modulu, pokud nevidí definici funkce.

# Compiler pipeline

## Základní architektura

Typická native compiler pipeline:

```text
source code (.c/.cpp/.rs)
    ↓
frontend
    lexer, parser, semantic analysis
    ↓
AST
    stromová reprezentace zdrojového programu
    ↓
IR
    nižší reprezentace vhodná pro optimalizace
    ↓
middle-end optimizer
    machine-independent passes
    ↓
backend
    machine-specific passes
    ↓
object file / executable
```

Tohle je **obecný model překladače**. Není to ještě "LLVM-specific". LLVM používá stejnou logiku, jen pro jednotlivé části používá konkrétní komponenty: například Clang jako frontend, LLVM IR jako IR a LLVM backendy pro x86-64/ARM64/RISC-V.

## Frontend

Frontend rozumí konkrétnímu jazyku.

Řeší:

- **tokenizaci** — rozdělí text programu na tokeny, například klíčová slova, identifikátory, operátory, závorky a literály;
- **parsing** — z tokenů sestaví syntaktickou strukturu programu podle gramatiky jazyka;
- **syntaktické chyby** — odhalí špatně napsaný program, například chybějící závorku, středník nebo neplatnou konstrukci;
- **typovou kontrolu** — ověří, že operace dávají smysl pro dané typy, například že nesčítáš objekt s funkcí;
- **overload resolution** — vybere správnou přetíženou funkci nebo metodu podle typů argumentů;
- **semantic analysis** — ověří význam programu, například scope proměnných, viditelnost symbolů, návratové typy a pravidla jazyka;
- **vytvoření AST** — převede program do stromové reprezentace, která zachycuje strukturu a význam zdrojového kódu;
- **převod do IR** — sníží jazykově specifický AST do obecnější reprezentace vhodné pro optimalizace.

Příklad: **Clang** je frontend pro C/C++/Objective-C nad LLVM.

## Middle-end

Middle-end optimalizuje program nad IR. Neřeší ještě konkrétní CPU. Pracuje s hodnotami, větvemi, smyčkami, funkcemi a datovými závislostmi.

Sem patří například:

- **constant folding** — spočítá konstantní výrazy už při kompilaci, takže se nemusí počítat za běhu;
- **constant propagation** — dosadí známé konstantní hodnoty dál v programu a tím otevře další optimalizace;
- **dead code elimination** — odstraní kód, který nemůže ovlivnit výsledek programu;
- **common subexpression elimination** — najde opakovaný výpočet a spočítá ho jen jednou;
- **inlining** — vloží tělo malé nebo často volané funkce přímo na místo volání;
- **loop invariant code motion** — vytáhne ze smyčky výpočty, které se mezi iteracemi nemění;
- **loop unrolling** — rozbalí část smyčky, aby se snížil počet skoků a testů podmínky;
- **vectorization** — převede nezávislé operace nad polem na SIMD instrukce, které zpracují více prvků najednou.

## Backend

Backend zná cílovou architekturu.

Řeší:

- **výběr instrukcí** — převede obecné IR operace na konkrétní instrukce cílového procesoru;
- **register allocation** — rozhodne, které hodnoty budou v registrech a které se musí dočasně uložit do paměti;
- **instruction scheduling** — přeuspořádá nezávislé instrukce tak, aby CPU méně čekalo na pomalé operace;
- **branch placement** — uspořádá větve a bloky kódu tak, aby častá cesta měla lepší layout v instruction cache;
- **peephole optimalizace** — lokálně nahradí krátkou sekvenci instrukcí kratší nebo rychlejší variantou;
- **ABI/calling convention** — dodrží pravidla platformy pro volání funkcí, předávání argumentů, návratové hodnoty a použití registrů;
- **finální assembly/object code** — vygeneruje výsledný strojový kód nebo objektový soubor pro linker.

# AST, IR, CFG a SSA

## AST

**AST (Abstract Syntax Tree)** je stromová reprezentace zdrojového programu.

Příklad:

```c
return a + b * c;
```

AST zachytí význam:

```text
Return
└── Add
    ├── a
    └── Multiply
        ├── b
        └── c
```

Důležité: AST je pořád blízko zdrojovému jazyku. Hodí se pro typovou kontrolu a jazykovou analýzu, ale není ideální pro nízkoúrovňové optimalizace.

## IR

**IR (Intermediate Representation)** je mezireprezentace mezi AST a machine code.

LLVM IR je:

- typované;
- nižší než zdrojový jazyk;
- vyšší než konkrétní assembly;
- vhodné pro optimalizační passes;
- nezávislé na konkrétní cílové architektuře.

Smysl IR:

```text
many languages -> one IR -> many CPU backends
```

Díky tomu se optimalizace nemusí psát zvlášť pro každý jazyk a každou architekturu.

## CFG

**CFG (Control Flow Graph)** popisuje, kudy může program běžet.

Program se rozdělí na **basic blocky**. Basic block je sekvence instrukcí, do které se vstoupí na začátku a odejde na konci.

Příklad:

```c
if (x > 0) {
    y = x + 1;
} else {
    y = 0;
}
return y;
```

CFG mentálně:

```text
entry
  ↓
test x > 0
  ├─ true  -> y = x + 1 ┐
  └─ false -> y = 0     ├-> return y
```

CFG je základ pro optimalizace větví, smyček, dead code elimination a branch placement.

## SSA

**SSA (Static Single Assignment)** znamená, že každá IR hodnota je definována právě jednou.

Zdrojový kód:

```c
x = 1;
x = x + 2;
```

SSA intuice:

```text
x1 = 1
x2 = x1 + 2
```

U spojení větví vzniká **phi function**:

```text
true branch:  y1 = x + 1
false branch: y2 = 0
join:         y3 = phi(y1, y2)
```

Proč SSA pomáhá:

- jasně ukazuje závislosti mezi hodnotami;
- usnadňuje constant propagation;
- usnadňuje dead code elimination;
- pomáhá register allocation;
- zjednodušuje analýzu smyček.

# LLVM jako konkrétní implementace pipeline

LLVM není druhá odlišná struktura vedle compiler pipeline. Je to **konkrétní implementace té samé pipeline**.

Obecně:

```text
source code -> frontend -> IR -> optimizer -> backend -> machine code
```

V LLVM světě:

```text
C/C++ source
    -> Clang frontend
    -> LLVM IR
    -> LLVM middle-end passes
    -> LLVM backend
    -> x86-64 / ARM64 / RISC-V machine code
```

Stejná struktura, konkrétní názvy:

| Obecný pojem | V LLVM |
|---|---|
| frontend | Clang pro C/C++, rustc frontend pro Rust, Swift frontend atd. |
| IR | LLVM IR |
| middle-end optimizer | LLVM passes nad IR |
| backend | LLVM backend pro x86-64, ARM64, RISC-V... |
| machine code | výsledný objektový soubor nebo executable |

![[Assets/ESW/llvm-pipeline.svg]]

Praktický důsledek: nový jazyk může generovat LLVM IR a získat existující optimizer a backendy. Nový backend zase může obsloužit více jazyků, které LLVM IR používají.

# Optimalizační průchody

Optimalizační průchod (**pass**) je jedna analýza nebo transformace programu. Passes se často řetězí: jeden pass zjednoduší program, další díky tomu najde další optimalizaci.

## High-level passes

High-level passes pracují nad IR, CFG a SSA. Ještě neřeší konkrétní registry ani instrukce procesoru.

### Constant folding

Spočítá konstantní výraz během kompilace.

```c
int seconds = 60 * 60 * 24;
```

Výsledek v binárce může být rovnou:

```c
int seconds = 86400;
```

Runtime už neplatí za násobení.

### Constant propagation

Když compiler ví, že hodnota je konstantní, může ji dosadit dál.

```c
const int debug = 0;
if (debug) {
    log();
}
```

Po dosazení `debug = 0` se z větve stane nedosažitelný kód. Pak přijde DCE.

### Dead Code Elimination

Odstraní kód, který nemůže ovlivnit výsledek programu.

Typicky:

- větev, která se nikdy nespustí;
- výpočet, jehož výsledek se nikdy nepoužije;
- funkce, která po inliningu už nemá žádný efekt.

### Common Subexpression Elimination

Najde opakovaný výpočet a spočítá ho jednou.

```c
x = (a * b) + c;
y = (a * b) + d;
```

Může se změnit na:

```c
tmp = a * b;
x = tmp + c;
y = tmp + d;
```

### Function inlining

Vloží tělo malé nebo často volané funkce přímo na místo volání.

Výhody:

- odstraní call overhead;
- umožní constant propagation přes hranici funkce;
- otevře DCE a další optimalizace.

Riziko:

- příliš agresivní inlining zvětší binárku;
- větší kód může zhoršit instruction cache;
- proto compiler používá heuristiky.

### Loop Invariant Code Motion

Vytáhne ze smyčky výpočet, který se mezi iteracemi nemění.

```c
for (int i = 0; i < n; i++) {
    out[i] = in[i] * expensive_scale(config);
}
```

Lepší tvar:

```c
double scale = expensive_scale(config);
for (int i = 0; i < n; i++) {
    out[i] = in[i] * scale;
}
```

Compiler to udělá jen tehdy, když je bezpečné přesunout volání mimo smyčku. Pokud funkce může mít side effect, vyhodit výjimku nebo záviset na globálním stavu, nemusí to udělat.

### Loop unrolling

Zvětší tělo smyčky, aby se snížil počet skoků a testů podmínky.

Pomáhá:

- snížit loop overhead;
- zvětšit instrukční okno pro CPU;
- někdy pomoci vectorizaci.

Riziko:

- větší kód;
- horší instruction cache;
- ne vždy rychlejší.

### Vectorization

Převede skalární operace na SIMD operace.

```c
for (int i = 0; i < n; i++) {
    c[i] = a[i] + b[i];
}
```

Pokud jsou iterace nezávislé a data se nepřekrývají, compiler může použít SSE/AVX/NEON a sečíst více prvků najednou.

Typické překážky:

- pointer aliasing;
- nepředvídatelné větve uvnitř smyčky;
- špatný data layout;
- závislost mezi iteracemi.

## Low-level passes

Low-level passes už závisí na cílové architektuře.

### Instruction selection

Vybere konkrétní strojové instrukce pro IR operace.

Například obecné "integer add" se musí převést na instrukci dané ISA.

### Register allocation

Rozhoduje, které hodnoty budou v registrech a které musí do paměti.

Pokud je současně živých příliš mnoho hodnot, vzniká **spilling**:

```text
registers full
    ↓
store value to stack
    ↓
use register for something else
    ↓
load value back later
```

V hot loopu může spilling výrazně zpomalit program.

### Instruction scheduling

Přehází nezávislé instrukce tak, aby CPU méně čekalo.

Příklad: pokud load z paměti trvá déle, backend může mezi load a použití hodnoty vložit jiné nezávislé instrukce.

### Peephole optimization

Lokálně nahradí krátkou sekvenci instrukcí kratší nebo rychlejší sekvencí.

Příklad:

```text
x * 2  ->  x << 1
```

Platí jen pokud je náhrada bezpečná pro daný typ a architekturu.

### Branch placement

Uspořádá větve tak, aby častá cesta měla lepší layout v instruction cache a méně skoků.

PGO zde pomáhá, protože dodá reálná data o tom, která větev je hot.

# Limity překladače

Compiler optimalizuje jen to, co může bezpečně dokázat.

## Aliasing

Aliasing znamená, že dvě reference nebo pointery mohou ukazovat na stejnou paměť.

```c
void add(int *a, int *b, int *c, int n) {
    for (int i = 0; i < n; i++) {
        c[i] = a[i] + b[i];
    }
}
```

Compiler nemusí vědět, jestli `c` nepřekrývá `a` nebo `b`. Pokud se překrývají, vectorizace by mohla změnit výsledek.

Možná pomoc v C/C++:

```c
void add(int * restrict a, int * restrict b, int * restrict c, int n)
```

`restrict` je slib programátora, že pointery nealiasují.

## Side effects

Compiler nesmí odstranit nebo přesunout operaci, která má pozorovatelný efekt.

Side effect může být:

- zápis do globální proměnné;
- I/O;
- volatile access;
- atomic operation;
- vyhození výjimky;
- volání funkce, jejíž tělo compiler nevidí.

## Runtime data

Compiler nezná hodnoty, které přijdou až za běhu. Proto nemusí vědět:

- která větev bude častá;
- jaký konkrétní typ přijde do polymorfního volání;
- jak velké budou vstupy;
- jestli workload odpovídá benchmarku.

To řeší PGO nebo JIT profiling.

## Virtual dispatch

U `virtual`/`abstract` volání nemusí být jasné, jaká implementace se spustí.

Důsledek:

- horší inlining;
- méně constant propagation;
- více nepřímých skoků;
- horší branch prediction.

Moderní JITy i AOT compilery umí **devirtualizaci**, pokud dokážou konkrétní typ odvodit.

## Hranice kompilačních jednotek

Bez LTO compiler často nevidí tělo funkce z jiného `.c/.cpp` souboru. Pak nemůže dobře inlinovat ani odstranit mrtvý kód přes hranici modulu.

# Compiler flags a build režimy

## Optimalizační úrovně

- **`-O0`** — bez optimalizací, vhodné pro debug, výkon není reprezentativní.
- **`-O1`** — základní optimalizace.
- **`-O2`** — běžný release default, dobrý poměr výkonu, velikosti a compile time.
- **`-O3`** — agresivnější inlining, unrolling, vectorization; nemusí být vždy rychlejší.
- **`-Os` / `-Oz`** — optimalizace na velikost binárky; někdy zlepší instruction cache.
- **`-Ofast`** — agresivní optimalizace, může porušit striktní standardní sémantiku, hlavně floating-point.

Prakticky: začni s `-O2`, měř, potom zkoušej `-O3`, `-march=native`, LTO nebo PGO.

## Debug vs release

Profilovat debug build pro výkon je špatně.

Debug build:

- má vypnuté nebo omezené optimalizace;
- neinlinuje jako release;
- má jiný layout kódu;
- může obsahovat dodatečné kontroly;
- neodpovídá produkčnímu chování.

Performance profiluj na release buildu s reprezentativními vstupy.

## `-march=native`

`-march=native` dovolí compileru použít instrukce konkrétního CPU, na kterém se kompiluje.

Výhoda:

- AVX/SSE/BMI/NEON podle CPU;
- lepší vectorizace;
- lepší instruction selection.

Riziko:

- binárka nemusí běžet na starším nebo jiném CPU.

## LTO

**LTO (Link-Time Optimization)** posune část optimalizace až do linkování, kdy je vidět větší část programu.

```text
file1.cpp -> object/IR ┐
file2.cpp -> object/IR ├-> linker optimizer -> executable
file3.cpp -> object/IR ┘
```

Výhoda:

- cross-module inlining;
- odstranění nepoužitého kódu;
- lepší specializace.

Cena:

- delší build;
- vyšší paměťová náročnost;
- někdy složitější debug.

# PGO, JIT a profiling

## PGO

**Profile-Guided Optimization** dodá AOT compileru informaci o reálném běhu programu.

Postup:

```text
1. compile with instrumentation
2. run representative workload
3. recompile with collected profile
```

PGO pomáhá hlavně:

- branch layout;
- inlining rozhodnutí;
- hot/cold splitting;
- loop optimizations;
- instruction cache layout.

Podmínka: profil musí odpovídat reálnému workloadu. Špatný profil může optimalizaci zhoršit.

## PGO vs JIT

PGO a JIT řeší podobnou věc: optimizer potřebuje vědět, co je hot.

**PGO:**

- sbírá data v předchozím běhu;
- potom znovu přeloží program;
- výsledná binárka je optimalizovaná před spuštěním.

**JIT:**

- sbírá data během aktuálního běhu;
- překládá hot metody za běhu;
- může reagovat na runtime typy a skutečné větve;
- má warm-up a compilation overhead.

## Profiling compiled programs

Benchmark říká, jestli je program rychlý. Profiling říká, kde tráví čas.

Sampling profiler:

- pravidelně vzorkuje instruction pointer / stack;
- má nízký overhead;
- dává statistický obraz hot path.

Instrumentation profiler:

- vloží měřicí kód do funkcí;
- přesnější pro konkrétní volání;
- má vyšší overhead;
- může změnit chování programu.

## Hardware performance counters

Moderní CPU mají PMU čítače.

Užitečné metriky:

- **cycles** — kolik CPU cyklů program spotřeboval;
- **instructions** — kolik instrukcí se provedlo;
- **IPC** — instructions per cycle;
- **cache-misses** — cache miss rate;
- **branch-misses** — špatně predikované větve;
- **page-faults** — problémy se stránkováním;
- **context-switches** — zásahy scheduleru.

Interpretace:

```text
low IPC + high cache misses
    -> memory/cache bottleneck

low IPC + high branch misses
    -> branch prediction problem

high cycles in lock code
    -> synchronization bottleneck
```

Linux nástroje:

```bash
perf stat ./program
perf record ./program
perf report
perf annotate
```

## Flame graph

Flame graph vizualizuje sampling profiler.

- Šířka bloku = kolik vzorků bylo v daném stacku.
- Svislá osa = call stack.
- Široké bloky = kandidáti na optimalizaci.

Flame graph neříká automaticky, co je chyba. Ukazuje, kde program tráví čas. Interpretace závisí na workloadu.

## Profiling workflow

Správný postup:

1. Benchmarkem ověř, že problém existuje.
2. Spusť sampling profiler.
3. Najdi hot path.
4. Rozliš CPU, cache, branch, lock, I/O nebo GC problém.
5. Změň jednu věc.
6. Ověř stejným benchmarkem.
7. Zkontroluj, že se nezhoršila latency, paměť ani jiný workload.

Nezačínej assembly analýzou. Nejdřív high-level profil. K `perf annotate` a hardware counterům jdi až tehdy, když hot path opravdu vypadá jako CPU/cache problém.

# Časté chyby v myšlení

## "Compiler to určitě optimalizuje"

Možná ano, možná ne. Compiler optimalizuje jen to, co umí bezpečně dokázat.

Typické blokátory:

- aliasing;
- side effects;
- volatile/atomic;
- virtual dispatch;
- chybějící LTO;
- neznámý runtime workload.

## "`-O3` je vždy rychlejší než `-O2`"

Není. `-O3` může zvětšit kód, zhoršit instruction cache nebo zvolit agresivní heuristiku, která pro daný workload nevyjde.

## "Méně instrukcí znamená rychlejší program"

Ne vždy. Program může být limitovaný cache missi, branch prediction, memory bandwidth, I/O nebo locky. Někdy více instrukcí s lepší lokalitou vyhraje.

## "Debug profiling stačí"

Nestačí. Debug build má jiné optimalizace, jiný layout kódu a jiné chování než release.

# Zkouškové minimum

## Co je compiler frontend?

Frontend je část překladače, která rozumí konkrétnímu jazyku. Dělá lexing, parsing, semantic analysis, typovou kontrolu, vytváří AST a převádí program do IR.

## Co je AST?

AST je stromová reprezentace struktury zdrojového programu. Zachycuje význam výrazů a příkazů, ale je pořád blízko zdrojovému jazyku.

## Co je IR?

IR je intermediate representation: meziformát mezi zdrojovým jazykem a machine code. LLVM IR je vhodné pro optimalizace a je nezávislé na konkrétní CPU architektuře.

## Co je CFG?

Control Flow Graph popisuje tok řízení mezi basic blocky. Používá se pro analýzu větví, smyček, dead code elimination a branch placement.

## Co je SSA?

Static Single Assignment je forma IR, kde každá hodnota má právě jednu definici. Při spojení větví se používá phi function.

## Jaký je rozdíl mezi high-level a low-level passes?

High-level passes pracují nad IR a jsou machine-independent. Low-level passes pracují v backendu a závisí na konkrétní architektuře, registrech, instrukcích a ABI.

## Co je PGO?

Profile-Guided Optimization je optimalizace podle profilovacích dat. Program se přeloží s instrumentací, spustí na reprezentativním workloadu a potom se znovu přeloží s profilem.

## Co jsou hardware performance counters?

CPU čítače nízkoúrovňových událostí, například cycles, instructions, cache misses, branch misses, page faults. Pomáhají rozlišit CPU, cache, branch nebo OS problém.

# Mini tahák

```text
Compiler pipeline:
    source -> frontend -> AST -> IR -> optimizer -> backend -> machine code

Frontend:
    language-specific, parser, semantic analysis, AST

IR:
    common representation for optimization

CFG:
    graph of basic blocks and branches

SSA:
    one definition per value, phi at joins

High-level passes:
    constant folding, DCE, CSE, inlining, LICM, unrolling, vectorization

Low-level passes:
    instruction selection, register allocation, scheduling, peephole, branch placement

Compiler limits:
    aliasing, side effects, runtime data, virtual dispatch, no LTO

Flags:
    -O0 debug, -O2 release default, -O3 aggressive, -Os size, -Ofast risky

PGO:
    instrument -> run workload -> recompile with profile

Profiling:
    benchmark says how fast, profiler says where time goes

perf:
    cycles, instructions, IPC, cache misses, branch misses
```
