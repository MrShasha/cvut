# Proč cache vůbec existuje

CPU umí vykonávat instrukce velmi rychle. DRAM je proti tomu pomalá. Kdyby procesor čekal na každý přístup do hlavní paměti, většinu času by nedělal výpočet, ale stál na paměti.

Typická orientační čísla:

```text
register        ~1 cycle
L1 cache        ~4 cycles
L2 cache        ~10-15 cycles
L3 cache        ~30-50 cycles
DRAM            ~200+ cycles
disk/network    ještě mnohem víc
```

Při CPU na 3 GHz trvá jeden cyklus zhruba 0.33 ns. Přístup do DRAM za 70-100 ns tedy znamená stovky cyklů čekání.

## Proč nestačí rychlejší CPU

Zrychlit CPU je jednodušší říct než udělat. Paměť má fyzikální limity:

- signál musí cestovat mimo jádro CPU;
- DRAM buňka je pomalá proti SRAM;
- řadič paměti musí otevřít řádek, načíst data a případně obnovit obsah;
- šířka paměťové sběrnice a počet kanálů jsou omezené;
- více jader soutěží o stejnou paměťovou propustnost.

Cache řeší tenhle rozdíl pomocí předpokladu, že programy mají locality: když použiješ nějaká data teď, pravděpodobně použiješ blízká data nebo stejná data znovu.

# Memory hierarchy

Paměťová hierarchie je trade-off mezi rychlostí, kapacitou a cenou.

| Úroveň | Typická technologie | Vlastnost |
|---|---|---|
| Registry | flip-flopy v CPU | nejrychlejší, extrémně malé |
| L1/L2/L3 cache | SRAM | rychlá, drahá, malá |
| DRAM | dynamická RAM | pomalejší, levnější, velká |
| SSD/disk | storage | persistentní, o řády pomalejší |

## SRAM vs DRAM

**SRAM** se používá pro cache:

- drží hodnotu bez refresh cyklu;
- je rychlá;
- zabírá hodně plochy na čipu;
- je drahá na bit.

**DRAM** se používá pro hlavní paměť:

- ukládá bit jako náboj v kondenzátoru;
- musí se obnovovat;
- čtení řádku je destruktivní na úrovni buňky a obsah se musí obnovit přes sense amplifiers;
- je mnohem hustší a levnější na bit než SRAM.

Pointa pro software: cache je malá a rychlá, DRAM je velká a pomalá. Efektivní kód se snaží pracovat s daty tak, aby aktivní část dat zůstala v cache.

## Cache line

Cache nepracuje s jednotlivými bajty. Z paměti se do cache typicky přenáší **cache line** o velikosti 64 B.

Když přečteš `array[0]`, CPU často načte celou linku:

```text
int32 array:

cache line 64 B = 16 hodnot typu int

array[0] array[1] array[2] ... array[15]
```

První přístup může být cache miss. Další přístupy na `array[1]`, `array[2]`, ... už mohou být cache hit.

## Spatial locality

Spatial locality znamená, že po přístupu na adresu pravděpodobně brzy použiješ blízké adresy.

Dobrý příklad:

```cpp
for (int i = 0; i < n; ++i) {
    sum += a[i];
}
```

To je rychlé, protože data jsou v paměti vedle sebe a hardware prefetcher umí rozpoznat sekvenční přístup.

## Temporal locality

Temporal locality znamená, že stejná data použiješ znovu v krátkém čase.

Dobrý příklad:

```cpp
for (int iter = 0; iter < 1000; ++iter) {
    for (int i = 0; i < small_n; ++i) {
        a[i] = update(a[i]);
    }
}
```

Pokud se `a` vejde do cache, opakované průchody jsou levné.

## Working set

Working set je aktivní množina dat, se kterou program právě pracuje.

Pokud se working set vejde do cache, výkon je dobrý. Pokud je větší než cache, data se pořád vyhazují a znovu načítají.

```text
working set <= cache capacity  -> hodně hitů
working set > cache capacity   -> capacity misses
```

To je důvod, proč se algoritmy často blokují na menší části dat: nechceš pracovat s celou maticí najednou, chceš pracovat s blokem, který se vejde do cache.

# Cache hit, cache miss a typy missů

## Cache hit

Cache hit znamená, že data už jsou v cache. CPU pokračuje rychle.

## Cache miss

Cache miss znamená, že data v cache nejsou. CPU musí čekat na nižší úroveň hierarchie: L2, L3 nebo DRAM.

Cache miss není vždy stejný problém. Různé příčiny mají různá řešení.

| Typ missu | Příčina | Typické řešení |
|---|---|---|
| **Cold miss** | první přístup k datům | prefetching, warm-up, změna pořadí práce |
| **Capacity miss** | working set je větší než cache | blocking/tiling, menší data, komprese layoutu |
| **Conflict miss** | různé adresy padají do stejného cache setu | změna stride, padding, jiný layout |
| **True sharing miss** | více jader opravdu sdílí stejná data | méně sdílení, sharding, redukce atomics |
| **False sharing miss** | různá data leží na stejné cache line | padding, `alignas(64)`, per-thread data |

> [!info]- Cache set, cache line a associativita
> Cache je rozdělená na **sety**. Každý set obsahuje několik **cache lines**.
>
> - **cache line** = blok dat z RAM, typicky 64 B;
> - **cache set** = skupina cache lines;
> - **N-way set-associative cache** = každý set má N míst, tedy N cache lines;
> - **way** = jedno konkrétní místo pro cache line uvnitř setu.
>
> Příklad:
>
> ```text
> L1 cache      = 32 KB
> cache line    = 64 B
> associativita = 8-way
>
> celkem lines = 32 KB / 64 B = 512 cache lines
> počet setů   = 512 lines / 8 ways = 64 sets
> ```
>
> Struktura:
>
> ```text
> Cache
> ├── Set 0
> │   ├── Way 0 -> cache line
> │   ├── Way 1 -> cache line
> │   └── ...
> │   └── Way 7 -> cache line
> ├── Set 1
> │   ├── Way 0 -> cache line
> │   └── ...
> └── Set 63
>     ├── Way 0 -> cache line
>     └── ...
> ```
>
> CPU rozdělí adresu zhruba takto:
>
> ```text
> [ tag | set index | offset ]
> ```
>
> - **offset** vybírá bajt uvnitř cache line;
> - **set index** vybírá cache set;
> - **tag** říká, která oblast RAM v dané line skutečně leží.
>
> Čtení adresy tedy probíhá takto: CPU vybere set podle `set index`, uvnitř setu porovná tagy všech ways, a když tag najde, je to **cache hit**. Když tag nenajde, je to **cache miss** a musí se načíst nová cache line.
>
> Krátce: **cache line** je blok dat, **cache set** je skupina linek, **8-way cache** znamená 8 linek v každém setu. **Direct-mapped cache** je speciální případ `1-way`.

## Cold miss

Cold miss je nevyhnutelný první miss. Data ještě nikdy nebyla načtena.

Příklad: první průchod velkým polem.

## Capacity miss

Capacity miss vzniká, když cache nestačí na working set.

Příklad: algoritmus pořád střídá několik velkých polí, jejichž aktivní část je větší než L1/L2.

Řešení: rozdělit práci do bloků.

## Conflict miss

Conflict miss vzniká kvůli mapování adres do cache setů. I když je v cache celkově volné místo, konkrétní set může být přeplněný.

Typický problém je stride, který je mocninou dvojky a opakovaně trefuje stejné sety.

```text
čteš adresy po 4096 B
cache index bity se opakují
data se perou o stejné sety
```

Řešení:

- změnit velikost struktury;
- přidat padding;
- změnit pořadí průchodu;
- nepoužívat patologický stride.

# Cache organization

Cache není jedna velká tabulka, kde může být libovolná adresa kdekoliv. Hardware musí najít data za pár cyklů, takže cache je organizovaná do setů a ways.

## Direct-mapped cache

Každá adresa může být jen na jednom místě.

Výhoda:

- jednoduchý a rychlý hardware.

Nevýhoda:

- vysoké riziko conflict missů.

## Fully associative cache

Data mohou být kdekoliv v cache.

Výhoda:

- nejméně conflict missů.

Nevýhoda:

- drahé vyhledávání, protože hardware musí porovnávat mnoho tagů.

Používá se spíš u malých struktur, ne jako velká L1/L2 data cache.

## Set-associative cache

Běžný kompromis. Adresa určí set, ale uvnitř setu může být ve více ways.

```text
adresa -> cache set
cache set -> několik ways
```

Například 8-way cache znamená, že jedna adresa patří do konkrétního setu, ale v tomto setu má 8 možných míst.

## Tag, set, offset

Paměťová adresa se pro cache rozpadne na části:

```text
[ tag ][ set/index ][ offset ]
```

- **offset** říká, který bajt v cache line chceš;
- **set/index** říká, do kterého cache setu adresa patří;
- **tag** ověřuje, jestli je v setu opravdu správná paměťová adresa.

U 64B cache line je offset 6 bitů, protože `2^6 = 64`.

# Sequential vs random access

![[Assets/ESW/cache-locality-layout.svg]]

## Sequential access

Sekvenční přístup je cache-friendly:

```cpp
for (int i = 0; i < n; ++i) {
    sum += a[i];
}
```

Výhody:

- využívá celou cache line;
- hardware prefetcher umí načítat dopředu;
- má málo branch problémů;
- často se dobře vektorizuje.

## Random access

Náhodný přístup je cache-unfriendly:

```cpp
for (int i = 0; i < n; ++i) {
    sum += a[index[i]];
}
```

Problémy:

- každá hodnota může být v jiné cache line;
- prefetcher neví, co načíst dopředu;
- vzniká mnoho nezávislých DRAM přístupů;
- pokud další adresa závisí na předchozí hodnotě, CPU nemůže dobře paralelizovat čekání.

## Linked list vs array

Linked list:

```text
[data|next] -> [data|next] -> [data|next]
```

Uzel může být kdekoliv na heapu. Každý `next` může způsobit nový cache miss.

Array:

```text
[d0][d1][d2][d3][d4][d5]...
```

Data jsou kontinuálně. Jeden cache miss načte více prvků.

Proto pole často porazí linked list i v situacích, kde mají papírově podobnou složitost.

# Data layout

## AoS vs SoA

AoS znamená Array of Structures:

```cpp
struct Entity {
    float x, y, z;
    float vx, vy, vz;
    int health;
};

std::vector<Entity> entities;
```

Když zpracováváš jen pozice, cache tahá i `health` a další pole, která nepotřebuješ.

SoA znamená Structure of Arrays:

```cpp
struct Entities {
    std::vector<float> x, y, z;
    std::vector<float> vx, vy, vz;
    std::vector<int> health;
};
```

Když zpracováváš jen `x/y/z`, čteš kompaktní sekvenční pole. To pomáhá cache i SIMD.

## Hot/cold splitting

Hot data jsou data používaná často. Cold data jsou data používaná zřídka.

Špatně:

```cpp
struct User {
    int id;
    int score;
    char large_profile_json[4096];
};
```

Pokud hot loop potřebuje jen `id` a `score`, tahání `large_profile_json` zhorší cache.

Lépe:

```cpp
struct UserHot {
    int id;
    int score;
};

struct UserCold {
    std::string profile_json;
};
```

## Dynamická alokace a pointer chasing

Každá heap alokace může skončit na jiném místě paměti. Hodně malých objektů znamená:

- horší spatial locality;
- větší pointer chasing;
- více metadat alokátoru;
- horší prefetching;
- větší tlak na TLB.

Častá řešení:

- `std::vector` místo linked struktury;
- arena/pool allocator;
- ukládat objekty inline;
- zmenšit objekt footprint;
- oddělit hot a cold fields;
- pracovat po blocích.

# Cache-efficient matrix multiplication

Matrix multiplication je klasický příklad, kde stejná asymptotická složitost může mít úplně jiný výkon.

## Row-major layout

C/C++ ukládá 2D pole po řádcích:

```text
A[0][0] A[0][1] A[0][2] ...
A[1][0] A[1][1] A[1][2] ...
```

Přístup po řádku je sekvenční. Přístup po sloupci má stride.

## Naivní implementace

```cpp
for (int i = 0; i < N; ++i) {
    for (int j = 0; j < N; ++j) {
        for (int k = 0; k < N; ++k) {
            C[i][j] += A[i][k] * B[k][j];
        }
    }
}
```

Problém:

- `A[i][k]` jde po řádku, to je dobré;
- `B[k][j]` jde po sloupci, to je špatné pro row-major layout;
- `C[i][j]` se opakovaně aktualizuje, ale přístup k `B` často dominuje.

## Loop order matters

Změna pořadí smyček může zlepšit locality:

```cpp
for (int i = 0; i < N; ++i) {
    for (int k = 0; k < N; ++k) {
        auto aik = A[i][k];
        for (int j = 0; j < N; ++j) {
            C[i][j] += aik * B[k][j];
        }
    }
}
```

Teď vnitřní smyčka jde přes `B[k][j]` po řádku a přes `C[i][j]` po řádku.

## Blocking / tiling

Tiling rozdělí matici na bloky, které se vejdou do cache.

```cpp
for (int ii = 0; ii < N; ii += BS) {
    for (int kk = 0; kk < N; kk += BS) {
        for (int jj = 0; jj < N; jj += BS) {
            for (int i = ii; i < std::min(ii + BS, N); ++i) {
                for (int k = kk; k < std::min(kk + BS, N); ++k) {
                    auto aik = A[i][k];
                    for (int j = jj; j < std::min(jj + BS, N); ++j) {
                        C[i][j] += aik * B[k][j];
                    }
                }
            }
        }
    }
}
```

Pointa:

- nepracuješ s celou maticí najednou;
- opakovaně používáš bloky, které jsou už v cache;
- snižuješ capacity misses;
- dáváš compileru a CPU lepší šanci na vektorizaci a prefetch.

Velikost bloku se volí podle cache, typu dat a architektury. Není univerzální magické číslo.

## Cache-aware vs cache-oblivious

**Cache-aware** algoritmus zná přibližnou velikost cache nebo bloku a podle toho volí `BS`.

**Cache-oblivious** algoritmus nepoužívá konkrétní velikost cache, ale rekurzivně dělí problém tak, že se některé podproblémy přirozeně vejdou do cache.

Pro státnice většinou stačí: tiling/blocking zmenšuje working set vnitřní smyčky.

# Write policies a streaming writes

Cache se netýká jen čtení. Zápisy mají vlastní pravidla.

## Write-through

Write-through zapisuje změnu do cache i do nižší úrovně paměti hned.

Výhoda:

- jednodušší konzistence.

Nevýhoda:

- více zápisů do nižší paměti.

## Write-back

Write-back zapíše změnu jen do cache line a označí ji jako dirty. Do nižší paměti se zapíše až při evikci.

Výhoda:

- méně trafficu do paměti;
- více zápisů do stejné cache line se může sloučit.

Nevýhoda:

- složitější coherency;
- dirty data musí být zapsána při evikci.

## Write-allocate

Při zápisu do adresy, která není v cache, CPU často nejdřív načte celou cache line do cache a pak do ní zapíše.

To je dobré, pokud budeš linku dál používat. Je to špatné, pokud jen streamuješ velký výstup a stará data nepotřebuješ.

## Write-combining a streaming stores

U velkých sekvenčních zápisů může být výhodné použít non-temporal/streaming stores, které omezí znečištění cache daty, která už nebudeš číst.

Mentální model:

```text
normální store       -> může zatáhnout cache line do cache
streaming store      -> zapisuje sekvenčně a snaží se cache tolik neznečistit
```

Tohle je nízkoúrovňová optimalizace. Má smysl hlavně ve výkonnostně kritickém native kódu po měření.

# Multi-core cache, MESI a false sharing

Každé jádro má vlastní L1/L2 cache. Některá cache, typicky L3, může být sdílená. Když více jader pracuje se stejnou pamětí, hardware musí udržovat cache coherency.

## MESI

MESI je zjednodušený model stavů cache line:

| Stav | Význam |
|---|---|
| **M - Modified** | linka je změněná a jen v tomto jádru |
| **E - Exclusive** | linka je čistá a jen v tomto jádru |
| **S - Shared** | linka je čistá a sdílená více jádry |
| **I - Invalid** | linka je neplatná |

Když jedno jádro chce zapisovat do linky, kterou mají jiná jádra jako shared, musí ostatní kopie invalidovat. To stojí čas a vytváří traffic mezi jádry.

## True sharing

True sharing znamená, že více vláken opravdu pracuje se stejnými daty.

Příklad:

```cpp
std::atomic<long> counter{0};

void worker() {
    counter.fetch_add(1, std::memory_order_relaxed);
}
```

Každé jádro chce zapisovat do stejné cache line. Linka pořád migruje mezi jádry. Atomická operace je korektní, ale škálování může být špatné.

Řešení:

- per-thread čítače;
- sharding;
- batching;
- redukce na konci.

## False sharing

False sharing znamená, že vlákna logicky nesdílí stejnou proměnnou, ale jejich proměnné leží ve stejné cache line.

```cpp
struct Counters {
    std::atomic<long> a;
    std::atomic<long> b;
};

Counters counters;
```

Pokud jedno vlákno zapisuje `a` a druhé `b`, hardware pořád invaliduje celou cache line. Pro CPU je jednotka coherency cache line, ne jednotlivá proměnná.

Řešení:

```cpp
struct alignas(64) PaddedCounter {
    std::atomic<long> value;
};

struct Counters {
    PaddedCounter a;
    PaddedCounter b;
};
```

Pozor: padding není zadarmo. Zvětšuje paměťový footprint. Používej ho tam, kde měření ukáže cache line ping-pong.

# NUMA

UMA znamená Uniform Memory Access: přístup k paměti stojí přibližně stejně ze všech CPU.

NUMA znamená Non-Uniform Memory Access: každý socket má blízkou lokální paměť a vzdálenou paměť na jiném socketu.

```text
CPU socket 0 -- local RAM 0
CPU socket 1 -- local RAM 1

CPU 0 -> RAM 0 = rychlejší
CPU 0 -> RAM 1 = pomalejší
```

## Proč NUMA ovlivňuje výkon

Na multi-socket serveru může vzdálený přístup stát výrazně víc než lokální. Problém se zhorší, když:

- vlákno běží na socketu 0, ale data jsou na socketu 1;
- scheduler přesouvá vlákno mezi sockety;
- jeden globální lock používají vlákna ze všech socketů;
- alokace proběhla v jiném vlákně než výpočet.

## First-touch policy

Mnoho OS používá first-touch policy: fyzická stránka se alokuje na NUMA uzlu toho CPU, který se jí poprvé dotkne.

Špatný pattern:

```text
main thread inicializuje celé pole na socketu 0
worker threads na socketu 1 pak čtou vzdálenou paměť
```

Lepší:

```text
každý worker inicializuje část dat, kterou bude zpracovávat
data se alokují blízko workeru
```

## Thread migration a CPU affinity

Thread migration znamená, že OS přesune vlákno na jiné jádro nebo socket. To může zničit locality:

- cache daného jádra je studená;
- data mohou být na vzdáleném NUMA uzlu;
- locky a atomics mohou začít migrovat mezi sockety.

Nástroje:

```bash
numactl --hardware
numactl --cpunodebind=0 --membind=0 ./program
```

V C/C++ existuje CPU affinity přes OS API. V JVM záleží na runtime, GC a nastavení procesu; NUMA se řeší spíš na úrovni deploymentu, GC konfigurace a pinningu procesu než běžným aplikačním kódem.

# Instruction cache a self-evicting code

Cache není jen pro data. CPU má také instruction cache, která drží instrukce programu.

Self-evicting code vznikne, když hot path obsahuje tolik instrukcí, že se nevejde do instruction cache. CPU pak nečeká na data, ale na načítání instrukcí.

Typické příčiny:

- agresivní inlining;
- obrovské funkce;
- C++ template bloat;
- logging/profiling instrumentace v hot path;
- velké množství málo používaných větví v jedné hot funkci.

Projevy:

- nízké IPC;
- frontend stalls;
- I-cache misses;
- zhoršení po zapnutí instrumentačního profileru.

Řešení:

- držet hot path malou;
- oddělit cold path;
- nepřehánět inlining velkých funkcí;
- používat PGO;
- pro profiling preferovat sampling, pokud instrumentace mění chování.

# Jak cache souvisí se synchronizací a JVM

## Synchronizace

Synchronizace často zpomaluje právě přes cache:

- mutex má interní stav v cache line;
- atomic counter nutí jádra přehazovat cache line;
- rw-lock může mít sdílené počítadlo readerů;
- false sharing může vytvořit contention bez logického sdílení dat;
- spinlock může generovat velký coherency traffic.

To navazuje na 5. kapitolu: lock není drahý jen kvůli OS. Drahé může být i to, že více jader bojuje o stejnou cache line.

## JVM

V JVM se cache projevuje přes layout objektů a alokace:

- objekty na heapu mají header;
- reference znamenají pointer chasing;
- `ArrayList<int>` v Javě neexistuje, `List<Integer>` znamená boxované objekty;
- pole primitiv je cache-friendly;
- TLAB dává vláknu lokální alokační buffer, takže nové objekty stejného vlákna často leží blízko sebe;
- GC může data přesouvat a tím někdy locality zlepšit, ale GC pauzy a pohyb objektů mají vlastní cenu.

Téma JVM layoutu se rozebírá hlouběji v pozdějších kapitolách.

# Profiling cache problémů

Cache problém často poznáš podle toho, že CPU není plně využité výpočtem, ale čeká na paměť.

## Signály

- nízké IPC;
- vysoký počet cache missů;
- vysoké backend memory stalls;
- velký rozdíl mezi sekvenční a náhodnou verzí;
- výkon se zhoršuje s velikostí datasetu skokově, když překročí L1/L2/L3;
- přidání vláken nezrychluje kvůli memory bandwidth nebo coherency.

## `perf stat`

Základní kontrola:

```bash
perf stat -e cycles,instructions,cache-references,cache-misses,branches,branch-misses ./program
```

Užitečné metriky:

| Metrika | Co naznačuje |
|---|---|
| nízké IPC | CPU čeká, často na paměť nebo větve |
| vysoké `cache-misses` | špatná locality nebo velký working set |
| vysoké `LLC-load-misses` | data nejsou ani v last-level cache |
| vysoké `branch-misses` | problém s větvením, ne nutně cache |
| vysoké context switches | problém se schedulerem/synchronizací |

## Experimenty

Dobré jednoduché experimenty:

- porovnej sekvenční a náhodný průchod;
- měň velikost datasetu a sleduj skoky výkonu u L1/L2/L3;
- otestuj AoS vs SoA;
- otestuj per-thread data proti sdílenému atomic counteru;
- u matrix multiplication porovnej loop order a tiling;
- měř p95/p99, pokud cache miss způsobuje tail latency.

# Cache-friendly pravidla

- Preferuj sekvenční přístup.
- Zmenši working set.
- Nepoužívej pointer-heavy struktury v hot path bez důvodu.
- Ukládej hot data vedle sebe.
- Odděl cold data mimo hot path.
- Používej `std::vector` a kompaktní layout, pokud to dává smysl.
- U read-mostly dat zvaž immutable snapshot nebo RCU.
- U per-thread statistik nepoužívej jeden globální atomic counter.
- Pozor na false sharing u polí struktur a čítačů.
- U velkých výpočtů používej blocking/tiling.
- Měř přes reálný workload, ne jen microbenchmark.

# Zkouškové minimum

**Cache line:** základní jednotka přenosu mezi pamětí a cache, typicky 64 B.

**Spatial locality:** program brzy použije data blízko aktuální adresy.

**Temporal locality:** program brzy znovu použije stejná data.

**Working set:** aktivní množina dat, se kterou program právě pracuje. Když se vejde do cache, výkon je výrazně lepší.

**Cold miss:** první přístup k datům.

**Capacity miss:** cache je příliš malá pro aktivní data.

**Conflict miss:** různé adresy se mapují do stejného cache setu.

**True sharing:** více jader opravdu sdílí stejnou proměnnou nebo cache line.

**False sharing:** vlákna mění různé proměnné, ale ty leží ve stejné cache line.

**Set-associative cache:** adresa určí set, uvnitř setu může být data ve více ways.

**Tag/set/offset:** části adresy pro kontrolu identity linky, výběr setu a výběr bajtu uvnitř cache line.

**Proč je pole rychlejší než linked list:** pole je kontinuální a využívá cache line/prefetching; linked list skáče po heapu a vytváří pointer chasing.

**Tiling/blocking:** rozdělení výpočtu na bloky, které se vejdou do cache.

**NUMA:** přístup k lokální paměti je rychlejší než k paměti jiného socketu.

**Self-evicting code:** hot code je tak velký, že vytlačuje sám sebe z instruction cache.

```text
cache exists:
    CPU je rychlé, DRAM je pomalá

    typicky 64 B, jednotka přenosu a coherency

locality:

    temporal = stejná data znovu

misses:

    pracuj s blokem, který se vejde do cache

```

# Jak navazuje další téma

Další kapitola řeší serializaci a RPC. Cache s tím souvisí přímo: datový formát není jen otázka velikosti na disku nebo v síti. Layout dat rozhoduje, kolik cache missů vznikne při parsování, validaci a průchodu strukturou. Binární formáty, zero-copy přístup a kompaktní reprezentace jsou rychlé hlavně proto, že lépe pracují s pamětí.
