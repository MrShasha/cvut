# Proč je multi-threading těžký

V jednom vlákně platí praktická intuice:

```text
instruction 1
instruction 2
instruction 3
```

Compiler, JIT i CPU mohou instrukce interně přeskládat, ale výsledek musí odpovídat programu. Tomu se říká **as-if-serial semantics**: pro jedno vlákno se program tváří, jako by běžel v pořadí zdrojového kódu.

Ve více vláknech už nestačí sledovat jedno pořadí. Druhé vlákno může vidět:

- starou hodnotu;
- jen část změn;
- změny v jiném pořadí;
- porušený invariant objektu;
- výsledek, který se lokálně v jednom vlákně zdál nemožný.

## Tři základní problémy

| Problém | Otázka | Příklad |
|---|---|---|
| **Atomicity** | Je operace nedělitelná? | `counter++` není jeden krok. |
| **Visibility** | Uvidí jiné vlákno můj zápis? | `running = false` bez synchronizace nemusí zastavit worker. |
| **Ordering** | Uvidí jiné vlákno zápisy ve správném pořadí? | `ready = true` může být vidět dřív než připravená `data`. |

Typický bug:

```java
class Example {
    int data;
    boolean ready;

    void writer() {
        data = 42;
        ready = true;
    }

    void reader() {
        if (ready) {
            use(data); // bez synchronizace není garantováno data == 42
        }
    }
}
```

Problém není jen CPU. Přesouvat operace může i JIT, pokud tím neporuší výsledek jednoho vlákna. Ve vícevláknovém programu potřebuješ explicitní synchronizační hranici.

# Data race a Java Memory Model

## Data race

**Data race** vzniká, když platí:

```text
1. dvě nebo více vláken přistupují ke stejné sdílené proměnné;
2. alespoň jeden přístup je zápis;
3. mezi přístupy není správná synchronizace.
```

Příklad:

```java
class Counter {
    int value = 0;

    void increment() {
        value++;
    }
}
```

`value++` je přibližně:

```text
load value
add 1
store value
```

Dvě vlákna mohou načíst stejnou starou hodnotu a jedna inkrementace se ztratí.

```text
initial value = 0

Thread A: read 0 -> write 1
Thread B: read 0 -> write 1

expected = 2
actual   = 1
```

Data race v Javě není totéž jako undefined behavior v C++. JVM pořád musí zachovat například typovou bezpečnost. Ale z pohledu programu nemáš použitelnou garanci viditelnosti a pořadí, takže výsledek je nedeterministický a nesmíš na něj spoléhat.

## Java Memory Model

**Java Memory Model (JMM)** definuje, kdy jsou efekty jedné akce viditelné jiné akci v jiném vlákně.

Řeší hlavně:

- visibility;
- ordering;
- volatile semantics;
- monitor lock/unlock;
- thread start/join;
- final fields;
- safe publication.

JMM není fyzická RAM ani "main memory vs cache" obrázek. Je to pravidlový model, který říká, jak se musí chovat Java program, JVM a JIT optimalizace.

## Happens-before

Nejdůležitější pojem je **happens-before**.

Pokud akce A happens-before akce B, pak:

- efekty A musí být viditelné pro B;
- A je z hlediska JMM před B;
- JIT/CPU nesmí vytvořit pozorování, které by tento vztah porušilo.

Důležitá pravidla:

| Pravidlo      | Význam                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| Program order | Akce v jednom vlákně jsou ordered podle programu.                                                |
| Monitor rule  | `monitorexit` / unlock monitoru happens-before následný `monitorenter` / lock stejného monitoru. |
| Volatile rule | Zápis do `volatile` proměnné happens-before následné čtení stejné volatile proměnné.             |
| Thread start  | `Thread.start()` happens-before kód ve spuštěném vlákně.                                         |
| Thread join   | Akce v threadu happens-before úspěšný návrat z `Thread.join()`.                                  |
| Transitivity  | Pokud A HB B a B HB C, pak A HB C.                                                               |

Pozor na přesnost: neplatí "`lock()` happens-before `unlock()`". Správné pravidlo je **unlock jednoho vlákna happens-before následný lock stejného monitoru v jiném vlákně**.

## Safe publication

Safe publication znamená, že jinému vláknu nepředáš objekt tak, aby ho mohlo vidět napůl inicializovaný.

Bezpečné způsoby publikace:

- uložit referenci do `volatile` fieldu;
- uložit referenci pod stejným lockem, pod kterým ji jiné vlákno čte;
- publikovat přes thread-safe kolekci;
- inicializovat objekt před `Thread.start()`;
- použít správně konstruovaný immutable objekt s `final` fieldy.

Příklad immutable snapshot:

```java
final class Config {
    final int timeoutMs;
    final String endpoint;

    Config(int timeoutMs, String endpoint) {
        this.timeoutMs = timeoutMs;
        this.endpoint = endpoint;
    }
}

private volatile Config config = new Config(1000, "prod");

Config current() {
    return config;
}

void update(Config next) {
    config = next; // volatile write bezpečně publikuje novou referenci
}
```

Tohle je dobrý pattern pro read-mostly konfigurace: read path je bez locku, update publikuje celou novou immutable verzi.

# Memory barriers a volatile

## Memory barriers

**Memory barrier** nebo **memory fence** je mechanismus, který omezuje přeuspořádání paměťových operací.

Může omezovat:

- compiler/JIT reordering;
- CPU out-of-order execution;
- práci store bufferů;
- viditelnost zápisů mezi jádry;
- některé optimalizace okolo load/store instrukcí.

Zjednodušené typy:

| Bariéra | Co hlídá |
|---|---|
| LoadLoad | load před bariérou zůstane před load po bariéře |
| LoadStore | load před bariérou zůstane před store po bariéře |
| StoreStore | store před bariérou zůstane před store po bariéře |
| StoreLoad | store před bariérou zůstane před load po bariéře; často nejdražší |

Barrier není jen "flush cache do RAM". Moderní CPU cache jsou koherentní; důležitější je ordering, store buffers a komunikace mezi jádry.

## Acquire/release

Acquire/release je praktický mentální model.

```text
release:
    operace před release nesmí být přesunuty za release
    typicky publikace hotových dat

acquire:
    operace po acquire nesmí být přesunuty před acquire
    typicky čtení publikovaných dat
```

Producer/consumer:

```java
class Holder {
    int data;
    volatile boolean ready;

    void producer() {
        data = 42;
        ready = true; // volatile write: release-like
    }

    void consumer() {
        if (ready) {  // volatile read: acquire-like
            use(data);
        }
    }
}
```

Když `consumer()` uvidí `ready == true`, musí vidět i zápisy, které v produceru proběhly před volatile write.

## Co zajišťuje volatile

`volatile` v Javě zajišťuje:

- **visibility** — čtení volatile proměnné vidí hodnoty publikované volatile zápisem podle JMM;
- **ordering** — volatile read/write tvoří synchronizační hranici;
- **atomicitu samotného čtení/zápisu** dané volatile proměnné.

`volatile` nezajišťuje atomicitu složených operací:

```java
class BadCounter {
    volatile int counter;

    void increment() {
        counter++; // read + add + write, není atomické
    }
}
```

Správně pro counter:

```java
AtomicInteger counter = new AtomicInteger();

void increment() {
    counter.incrementAndGet();
}
```

## Kdy volatile stačí

`volatile` je vhodné pro:

- stop flag;
- status flag;
- jeden writer, více readerů;
- publikaci immutable snapshotu;
- jednoduchý stav bez compound update;
- referenci na objekt, který už je správně inicializovaný.

Stop flag:

```java
class Worker {
    private volatile boolean running = true;

    void stop() {
        running = false;
    }

    void run() {
        while (running) {
            doWork();
        }
    }
}
```

## Kdy volatile nestačí

`volatile` nepoužívej samotné pro:

- `counter++`;
- check-then-act;
- invariant přes více proměnných;
- kritickou sekci;
- lazy initialization bez správného patternu;
- změnu objektu, jehož vnitřek není immutable/thread-safe.

Check-then-act bug:

```java
if (!initialized) {
    initialized = true;
    init();
}
```

I kdyby `initialized` bylo volatile, více vláken může projít podmínkou a zavolat `init()`.

## Double-checked locking

Správný double-checked locking musí mít `volatile`:

```java
final class Singleton {
    private static volatile Singleton instance;

    static Singleton get() {
        Singleton local = instance;
        if (local == null) {
            synchronized (Singleton.class) {
                local = instance;
                if (local == null) {
                    local = new Singleton();
                    instance = local;
                }
            }
        }
        return local;
    }
}
```

`volatile` řeší safe publication a ordering reference `instance`.

# Synchronized, monitory a JVM locking

## Co synchronized zajišťuje

`synchronized` řeší tři věci najednou:

- **mutual exclusion** — jen jedno vlákno drží daný monitor;
- **visibility** — unlock publikuje změny pro následný lock stejného monitoru;
- **ordering** — monitor enter/exit tvoří synchronizační hranice.

```java
private final Object lock = new Object();
private int value;

void write(int x) {
    synchronized (lock) {
        value = x;
    }
}

int read() {
    synchronized (lock) {
        return value;
    }
}
```

Pokud reader získá stejný monitor po writerovi, uvidí zápis writeru.

## Bytecode

Synchronized blok se překládá na instrukce:

```text
monitorenter
monitorexit
```

Compiler musí zajistit, že `monitorexit` proběhne i při výjimce. Reálně je to struktura jako `try/finally`.

```java
synchronized (lock) {
    work();
}
```

Mentálně:

```text
monitorenter lock
try:
    work()
finally:
    monitorexit lock
```

Synchronized instance metoda zamyká `this`. Static synchronized metoda zamyká `Class` objekt.

## Reentrant monitor

Java monitor je reentrantní. Stejné vlákno může stejný monitor získat opakovaně.

```java
synchronized void a() {
    b();
}

synchronized void b() {
    // stejné vlákno už drží this monitor, vstup je povolen
}
```

Runtime drží recursion count. Lock se skutečně uvolní až po odpovídajícím počtu exitů.

## Thin, fat a biased locking

JVM nechce při každém `synchronized` dělat syscall. HotSpot používá různé reprezentace podle situace.

|Stav|Co to znamená|Typická situace|Cena|
|---|---|---|---|
|**No contention**|Lock sice existuje, ale reálně o něj nikdo nesoupeří. Vlákno ho získá hned.|lock bere jedno vlákno nebo se vlákna nestřetnou|velmi nízká|
|**Thin lock**|Lehký interní stav monitoru. JVM drží lock levně přes mark word / lock record / CAS, bez plného monitoru.|krátký `synchronized`, žádné nebo minimální soupeření|nízká|
|**Fat lock**|Nafouknutý monitor, tedy plná monitor struktura (`ObjectMonitor`) s ownerem, frontami a wait setem.|contention, čekání, `wait/notify`|vyšší, monitor + park/unpark|

**Biased locking** byla historická optimalizace pro případ, kdy stejný objekt zamyká opakovaně stejné vlákno. V moderních JVM se s ní prakticky nepočítá; od JDK 15 je deprecated a vypnutá ve výchozím nastavení. U zkoušky ji stačí znát jako historickou vrstvu: levná pro single-thread lock, drahá při revocation.

**Thin locking** je běžná levná cesta pro uncontended lock. Využívá object header, mark word, lock record na stacku a CAS.

**Fat locking** znamená nafouknutí na plnohodnotný monitor. Použije se při contention, `wait()`, složitějším monitor state nebo když lehká cesta nestačí.

## Lock inflation

**Lock inflation** je přechod:

```text
thin lock -> fat monitor
```

Děje se například při:

- více vláknech čekajících na stejný monitor;
- `wait()/notify()`;
- delším contention;
- potřebě monitor wait setu.

Důležitá pointa: `synchronized` není automaticky drahý OS mutex. Drahý je hlavně contended monitor: context switches, park/unpark, scheduler latency a cache line bouncing.

## wait/notify

Každý Java monitor má wait set:

- `wait()` — aktuální vlákno musí držet monitor, uvolní ho a čeká;
- `notify()` — probudí jedno čekající vlákno;
- `notifyAll()` — probudí všechna čekající vlákna.

Správný pattern:

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    useSharedState();
}
```

Používej `while`, ne `if`, protože:

- existují spurious wakeups;
- `notify` neznamená, že podmínka pořád platí;
- jiné vlákno mohlo stav změnit před tím, než se probuzené vlákno znovu dostalo k monitoru.

# ReentrantLock, Conditions a read-mostly workload

## ReentrantLock

`ReentrantLock` je explicitní lock z `java.util.concurrent.locks`.

```java
private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();
    try {
        work();
    } finally {
        lock.unlock();
    }
}
```

`unlock()` musí být ve `finally`, jinak výjimka může lock navždy držet.

ReentrantLock nabízí:

- `tryLock()`;
- `tryLock(timeout, unit)`;
- `lockInterruptibly()`;
- fair/unfair režim;
- více `Condition` front nad jedním lockem;
- explicitní kontrolu životnosti locku.

Fair lock snižuje starvation, ale často zhoršuje throughput kvůli scheduler overheadu. Unfair lock může být rychlejší, protože dovolí "barging": nové vlákno může získat lock před starším čekajícím.

## Condition

`Condition` je obdoba `wait/notify`, ale pro `ReentrantLock`.

```java
final ReentrantLock lock = new ReentrantLock();
final Condition notEmpty = lock.newCondition();
final ArrayDeque<Job> queue = new ArrayDeque<>();

Job take() throws InterruptedException {
    lock.lock();
    try {
        while (queue.isEmpty()) {
            notEmpty.await();
        }
        return queue.removeFirst();
    } finally {
        lock.unlock();
    }
}

void put(Job job) {
    lock.lock();
    try {
        queue.addLast(job);
        notEmpty.signal();
    } finally {
        lock.unlock();
    }
}
```

Výhoda proti jednomu monitor wait setu: jeden lock může mít více podmínek, například `notEmpty` a `notFull`.

## Read-mostly možnosti

Read-mostly workload znamená mnoho čtení a málo zápisů.

Možnosti:

| Mechanismus | Čtení | Zápis | Kdy dává smysl |
|---|---|---|---|
| `synchronized` / `ReentrantLock` | serializované | jednoduché | malý stav, nízký contention |
| `ReadWriteLock` | více readerů současně | writer exkluzivní | dlouhé čtení, málo zápisů |
| `StampedLock` | optimistic read + validace | writer exkluzivní | read-mostly, ochota řešit složitější API |
| volatile immutable snapshot | lock-free read | kopie při update | konfigurace, feature flags |
| `CopyOnWriteArrayList` | rychlá iterace | kopie celého pole | mnoho iterací, málo změn |
| `ConcurrentHashMap` | škálovatelné read/write | interní CAS/locky | sdílená mapa s paralelním přístupem |

`ReadWriteLock` není automaticky rychlejší než obyčejný lock. U krátkých read sekcí může overhead metadat zničit výhodu paralelních readerů.

`StampedLock` není reentrantní. Je výkonný, ale snadno se používá špatně.

# Atomics, CAS a LongAdder

## Atomic classes

Java poskytuje atomické wrappery:

- `AtomicInteger`;
- `AtomicLong`;
- `AtomicBoolean`;
- `AtomicReference`;
- `AtomicIntegerArray`;
- `AtomicLongArray`;
- `AtomicReferenceArray`;
- `AtomicStampedReference`;
- `AtomicMarkableReference`.

Příklad:

```java
AtomicInteger counter = new AtomicInteger();

int next = counter.incrementAndGet();
```

Srovnání:

| Mechanismus | Visibility | Ordering | Atomic increment |
|---|---:|---:|---:|
| plain `int` | ne | ne | ne |
| `volatile int` | ano | ano | ne |
| `AtomicInteger` | ano | ano | ano |
| `synchronized` | ano | ano | ano |

## CAS

**CAS** znamená compare-and-set / compare-and-swap.

```text
CAS(address, expected, newValue):
    atomically:
        if *address == expected:
            *address = newValue
            return true
        else:
            return false
```

Java atomic increment je mentálně CAS loop:

```java
int incrementAndGet() {
    while (true) {
        int old = value.get();
        int next = old + 1;
        if (value.compareAndSet(old, next)) {
            return next;
        }
    }
}
```

CAS je optimistická konkurence:

```text
přečti starý stav
spočítej nový stav
zkus atomicky vyměnit
když někdo mezitím změnil stav, opakuj
```

Výhody:

- neblokuje thread jako monitor;
- rychlé při nízkém contention;
- základ atomic tříd a lock-free struktur;
- dobré pro malý sdílený stav.

Nevýhody:

- retry loop při contention;
- cache line bouncing;
- ABA problém;
- složitější dokazování korektnosti;
- špatné pro dlouhou kritickou sekci nebo více invariantů.

## Atomic field updaters a VarHandle

Atomic field updater umožňuje atomicky měnit `volatile` field uvnitř objektu bez samostatného atomic wrapper objektu.

```java
class Node {
    volatile Node next;
}

static final AtomicReferenceFieldUpdater<Node, Node> NEXT =
    AtomicReferenceFieldUpdater.newUpdater(Node.class, Node.class, "next");

boolean ok = NEXT.compareAndSet(node, expected, update);
```

Výhody:

- menší memory overhead;
- méně objektů;
- lepší layout u velkého množství nodů;
- užitečné v low-level concurrent strukturách.

Nevýhody:

- horší čitelnost;
- runtime chyby při špatném názvu/typu fieldu;
- field musí být `volatile`;
- reflection-like overhead a omezení.

Modernější nízkoúrovňová API jsou **VarHandle** a interní JVM intrinsics. Pro běžný aplikační kód ale často stačí atomic třídy a concurrent kolekce.

## LongAdder

`AtomicLong` může škálovat špatně, když mnoho vláken aktualizuje stejný counter:

```text
všechna vlákna chtějí jednu cache line
CAS často selhává
cache line migruje mezi jádry
throughput neroste s počtem vláken
```

`LongAdder` rozloží counter do více buněk:

```text
base + cell[0] + cell[1] + cell[2] + ...
```

Vlákna aktualizují různé buňky, takže je méně CAS konfliktů.

Vhodné pro:

- metriky;
- statistiky;
- request counters;
- high-contention countery.

Nevýhody:

- vyšší memory overhead;
- `sum()` není transakční snapshot při současných updatech;
- nevhodné, když potřebuješ přesnou okamžitou hodnotu pro rozhodování.

# Non-blocking algoritmy

## Blocking vs non-blocking

Blocking algoritmus může zastavit celé vlákno, protože čeká na lock, monitor, condition nebo scheduler.

Non-blocking algoritmus se snaží nepoužívat blokující lock. Typicky staví na CAS a retry loopu.

Non-blocking neznamená "bez čekání". CAS loop také čeká, jen jiným způsobem: vlákno opakuje práci, dokud se mu nepodaří atomická změna.

## Progress guarantees

| Úroveň           | Záruka                                                               | Typický problém                      |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------ |
| Blocking         | Vlákno může čekat na jiné vlákno držící lock.                        | deadlock, priority inversion, convoy |
| Obstruction-free | Vlákno uspěje, pokud běží samo bez interference.                     | livelock při contention              |
| Lock-free        | Systém jako celek dělá pokrok: alespoň jedno vlákno dokončí operaci. | starvation konkrétního vlákna        |
| Wait-free        | Každé vlákno dokončí operaci v konečném počtu kroků.                 | velmi těžká implementace, overhead   |

Klíčová zkoušková věta:

```text
lock-free neznamená wait-free
```

Lock-free garantuje pokrok systému. Wait-free garantuje pokrok každého vlákna.

## Linearizability

Thread-safe nestačí jako přesná specifikace concurrent struktury. Potřebuješ vědět, zda se operace jeví atomicky.

**Linearizability** znamená, že každá operace má jeden okamžik mezi začátkem a koncem volání, kde se logicky stane. Tento okamžik je **linearization point**.

U CAS algoritmů je linearization point často úspěšný CAS.

Příklad:

```text
push(x) začal
push(x) dělá CAS head
CAS uspěl    <- linearization point
push(x) končí
```

Od tohoto bodu musí ostatní operace vidět nový stav stacku.

## Treiber stack

Treiber stack je klasický lock-free LIFO stack založený na `AtomicReference`.

```java
final class TreiberStack<T> {
    private final AtomicReference<Node<T>> top = new AtomicReference<>();

    void push(T value) {
        Node<T> node = new Node<>(value);
        while (true) {
            Node<T> oldTop = top.get();
            node.next = oldTop;
            if (top.compareAndSet(oldTop, node)) {
                return;
            }
        }
    }

    T pop() {
        while (true) {
            Node<T> oldTop = top.get();
            if (oldTop == null) {
                return null;
            }
            Node<T> next = oldTop.next;
            if (top.compareAndSet(oldTop, next)) {
                return oldTop.value;
            }
        }
    }

    static final class Node<T> {
        final T value;
        Node<T> next;

        Node(T value) {
            this.value = value;
        }
    }
}
```

Proč je lock-free:

- když CAS jednoho vlákna selže, znamená to, že jiné vlákno změnilo `top`;
- tedy někdo jiný udělal pokrok;
- systém jako celek se posouvá.

Proč není wait-free:

- jedno konkrétní vlákno může opakovaně prohrávat CAS;
- teoreticky může dlouho hladovět.

## ABA problém

CAS kontroluje aktuální hodnotu, ne historii.

```text
Thread A přečte top = A
Thread B popne A
Thread B pushne A zpět
Thread A pořád vidí top = A
CAS uspěje, ale struktura se mezitím změnila
```

V Javě GC výrazně pomáhá s memory reclamation: objekt se neuvolní, dokud na něj existuje reference. To ale neznamená, že ABA nikdy neexistuje. ABA může být logický problém, například když se stejný objekt/node znovu použije.

Řešení:

- `AtomicStampedReference` — reference + verze;
- `AtomicMarkableReference` — reference + boolean mark;
- version counter;
- nepoužívat reuse nodů;
- v unmanaged jazycích hazard pointers nebo epoch-based reclamation.

## Memory reclamation

V C/C++ je memory reclamation u lock-free struktur těžká: nemůžeš uvolnit node, dokud ho může držet jiné vlákno v lokální proměnné.

Řešení v native světě:

- hazard pointers;
- epoch-based reclamation;
- RCU;
- reference counting s opatrností.

V Javě GC tenhle problém zjednodušuje. Pokud vlákno drží referenci na node, GC ho neuvolní. Pořád ale zůstává:

- ABA jako logický problém;
- ordering;
- linearizability;
- contention na jedné cache line;
- náklady na alokace a GC pressure.

## ConcurrentHashMap přesněji

Moderní `ConcurrentHashMap` není jednoduše "celá lock-free". Přesnější popis:

- čtení je obvykle bez blokování a škáluje dobře;
- update používá CAS tam, kde to jde;
- při kolizích nebo složitějším update se používá jemnozrnná synchronizace nad bucketem/binem;
- resize je kooperativní;
- není tam jeden globální lock pro celou mapu.

Praktická pointa: používej knihovní concurrent struktury dřív než vlastní lock-free struktury. Jsou roky laděné a mají vyřešené hraniční případy.

# Performance bottlenecks synchronizace

Synchronizace může být drahá více způsoby:

- **lock contention** — mnoho vláken chce stejný lock;
- **atomic contention** — mnoho vláken CASuje stejnou proměnnou;
- **cache line bouncing** — cache line s lockem/counterem migruje mezi jádry;
- **false sharing** — nezávislé proměnné sdílí jednu cache line;
- **context switch** — vlákno usne a OS naplánuje jiné;
- **scheduler latency** — lock holder zrovna neběží;
- **memory barriers** — omezují JIT/CPU optimalizace;
- **oversubscription** — vláken je víc než CPU jader;
- **GC/safepoints** — JVM runtime může do měření přidat pauzy.

## Blocking vs spinning

| Čekání | Co se děje | Kdy dává smysl | Riziko |
|---|---|---|---|
| Blocking | thread se zaparkuje, scheduler pustí jiné vlákno | delší čekání, I/O, contention | context switch, wakeup latency |
| Spinning | thread aktivně zkouší dál | extrémně krátké čekání | pálení CPU, cache traffic |
| CAS retry | thread přepočítává a opakuje CAS | malý stav, nízký contention | livelock-like chování, bouncing |

Non-blocking kód při vysokém contention může být pomalejší než jednoduchý lock, protože všechna vlákna pořád aktivně bojují o stejnou cache line.

## Backoff

**Backoff** říká: když CAS selže, nezkoušej okamžitě znovu stejnou operaci ve stejném okamžiku jako všechna ostatní vlákna. Udělej krátkou pauzu, `pause`, `yield`, náhodné čekání nebo jiný delay.

| Bez backoff | S backoff |
|---|---|
| Vlákna po CAS failu hned znovu útočí na stejnou cache line. | Vlákna se trochu rozprostřou v čase. |
| Vzniká hodně současných CAS pokusů. | Je menší šance, že se všichni trefí do stejného okamžiku. |
| Více CAS failů. | Méně CAS failů při contention. |
| Více cache-line bouncing mezi jádry. | Méně cache-line bouncing. |
| Throughput při contention může spadnout. | Throughput při contention může vzrůst. |

Jednoduchý mentální model:

```text
CAS fail
-> nezkoušej hned znovu
-> krátce počkej / udělej pause / ustup scheduleru
-> zkus znovu
```

Typy backoff:

| Typ | Co dělá | Výhoda | Nevýhoda |
|---|---|---|---|
| **Fixed backoff** | vždy čeká stejnou dobu, například 100 ns | jednoduchý | nemusí sedět pro různý contention |
| **Randomized backoff** | čeká náhodný interval, například 50-200 ns | vlákna se nebudí znovu najednou | horší predikovatelnost |
| **Exponential backoff** | po každém failu zvětšuje čekání až do limitu | dobře tlumí vysoký contention | může zbytečně zvyšovat latenci |
| **Spin hint** | použije například `Thread.onSpinWait()` | říká CPU, že jde o spin loop | neřeší dlouhé čekání |
| **Algorithmic backoff** | změní hot spot, například `LongAdder` místo jednoho `AtomicLong` | často nejlepší řešení | mění datovou strukturu/semantiku |

CAS loop bez pauzy:

```java
while (!ref.compareAndSet(old, next)) {
    old = ref.get();
    next = compute(old);
}
```

Při vysokém contention se hodí backoff:

- fixed backoff;
- randomized backoff;
- exponential backoff;
- `Thread.onSpinWait()` pro spin wait hint;
- změna algoritmu, například `LongAdder` místo jednoho `AtomicLong`.

Backoff nespraví špatný design. Jen snižuje hromadné srážky vláken.

## Praktické zásady

1. Sdílej co nejméně.
2. Preferuj immutable data a safe publication.
3. Kritickou sekci drž krátkou.
4. Nedělej I/O pod lockem.
5. Nepoužívej jeden globální hot lock.
6. Pro counter s vysokým contention zvaž `LongAdder`.
7. Pro mapu použij `ConcurrentHashMap`, ne vlastní lock-free mapu.
8. Lock-free piš jen tehdy, když umíš určit linearization point a otestovat corner cases.
9. Měř throughput i p95/p99 latenci.
10. Sleduj thread dumps, JFR, async-profiler, lock contention events a allocation rate.

# Časté chyby

- **`volatile int counter; counter++;`** Visibility ano, atomicita ne.
- **Synchronizace na novém objektu.** `synchronized (new Object())` nic nechrání.
- **Zapomenutý `unlock()`.** U `ReentrantLock` vždy `try/finally`.
- **`wait()` pod `if`.** Musí být `while` nebo predikát.
- **Check-then-act bez synchronizace.** `if (!map.containsKey(k)) map.put(k, v)` není atomické.
- **Double-checked locking bez volatile.** Není safe publication.
- **Myslet si, že `ConcurrentHashMap` dělá složené operace atomické.** Použij `computeIfAbsent`, `compute`, `merge`.
- **Považovat lock-free za automaticky rychlejší.** Při contention může CAS loop škálovat hůř než lock.
- **Ignorovat false sharing.** Dva nezávislé countery ve stejné cache line mohou zničit výkon.
- **Míchat různé locky pro stejná data.** Pokud writer zamyká `lockA` a reader `lockB`, žádný happens-before pro data nevzniká.

# Jak vybrat mechanismus

| Situace | Vhodná volba |
|---|---|
| Jednoduchý stop flag | `volatile boolean` |
| Publikace immutable konfigurace | `volatile Config` |
| Jednoduchý atomic counter s nízkým contention | `AtomicLong` |
| Counter s vysokým contention | `LongAdder` |
| Více proměnných a invariant | `synchronized` / `ReentrantLock` |
| Čekání na stav fronty | `wait/notify` nebo `Condition`, často raději `BlockingQueue` |
| Sdílená mapa | `ConcurrentHashMap` |
| Read-mostly seznam listenerů | `CopyOnWriteArrayList` |
| Read-mostly struktura s větší kontrolou | immutable snapshot / `ReadWriteLock` / `StampedLock` |
| Vlastní lock-free struktura | jen po měření a s jasným linearization pointem |

# Zkouškové minimum

**Data race:** dvě vlákna přistupují ke stejné proměnné, alespoň jeden přístup je zápis a chybí synchronizace. V Javě to neznamená C++-style undefined behavior, ale ztrácíš garance visibility/orderingu.

**JMM:** pravidla viditelnosti a pořadí mezi vlákny. Základní vztah je happens-before.

**Happens-before:** pokud A happens-before B, efekty A musí být viditelné pro B. Příklady: volatile write -> následný volatile read stejné proměnné, monitor unlock -> následný monitor lock stejného monitoru, thread start/join.

**Volatile:** visibility + ordering pro proměnnou. Volatile write je release-like, volatile read acquire-like. Nestačí pro `counter++`.

**Synchronized:** mutual exclusion + visibility + ordering. Bytecode používá `monitorenter`/`monitorexit`. Unlock monitoru happens-before následný lock stejného monitoru.

**Thin/fat locking:** thin lock je levná uncontended cesta přes object header/CAS. Fat monitor je dražší cesta pro contention nebo `wait/notify`. Biased locking je historická optimalizace.

**ReentrantLock:** explicitní lock s `tryLock`, timeoutem, interruptible lockingem, fair/unfair režimem a `Condition`. `unlock()` patří do `finally`.

**CAS:** atomicky porovná aktuální hodnotu s expected a případně nastaví new value. Základ atomic tříd a lock-free algoritmů.

**LongAdder:** counter rozdělený do více buněk pro high contention. Lepší throughput, horší okamžitá přesnost snapshotu.

**Lock-free vs wait-free:** lock-free garantuje pokrok systému, wait-free garantuje dokončení každého vlákna v konečném počtu kroků.

**Linearizability:** každá operace concurrent struktury se musí jevit, jako by proběhla atomicky v jednom linearization pointu.

# Mini tahák

```text
atomicity  = operace je nedělitelná

  shared variable + write + no synchronization

  pravidla visibility/orderingu pro Java threads

  A HB B => efekty A viditelné pro B

  write = release-like
  read  = acquire-like
  good: flags, immutable snapshot
  bad: counter++, check-then-act

  monitorenter / monitorexit
  mutual exclusion + HB

  thin = cheap uncontended

  biased = historical optimization

```
