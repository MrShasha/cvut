# Proč je benchmarking těžký

## Program neběží izolovaně

Výsledek benchmarku ovlivňuje víc věcí než jen kód:

- CPU frekvence a turbo boost;
- thermal throttling;
- OS scheduler;
- jiné procesy;
- přerušení a kernel;
- stav cache;
- branch predictor;
- memory allocator;
- GC nebo JIT;
- NUMA;
- disk a síť;
- virtualizace nebo kontejner.

Proto jeden běh programu není důkaz. Je to jen pozorování.

## Jeden běh nestačí

Když benchmark spustíš jednou, nevíš, jestli měříš:

- stabilní výkon;
- cold start;
- náhodný zásah scheduleru;
- GC pauzu;
- zahřátý nebo studený cache stav;
- turbo boost na začátku běhu;
- throttling po zahřátí CPU.

Správný benchmark se opakuje. Měří se více iterací a často i více samostatných spuštění procesu.

## Benchmark není důkaz bez kontextu

Číslo samo o sobě nestačí.

Špatný report:

```text
verze B je rychlejší
```

Lepší report:

```text
Na CPU Ryzen 7 5800X, Linux 6.x, release build -O2,
dataset 10M záznamů, 10 warm-up iterací, 30 měřených iterací:

verze A median 124 ms, p95 131 ms
verze B median 91 ms, p95 97 ms
speedup median 1.36x
```

# Benchmarking vs profiling

Tyto pojmy se často pletou.

## Benchmarking

Benchmarking odpovídá na otázky:

- Jak dlouho operace trvá?
- Kolik operací za sekundu systém zvládne?
- Je verze B rychlejší než verze A?
- Nezavedli jsme performance regression?
- Jak se výkon mění s velikostí vstupu?

Benchmark měří výsledek.

## Profiling

Profiling odpovídá na otázky:

- Kde program tráví čas?
- Které funkce jsou hot path?
- Kde vznikají alokace?
- Je problém CPU, cache, branch, lock, I/O nebo GC?
- Které volání nebo smyčka je bottleneck?

Profiler hledá příčinu.

## Správný workflow

```text
benchmark -> zjistí, že problém existuje
profiling -> najde příčinu
změna -> opraví jednu věc
benchmark -> ověří zlepšení
```

Bez benchmarku nevíš, jestli zlepšení existuje. Bez profileru často optimalizuješ špatné místo.

# Co vlastně měřit

## Latency

**Latency** je doba jedné operace.

Příklady:

- jeden HTTP request trvá 40 ms;
- jedno parsování JSONu trvá 2 ms;
- jedna database query trvá 12 ms;
- jedna GC pause trvá 180 ms.

Latency je důležitá pro interaktivní systémy, web, hry, trading, real-time a služby se SLA.

## Throughput

**Throughput** je množství práce za čas.

Příklady:

- 100 000 requests/s;
- 800 MB/s parsed data;
- 50 000 messages/s;
- 2 GB/s memory copy.

Throughput je důležitý pro servery, batch processing, data pipelines a zpracování velkých objemů dat.

## Latency a throughput nejsou totéž

Systém může mít dobrý throughput, ale špatnou latency.

Příklad:

```text
server zvládne hodně requestů za sekundu,
ale každých pár minut má 800 ms pauzu kvůli GC
```

Průměr může vypadat dobře, ale uživatel cítí dlouhé pauzy.

## CPU time vs wall-clock time

**Wall-clock time** je reálný čas od začátku do konce.

```text
start 10:00:00.000
end   10:00:01.000
wall-clock = 1 s
```

Zahrnuje čekání na I/O, scheduler, locky, sleep, síť, disk.

**CPU time** je čas, kdy CPU skutečně vykonával tvůj proces.

Když program čeká na síť, wall-clock roste, ale CPU time skoro ne.

## User, system, real time

Nástroj `/usr/bin/time` typicky ukazuje:

- **real** - wall-clock time;
- **user** - CPU čas v user-space;
- **sys** - CPU čas v kernelu.

Interpretace:

```text
real vysoké, user+sys nízké
    -> program hodně čeká

user vysoké
    -> CPU-bound výpočet

sys vysoké
    -> hodně syscallů, I/O nebo kernel práce
```

## Paměť, alokace a energie

Výkon není jen čas.

Můžeš měřit:

- peak RSS;
- heap usage;
- allocation rate;
- počet objektů;
- GC pauses;
- cache misses;
- memory bandwidth;
- energii přes RAPL.

Optimalizace, která sníží latency, ale zdvojnásobí paměť, nemusí být dobrá.

# Typy benchmarků

## Microbenchmark

Microbenchmark měří malý kus kódu:

- jednu funkci;
- parser;
- hash mapu;
- jednu smyčku;
- alokační strategii;
- lock nebo atomic operation.

Výhody:

- izoluje konkrétní problém;
- rychle se spouští;
- hodí se pro porovnání algoritmů.

Nevýhody:

- snadno měří nerealistický workload;
- compiler/JIT může benchmark optimalizovat pryč;
- nemusí odpovídat chování celé aplikace;
- špatně zachytí cache, I/O a interakce komponent.

## Application benchmark

Application benchmark měří celý scénář:

- zpracování requestu;
- import datasetu;
- rendering scény;
- build projektu;
- ETL pipeline.

Výhody:

- realističtější;
- zahrnuje interakce komponent;
- lépe ukazuje dopad na uživatele.

Nevýhody:

- více šumu;
- hůř se hledá příčina;
- běží déle;
- potřebuje stabilní testovací prostředí.

## Load test

Load test měří systém pod zátěží:

- kolik requestů/s zvládne;
- jak roste latency s počtem klientů;
- kdy systém saturuje;
- jak vypadá p95/p99;
- co se stane při špičce.

Load test je důležitý pro servery a distribuované systémy. Není náhrada microbenchmarku, ale odpovídá na jiné otázky.

# Návrh správného experimentu

## Hypotéza

Benchmark by měl začít otázkou.

Špatně:

```text
Změřím, jestli je to rychlé.
```

Lépe:

```text
Chci ověřit, jestli nahrazení LinkedList za ArrayList
zrychlí sekvenční průchod 10M prvků.
```

## Baseline

Baseline je referenční stav, proti kterému porovnáváš změnu.

Bez baseline nevíš, jestli je nová verze lepší nebo horší.

```text
T_reference = čas původní verze
T_new       = čas nové verze
speedup     = T_reference / T_new
```

## Jedna změna najednou

Když změníš algoritmus, compiler flags a datový formát najednou, nevíš, co způsobilo výsledek.

Správně:

```text
1. změň jednu věc
2. změř
3. vyhodnoť
4. pokračuj další změnou
```

## Reprezentativní data

Benchmark s malým, čistým a umělým vstupem může lhát.

Reálná data často mají:

- skew;
- outliers;
- různé velikosti záznamů;
- chybějící hodnoty;
- duplicity;
- špatnou lokalitu;
- jiný poměr read/write operací.

Benchmarkuj data, která odpovídají tomu, co bude systém skutečně zpracovávat.

## Warm-up

Warm-up je fáze, kdy program běží, ale výsledky se ještě neměří.

Důvody:

- načtení tříd/knihoven;
- inicializace runtime;
- JIT kompilace;
- branch predictor training;
- zahřátí cache;
- stabilizace GC;
- lazy inicializace.

U JVM je warm-up povinný. U native programů také může hrát roli kvůli cache, filesystem cache, branch predictorům a lazy inicializaci.

## Iterace a runs

Rozlišuj:

- **iteration** - jedno měření uvnitř běhu;
- **run/fork** - nové spuštění celého procesu.

Příklad:

```text
for run in 1..10:
    warm-up
    for iteration in 1..30:
        measure
```

Iterace omezují náhodný šum. Runs ukazují, jestli výsledek drží i přes nový start procesu.

# Measurement noise

## Co je noise

Noise je variabilita výsledků, která nepochází z měřeného kódu.

Příklad:

```text
run 1: 100 ms
run 2: 102 ms
run 3: 180 ms
```

Třetí běh může být GC pauza, scheduler, thermal throttling nebo jiný proces.

## Běžné zdroje šumu

- **CPU frequency scaling** - CPU mění frekvenci podle zátěže a teploty.
- **Turbo boost** - krátký benchmark může běžet na vyšší frekvenci než dlouhý.
- **Thermal throttling** - po zahřátí CPU sníží frekvenci.
- **OS scheduler** - proces se přesune na jiné jádro nebo je přerušen.
- **Hyper-threading/SMT** - souběžné vlákno sdílí execution units a cache.
- **Cache state** - cold cache vs warm cache.
- **Branch predictor state** - předchozí běh ovlivní predikci větví.
- **JIT/GC** - runtime mění výkon během běhu.
- **NUMA** - vlákno běží na jiném socketu než data.
- **Virtualizace/kontejnery** - sdílené CPU, throttling, noisy neighbor.

## Jak noise omezit

Možnosti:

- používej stejný stroj;
- měř na release buildu;
- zavři zbytečné procesy;
- opakuj měření;
- používej warm-up;
- pinni proces na jádro, pokud to dává smysl;
- sleduj CPU frekvenci a teplotu;
- drž data a vlákna na stejném NUMA node;
- odděl CPU benchmark od diskového/síťového I/O;
- reportuj variance a percentily.

Ne vždy jde noise odstranit. Cílem je vědět, jak velký je, a neinterpretovat rozdíl 1 % jako výhru, když šum je 5 %.

# JVM benchmarking

## Proč je JVM speciální

JVM program se během běhu mění:

```text
class loading
    ↓
interpretace bytecodu
    ↓
C1 JIT
    ↓
profiling counters
    ↓
C2 JIT
    ↓
deoptimization / recompilation
```

První iterace často neměří steady state výkon.

## Typické chyby

### Dead Code Elimination

Pokud výsledek benchmarku nepoužiješ, JIT může celý výpočet odstranit.

```java
for (int i = 0; i < n; i++) {
    compute(i); // výsledek se nikde nepoužije
}
```

### Constant folding

Pokud benchmark pracuje s konstantami, JIT může výsledek spočítat předem.

```java
int x = 60 * 60 * 24;
```

### Loop hoisting

Pokud výpočet uvnitř smyčky nezávisí na iteraci, JIT ho může přesunout ven.

### Allocation elimination

Pokud objekt neuniká, JIT může alokaci odstranit pomocí escape analysis.

## JMH

**JMH (Java Microbenchmark Harness)** je standardní nástroj pro Java microbenchmarky.

Řeší:

- warm-up;
- forks;
- iterations;
- dead code elimination;
- blackhole;
- benchmark modes;
- statistiku.

Zjednodušený příklad:

```java
@Benchmark
public int parse() {
    return Integer.parseInt("12345");
}
```

U benchmarku, který vrací výsledek, JMH brání tomu, aby JIT výpočet jednoduše odstranil.

## JMH modes

- **Throughput** - operace za čas.
- **AverageTime** - průměrný čas operace.
- **SampleTime** - vzorkování časů operací.
- **SingleShotTime** - jednorázový běh, vhodný pro cold start scénáře.

# C-C++ benchmarking

## Release build

C/C++ benchmark v debug buildu často nemá hodnotu pro výkon.

Používej:

```bash
-O2
-O3 jen po měření
-march=native pouze pokud binárka běží na stejném typu CPU
```

## Compiler může benchmark odstranit

Když compiler pozná, že výsledek nemá efekt, odstraní výpočet.

```c
for (int i = 0; i < n; i++) {
    x += i;
}
```

Pokud `x` nikdo nepoužije, loop může zmizet.

Benchmark frameworky proto mají mechanismy typu:

- `DoNotOptimize`;
- `ClobberMemory`;
- volatile sink;
- blackhole.

## Google Benchmark

Google Benchmark řeší opakování, časování a ochranu před některými optimalizacemi.

Zjednodušeně:

```cpp
static void BM_Sum(benchmark::State& state) {
    for (auto _ : state) {
        auto result = sum(data);
        benchmark::DoNotOptimize(result);
    }
}
BENCHMARK(BM_Sum);
```

## perf

`perf stat` doplní čas o hardware counters:

```bash
perf stat -e cycles,instructions,cache-misses,branch-misses ./program
```

To pomůže poznat, jestli zlepšení pochází z menšího počtu instrukcí, lepší cache locality nebo menšího počtu branch miss.

# Hardware performance counters

Hardware performance counters jsou čítače přímo v CPU. Neříkají jen "program byl rychlý/pomalý", ale ukazují, co se na procesoru dělo.

## Proč měřit counters

Čas sám o sobě nestačí. Dvě verze programu mohou mít podobný wall-clock time, ale úplně jiný důvod:

- jedna verze vykoná méně instrukcí;
- druhá má lepší cache locality;
- třetí má méně branch mispredictions;
- čtvrtá čeká na paměť nebo I/O.

Counters pomáhají ověřit hypotézu. Pokud tvrdíš, že optimalizace zlepšila cache locality, měl by klesnout počet cache missů nebo aspoň jejich dopad na čas.

## Základní counters

| Counter | Co znamená | Jak ho číst |
|---|---|---|
| `cycles` | počet CPU cyklů | hrubá cena běhu na CPU |
| `instructions` | počet vykonaných instrukcí | jestli program dělá méně práce |
| `IPC` | instructions per cycle | jak dobře CPU využívá pipeline |
| `cache-references` | přístupy do cache | kontext pro cache misses |
| `cache-misses` | chybějící data v cache | locality problém nebo velký working set |
| `branches` | počet větví | kontext pro branch misses |
| `branch-misses` | špatně predikované větve | penalty kvůli branch prediction |
| `context-switches` | přepnutí vláken | scheduler/synchronizace/čekání |
| `page-faults` | výpadky stránek | problém s pamětí, mmap, lazy allocation |

## Interpretace counters

Nízké IPC často znamená, že CPU čeká:

- na paměť;
- na závislosti mezi instrukcemi;
- na branch misprediction;
- na synchronizaci;
- na front-end CPU, pokud je kód příliš velký nebo špatně predikovaný.

Vysoký počet instrukcí může znamenat algoritmický problém. Vysoký počet cache missů znamená problém s layoutem dat, working setem nebo přístupovým vzorem. Vysoký počet context switchů často ukazuje na blokování, lock contention nebo špatně nastavený load test.

## `perf stat`, `perf record`, `perf annotate`

`perf stat` dá agregovaná čísla:

```bash
perf stat -e cycles,instructions,cache-misses,branch-misses ./program
```

`perf record` nasbírá profil:

```bash
perf record ./program
perf report
```

`perf annotate` ukáže problém až na úroveň instrukcí:

```bash
perf annotate
```

Prakticky: nejdřív změř čas a základní counters přes `perf stat`. Pokud nevíš, kde problém vzniká, použij `perf record/report`. Pokud řešíš hot loop v native kódu, dává smysl `perf annotate`.

# Statistická interpretace výsledků

## Mean, median, percentily

| Metrika | Co říká | Kdy je užitečná |
|---|---|---|
| mean | aritmetický průměr | stabilní data bez velkých outlierů |
| median / p50 | prostřední hodnota | robustní běžný případ |
| p95 | 95 % hodnot je menších | pomalé případy u služby |
| p99 | 99 % hodnot je menších | tail latency |
| max | nejhorší hodnota | hledání extrémních pauz |

Průměr sám nestačí, hlavně u latency.

## Variance a standard deviation

Variance říká, jak moc výsledky kolísají.

Nízká variance:

```text
100 ms, 101 ms, 99 ms, 100 ms
```

Vysoká variance:

```text
100 ms, 105 ms, 180 ms, 95 ms
```

Při vysoké varianci je těžké tvrdit, že malý rozdíl mezi verzemi je skutečný.

## Confidence interval

Confidence interval odhaduje rozsah, kde pravděpodobně leží skutečná hodnota.

Příklad:

```text
verze A: 100 ms ± 2 ms
verze B: 96 ms ± 2 ms
```

To je pravděpodobně skutečné zlepšení.

```text
verze A: 100 ms ± 8 ms
verze B: 96 ms ± 8 ms
```

Tady je rozdíl nejistý.

## Speedup

```text
speedup = T_reference / T_optimized
```

Příklad:

```text
reference = 200 ms
optimized = 100 ms
speedup = 2x
```

Percent improvement:

```text
improvement = (T_reference - T_optimized) / T_reference * 100 %
```

Pozor:

```text
2x faster = 50 % méně času
```

Neplést speedup a procenta.

# Amdahlova intuice

Amdahlův zákon říká, že celkové zrychlení programu je omezené částí, kterou nezrychlíš.

Pokud optimalizuješ jen 10 % běhu, nemůžeš dostat 10x zrychlení celého programu. I kdybys těch 10 % zrychlil nekonečně, zbylých 90 % času zůstane.

```text
speedup_total = 1 / ((1 - p) + p / s)

p = část programu, kterou optimalizujeme
s = speedup této části
```

Příklad:

```text
p = 0.20       // optimalizujeme 20 % běhu
s = 10         // tuto část zrychlíme 10x

speedup_total = 1 / (0.80 + 0.20 / 10)
              = 1 / 0.82
              = 1.22x
```

Lokálně obrovská optimalizace tedy dá jen 22 % celkové zlepšení, protože 80 % programu zůstalo beze změny.

Praktický význam:

- nejdřív hledej hot path profilingem;
- neoptimalizuj část, která tvoří malé procento času;
- měř celkový dopad, ne jen lokální microbenchmark;
- u paralelizace počítej se serial částí programu;
- pokud se bottleneck přesune jinam, další optimalizace původního místa už nepomůže.

# Load testing a tail latency

## Closed-loop vs open-loop

**Closed-loop** load generator pošle request, počká na odpověď a pak pošle další.

Výhoda:

- jednoduchý model klienta.

Nevýhoda:

- když server zpomalí, generátor automaticky posílá méně requestů;
- může skrýt overload.

**Open-loop** posílá requesty podle pevné rychlosti, například 1000 requestů/s, bez ohledu na odpovědi.

Výhoda:

- lépe testuje chování pod pevnou příchozí zátěží.

Nevýhoda:

- složitější vyhodnocení;
- může rychle zahltit systém.

## Saturation point

Saturation point je místo, kde systém narazí na limit:

- CPU;
- thread pool;
- database connections;
- lock contention;
- memory bandwidth;
- network;
- disk.

Za tímto bodem throughput už moc neroste, ale latency roste prudce.

## Queueing intuition

Jak se využití systému blíží 100 %, fronty rostou nelineárně.

```text
nízké využití -> requesty skoro nečekají
vysoké využití -> requesty stojí ve frontě
skoro 100 % -> malé špičky způsobí velké latence
```

Proto p99 roste často dřív, než CPU ukazuje trvalých 100 %.

## Tail latency

Tail latency jsou pomalé konce distribuce: p95, p99, p999.

Příčiny:

- GC pauses;
- lock contention;
- queueing;
- slow database query;
- page faults;
- cache misses;
- network retries;
- noisy neighbor ve virtualizaci.

U serverů často rozhoduje p99, ne průměr.

# Benchmarking checklist

## Před měřením

- Mám jasnou otázku?
- Mám baseline?
- Měřím release build?
- Mám reprezentativní data?
- Vím, jestli měřím latency, throughput, paměť nebo energii?
- Je benchmark dost dlouhý?
- Mám warm-up, pokud je potřeba?
- Izoluji jednu změnu?

## Během měření

- Opakuji iterace?
- Opakuji celé runs/forks?
- Sleduji šum?
- Sleduji CPU frekvenci/teplotu, pokud je to důležité?
- Neplete se do měření disk nebo síť, pokud měřím CPU?
- U JVM používám JMH nebo podobnou metodiku?
- U C/C++ bráním optimalizaci benchmarku pryč?

## Po měření

- Porovnávám median/p95/p99, ne jen průměr?
- Uvádím variance nebo confidence interval?
- Počítám speedup správně?
- Zkontroloval jsem regression v jiném workloadu?
- Umím výsledek vysvětlit profilerem nebo counters?
- Dokumentuji hardware, OS, build flags a data?

# Časté chyby

- měření debug buildu;
- jeden krátký běh;
- nereprezentativní data;
- ignorování warm-up;
- ignorování GC/JIT;
- měření průměru bez percentilů;
- porovnávání výsledků z různých strojů;
- změna více věcí najednou;
- benchmark, který compiler/JIT optimalizoval pryč;
- load test, který neukazuje saturation a p99.

# Jak dokumentovat benchmark

Dobrý benchmark report obsahuje:

- cíl měření;
- hardware;
- OS a verze runtime;
- compiler/JVM flags;
- dataset;
- počet warm-up iterací;
- počet měřených iterací;
- počet runs/forks;
- měřené metriky;
- mean/median/p95/p99;
- variance nebo confidence interval;
- baseline a porovnání;
- odkaz na kód benchmarku.

# Zkouškové minimum

## Jaký je rozdíl mezi benchmarkingem a profilingem?

Benchmarking měří, jak rychlý program je nebo jestli je verze B rychlejší než verze A. Profiling hledá, kde program tráví čas a proč je pomalý.

## Co je microbenchmark?

Microbenchmark měří malou izolovanou část programu, například jednu funkci nebo datovou strukturu. Je dobrý pro izolaci problému, ale může být nerealistický.

## Co je application benchmark?

Application benchmark měří celý scénář nebo celou aplikaci. Je realističtější než microbenchmark, ale má více šumu a hůř se z něj hledá příčina.

## Proč je warm-up důležitý?

První iterace často měří class loading, JIT kompilaci, cold cache, lazy inicializaci nebo nestabilní runtime stav. Warm-up umožní měřit steady state výkon.

## Co je measurement noise?

Noise je variabilita výsledků, která nepochází z měřeného kódu, například scheduler, CPU frequency scaling, GC, cache state, NUMA nebo jiné procesy.

## Proč nestačí průměrná latency?

Průměr skryje pomalé requesty. U serverů uživatelé často cítí p95/p99 latency, která vzniká kvůli frontám, GC, lockům, I/O nebo síti.

## Co je speedup?

Speedup je poměr času původní a optimalizované verze:

```text
speedup = T_reference / T_optimized
```

## Co říká Amdahlův zákon?

Amdahlův zákon říká, že celkové zrychlení je omezené částí programu, kterou nezrychlíš. Optimalizace malé části hot path proto nemůže dramaticky zrychlit celý program.

## Co jsou hardware performance counters?

CPU čítače nízkoúrovňových událostí: cycles, instructions, IPC, cache misses, branch misses, page faults. Pomáhají určit typ bottlenecku.

## Jak správně postupovat při optimalizaci?

Nejdřív benchmarkem ověř problém, profilerem najdi příčinu, změň jednu věc, benchmarkem ověř zlepšení a zkontroluj, že nevznikla regression.

# Mini tahák

```text
Benchmarking:
    měří výsledek výkonu

Profiling:
    hledá příčinu výkonového problému

Latency:
    čas jedné operace

Throughput:
    operace za čas

Wall-clock:
    reálný čas včetně čekání

CPU time:
    čas skutečně strávený na CPU

Microbenchmark:
    malý izolovaný kus kódu

Application benchmark:
    celý scénář

Load test:
    systém pod zátěží

Warm-up:
    běh před měřením, stabilizace runtime/cache/JIT

Noise:
    scheduler, CPU freq, GC, cache, NUMA, virtualizace

JMH:
    standard pro Java microbenchmarky

perf:
    counters + sampling profiler na Linuxu

Speedup:
    T_old / T_new

p99:
    99 % hodnot je rychlejších, 1 % pomalejších
```

# Jak navazuje další téma

Po benchmarkingu dává smysl jít do synchronizace a paralelního výkonu. Teď už máme metodiku, jak měřit, jestli lock, atomic operation, false sharing nebo změna datové struktury skutečně pomáhá, nebo jen vypadá dobře v jednom náhodném běhu.
