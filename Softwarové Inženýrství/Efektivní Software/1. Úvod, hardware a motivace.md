# Motivace a definice efektivního softwaru

**Efektivní software** = software, který využívá dostupné zdroje (CPU, paměť, energie, síť) efektivně — tedy vytěží z hardwaru co nejvíce při co nejnižších nákladech.

Proč na tom záleží? Dva pohledy:

**Výkon (Performance):**
- **Latence** (response time) — jak rychle dostanu odpověď? Záleží u real-time systémů, her, lékařských přístrojů.
- **Propustnost** (throughput) — kolik práce udělám za jednotku času? Záleží u serverů, datových pipeline, dávkového zpracování.

Latence a propustnost nejsou totéž. Systém může zvládnout hodně požadavků za sekundu, ale zároveň mít špatnou uživatelskou zkušenost, pokud občas nastane dlouhá pauza. Proto se u serverů často neřeší jen průměr, ale i percentily:

- **p50 / median** — běžný případ.
- **p95** — pomalejší požadavky, které už cítí část uživatelů.
- **p99 / p999** — tail latency, tedy nejhorší případy; často je zhoršují GC pauzy, lock contention, page faults nebo čekání na síť.

**Náklady (Cost):**
- CPU čas, paměť, šířka pásma, energie = **peníze ve velkém měřítku**. Amazon snížil latenci o 100 ms a tržby vzrostly o 1 %. Google zjistil, že zpomalení o 500 ms sníží traffic o 20 %.
- Na embedded a mobilních zařízeních je energie fyzické omezení, ne jen cena.

**Omezení (Constraints):**
- Vestavěné systémy, mobilní zařízení, real-time deadlines — musíš se vejít do limitovaného hardwaru.

## Výkon jako trade-off

Výkon obvykle není první priorita. Nejdřív musí program dělat správnou věc a musí být možné ho udržovat.

Typické pořadí priorit:

1. Správnost.
2. Bezpečnost a spolehlivost.
3. Udržovatelnost a čitelnost.
4. Pozorovatelnost: logy, metriky, tracing.
5. Výkon.

Rychlý, ale chybný program je k ničemu. Stejně tak optimalizace, která zrychlí nepodstatnou část kódu, ale rozbije čitelnost, se dlouhodobě často nevyplatí. Výkon se řeší hlavně tehdy, když porušuje SLA, prodražuje infrastrukturu, brání škálování nebo je fyzickým limitem daného zařízení.

> [!note] Inženýrský pohled
> Optimalizace není o eleganci — je o měřitelném výsledku. Nikdy neoptimalizuj bez benchmarku. Nikdy neutrácej čas na kód, který není bottleneck.

# Optimalizační přístup a technologický stack

## Iterativní cyklus výkonnostní optimalizace

Jediný správný přístup je empirický a iterativní:

```
1. MĚŘ    → najdi co je pomalé (profiler, benchmarky)
2. ROZUMĚJ → zjisti PROČ je to pomalé (cache miss? lock contention? I/O?)
3. ZMĚŇ   → oprav jednu věc najednou
4. OVĚŘ   → změřil jsi zlepšení? Nezavedl jsi regresi?
```

**Proč opravovat jen jednu věc najednou?** Protože jinak nevíš, která změna co způsobila. Vědecká metoda platí i v softwarovém inženýrství.

## Benchmarking vs profiling

Tyto pojmy se často pletou:

- **Benchmarking** měří, jak rychlé něco je. Odpovídá na otázky typu: trvá operace 5 ms nebo 50 ms? Je verze B rychlejší než verze A? Zlepšil se throughput?
- **Profiling** hledá, kde a proč se čas nebo paměť ztrácí. Odpovídá na otázky typu: která metoda je hot? Alokujeme příliš mnoho objektů? Čekáme na lock, disk, síť nebo GC?

Správný postup je: benchmark ukáže problém, profiler najde příčinu, změna problém opraví a benchmark ověří, že se výkon opravdu zlepšil.

### Microbenchmark vs application benchmark

**Microbenchmark** měří malý kus kódu: jednu funkci, parser, datovou strukturu nebo synchronizační primitivum. Hodí se pro izolaci problému, ale může lhát, pokud neodpovídá reálnému workloadu.

**Application benchmark** měří větší scénář nebo celou aplikaci. Je realističtější, ale výsledek má víc šumu a hůř se z něj hledá konkrétní příčina.

## Technologický zásobník

Každá vrstva zásobníku může být bottleneck:

```
Tvoje aplikace
  ↓ Knihovny
  ↓ Překladač (C/C++) nebo JIT (JVM)
  ↓ Runtime / GC / JIT kompilátor
  ↓ Operační systém (scheduler, virtual memory, I/O)
  ↓ Virtualizace (KVM, Docker)
  ↓ Hardware (pipeline, caches, superscalar, SIMD)
```

**Lidský překlad:** Než začneš optimalizovat svůj kód, ujisti se, že problém není v jiné vrstvě. Pomalá databáze? Špatné indexy? GC pause v JVM? Špatná konfigurace OS? Virtualizační overhead?

# Hardware: procesory a paměťová hierarchie

## Paměťová hierarchie — fyzická realita

Paměť není flat array. Je to pyramida rychlosti vs. kapacity:

| Vrstva | Typická latence | Kapacita |
|---|---|---|
| Registry | < 1 ns | desítky B |
| L1 cache | ~4 cykly (~1–2 ns) | 32–64 KB |
| L2 cache | ~12 cykly (~3–5 ns) | 256 KB – 1 MB |
| L3 cache | ~40 cykly (~10–20 ns) | 8–64 MB |
| DRAM | ~200 cykly (~60–100 ns) | GBs |
| SSD | ~100 000 ns | TBs |
| HDD | ~10 000 000 ns | TBs |

**Fyzikální analogie:** Představ si, že programátor stojí v centru Prahy (CPU). Registry jsou věci v kapse — dosáhneš okamžitě. L1 cache je v místnosti. L2 je v budově. L3 je v sousední ulici. DRAM je na druhém konci města. Disk je v jiném státě.

**Kritická implikace:** Přístup do DRAM je 200x pomalejší než L1 cache. Pokud tvůj algoritmus "mine" do DRAM, CPU čeká. Moderní CPU je tak rychlé, že je paměť absolutní bottleneck pro většinu neoptimalizovaných programů.

## Cache line — základní jednotka přenosu

Cache pracuje v blocích nazývaných **cache line** (typicky **64 bajtů**). Při čtení jednoho bajtu z DRAM se do cache načte celých 64 bajtů.

**Implikace pro programátora:**
- Data, která jsou v paměti blízko sebe, jsou přečtena najednou → spatial locality.
- Data, ke kterým přistupuješ opakovaně, zůstanou v cache → temporal locality.
- Linked list = katastrofa pro cache (každý uzel je jinde v paměti).
- Array = ráj pro cache (kontinuální data, sequential access pattern).

## Locality a working set

**Spatial locality** znamená, že program pracuje s daty, která jsou blízko sebe v paměti. Proto je sekvenční průchod polem typicky rychlý: CPU načte cache line a využije většinu dat v ní.

**Temporal locality** znamená, že program opakovaně používá stejná data v krátkém čase. Pokud se často používaná data vejdou do cache, CPU nemusí čekat na DRAM.

**Working set** je množina dat, se kterou program aktivně pracuje v daném období. Pokud se working set vejde do L1/L2/L3 cache, program běží výrazně lépe. Pokud je working set větší než cache, přibývá cache missů a výkon může být limitovaný pamětí místo výpočtem.

# Instruction-Level Parallelism (ILP)

ILP znamená **paralelismus uvnitř jednoho vlákna na jednom CPU jádře**. Programátor pořád píše sekvenční kód, ale hardware se snaží najít nezávislé instrukce a provádět je překrytě nebo zároveň.

Tohle je jiné než více vláken nebo více jader. ILP zrychluje **jeden instruction stream**. Multicore zrychluje práci tím, že běží **více instruction streams paralelně**.

## Instruction pipeline

Bez pipeline by CPU dokončil celou instrukci a až potom začal další. To špatně využívá hardware: fetch jednotka, decoder, ALU a write-back část by většinu času čekaly.

Pipeline rozdělí zpracování instrukce na fáze:

```text
Fetch -> Decode -> Execute -> Memory -> Write-back
```

Jedna instrukce má pořád latenci několik cyklů, ale fáze různých instrukcí se překrývají:

```text
cyklus:  1  2  3  4  5  6  7
I1:      F  D  E  M  W
I2:         F  D  E  M  W
I3:            F  D  E  M  W
```

Ideální scalar pipeline po naplnění dokončí přibližně **jednu instrukci za cyklus**. Neznamená to, že instrukce trvá jeden cyklus. Znamená to, že CPU drží pipeline plnou.

Problém: pipeline funguje dobře jen tehdy, když CPU ví, jaká instrukce přijde dál, a instrukce nemusí čekat na výsledek předchozí instrukce.

## Superscalar CPU

Superscalar CPU jde dál než obyčejná pipeline: v jednom jádře má více výpočetních jednotek a může v jednom cyklu začít nebo dokončit více nezávislých instrukcí.

Typické jednotky:

- integer ALU;
- floating-point / SIMD jednotky;
- load/store jednotky;
- branch jednotka.

Příklad nezávislých instrukcí:

```text
a = b + c
x = y * z
p = q + r
```

Tyto instrukce na sobě nezávisí, takže superscalar core je může rozdělit do různých execution units.

Příklad závislého řetězce:

```text
a = b + c
d = a * 3
e = d + 1
```

Tady další instrukce čeká na výsledek předchozí. Superscalar hardware má více jednotek, ale nemá co paralelně provádět. Tomu se říká **dependency chain**.

Praktický důsledek: někdy je rychlejší kód s více instrukcemi, pokud má méně závislostí a lepší locality. Počet instrukcí sám o sobě nestačí.

## Out-of-order execution

Out-of-order execution znamená, že CPU může provést pozdější nezávislou instrukci dřív, pokud předchozí instrukce čeká třeba na data z paměti.

Příklad:

```text
load a from memory      // může čekat desítky cyklů
x = y + z              // nezávislé, CPU to může provést mezitím
use a
```

CPU interně přehází práci kvůli výkonu, ale navenek musí zachovat výsledek, jako by program běžel sekvenčně. K tomu slouží například **reorder buffer**: instrukce se mohou provést mimo pořadí, ale výsledky se commitují v korektním pořadí.

Limity out-of-order execution:

- dlouhý dependency chain nejde magicky paralelizovat;
- cache miss může zastavit instrukce, které potřebují stejná data;
- malý instruction window znamená, že CPU nevidí dost nezávislé práce dopředu;
- špatná branch prediction zahodí spekulativně vykonanou práci.

## Branch prediction

Podmíněné skoky (`if`, `while`, `for`) jsou problém pro pipeline. CPU musí vědět, jakou instrukci fetchovat dál. Jenže u větve to často závisí na hodnotě, která ještě není spočítaná.

Branch predictor odhaduje, kudy program půjde, a CPU začne spekulativně vykonávat instrukce z odhadnuté větve.

Když je odhad správný, pipeline běží plynule. Když je odhad špatný, CPU musí zahodit spekulativní práci a pipeline znovu naplnit. Tomu se říká **pipeline flush**.

```text
predict OK     -> pipeline pokračuje
predict wrong  -> flush, ztráta často desítky cyklů
```

Dobře predikovatelné větve:

- smyčka, která běží tisíckrát;
- `if`, který je skoro vždy true;
- data se stabilním vzorem.

Špatně predikovatelné větve:

- větvení podle náhodných dat;
- střídání true/false bez vzoru;
- data-dependent hot path.

Implikace: branchless programming, tabulky, SIMD nebo změna layoutu dat mohou být rychlejší, i když kód na první pohled dělá více jednoduchých operací.

## IPC, stalls a proč pipeline neběží ideálně

**IPC** znamená instructions per cycle. Říká, kolik instrukcí CPU reálně dokončí za jeden cyklus.

| Situace | Co to znamená |
|---|---|
| Vysoké IPC | CPU má dost nezávislé práce a pipeline je dobře využitá. |
| Nízké IPC + cache misses | CPU čeká na paměť. |
| Nízké IPC + branch misses | CPU zahazuje práci kvůli špatné predikci větví. |
| Nízké IPC bez cache missů | Často dependency chains, málo ILP nebo špatný instruction mix. |

Proto se výkon neměří jen časem. V dalších lekcích se k tomu vrací hardware counters: `cycles`, `instructions`, `IPC`, `cache-misses`, `branch-misses`.

## Superscalar vs multicore

Superscalar a multicore jsou dvě různé věci:

| Pojem | Kde vzniká paralelismus | Co běží paralelně | Typický limit |
|---|---|---|---|
| **Pipeline** | uvnitř jednoho jádra | fáze různých instrukcí | větve, závislosti, cache miss |
| **Superscalar** | uvnitř jednoho jádra | více nezávislých instrukcí z jednoho vlákna | málo ILP, dependency chains |
| **Out-of-order** | uvnitř jednoho jádra | pozdější nezávislé instrukce před staršími čekajícími | instruction window, memory latency |
| **Multicore** | mezi jádry | více vláken nebo procesů | synchronizace, memory bandwidth, rozdělení práce |

Krátce:

- **superscalar** = jedno jádro se snaží zrychlit jedno vlákno;
- **multicore** = více jader běží více vláken;
- **SIMD** = jedna instrukce zpracuje více datových prvků najednou;
- **SMT/Hyper-Threading** = jedno fyzické jádro se tváří jako více logických vláken, aby lépe zaplnilo nevyužité jednotky.

Když program běží v jednom vlákně, více jader mu samo od sebe nepomůže. Pomůže ILP, cache locality, SIMD, lepší algoritmus nebo paralelizace programu na více nezávislých částí.

# Task parallelism a vlákna

## CPU-bound, memory-bound a I/O-bound programy

Než přidáš vlákna, musíš vědět, na co program čeká:

- **CPU-bound** — program většinu času počítá. Pomáhá lepší algoritmus, SIMD, cache locality nebo paralelizace.
- **Memory-bound** — program čeká na data z paměti. Další jádra často nepomohou, protože všechna soupeří o memory bandwidth.
- **I/O-bound** — program čeká na disk, síť nebo databázi. Často pomůže batching, caching, asynchronní I/O nebo omezení zbytečných volání.

## Kdy pomáhají vlákna

Vlákna pomáhají, pokud je bottleneck **CPU-bound** a problém lze rozdělit na nezávislé části.

**Amdahlův zákon** — pokud je $p$ část kódu paralelizovatelná, maximální zrychlení s $n$ procesory je:
$$S(n) = \frac{1}{(1-p) + \frac{p}{n}}$$

**Lidský překlad:** Pokud 10 % kódu je sekvenční, maximální zrychlení je 10×, bez ohledu na počet jader. Sekvenční bottleneck (inicializace, I/O, logging) limituje vše.

## Kdy vlákna nepomáhají (nebo škodí)

- **Memory-bound kód** — přidáváš jádra, ale všechna čekají na DRAM. Přidáním jader problém s pamětí nevyřešíš.
- **I/O-bound kód** — čekáš na síť nebo disk. Asynchronní I/O (non-blocking) je lepší řešení než vlákna.
- **Lock contention** — příliš jemná synchronizace → vlákna si překáží → výkon klesá s přidáváním jader.

## Časté chyby v intuici

- **Stačí spočítat Big-O.** Nestačí. Big-O neřeší cache locality, branch prediction, alokace, konstantní faktory ani synchronizaci.
- **Více vláken znamená rychlejší program.** Ne nutně. Vlákna mohou zvýšit context switching, lock contention, cache coherence traffic a GC pressure.
- **Optimalizace bez měření je dobrý odhad.** Většinou není. Bez měření často optimalizuješ část, která netvoří bottleneck.
- **Průměrná latence stačí.** U serverů často rozhoduje tail latency, hlavně p95/p99.

> Ke státnicím: Efektivní software = latence + throughput + náklady. Paměťová hierarchie je klíčový bottleneck. ILP (superskalar, pipeline, OOO, branch prediction) je důvod, proč moderní CPU jsou tak rychlé — a proč je těžké je vytížit. Amdahlův zákon říká, proč paralelismus není stříbrná kulka.
