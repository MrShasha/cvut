# Proč řešit paměť v Javě

## Big-O nestačí

Dvě struktury mohou mít stejnou asymptotickou složitost, ale úplně jiný výkon.

```text
O(1) lookup v HashMap<Integer, Integer>
O(1) lookup v primitive int->int open-addressing mapě
```

Obě mohou být O(1), ale první používá objekty, reference, boxing a pointer chasing. Druhá může mít data v několika kompaktních arrays. Rozdíl se projeví v:

- memory footprint;
- cache misses;
- allocation rate;
- GC pressure;
- p99 latency;
- throughput.

## Co Java skrývá

Java kód:

```java
List<Integer> ids = new ArrayList<>();
ids.add(42);
```

Vypadá jednoduše, ale runtime může vytvořit:

- `ArrayList` objekt;
- interní `Object[]`;
- `Integer` objekt pro hodnotu;
- reference z array na boxed objekt;
- případné další alokace při resize.

Proto je potřeba rozlišovat:

- hodnotu;
- objekt;
- referenci;
- array;
- objektový graf;
- retained memory.

# Memory analysis workflow

## Statická vs. dynamická analýza

| Typ | Co sleduje | Kdy se hodí | Nástroje |
|---|---|---|---|
| **Statická analýza paměti** | snapshot heapu v jednom okamžiku | co zabírá heap teď | heap dump, object histogram, Eclipse MAT |
| **Dynamická analýza paměti** | alokace a změny v čase | kdo alokuje, proč roste heap, GC pressure | JFR, async-profiler allocation mode, profilers |

Statická analýza odpovídá: **co je v heapu**.

Dynamická analýza odpovídá: **kdo to vytváří a jak rychle**.

## Object histogram

Object histogram je rychlý přehled podle tříd:

```bash
jcmd <pid> GC.class_histogram
jmap -histo:live <pid>
```

Ukázka:

```text
 num     #instances         #bytes  class name
   1:       1200000      960000000  [B
   2:        300000       24000000  java.lang.String
   3:        250000       16000000  java.util.HashMap$Node
```

Interpretace:

- `#instances` říká počet objektů dané třídy;
- `#bytes` říká jejich shallow součet;
- `[B` znamená `byte[]`, `[I` znamená `int[]`, `[Ljava.lang.Object;` znamená `Object[]`.

Pozor: `jmap -histo:live` může vyvolat Full GC / stop-the-world, aby ukázal jen live objekty. Na produkci opatrně.

## Heap dump

Heap dump je snapshot celého heapu. Používá se, když histogram nestačí.

```bash
jcmd <pid> GC.heap_dump /tmp/app.hprof
```

V heap dumpu hledáš:

- největší retained objects;
- dominator tree;
- paths to GC roots;
- podezřelé kolekce;
- objekty, které měly zmizet po requestu/jobu;
- velké arrays;
- opakující se wrapper objekty (`Integer`, `Long`, `String`, DTO).

Heap dump může být velký a jeho vytvoření může zastavit aplikaci. U produkce je lepší plánovat dopad nebo použít JFR/allocation profiling.

## Allocation profiling

Heap dump ukáže, co přežilo. Allocation profiling ukáže, kdo vytváří objekty.

Hodí se, když:

- GC běží příliš často;
- latency má špičky kvůli alokacím;
- objektů po GC moc nezůstává, ale allocation rate je vysoký;
- chceš najít hot path, která vytváří zbytečné objekty.

Nástroje:

- JFR allocation events;
- async-profiler `-e alloc`;
- IntelliJ/VisualVM profiler;
- APM alokační metriky.

# Shallow size, retained size a dominator tree

## Shallow size

**Shallow size** = paměť, kterou zabírá samotný objekt.

Příklad:

```java
class Node {
    int value;
    Node next;
}
```

Shallow size zahrnuje:

- object header;
- field `int value`;
- referenci `next`;
- padding kvůli zarovnání.

Nezahrnuje objekt, na který `next` ukazuje.

## Retained size

**Retained size** = kolik paměti by se uvolnilo, kdyby tento objekt zmizel a tím se odpojily objekty dosažitelné výhradně přes něj.

Příklad:

```java
class Cache {
    Map<String, byte[]> data = new HashMap<>();
}
```

Shallow size objektu `Cache` může být malý. Retained size může být gigabajty, pokud `Cache` drží velkou mapu, klíče, hodnoty a arrays.

Prakticky:

- shallow size říká "kolik stojí tento objekt";
- retained size říká "kolik paměti drží při životě".

## Dominator tree

Objekt A **dominuje** objekt B, pokud každá cesta z GC rootů k B vede přes A.

Dominator tree v MAT/JProfileru pomáhá najít vlastníka paměti:

```text
GC Roots
  -> static CacheManager
      -> HashMap
          -> entries
              -> byte[]
```

Pokud `CacheManager` dominuje velké mapě, víš, že odstranění nebo omezení cache uvolní paměť.

## Paths to GC roots

**Paths to GC roots** odpovídá na otázku: proč objekt ještě žije?

Typické cesty:

- static field;
- thread stack;
- `ThreadLocal`;
- active listener;
- cache/map;
- class loader;
- JNI reference.

U memory leaku je často nejdůležitější najít právě cestu ke GC rootu, ne jen třídu objektu.

# Primitiva, objekty, reference a arrays

## Primitiva vs objekty

Primitiva (`int`, `long`, `double`, `boolean`) mohou být uložená přímo v poli nebo jako field objektu.

Objekt má navíc:

- object header;
- class pointer;
- fieldy;
- padding;
- identitu objektu;
- možnost být zamčený / sledovaný GC.

Přibližné velikosti v běžné 64bit HotSpot JVM s compressed OOPs:

| Hodnota | Typicky |
|---|---:|
| `int` | 4 B |
| `long` | 8 B |
| reference s compressed OOP | 4 B |
| reference bez compressed OOP | 8 B |
| object header | cca 12-16 B podle objektu/JVM |
| zarovnání objektu | často na 8 B |

Konkrétní čísla ověřuj nástrojem **JOL (Java Object Layout)**, protože závisí na JVM, flags a alignmentu.

## Arrays

Primitive array:

```java
int[] xs = new int[1_000_000];
```

Data jsou v jednom kontinuálním bloku:

```text
[header][length][int][int][int][int]...
```

Object array:

```java
Integer[] xs = new Integer[1_000_000];
```

Array drží reference:

```text
[header][length][ref][ref][ref]...
                  |    |    |
                  v    v    v
              Integer objects on heap
```

To znamená víc objektů, víc pointer chasing a horší cache locality.

## Multidimensional arrays

Java `int[][]` není kompaktní 2D matice. Je to array referencí na další arrays:

```java
int[][] matrix = new int[1000][1000];
```

Mentálně:

```text
int[][] -> references to 1000 separate int[] rows
```

Pro cache-friendly numerické výpočty je často lepší ploché pole:

```java
int[] matrix = new int[rows * cols];
int value = matrix[row * cols + col];
```

# Autoboxing a boxing overhead

## Autoboxing

Autoboxing je automatický převod primitiva na objektový wrapper.

```java
List<Integer> list = new ArrayList<>();
list.add(42); // int -> Integer
```

Unboxing je opačný směr:

```java
int x = list.get(0); // Integer -> int
```

Problém není syntaxe. Problém je, že boxed hodnota je objekt.

## Integer cache

`Integer.valueOf()` typicky cachuje malé hodnoty, standardně `-128..127`.

```java
Integer a = 42;
Integer b = 42;
```

To může použít stejný cached objekt. Ale nespoléhej na to jako na výkonové řešení:

- mimo cache se alokuje;
- kolekce pořád drží reference;
- `ArrayList<Integer>` pořád není kompaktní `int[]`;
- identita wrapperů je past pro `==`.

## `List<Integer>` vs `int[]`

`int[]`:

- jeden objekt array;
- hodnoty přímo za sebou;
- dobrá spatial locality;
- nízký memory footprint;
- žádný boxing.

`ArrayList<Integer>`:

- `ArrayList` objekt;
- interní `Object[]`;
- reference v array;
- `Integer` objekty;
- pointer chasing;
- vyšší GC pressure.

Pro velké množství čísel je `int[]`, `long[]` nebo type-specific kolekce obvykle lepší než `List<Integer>` / `List<Long>`.

# Java kolekce a jejich overhead

## ArrayList

`ArrayList<T>` je wrapper nad `Object[]`.

Vlastnosti:

- dobrá locality pro reference v array;
- rychlý random access;
- amortizovaně O(1) append;
- resize kopíruje celé interní pole;
- pro primitiva způsobuje boxing.

Pokud znáš velikost předem:

```java
List<Item> items = new ArrayList<>(expectedSize);
```

Tím omezíš resize a zbytečné dočasné arrays.

## LinkedList

`LinkedList` je v Javě často horší volba, než vypadá.

Každý node má:

- vlastní objekt;
- reference na předchozí a další node;
- referenci na item;
- špatnou cache locality.

`LinkedList` se hodí jen ve specifických případech. Pro běžné iterace, fronty a seznamy bývá lepší `ArrayList` nebo `ArrayDeque`.

## HashMap

`HashMap<K,V>` používá array bucketů a nody.

Zjednodušeně:

```text
HashMap
  -> Node[] table
      -> Node(hash, key, value, next)
```

Overhead:

- `HashMap` objekt;
- `Node[]`;
- jeden `Node` objekt pro většinu entries;
- reference na key/value;
- boxing, pokud key/value jsou wrappery;
- horší locality kvůli nodům rozptýleným po heapu.

Default load factor je 0.75. Když počet prvků překročí threshold, mapa se zvětší a entries se přerozdělí.

Pokud víš počet prvků:

```java
int capacity = (int) (expectedSize / 0.75f) + 1;
Map<K, V> map = new HashMap<>(capacity);
```

## Resizing

Resize je O(n), protože se alokuje větší array a přenesou/reorganizují se prvky.

Amortizovaně může být insert O(1), ale v latency-sensitive aplikaci může jeden resize vytvořit špičku.

Resize bolí hlavně:

- v request hot path;
- u velkých map/listů;
- při vysokém allocation rate;
- když resize spustí další GC pressure.

# Performance-oriented kolekce

## Type-specific kolekce

Type-specific kolekce ukládají primitiva bez boxingu.

Příklady knihoven:

- fastutil;
- Eclipse Collections;
- HPPC;
- Agrona;
- Trove.

Příklad:

```java
IntArrayList ids = new IntArrayList();
Int2ObjectMap<User> users = new Int2ObjectOpenHashMap<>();
```

Výhody:

- méně objektů;
- žádný boxing;
- lepší locality;
- menší heap;
- méně práce pro GC.

Nevýhody:

- další dependency;
- horší standardizace API;
- někdy složitější generics/interoperabilita;
- musíš hlídat semantiku default hodnot.

## Chaining vs open addressing

Java `HashMap` používá chaining/tree bins. Hodí se pro obecné objekty, ale entries jsou přes reference.

Open addressing drží data přímo v tabulce:

```text
keys:   [_, 17, _, 42, 99, _]
values: [_,  A, _,  B,  C, _]
```

Kolize se řeší hledáním jiného slotu:

- linear probing;
- quadratic probing;
- double hashing;
- Robin Hood hashing.

Výhoda open addressing:

- méně objektů;
- lepší cache locality;
- menší GC pressure.

Nevýhoda:

- mazání je složitější;
- výkon silně závisí na load factoru a kvalitě hash funkce;
- vysoký load factor zhoršuje probing.

## Praktická pravidla

1. Pro malé kolekce neoptimalizuj předčasně.
2. Pro velké primitive kolekce nepoužívej `List<Integer>` bez důvodu.
3. Pro fronty preferuj `ArrayDeque` před `LinkedList`.
4. Nastav initial capacity, pokud znáš velikost.
5. Sleduj allocation rate, ne jen velikost heapu.
6. Pokud je `HashMap$Node` vysoko v histogramu, podívej se na mapy a jejich retained size.
7. Pokud je `[B` vysoko v histogramu, hledej buffery, payloady, serializaci, cache a stringy.
8. Pokud je `String` vysoko, zkontroluj duplicity, parsing, internování a cache.

# Časté memory leaky v Javě

## Co je memory leak v Javě

Memory leak v Javě znamená: objekt je logicky mrtvý, ale pořád dosažitelný z GC rootů.

GC ho neuvolní, protože z pohledu JVM je stále živý.

## Typické příčiny

| Příčina | Problém | Jak poznat |
|---|---|---|
| Static cache | mapa roste bez limitu | dominator tree vede přes static field |
| `ThreadLocal` | hodnota zůstane ve worker threadu | path to GC root vede přes `Thread` |
| Listener/callback | objekt je registrovaný, ale nikdy odregistrovaný | path vede přes event bus/listener list |
| Neomezená fronta | producer je rychlejší než consumer | roste queue retained size |
| ClassLoader leak | staré třídy nejdou uvolnit | typické u app serverů/pluginů |
| Cache bez eviction | data se nikdy nevyhazují | stabilně roste old generation |

`ThreadLocal` v thread poolech je častá past:

```java
static final ThreadLocal<byte[]> buffer = new ThreadLocal<>();

void handle() {
    buffer.set(new byte[1024 * 1024]);
    // chybí buffer.remove()
}
```

Worker thread žije dlouho, takže hodnota může přežívat mnoho requestů.

Správně:

```java
try {
    buffer.set(tmp);
    work();
} finally {
    buffer.remove();
}
```

## Workflow při podezření na leak

1. Sleduj heap after GC, ne jen aktuální heap.
2. Udělej heap dump ve stabilním bodě.
3. Najdi velké retained objects.
4. Otevři dominator tree.
5. U podezřelých objektů najdi paths to GC roots.
6. Zkontroluj, jestli je reference logicky oprávněná.
7. Potvrď fix opakovaným měřením.

# Zkouškové minimum

**Static memory analysis:** snapshot heapu, například object histogram nebo heap dump. Ukazuje, co je v paměti v daném okamžiku.

**Dynamic memory analysis:** sleduje alokace v čase. Hodí se pro allocation rate a GC pressure.

**Shallow size:** paměť samotného objektu.

**Retained size:** paměť, která by se uvolnila, kdyby objekt zmizel. Důležité pro hledání memory leaků.

**Dominator tree:** ukazuje, které objekty drží jiné objekty při životě.

**Paths to GC roots:** ukazuje, proč objekt ještě není uvolnitelný.

**Autoboxing:** automatický převod primitiva na wrapper objekt. Může způsobit vyšší memory footprint, alokace, GC pressure a horší cache locality.

**`List<Integer>` vs `int[]`:** `int[]` drží hodnoty přímo za sebou, `List<Integer>` drží reference na objekty `Integer`.

**LinkedList:** často pomalý kvůli mnoha node objektům a špatné cache locality.

**HashMap overhead:** table + node objekty + reference + key/value objekty. Initial capacity a load factor ovlivňují paměť i resize.

**Type-specific kolekce:** ukládají primitiva bez boxingu, typicky menší heap a lepší locality.

```text
object histogram:
  rychlý přehled počtu objektů a shallow bytes podle tříd

heap dump:
  celý snapshot heapu, hledej retained size a paths to GC roots

shallow:
  jen samotný objekt

retained:
  objekt + vše, co drží výhradně on

dominator:
  objekt, přes který vede každá cesta k jinému objektu

memory leak:
  logicky mrtvý, ale dosažitelný objekt

int[]:
  kompaktní data

ArrayList<Integer>:
  Object[] + Integer objekty + reference

ArrayList:
  dobrá locality referencí, resize může bolet

LinkedList:
  mnoho node objektů, špatná locality

HashMap:
  Node[] + Node objects, load factor 0.75

  data přímo v tabulce, lepší locality, složitější deletion

  změř -> najdi retained/allocation hot spot -> změň strukturu -> ověř
```
