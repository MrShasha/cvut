# Proč existuje automatic memory management

## Ruční správa paměti

V C/C++ programátor často explicitně alokuje a uvolňuje paměť:

```c
User *u = malloc(sizeof(User));
/* práce s u */
free(u);
```

Výhoda:

- přesná kontrola nad lifetime objektu;
- žádná GC pauza;
- vhodné pro low-level systémy a realtime části.

Nevýhoda:

- memory leak;
- use-after-free;
- double free;
- dangling pointer;
- složitý ownership;
- bezpečnostní chyby.

## Java model

V Javě objekt vytvoříš:

```java
User user = new User();
```

Ale běžně nepíšeš:

```java
free(user);
delete user;
```

Paměť heapu spravuje JVM. Garbage collector:

- najde živé objekty;
- pozná nedosažitelné objekty;
- uvolní paměť;
- u některých collectorů přesune živé objekty;
- udržuje heap v použitelném stavu pro rychlou alokaci.

To zjednodušuje programování a snižuje riziko use-after-free, ale přidává runtime overhead a možné pauzy.

## Memory leak v Javě stále existuje

Špatná intuice:

```text
Java má GC, takže memory leak nemůže vzniknout.
```

Správně:

```text
Memory leak v Javě = objekt už logicky nepotřebujeme,
ale pořád je dosažitelný z GC roots.
```

Příklad:

```java
static final List<byte[]> cache = new ArrayList<>();

void handle() {
    cache.add(new byte[1024 * 1024]);
}
```

Každý `byte[]` je stále dosažitelný:

```text
static field -> ArrayList -> Object[] -> byte[]
```

GC ho nesmí uvolnit, protože z pohledu JVM je objekt živý.

# Tracing GC, GC roots a reachability

## Co je garbage

JVM neví, jestli objekt "dává smysl" z pohledu business logiky. JVM umí rozhodnout jen dosažitelnost.

Objekt je **live**, pokud existuje cesta:

```text
GC root -> ... -> objekt
```

Objekt je **garbage**, pokud žádná taková cesta neexistuje.

Příklad:

```text
GC Roots
   |
   v
   A -> B -> C

   D -> E
```

`A`, `B`, `C` jsou živé. `D` a `E` jsou garbage, i když se mezi sebou mohou odkazovat. Důležité je, že nejsou dosažitelné z roots.

## Typické GC roots

GC roots jsou startovní body, odkud GC prochází object graph.

| Root                    | Co znamená                                                  |
| ----------------------- | ----------------------------------------------------------- |
| Java stack frames       | lokální proměnné, parametry a operand stack aktivních metod |
| Active Java threads     | živé `Thread` objekty a stav vláken                         |
| Static fields           | `static` reference-pole načtených tříd                      |
| JNI references          | reference držené native kódem                               |
| Class loaders / classes | metadata tříd a přes ně dosažitelné objekty                 |
| Monitors                | objekty používané v `synchronized`                          |
| JVM internals           | reference queue, interned strings, JVMTI, runtime struktury |

Detaily GC roots byly v 11. lekci. Pro GC algoritmy tady stačí vědět: **co je dosažitelné z roots, to GC ponechá**.

## Mark phase

Tracing GC typicky začne od roots a prochází reference.

Zjednodušený algoritmus:

```text
worklist = all GC roots

while worklist not empty:
  obj = worklist.pop()

  if obj is not marked:
    mark(obj)
    for each reference in obj:
      worklist.push(reference)
```

Po mark fázi:

- označené objekty jsou live;
- neoznačené objekty jsou garbage;
- další fáze rozhodne, jestli se garbage jen uvolní, nebo se live objekty přesunou/zkopírují.

## Proč GC potřebuje OopMap

Při GC musí JVM vědět, kde jsou reference:

- v registrech;
- ve stack framech;
- v object fieldech;
- v arrays;
- v JNI strukturách.

JIT kód není jednoduchý Java bytecode. Hodnoty mohou být v registrech, na stacku nebo optimalizované pryč. Proto JVM používá metadata jako **OopMap**, která pro konkrétní safepoint říkají, kde leží object references.

Bez toho by moving collector nemohl bezpečně aktualizovat reference po přesunu objektů.

# Stop-the-world, safepoints a concurrent práce

## Stop-the-world

**Stop-the-world (STW)** znamená, že JVM zastaví aplikační Java vlákna, provede část GC práce a pak je pustí dál.

STW je jednoduchý pro GC, protože object graph se během pauzy nemění.

Nevýhoda:

```text
aplikace nereaguje
latency spike
p95/p99 se zhorší
```

STW pauza není jen samotná GC práce. Pauza může obsahovat také čekání, než všechna vlákna dorazí do safepointu:

```text
visible pause = time to safepoint + GC work
```

To navazuje na safepoints z 8. lekce.

## Concurrent GC

Concurrent collector dělá část práce souběžně s aplikací.

Příklad:

```text
aplikace běží
GC současně markuje object graph
aplikace mezitím mění reference
GC musí změny zachytit přes barriers
```

Výhoda:

- kratší STW pauzy;
- lepší tail latency.

Nevýhoda:

- vyšší runtime overhead;
- složitější algoritmus;
- více metadat;
- GC a aplikace soutěží o CPU;
- vzniká floating garbage.

**Floating garbage** jsou objekty, které se stanou garbage během concurrent mark fáze, ale collector je uvolní až v dalším cyklu.

## Tri-color marking

Concurrent mark se často vysvětluje přes tri-color model:

| Barva | Význam |
|---|---|
| White | objekt ještě nebyl navštíven |
| Gray | objekt je nalezený, ale jeho reference ještě nejsou zpracované |
| Black | objekt i jeho reference jsou zpracované |

Problém concurrent GC: aplikace může během mark fáze změnit reference tak, že by GC ztratil cestu k živému objektu.

Proto existují **barriers**:

- write barrier při zápisu reference;
- read/load barrier při čtení reference u některých collectorů;
- metadata pro dohledání změn object graphu.

# Generational hypothesis a organizace heapu

## Generational hypothesis

Generational hypothesis říká:

```text
většina objektů zemře mladá
```

Typické krátce žijící objekty:

- dočasné DTO;
- iterátory;
- boxing objekty;
- stringy vytvořené během parsingu;
- malé kolekce uvnitř requestu;
- mezivýsledky stream/lambda pipeline.

Pokud většina objektů umře brzy, dává smysl sbírat mladou část heapu často a starou část méně často.

## Young a Old generation

Klasický generational heap:

```text
Heap
├── Young generation
│   ├── Eden
│   ├── Survivor From
│   └── Survivor To
└── Old generation
```

Role:

| Část | Co tam typicky je |
|---|---|
| Eden | nové objekty alokované přes TLAB / bump pointer |
| Survivor | objekty, které přežily Young GC |
| Old generation | objekty, které přežily více cyklů nebo jsou velké/dlouho žijící |

## Young GC / Minor GC

Young GC se spustí typicky, když se zaplní Eden.

Zjednodušený průběh:

```text
1. zastav aplikační vlákna
2. najdi živé objekty v Young generation
3. zkopíruj přeživší objekty do Survivor To nebo Old generation
4. vyprázdni Eden
5. prohoď Survivor From/To
6. pokračuj v aplikaci
```

Proč je to rychlé:

- Young generation je menší než celý heap;
- většina young objektů je už mrtvá;
- copying collector zpracuje hlavně živé objekty;
- po GC je Eden souvisle volný pro bump-pointer alokaci.

## Promotion a tenuring

Objekt se přesune do Old generation, když:

- přežil dost Young GC cyklů;
- Survivor space nemá dost místa;
- objekt je příliš velký;
- GC heuristika rozhodne, že promotion je výhodnější.

Tomu se říká **promotion** nebo **tenuring**.

Problém nastane, když aplikace vytváří mnoho objektů, které žijí "středně dlouho":

```text
neumřou v Eden
přežijí pár Young GC
přesunou se do Old
brzy potom zemřou
```

To zvyšuje tlak na Old generation a vede k dražším kolekcím.

## Minor, Major a Full GC

Terminologie se mezi JVM a nástroji může lišit, ale prakticky:

| Název | Co typicky sbírá | Dopad |
|---|---|---|
| **Minor / Young GC** | Young generation | časté, relativně krátké |
| **Major / Old GC** | Old generation | dražší, méně časté |
| **Full GC** | celý heap a často i další JVM metadata | nejdražší, STW, špatný signál pro latenci |

Full GC v produkční low-latency službě je typicky incident nebo minimálně signál k analýze.

# Základní algoritmy GC

## Mark-sweep

Mark-sweep:

```text
1. mark: označ živé objekty
2. sweep: projdi heap a uvolni neoznačené objekty
```

Výhoda:

- nemusí přesouvat objekty;
- jednoduchý základní model.

Nevýhoda:

- fragmentace;
- alokace musí hledat vhodnou díru;
- velké objekty mohou selhat, i když je celkově volné místo.

## Mark-compact

Mark-compact:

```text
1. mark: označ živé objekty
2. compact: posuň živé objekty k sobě
3. oprav všechny reference
```

Výhoda:

- odstraní fragmentaci;
- po compaction je volné místo souvislé;
- alokace může být zase bump-pointer.

Nevýhoda:

- přesun objektů je drahý;
- musí se aktualizovat reference;
- typicky vyžaduje delší pauzu nebo složitý concurrent algoritmus.

## Copying / evacuation

Copying collector rozdělí prostor na zdroj a cíl:

```text
From space -> live objekty zkopíruj do To space
po GC: To se stane novým aktivním prostorem
```

V JVM se často mluví o **evacuation**: živé objekty se evakuují z jednoho regionu/prostoru do jiného.

Výhoda:

- zpracuje jen živé objekty;
- mrtvé objekty se nemusí jednotlivě uvolňovat;
- výsledkem je kompaktní layout.

Nevýhoda:

- potřebuje cílový prostor;
- přesouvání objektů vyžaduje opravu referencí;
- pokud je live set velký, copying je drahý.

## Shrnutí algoritmů

| Algoritmus | Co dělá | Silná stránka | Slabina |
|---|---|---|---|
| Mark-sweep | označí live, uvolní dead | jednoduchý, nepřesouvá objekty | fragmentace |
| Mark-compact | označí live, přesune je k sobě | žádná fragmentace | drahá compaction |
| Copying / evacuation | kopíruje live objekty jinam | rychlé pro young gen s malým live setem | potřebuje prostor a kopíruje live data |
| Concurrent tracing | markuje/přesouvá za běhu aplikace | nízké pauzy | barriers, overhead, složitost |

# Barriers, card table a remembered sets

## Problém Old -> Young referencí

Při Young GC sbíráme jen Young generation. Ale starý objekt může ukazovat na mladý objekt:

```text
Old object -> Young object
```

Kdyby GC při Young GC ignoroval Old generation, mohl by mladý objekt omylem považovat za mrtvý.

Naivní řešení:

```text
při každém Young GC projdi celý Old generation
```

To je příliš drahé.

## Write barrier

JVM proto používá write barrier: malý kus kódu, který se provede při zápisu reference.

Příklad:

```java
oldObject.child = youngObject;
```

Zjednodušeně:

```text
write reference
if source is old and target is young:
  record this information
```

Barrier není zámek. Je to runtime mechanismus, který udržuje metadata pro GC.

## Card table

Card table rozdělí heap na malé bloky, typicky "cards".

```text
Heap:
[card 0][card 1][card 2][card 3][card 4]...

Card table:
[ clean][ clean][ dirty][ clean][ clean]...
```

Když se v části heapu zapíše reference, JVM označí odpovídající kartu jako dirty.

Při Young GC pak nemusí procházet celý Old generation. Stačí projít dirty cards, kde mohou být reference do Young generation.

## Remembered Set

Remembered Set je přesnější metadata struktura: pamatuje, odkud mohou vést reference do určité oblasti/regionu.

Zjednodušeně:

```text
region Y má remembered set:
  sem mohou ukazovat reference z regionů A, C, F
```

G1 používá remembered sets na úrovni regionů. Díky tomu může sbírat jen vybrané regiony, aniž by musel skenovat celý heap.

Trade-off:

- méně práce během GC;
- více práce při zápisech referencí;
- více paměti na metadata;
- složitější tuning u workloadů s mnoha cross-region referencemi.

# Parallel collector

Parallel collector je throughput-first collector.

Cíl:

```text
maximalizovat čas, kdy aplikace běží
minimalizovat procento času strávené v GC
neoptimalizovat primárně krátké pauzy
```

## Parallel Scavenge

Young generation sbírá copying collectorem s více GC vlákny.

Vhodné pro:

- batch processing;
- analytické úlohy;
- build nástroje;
- offline výpočty;
- služby, kde pauza stovky milisekund není problém.

Nevhodné pro:

- low-latency API;
- trading;
- realtime-ish aplikace;
- interaktivní systémy citlivé na p99.

## Parallel Old / Mark-Compact

Old generation může použít parallel mark-compact.

Výhoda:

- využije více CPU jader;
- dobrý throughput.

Nevýhoda:

- pořád může mít dlouhé STW pauzy;
- Full GC na velkém heapu může trvat sekundy;
- pro latency-sensitive workload je to problém.

Prakticky: Parallel GC je dobrý, když řešíš hlavně throughput, ne tail latency.

# Garbage-First (G1) collector

![[Assets/ESW/jvm-g1-gc-cycle.svg]]

## Proč G1 existuje

G1 je obecný serverový collector v HotSpot JVM a od JDK 9 je výchozí collector.

Cíl:

- rozumný throughput;
- kratší a predikovatelnější pauzy než starší throughput-first collectory;
- práce s většími heapy;
- region-based management místo pevného Young/Old rozdělení.

G1 není "pauzy nikdy nebudou". G1 se snaží držet pauzy blízko cíle, ale není to tvrdá realtime garance.

Typický cíl:

```text
-XX:MaxGCPauseMillis=200
```

To je cíl heuristiky, ne smlouva.

## Region-based heap

G1 rozdělí heap na stejně velké regiony.

Region může mít roli:

- Eden;
- Survivor;
- Old;
- Humongous;
- Free.

Schéma:

```text
Heap:
[E][E][S][O][O][F][H][H][E][O][F][S]

E = Eden
S = Survivor
O = Old
F = Free
H = Humongous
```

Role regionů se mění podle potřeby. G1 nemusí mít jeden souvislý blok Young a jeden souvislý blok Old.

## Evacuation a collection set

G1 sbírá regiony přes evacuation.

Vybere množinu regionů, které bude sbírat:

```text
collection set = regiony vybrané pro GC
```

Živé objekty z těchto regionů přesune do jiných regionů. Po evacuaci je původní region volný.

To pomáhá proti fragmentaci.

## Garbage-First princip

G1 odhaduje, kolik garbage je v jednotlivých regionech a kolik bude stát jejich sběr.

Při mixed collections vybírá hlavně regiony, kde získá nejvíc volného místa za přijatelný čas.

Proto:

```text
Garbage-First = nejdřív sbírej regiony, kde je nejvíc garbage
```

## G1 fáze

Zjednodušený cyklus:

```text
Young GC
  sbírá Eden + Survivor

Concurrent Mark
  zjistí live data v Old regionech

Remark
  krátká STW fáze pro dokončení značení

Cleanup
  najde regiony vhodné k uvolnění / mixed GC

Mixed GC
  sbírá Young + vybrané Old regiony
```

## Young-only fáze

G1 často dělá Young GC:

- STW;
- evakuuje Eden/Survivor regiony;
- přeživší objekty jdou do Survivor nebo Old;
- upravuje velikost Young generation podle pause target.

Pokud chce kratší pauzy, může zmenšit Young generation. To ale znamená častější GC.

## Concurrent mark a mixed GC

Když Old occupancy překročí threshold, G1 spustí concurrent mark.

Typicky:

```text
Initial Mark      STW, často součást Young GC
Concurrent Mark   běží souběžně s aplikací
Remark            STW, dokončení změn
Cleanup           vyhodnocení regionů
Mixed GC          STW, Young + vybrané Old regiony
```

Mixed GC je důležitý, protože G1 nemusí najednou sbírat celý Old generation. Vybírá jen část regionů.

## Humongous objects

Humongous object je objekt větší než polovina G1 regionu.

Typicky:

- velké `byte[]`;
- velké `char[]`;
- velké buffer objects;
- velké serializované payloady;
- obří JSON/string operace.

Humongous objekty se alokují do souvislé sady humongous regionů.

Problém:

- hůře se s nimi manipuluje;
- mohou fragmentovat heap;
- mohou zvyšovat tlak na Old generation;
- mohou vyvolat drahé GC cykly nebo Full GC.

Řešení se vždy měří, ale typicky:

- snížit velikost jednorázových bufferů;
- streamovat místo načtení všeho do jednoho pole;
- omezit payload;
- zvážit `-XX:G1HeapRegionSize`;
- najít alokační hot spot přes profiler.

## Full GC u G1

Full GC u G1 je fallback.

Typické příčiny:

- G1 nestíhá uvolňovat paměť;
- příliš vysoký allocation rate;
- příliš velký live set;
- humongous fragmentation;
- evacuation failure;
- heap je moc malý.

V produkci je opakovaný Full GC signál, že je potřeba analyzovat heap, allocation rate a collector nastavení.

# Low-latency collectory ZGC a Shenandoah

ZGC a Shenandoah jsou low-latency collectory. Jejich cíl není maximalizovat throughput za každou cenu, ale držet krátké pauzy i u velkých heapů.

Společná idea:

```text
co nejvíc GC práce dělat concurrentně
minimalizovat STW fáze
přesouvat/kompaktovat objekty bez dlouhé pauzy
```

## ZGC

ZGC používá concurrent marking a concurrent relocation. Aby aplikace mohla běžet i během přesouvání objektů, používá load barriers a metadata v referencích.

Silné stránky:

- velmi krátké pauzy;
- vhodný pro velké heapy;
- dobrý pro latency-sensitive služby.

Cena:

- runtime overhead;
- vyšší komplexita;
- potřebuje dost CPU prostoru pro concurrent práci;
- nemusí být nejlepší pro maximální throughput.

## Shenandoah

Shenandoah má podobný cíl: krátké pauzy díky concurrent compaction.

Silné stránky:

- snižuje dlouhé STW compaction pauzy;
- dobře míří na latency-sensitive workloady;
- přesouvá velkou část práce mimo pauzy.

Cena:

- barriers a metadata overhead;
- složitější chování;
- výsledky závisí na workloadu a JDK.

## Kdy low-latency collector dává smysl

Dává smysl, když:

- p99/p999 latency je důležitější než absolutní throughput;
- heap je velký;
- Full GC pauzy jsou nepřijatelné;
- aplikace má dost CPU headroom;
- workload byl reálně změřen.

Nedává automaticky smysl, když:

- heap je malý;
- aplikace je batch;
- hlavní problém je leak;
- problém je databáze/síť, ne GC;
- nemáš měření.

# Reference counting vs tracing GC

## Reference counting

Reference counting drží u každého objektu čítač referencí.

```text
new reference  -> counter++
drop reference -> counter--
counter == 0   -> free object
```

Výhoda:

- objekt se může uvolnit hned;
- jednodušší mentální model pro některé typy zdrojů;
- determinističtější chování;
- používá se například v `shared_ptr`, Swift ARC nebo Pythonu.

Nevýhoda:

- cyklické reference;
- overhead při každém přiřazení reference;
- v multi-threaded programu často atomické inc/dec;
- cache coherency traffic;
- neuvolňuje celý nedosažitelný cyklus bez extra mechanismu.

Příklad cyklu:

```text
A -> B
B -> A

z roots už na A/B nic nevede
ale reference counters nejsou 0
```

Čistý reference counting by takový cyklus neuvolnil.

## Tracing GC

Java používá tracing GC přístup:

```text
začni z GC roots
projdi dosažitelné objekty
všechno nedosažitelné může být uvolněno
```

Výhoda:

- zvládá cyklické reference;
- nemusí měnit counter při každém přiřazení;
- dobře funguje s generational heapem;
- umožňuje copying/compaction a rychlou alokaci.

Nevýhoda:

- periodická GC práce;
- možné pauzy;
- složitější performance model.

Proto Java nepoužívá čistý reference counting jako hlavní správu paměti.

# Praktické dopady, logy a tuning

## Co sledovat

Při GC problému nesleduj jen "heap je vysoký". Důležité jsou trendy a důvod.

| Metrika | Co říká |
|---|---|
| Allocation rate | kolik paměti aplikace alokuje za sekundu |
| Live set after GC | kolik dat zůstává po kolekci |
| Pause time | jak dlouho jsou vlákna zastavená |
| GC frequency | jak často GC běží |
| Promotion rate | kolik objektů jde do Old generation |
| Old occupancy | jestli Old dlouhodobě roste |
| Humongous allocations | velké objekty, které mohou bolet G1 |
| Time to safepoint | jestli pauzu nezvětšuje čekání na safepoint |

## GC logging

Moderní JVM umí unified logging:

```bash
java -Xlog:gc*,safepoint ...
```

Často se loguje do souboru:

```bash
java -Xlog:gc*:file=gc.log:time,uptime,level,tags ...
```

Užitečné nástroje:

- JFR;
- GC logs;
- `jcmd`;
- heap dump;
- allocation profiler;
- async-profiler;
- Eclipse MAT / JProfiler / VisualVM podle situace.

## Typické symptomy

| Symptom | Pravděpodobná příčina | Co ověřit |
|---|---|---|
| Časté Young GC | vysoký allocation rate | allocation profiler, TLAB stats, hot allocation sites |
| Old generation dlouhodobě roste | leak nebo velký live set | heap dump, dominator tree, paths to GC roots |
| Full GC | heap pressure, fragmentation, humongous, evacuation failure | GC logs, humongous allocations, live set |
| Dlouhé pauzy | velký live set nebo collector nevhodný pro latency | pause breakdown, safepoints, collector |
| Nízký throughput | GC bere moc CPU | GC time %, allocation rate, heap size |
| Latency spikes bez velké GC práce | TTSP nebo safepoint problém | `safepoint` logy |

## Základní tuning pravidla

Nejdřív měř:

```text
GC logs + JFR + allocation profiling
```

Pak řeš:

1. Sniž allocation rate.
2. Zmenši live set.
3. Odstraň memory leak.
4. Zmenši velké dočasné objekty.
5. Zvol collector podle workloadu.
6. Nastav rozumně heap.
7. Teprve potom laď detailní GC flags.

Praktické poznámky:

- větší heap může snížit frekvenci GC, ale zvýšit cenu kolekce;
- příliš malý heap vede k časté GC práci;
- `-Xms` a `-Xmx` se na serveru často nastavují stejně kvůli stabilitě;
- pause target je cíl, ne záruka;
- tuning nevyřeší leak;
- `System.gc()` v aplikačním kódu je téměř vždy špatný nápad.

## Jak vybrat collector

Velmi zjednodušeně:

| Situace | Typická volba |
|---|---|
| Malý nástroj, jednoduchý program | default JVM collector obvykle stačí |
| Batch / throughput | Parallel GC může dávat smysl |
| Obecná serverová aplikace | G1 jako dobrý výchozí bod |
| Velký heap a citlivost na p99 | ZGC nebo Shenandoah změřit v testu |
| Memory leak | žádný collector to "neopraví" |

# Časté chyby

- **Myslet si, že GC řeší logickou potřebu objektů.** GC řeší dosažitelnost.
- **Řešit GC tuning před profilingem.** Bez allocation rate, live setu a logů jen hádáš.
- **Zvětšit heap a považovat hotovo.** Můžeš jen oddálit Full GC nebo leak.
- **Ignorovat allocation rate.** Krátkodobé objekty jsou levné, ale ne zadarmo.
- **Ignorovat humongous objects u G1.** Velké buffery mohou být hlavní problém.
- **Používat `System.gc()` jako správu paměti.** Typicky způsobí zbytečnou STW pauzu.
- **Zaměnit throughput a latency.** Collector s dobrým throughputem může mít špatné p99.
- **Ignorovat safepoint time.** Viditelná pauza nemusí být jen samotná GC práce.

# Zkouškové minimum

**Garbage:** objekt, který není dosažitelný z GC roots.

**GC roots:** stack frames, static fields, active threads, JNI references, class metadata, monitors a interní JVM reference.

**Tracing GC:** začne z roots, označí dosažitelné objekty a zbytek může uvolnit.

**Memory leak v Javě:** objekt už není logicky potřeba, ale stále je reachable.

**STW:** aplikační vlákna stojí, JVM provádí GC nebo jinou VM operaci.

**Concurrent GC:** část práce běží souběžně s aplikací, ale potřebuje barriers a má overhead.

**Generational hypothesis:** většina objektů umírá mladá, proto se Young generation sbírá často.

**Young GC:** sbírá Eden/Survivor, typicky copying/evacuation.

**Promotion:** přeživší objekty se přesouvají do Old generation.

**Mark-sweep:** uvolní garbage, ale fragmentuje heap.

**Mark-compact:** odstraní fragmentaci, ale musí přesouvat objekty a opravovat reference.

**Copying collector:** kopíruje live objekty do jiného prostoru, dobrý pro Young generation.

**Write barrier:** runtime kód při zápisu reference, který udržuje metadata pro GC.

**Card table / Remembered Set:** mechanismy, aby Young GC nemusel skenovat celý Old generation.

**Parallel GC:** throughput-first, může mít dlouhé STW pauzy.

**G1:** region-based collector, vybírá regiony s hodně garbage, umí mixed GC a má pause target.

**Humongous object:** u G1 objekt větší než polovina regionu; může zhoršit fragmentaci a GC.

**ZGC/Shenandoah:** low-latency collectory s velkou částí práce concurrentně.

**Reference counting:** okamžité uvolnění při counter 0, ale problém s cykly a overhead při reference updates.

# Mini tahák

```text
garbage:
  not reachable from GC roots

Java memory leak:
  logically dead, but still reachable

tracing GC:
  roots -> mark live -> reclaim non-live

young gen:
  Eden -> Survivor -> Old

young GC:
  collect young only
  copy live objects
  clear Eden

old gen:
  long-lived objects
  expensive to collect

STW:
  application threads paused

concurrent:
  GC work overlaps with application
  needs barriers

card table:
  dirty cards show where old-to-young refs may exist

remembered set:
  region-level remembered incoming references

G1:
  region heap
  young GC + concurrent mark + mixed GC

Full GC:
  bad sign for latency-sensitive services

tuning order:
  measure -> reduce allocations/live set -> choose collector -> tune flags
```
