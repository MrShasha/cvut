# Proč virtualizace patří do performance témat

## Moderní aplikace často neběží na bare metal

Dnes aplikace typicky běží v něčem z tohoto seznamu:

- virtual machine;
- Docker container;
- Kubernetes pod;
- cloud instance;
- CI runner;
- serverless runtime.

To znamená, že mezi aplikací a hardwarem je další vrstva:

```text
Application
  -> runtime / JVM / libc
  -> container nebo VM
  -> host OS nebo hypervisor
  -> hardware
```

Každá vrstva může přidat overhead nebo změnit viditelnost zdrojů.

## Co virtualizace ovlivňuje

Virtualizace a kontejnery mohou ovlivnit:

- CPU scheduling;
- CPU frequency a turbo behavior;
- steal time;
- memory limits;
- NUMA placement;
- page tables a TLB;
- disk I/O;
- network latency;
- system calls;
- performance counters;
- benchmark stabilitu.

Proto benchmark na laptopu, ve VM, v Dockeru a v Kubernetes podu nemusí dávat stejná čísla.

## Typický problém

Aplikace vidí:

```text
availableProcessors() = 16
```

Ale container má limit:

```text
CPU limit = 2 cores
```

Pokud runtime nebo framework vytvoří thread pooly podle 16 CPU, vznikne:

```text
oversubscription
context switching
CPU throttling
horší cache locality
latency spikes
horší GC behavior
```

# Bare metal, VM a container

## Bare metal

Bare metal znamená, že OS běží přímo na fyzickém serveru.

```text
Application
  -> Operating System
  -> Hardware
```

Výhoda:

- nejméně virtualizačního overheadu;
- lepší kontrola nad hardwarem;
- přímější přístup k performance counters;
- předvídatelnější I/O a NUMA.

Nevýhoda:

- horší flexibilita;
- horší izolace mezi workloady;
- složitější deployment;
- horší utilization, pokud není server dobře vytížený.

## Virtual machine

VM virtualizuje celý počítač.

```text
Application
  -> Guest OS
  -> Virtual hardware
  -> Hypervisor
  -> Host hardware
```

VM má vlastní:

- kernel;
- userspace;
- network stack;
- filesystem;
- virtual CPU;
- virtual RAM;
- virtual devices.

Silná stránka VM je izolace. Guest OS běží odděleně a může být jiný než host OS.

## Container

Container není malá VM.

Přesněji:

```text
Container je izolovaný proces nebo skupina procesů
běžící nad stejným kernelem hosta.
```

Schéma:

```text
Application
  -> container namespaces + cgroups
  -> host Linux kernel
  -> hardware
```

Container typicky nemá vlastní kernel. Sdílí kernel hosta a izolaci dostává přes Linux namespaces a cgroups.

## VM vs container

| Vlastnost | VM | Container |
|---|---|---|
| Kernel | vlastní guest kernel | sdílí host kernel |
| Izolace | silnější | lehčí, slabší než VM |
| Start | pomalejší, boot OS | rychlý, start procesu |
| Overhead | vyšší | nižší |
| Image | větší, často celý OS | menší, aplikační vrstvy |
| Resource limits | hypervisor / cloud scheduler | cgroups |
| Typické použití | cloud instance, silná izolace | deployment aplikací, microservices |

Krátce:

- VM izoluje na úrovni celého operačního systému;
- container izoluje pohled procesu na systém;
- container je levnější, ale sdílí kernel a má jiný bezpečnostní model.

# Hypervisor a CPU virtualizace

## Hypervisor / VMM

**Hypervisor** neboli **Virtual Machine Monitor (VMM)** je vrstva, která vytváří a spravuje VM.

Úkoly hypervisoru:

- vytvořit virtuální CPU;
- mapovat virtuální paměť na host paměť;
- emulovat nebo virtualizovat zařízení;
- plánovat VM na fyzická CPU;
- izolovat VM od sebe;
- zpracovat privilegované operace guest OS.

Klasické požadavky na VMM:

| Požadavek | Význam |
|---|---|
| Fidelity | VM se chová jako fyzický stroj, kromě výkonu |
| Safety | VM nemůže obejít hypervisor a ovládnout hardware |
| Efficiency | většina instrukcí běží přímo na CPU bez zásahu hypervisoru |

## Type 1 vs Type 2

**Type 1 hypervisor** běží přímo nad hardwarem:

```text
Hardware
  -> Hypervisor
  -> VM1 / VM2 / VM3
```

Příklady:

- VMware ESXi;
- Hyper-V;
- Xen;
- KVM v praxi jako součást Linux kernelu.

**Type 2 hypervisor** běží jako aplikace nad host OS:

```text
Hardware
  -> Host OS
  -> Hypervisor application
  -> VM
```

Příklady:

- VirtualBox;
- VMware Workstation;
- Parallels.

Type 2 je pohodlný pro desktop/dev prostředí. Type 1 je typický pro servery a cloud.

Poznámka k Windows/WSL2: Hyper-V se zavádí pod Windows jako hypervisor vrstva. Windows pak běží nad hypervisorem a WSL2 používá lehkou VM. To je důvod, proč WSL2 není obyčejný proces jako WSL1.

## Privilege rings

Na x86 OS kernel normálně běží v Ring 0, aplikace v Ring 3:

```text
Ring 0: kernel mode
Ring 3: user mode
```

Problém:

```text
Guest OS chce Ring 0.
Hypervisor také potřebuje kontrolu nad hardwarem.
```

Nemohou být dva skuteční vlastníci Ring 0 nad stejným hardwarem.

Starší řešení:

- guest kernel běží méně privilegovaně;
- privilegované instrukce vyvolají trap;
- hypervisor instrukci zachytí a emuluje;
- problematické x86 instrukce se řešily binary translation.

To bylo složité a drahé.

## Hardware-assisted virtualization

Intel VT-x a AMD-V přidaly režimy pro virtualizaci CPU.

Zjednodušeně:

```text
VMX root mode:
  hypervisor

VMX non-root mode:
  guest OS Ring 0
  guest apps Ring 3
```

Guest OS si myslí, že běží v Ring 0, ale CPU pořád dovolí hypervisoru kontrolovat citlivé operace.

Když guest provede operaci, kterou musí řešit hypervisor, nastane **VM exit**:

```text
guest běží
  -> privileged event
  -> VM exit
  -> hypervisor zpracuje událost
  -> VM entry
  -> guest pokračuje
```

VM exit je drahý, protože přepíná kontext mezi VM a hypervisorem. Moderní virtualizace se proto snaží VM exitů dělat co nejméně.

## vCPU, scheduling a steal time

VM dostane virtuální CPU:

```text
vCPU
```

Hypervisor mapuje vCPU na fyzická CPU jádra nebo hardware threads.

To mapování nemusí být stabilní:

```text
VM vCPU 0 dnes běží na core 3
později na core 9
```

**Steal time** je čas, kdy VM chtěla běžet, ale hypervisor jí fyzické CPU nedal.

Typický důvod:

- host je přetížený;
- běží moc VM;
- noisy neighbor spotřebovává CPU;
- cloud instance sdílí host s jinými workloady.

V guest Linuxu se steal time objevuje například v `top` jako `st`.

Vysoký steal time znamená:

```text
aplikace čeká mimo svoji kontrolu
latency roste
benchmark je nestabilní
CPU uvnitř VM může vypadat matoucí
```

## CPU overcommit

Overcommit znamená, že host přidělil více vCPU, než má fyzických CPU.

Příklad:

```text
host: 16 physical cores
VMs total: 64 vCPU
```

To může být v pořádku, pokud VM nejsou současně aktivní. Pokud ale všechny chtějí CPU najednou, vznikne contention.

Důsledek:

- steal time;
- horší p99 latency;
- méně stabilní benchmarky;
- horší cache locality kvůli migraci vCPU.

## CPU pinning

CPU pinning přiřadí VM nebo proces konkrétním CPU.

Výhoda:

- stabilnější performance;
- méně migrace;
- lepší cache locality;
- lepší NUMA kontrola.

Nevýhoda:

- horší flexibilita scheduleru;
- složitější provoz;
- riziko nevyužití CPU;
- špatné pinning nastavení může výkon zhoršit.

# Memory virtualizace

## Guest virtual, guest physical, host physical

Guest OS si myslí, že spravuje fyzickou RAM. Ve skutečnosti spravuje **guest physical memory**, kterou hypervisor mapuje na **host physical memory**.

Překlad adres:

```text
Guest Virtual Address
  -> Guest Page Table
  -> Guest Physical Address
  -> EPT/NPT
  -> Host Physical Address
```

Guest OS spravuje vlastní page tables. Hypervisor spravuje druhý překlad.

## EPT/NPT

Moderní CPU podporují nested paging hardwarově:

- Intel EPT;
- AMD NPT/RVI.

Bez nested paging musel hypervisor udržovat shadow page tables, což bylo složité a drahé.

S EPT/NPT CPU provede dvoustupňový překlad automaticky.

Trade-off:

- mnohem jednodušší a rychlejší než shadow page tables;
- pořád může růst cena page table walk;
- roste tlak na TLB;
- pomáhají huge pages a dobrá locality.

## TLB, VPID a flush overhead

TLB cacheuje překlady virtuálních adres.

Při přepínání mezi VM by bez tagování bylo nutné TLB často flushovat. To je drahé.

Mechanismy jako VPID/ASID umožňují tagovat TLB záznamy podle VM nebo address space, takže není nutné všechno zahazovat při každém VM entry/exit.

## Ballooning a swapping

Ballooning je technika, kdy hypervisor získává paměť zpět od VM.

Princip:

```text
host potřebuje paměť
  -> hypervisor požádá balloon driver v guestu
  -> driver alokuje paměť uvnitř VM
  -> guest má méně dostupné RAM
```

Pokud guest nebo host začne swapovat, performance často dramaticky klesá.

Pro JVM je swapping obzvlášť špatný:

- heap access začne být extrémně pomalý;
- GC pauzy mohou explodovat;
- latency je nepředvídatelná.

# I/O a network virtualizace

![[Assets/ESW/virtualization-io-paths.svg]]

## Proč je I/O virtualizace těžká

CPU instrukce mohou často běžet přímo na hardware. I/O je složitější:

- zařízení má registry;
- DMA zapisuje do paměti;
- přicházejí interrupts;
- paket nebo diskový blok prochází přes driver;
- VM musí být izolovaná od ostatních VM.

Proto existuje více úrovní I/O virtualizace: od pomalé emulace po téměř přímý hardware access.

## Full emulation

Hypervisor emuluje standardní zařízení, například síťovou kartu `e1000`.

Výhoda:

- guest OS nepotřebuje speciální driver;
- funguje i se starými OS.

Nevýhoda:

- mnoho VM exitů;
- software emulace zařízení;
- vyšší CPU overhead;
- horší throughput a latency.

## Virtio / paravirtualizace

Virtio je paravirtualizovaný I/O framework.

Guest ví, že běží virtualizovaně, a používá efektivní driver:

```text
guest virtio driver
  -> virtqueue ve sdílené paměti
  -> hypervisor backend
```

Typické varianty:

- `virtio-net`;
- `virtio-blk`;
- `virtio-scsi`.

Výhoda:

- méně VM exitů;
- méně kopírování;
- lepší throughput než emulace;
- standardní přístup v Linux/KVM světě.

Nevýhoda:

- guest potřebuje virtio driver;
- pořád existuje virtualizační vrstva.

## PCI pass-through a IOMMU

PCI pass-through přidělí fyzické zařízení přímo jedné VM.

Příklad:

```text
fyzická NIC -> VM
```

Guest používá skutečný driver pro dané zařízení.

IOMMU zajišťuje DMA izolaci, aby zařízení přiřazené jedné VM nemohlo zapisovat do paměti jiné VM.

Výhoda:

- near-native výkon;
- nízká latency;
- méně hypervisor overheadu.

Nevýhoda:

- zařízení typicky nejde snadno sdílet;
- horší live migration;
- méně flexibilní cloud scheduling.

## SR-IOV

SR-IOV umožňuje jedné fyzické kartě vytvořit více virtuálních PCI funkcí.

```text
Physical Function
  -> Virtual Function 1 -> VM1
  -> Virtual Function 2 -> VM2
  -> Virtual Function 3 -> VM3
```

Každá VM dostane vlastní Virtual Function, která se chová jako samostatná síťová karta.

Výhoda:

- výkon blízký pass-through;
- jedna fyzická NIC může obsloužit více VM;
- nízký overhead.

Nevýhoda:

- složitější provoz;
- méně flexibility pro migraci;
- některé síťové funkce v software switchi se obcházejí.

## DPDK

DPDK je framework pro userspace packet processing.

Místo klasické cesty:

```text
NIC interrupt -> kernel network stack -> userspace
```

DPDK používá:

```text
poll mode driver
hugepages
userspace DMA buffers
batch processing
zero-copy principy
```

Výhoda:

- extrémně vysoký packet throughput;
- nízký overhead per packet;
- vhodné pro virtual routers, telco, packet inspection, OVS-DPDK.

Nevýhoda:

- polluje CPU aktivně;
- složitější aplikace;
- obchází část běžného kernel network stacku;
- nehodí se pro běžnou web aplikaci.

## Síť v containeru a overlay network

Container má obvykle vlastní network namespace.

Typická Docker bridge cesta:

```text
container eth0
  -> veth pair
  -> bridge
  -> iptables/nftables
  -> host NIC
```

Kubernetes může přidat:

- CNI plugin;
- overlay network;
- service proxy;
- iptables/ipvs/eBPF;
- network policies;
- load balancing.

Overlay network zapouzdří paket do dalšího paketu, například VXLAN/Geneve.

Dopad:

- extra headers;
- menší efektivní MTU;
- CPU overhead;
- možná fragmentace;
- vyšší latency.

MTU problémy jsou zrádné: mohou způsobit packet drops, retransmissions a divné timeouty.

# Kontejnery: namespaces a cgroups

## Namespaces

Namespaces izolují pohled procesu na systém.

| Namespace | Co izoluje |
|---|---|
| PID | process tree, vlastní PID 1 uvnitř containeru |
| Network | interfaces, IP adresy, routy, porty |
| Mount | pohled na filesystem |
| User | mapování UID/GID |
| IPC | shared memory, semaphores |
| UTS | hostname/domain |
| Cgroup | pohled na cgroup hierarchii |

Namespace neomezuje zdroje. Jen mění, co proces vidí.

## Cgroups

Cgroups řídí resource usage.

Typicky:

- CPU;
- memory;
- I/O;
- pids;
- devices;
- hugetlb;
- cpuset.

Cgroups odpovídají na otázku:

```text
kolik zdrojů může proces/skupina procesů použít?
```

Container runtime jako Docker/containerd nastavuje namespaces a cgroups při startu containeru.

## Requests a limits v Kubernetes

**Request** říká scheduleru, kolik zdrojů pod potřebuje pro umístění.

**Limit** říká, kolik zdrojů může container maximálně použít.

Příklad:

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2"
    memory: "1Gi"
```

CPU limit vede k throttlingu. Memory limit může vést k OOMKilled.

QoS třídy:

| QoS | Zjednodušeně |
|---|---|
| Guaranteed | requests == limits pro CPU i memory |
| Burstable | něco nastavené, ale ne úplně stejně |
| BestEffort | žádné requests/limits |

Při tlaku na node mají horší QoS pody vyšší riziko eviction.

# CPU a memory limity v kontejnerech

## CPU shares, quota a throttling

CPU shares jsou relativní váha při soutěži o CPU.

CPU quota je tvrdší limit:

```text
period = 100 ms
quota = 200 ms
```

Znamená:

```text
container může spotřebovat ekvivalent 2 CPU cores za periodu
```

Pokud container vyčerpá quota před koncem periody:

```text
kernel ho throttluje
container čeká do další periody
```

Příklad:

```text
period = 100 ms
quota = 100 ms

aplikace spotřebuje quota za 35 ms
dalších až 65 ms může čekat
```

Dopad:

- latency spikes;
- nižší throughput;
- horší GC/JIT behavior;
- event loop může ztrácet čas;
- benchmarky jsou nestabilní.

## Oversubscription uvnitř containeru

Container má limit 2 CPU, ale aplikace vytvoří:

```text
32 worker threads
8 GC threads
4 JIT compiler threads
event loop + background threads
```

Důsledek:

- context switching;
- horší cache locality;
- CPU throttling;
- delší GC pauzy;
- horší p99 latency.

Thread pooly musí odpovídat reálně dostupnému CPU.

## Memory limit a OOMKilled

Container memory limit je tvrdý limit.

Pokud procesy v containeru překročí limit, kernel může zabít proces.

V Kubernetes to uvidíš jako:

```text
OOMKilled
```

U JVM je důležité:

```text
container memory != Java heap
```

JVM používá paměť i mimo heap:

- metaspace;
- code cache;
- thread stacks;
- direct buffers;
- GC metadata;
- JIT/compiler memory;
- native libraries;
- JNI allocations;
- malloc overhead;
- monitoring agent.

Proto je špatně:

```text
container limit = 512 MB
-Xmx512m
```

Heap sice může být "v limitu", ale mimo heap už nezbývá místo.

## Direct buffers a native memory

`DirectByteBuffer` používá native memory mimo Java heap.

Typický problém:

```text
heap after GC vypadá normálně
RSS containeru roste
pak přijde OOMKilled
```

To může způsobit:

- Netty direct buffers;
- mmap;
- JNI knihovny;
- velký počet thread stacks;
- native memory leak.

# JVM v containeru

## availableProcessors

JVM používá počet dostupných procesorů pro:

- ForkJoinPool common pool;
- parallel streams;
- GC threads;
- JIT compiler threads;
- některé framework defaulty.

Pokud JVM vidí fyzický host místo container limitu, nastaví příliš mnoho vláken.

Moderní JVM container limity obvykle respektují lépe, ale vždy je lepší ověřit, co runtime opravdu vidí:

```java
Runtime.getRuntime().availableProcessors()
```

## ActiveProcessorCount

Když potřebuješ JVM explicitně říct, s kolika CPU má počítat:

```text
-XX:ActiveProcessorCount=2
```

To ovlivní JVM heuristiky a defaulty, které vycházejí z počtu CPU.

Není to náhrada za správné nastavení thread poolů aplikace, ale pomůže sjednotit JVM pohled na CPU.

## Heap sizing v containeru

Moderní JVM umí nastavovat heap jako procento dostupné paměti:

```text
-XX:MaxRAMPercentage=75
```

To říká: heap může použít přibližně 75 % dostupné RAM podle JVM.

Ale musíš nechat headroom pro native memory:

```text
container memory > Java heap
```

Prakticky sledovat:

- heap used;
- heap after GC;
- metaspace;
- direct memory;
- thread count;
- RSS;
- container memory usage;
- OOMKilled events;
- GC logs.

## Native Memory Tracking

Native Memory Tracking pomáhá zjistit, kam mizí memory mimo heap.

Konceptuálně rozdělí paměť například na:

- Java heap;
- class/metaspace;
- thread stacks;
- code cache;
- GC;
- compiler;
- internal/native.

NMT není zadarmo, ale je užitečný pro diagnostiku, když heap není problém a container memory přesto roste.

# Performance problémy v izolovaném prostředí

## Noisy neighbor

Noisy neighbor je jiný workload na stejném fyzickém hostu, který spotřebovává sdílené zdroje.

Sdílené zdroje:

- CPU;
- LLC cache;
- memory bandwidth;
- disk I/O;
- network bandwidth;
- kernel locks;
- hypervisor resources.

Projev:

- vyšší latency;
- nižší throughput;
- větší variance benchmarku;
- vyšší steal time;
- více I/O wait;
- horší p99.

Bez změny kódu.

## Storage vrstvy

VM nebo container nemusí zapisovat přímo na disk.

Cesta ve VM:

```text
application
  -> guest filesystem
  -> virtual block device
  -> hypervisor
  -> host filesystem/storage
  -> physical disk / network storage
```

Container filesystem může používat overlay layers:

```text
base layer
dependency layer
application layer
writable container layer
```

Zápisy do writable container layer mohou mít overhead. Pro databáze nebo intenzivní I/O se používají volumes, bind mounts nebo persistent volumes.

## fsync a latency

Aplikace, která často volá:

```text
fsync
flush
sync writes
```

je velmi citlivá na storage latency.

Ve VM, cloudu nebo Kubernetes může storage latency kolísat kvůli:

- network storage;
- sdílenému disku;
- throttlingu;
- noisy neighbor;
- vrstvenému filesystemu.

## Benchmarking ve VM/containeru

Ve virtualizaci je důležité rozlišovat:

| Čas | Co znamená |
|---|---|
| Wall-clock time | reálný čas podle hodin |
| CPU time | čas, kdy proces skutečně běžel na CPU |
| Steal time | čas, kdy VM chtěla běžet, ale CPU dostala jiná VM |
| Throttled time | čas, kdy container nemohl běžet kvůli CPU quota |

CI runners často běží ve sdíleném prostředí, takže jsou vhodné hlavně pro:

- velké performance regrese;
- trend monitoring;
- porovnání s velkou rezervou.

Nejsou ideální pro jemné mikrobenchmarky.

## Hardware counters

Hardware performance counters nemusí být ve VM/containeru dostupné nebo přesné.

Důvody:

- hypervisor omezuje přístup;
- counters jsou sdílené;
- container nemá permissions;
- security policy;
- `perf_event_paranoid`;
- chybí `CAP_PERFMON` nebo jiné capability.

Výsledek:

```text
perf nemusí fungovat,
nebo čísla mohou zahrnovat noise ze sdíleného hostu.
```

# Praktická diagnostika

## Co zjistit jako první

Při performance problému ve VM/containeru zjisti:

| Otázka | Proč |
|---|---|
| Běží to ve VM, containeru, nebo obojím? | určuje možné zdroje overheadu |
| Jaké jsou CPU limits/requests? | throttling a oversubscription |
| Kolik CPU vidí JVM/aplikace? | thread pooly a GC threads |
| Je steal time vysoký? | host contention/noisy neighbor |
| Je throttled time vysoký? | CPU quota je bottleneck |
| Jaký je memory limit? | OOMKilled, heap sizing |
| Kolik je RSS vs Java heap? | native memory/direct buffers |
| Je I/O lokální nebo síťové? | storage latency |
| Je síť přes overlay? | MTU, packet overhead, latency |
| Jsou dostupné counters? | interpretace `perf` |

## Praktická pravidla

1. Neporovnávej benchmark z bare metal a Kubernetes bez kontextu.
2. Sleduj throttling a steal time, ne jen CPU utilization.
3. Nenastavuj `-Xmx` na celý container memory limit.
4. Thread pooly nastav podle reálně dostupného CPU.
5. U low-latency služeb buď opatrný s CPU limits.
6. Pro intenzivní I/O nepoužívej writable container layer jako databázové úložiště.
7. U overlay network kontroluj MTU a retransmissions.
8. U performance counters ověř, že měříš to, co si myslíš.

# Časté chyby

- **Brát container jako mini-VM.** Container sdílí kernel hosta.
- **Ignorovat cgroups.** Aplikace může vidět jiný svět než scheduler.
- **Řešit jen průměrnou latenci.** Throttling/noisy neighbor se často projeví v p99.
- **Měřit v CI malé rozdíly.** Sdílený runner může přidat větší noise než změna v kódu.
- **Nastavit CPU limit a divit se latency spikes.** Quota může způsobit throttling.
- **Nastavit `-Xmx` na celý memory limit.** JVM potřebuje i native memory.
- **Ignorovat direct buffers.** Heap může být v pořádku, ale RSS roste.
- **Zapomenout na overlay network a MTU.** Síť může být pomalejší kvůli vrstvě pod aplikací.
- **Použít DPDK/SR-IOV bez potřeby.** Výkon roste, ale ztrácí se část flexibility.

# Zkouškové minimum

**Virtualizace:** vrstva, která umožňuje běh VM nad sdíleným hardwarem.

**Hypervisor/VMM:** spravuje VM, virtualizuje CPU, paměť a I/O, izoluje VM.

**Type 1 hypervisor:** běží přímo nad hardwarem, typicky server/cloud.

**Type 2 hypervisor:** běží jako aplikace nad host OS, typicky desktop/dev.

**VT-x/AMD-V:** hardware podpora, kde guest OS může běžet v non-root Ring 0 a citlivé operace způsobí VM exit.

**VM exit:** přechod z guestu do hypervisoru; drahý, proto se minimalizuje.

**EPT/NPT:** hardwarový dvoustupňový překlad adres guest virtual -> guest physical -> host physical.

**Virtio:** paravirtualizované I/O přes efektivní virtqueue ve sdílené paměti.

**PCI pass-through:** fyzické zařízení je přiřazeno jedné VM, near-native výkon, menší flexibilita.

**SR-IOV:** jedna fyzická NIC vytvoří více Virtual Functions pro více VM.

**Container:** izolovaný proces/skupina procesů nad sdíleným kernelem hosta.

**Namespaces:** izolují pohled procesu na systém.

**Cgroups:** limitují zdroje jako CPU, memory, I/O a pids.

**CPU throttling:** container vyčerpá CPU quota a čeká do další periody.

**Steal time:** VM chtěla CPU, ale hypervisor jí ho nedal.

**OOMKilled:** container překročil memory limit a kernel zabil proces.

**JVM v containeru:** hlídat `availableProcessors()`, GC threads, heap sizing, direct memory a RSS.

**Noisy neighbor:** jiný workload na stejném hostu zhoršuje latency/throughput.

# Mini tahák

```text
VM:
  own guest OS kernel
  virtual hardware
  hypervisor underneath

container:
  same host kernel
  namespaces = isolation of view
  cgroups = resource limits

CPU virtualization:
  vCPU scheduled onto physical CPU
  steal time means VM waited for CPU

VT-x / AMD-V:
  guest Ring 0 in non-root mode
  sensitive events -> VM exit

memory virtualization:
  GVA -> GPA -> HPA
  EPT/NPT does nested translation in hardware

I/O:
  emulation = compatible but slow
  virtio = paravirtualized and efficient
  pass-through/SR-IOV = near-native but less flexible

container CPU:
  quota exhausted -> throttling
  too many threads -> context switching + p99 spikes

container memory:
  limit includes heap + native memory
  Xmx must leave headroom

benchmark:
  check steal, throttling, noisy neighbor, storage/network layer
```

# Jak navazuje další téma

Další lekce je shrnutí ke státnicím. Virtualizace uzavírá performance část tím, že ukazuje, proč nestačí rozumět jen aplikaci: ve skutečném provozu výkon ovlivňuje i hypervisor, scheduler, cgroups, síťová vrstva, storage a cloudové sdílení zdrojů.
