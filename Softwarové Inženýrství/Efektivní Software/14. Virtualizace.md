Virtualizace je důležitá pro performance, protože aplikace dnes často neběží přímo na fyzickém serveru.

Typická cesta:

```text
Application
  -> runtime / JVM
  -> container nebo VM
  -> host OS / hypervisor
  -> hardware
```

Hlavní pointa:

```text
Aplikace nemusí dostat tolik CPU, paměti, I/O a sítě,
kolik si myslí, že má.
```

# Proč virtualizace patří do performance témat

Virtualizace a kontejnery mohou změnit:

- kolik CPU aplikace reálně dostane;
- jak stabilní je latency;
- jestli JVM správně nastaví thread pooly a GC threads;
- kolik paměti je dostupné pro heap i native memory;
- jak drahá je síť a storage;
- jestli benchmark měří aplikaci, nebo noise hostitele.

Typický problém:

```text
JVM vidí 16 CPU
container má limit 2 CPU
aplikace vytvoří moc vláken
-> throttling, context switching, horší p99
```

# Bare metal, VM a container

## Bare metal

Bare metal:

```text
Application
  -> Operating System
  -> Hardware
```

Výhoda: nejméně overheadu, nejlepší kontrola nad hardwarem, stabilnější měření.

Nevýhoda: horší flexibilita, slabší izolace mezi workloady, horší utilization pokud server není dobře vytížený.

## Virtual machine

VM virtualizuje celý počítač:

```text
Application
  -> Guest OS
  -> Virtual hardware
  -> Hypervisor
  -> Hardware
```

VM má vlastní kernel, userspace, network stack, filesystem a virtual devices.

Výhoda: silná izolace, může běžet jiný OS než host, dobré pro cloud instance.

Nevýhoda: více vrstev, VM exits, virtualizované I/O, možné steal time.

## Container

Container není mini-VM.

Přesně:

```text
Container = izolovaný proces nebo skupina procesů
nad stejným kernelem hosta.
```

```text
Application
  -> namespaces + cgroups
  -> host Linux kernel
  -> hardware
```

| Vlastnost | VM | Container |
|---|---|---|
| Kernel | vlastní guest kernel | sdílí host kernel |
| Izolace | silnější | lehčí, slabší |
| Start | boot OS | start procesu |
| Overhead | vyšší | nižší |
| Limity | hypervisor/cloud | cgroups |
| Použití | cloud instance | deployment aplikací |

# Hypervisor a CPU virtualizace

## Hypervisor

Hypervisor/VMM spravuje virtuální stroje.

Dělá hlavně:

- virtualizaci CPU;
- mapování paměti;
- virtualizaci zařízení;
- izolaci VM;
- scheduling vCPU na fyzická CPU.

**Type 1 hypervisor** běží přímo nad hardwarem: ESXi, Hyper-V, Xen, KVM.

**Type 2 hypervisor** běží nad host OS: VirtualBox, VMware Workstation, Parallels.

## Privilege rings a VT-x/AMD-V

Problém: guest OS chce běžet v Ring 0, ale hypervisor musí mít kontrolu nad hardwarem.

Moderní CPU to řeší přes hardware-assisted virtualization:

```text
VMX root mode:
  hypervisor

VMX non-root mode:
  guest OS Ring 0 + guest apps Ring 3
```

Když guest udělá citlivou operaci, nastane **VM exit**:

```text
guest -> VM exit -> hypervisor -> VM entry -> guest
```

VM exit je drahý, proto se moderní virtualizace snaží minimalizovat počet exitů.

## vCPU, overcommit a steal time

VM dostane virtuální CPU:

```text
vCPU
```

Hypervisor mapuje vCPU na fyzická CPU. Mapování nemusí být stabilní.

**CPU overcommit**:

```text
host: 16 physical cores
VMs total: 64 vCPU
```

To funguje, dokud všechny VM nechtějí CPU zároveň.

**Steal time** je čas, kdy VM chtěla běžet, ale hypervisor jí CPU nedal.

Vysoký steal time znamená:

- host je přetížený;
- jiná VM je noisy neighbor;
- latency a benchmarky budou nestabilní.

# Memory virtualizace

Guest OS si myslí, že spravuje vlastní RAM. Ve skutečnosti hypervisor mapuje guest paměť na host paměť.

Překlad:

```text
Guest Virtual Address
  -> Guest Page Table
  -> Guest Physical Address
  -> EPT/NPT
  -> Host Physical Address
```

**EPT/NPT** je hardwarová podpora nested paging. Bez ní by hypervisor musel udržovat shadow page tables.

Dopady:

- dvoustupňový překlad může zvýšit cenu page walk;
- roste tlak na TLB;
- pomáhají huge pages a dobrá locality.

**Ballooning**: hypervisor vezme paměť zpět od VM přes balloon driver. Guest pak má méně efektivní RAM.

**Swapping** ve VM je pro výkon často katastrofa, hlavně u JVM heapu:

```text
heap access zpomalí
GC pauzy rostou
latency je nepředvídatelná
```

# I/O a network virtualizace

![[Assets/ESW/virtualization-io-paths.svg]]

I/O je těžší virtualizovat než CPU, protože zařízení používají registry, interrupts, DMA a drivers.

## Základní varianty

| Přístup | Idea | Výhoda | Nevýhoda |
|---|---|---|---|
| Emulace | hypervisor emuluje běžné zařízení | kompatibilita | hodně VM exitů, pomalé |
| Virtio | guest používá paravirtualizovaný driver | rychlé, méně kopírování | potřebuje driver |
| PCI pass-through | zařízení patří jedné VM | near-native výkon | špatné sdílení/migrace |
| SR-IOV | NIC vytvoří více Virtual Functions | near-native pro více VM | složitější síť/provoz |

## Virtio

Virtio používá sdílenou paměť:

```text
guest virtio driver
  -> virtqueue
  -> hypervisor backend
```

Typicky:

- `virtio-net`;
- `virtio-blk`;
- `virtio-scsi`.

Je to běžná efektivní cesta pro KVM/Linux.

## SR-IOV

SR-IOV:

```text
Physical Function
  -> Virtual Function 1 -> VM1
  -> Virtual Function 2 -> VM2
```

VM dostane vlastní VF jako síťovou kartu. Výkon je blízko pass-through, ale ztrácíš část flexibility, například live migration a některé funkce virtual switch.

## Overlay network

Kubernetes/container síť může přidat CNI, bridge, veth, iptables/eBPF, overlay.

Typická container cesta:

```text
container eth0
  -> veth pair
  -> bridge/CNI
  -> host NIC
```

Overlay síť jako VXLAN/Geneve přidá další header. Dopad:

- menší efektivní MTU;
- CPU overhead;
- možná fragmentace;
- vyšší latency.

## DPDK

DPDK obchází běžný kernel network stack:

```text
poll mode driver
hugepages
userspace packet processing
batching
```

Hodí se pro virtual routers, telco, packet processing, OVS-DPDK. Ne pro běžnou web aplikaci.

# Kontejnery a cgroups

## Namespaces

Namespaces izolují, co proces vidí.

| Namespace | Co izoluje |
|---|---|
| PID | process tree |
| Network | interfaces, IP, routing, ports |
| Mount | filesystem view |
| User | UID/GID mapping |
| IPC | shared memory, semaphores |
| UTS | hostname |

Namespace neomezuje zdroje. Jen izoluje pohled.

## Cgroups

Cgroups omezují zdroje:

- CPU;
- memory;
- I/O;
- pids;
- devices;
- cpuset.

Container runtime nastavuje namespaces a cgroups při startu containeru.

## Kubernetes requests/limits

**Request**: kolik zdrojů pod chce pro scheduling.

**Limit**: maximum, které container může použít.

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2"
    memory: "1Gi"
```

CPU limit typicky znamená throttling. Memory limit může znamenat OOMKilled.

## CPU throttling

CPU quota:

```text
period = 100 ms
quota = 200 ms
```

Container může použít ekvivalent 2 CPU cores za periodu.

Když quota dojde:

```text
container čeká do další periody
```

Dopad:

- latency spikes;
- horší p99;
- GC/JIT nemusí dostat CPU včas;
- event loop může stát.

## OOMKilled

Container memory limit zahrnuje celý proces, ne jen Java heap.

JVM memory:

- Java heap;
- metaspace;
- code cache;
- thread stacks;
- direct buffers;
- GC/JIT metadata;
- native libraries;
- monitoring agent.

Špatně:

```text
container limit = 512 MB
-Xmx512m
```

Mimo heap nezbývá místo, takže může přijít OOMKilled.

# JVM v containeru

## CPU

JVM používá počet CPU pro:

- GC threads;
- JIT compiler threads;
- ForkJoinPool;
- parallel streams;
- framework defaults.

Ověřit:

```java
Runtime.getRuntime().availableProcessors()
```

Když potřebuješ JVM říct počet CPU explicitně:

```text
-XX:ActiveProcessorCount=2
```

To nenahrazuje správné nastavení aplikačních thread poolů, ale sjednotí JVM heuristiky.

## Memory

Moderní JVM umí nastavit heap podle dostupné paměti:

```text
-XX:MaxRAMPercentage=75
```

Ale musí zůstat headroom:

```text
container memory > Java heap
```

Sledovat:

- heap after GC;
- RSS/container memory;
- direct memory;
- metaspace;
- thread count;
- GC logs;
- OOMKilled events.

Native Memory Tracking může pomoct, když heap vypadá OK, ale RSS roste.

# Performance diagnostika

## Typické problémy

| Symptom | Možná příčina |
|---|---|
| vysoký steal time | host overcommit, noisy neighbor |
| vysoký throttled time | CPU limit je bottleneck |
| OOMKilled | memory limit, native memory, direct buffers |
| p99 spikes | throttling, GC, storage, noisy neighbor |
| pomalé I/O | overlay FS, network storage, fsync latency |
| síťové timeouty | overlay network, MTU, retransmissions |
| nestabilní benchmark | sdílený host, CI runner, turbo/frequency, throttling |

## Co zjistit jako první

| Otázka | Proč |
|---|---|
| Běží to ve VM, containeru, nebo obojím? | jiné zdroje overheadu |
| Jaké jsou CPU request/limit? | throttling, scheduling |
| Kolik CPU vidí JVM? | thread pooly a GC threads |
| Je steal time vysoký? | host contention |
| Je throttling vysoký? | CPU quota bottleneck |
| Jaký je memory limit? | OOMKilled a heap sizing |
| RSS vs heap? | native memory/direct buffers |
| Je storage síťová nebo overlay? | latency variance |
| Je síť přes overlay? | MTU, packet overhead |

## Benchmarking

Ve virtualizaci rozlišuj:

| Metrika | Význam |
|---|---|
| Wall time | reálný čas podle hodin |
| CPU time | čas běhu na CPU |
| Steal time | VM chtěla CPU, ale nedostala ho |
| Throttled time | container čekal kvůli CPU quota |

CI/shared cloud je dobrý pro velké regrese a trendy, ne pro jemné mikrobenchmarky.

# Časté chyby

- Brát container jako mini-VM.
- Ignorovat cgroups a CPU throttling.
- Nastavit `-Xmx` na celý memory limit.
- Ladit JVM thread pooly podle fyzického hosta místo container limitu.
- Porovnávat bare metal benchmark s Kubernetes benchmarkem bez kontextu.
- Ignorovat steal time ve VM.
- Ignorovat direct buffers a native memory.
- Považovat CPU utilization za dostatečný signál výkonu.
- Zapomenout na overlay network, MTU a storage latency.

# Zkouškové minimum

**VM:** virtuální stroj s vlastním guest OS a virtual hardware.

**Container:** izolovaný proces/skupina procesů nad sdíleným host kernelem.

**Hypervisor/VMM:** spravuje VM, virtualizuje CPU, paměť a I/O.

**Type 1:** hypervisor přímo nad hardwarem. **Type 2:** hypervisor jako aplikace nad host OS.

**VT-x/AMD-V:** hardware podpora pro běh guest Ring 0 v non-root režimu.

**VM exit:** drahý přechod z guestu do hypervisoru.

**vCPU:** virtuální CPU plánované hypervisorem na fyzická CPU.

**Steal time:** VM chtěla běžet, ale hypervisor jí CPU nedal.

**EPT/NPT:** dvoustupňový překlad adres v hardware: guest virtual -> guest physical -> host physical.

**Virtio:** paravirtualizované I/O přes virtqueue.

**SR-IOV:** fyzická NIC poskytne více Virtual Functions pro VM.

**Namespaces:** izolují pohled procesu na systém.

**Cgroups:** omezují zdroje: CPU, memory, I/O, pids.

**CPU throttling:** container vyčerpá quota a čeká do další periody.

**OOMKilled:** container překročil memory limit.

**JVM v containeru:** hlídat CPU count, heap, native memory, direct buffers, RSS a GC logs.

# Mini tahák

```text
VM:
  app -> guest OS -> virtual hardware -> hypervisor -> hardware

Container:
  app -> namespaces/cgroups -> host kernel -> hardware

CPU:
  VM: steal time
  container: throttling

Memory:
  VM: EPT/NPT, ballooning, swapping
  container: memory limit, OOMKilled

JVM:
  availableProcessors()
  -XX:ActiveProcessorCount=N
  -XX:MaxRAMPercentage=...
  leave native memory headroom

I/O:
  emulation slow
  virtio good default
  pass-through/SR-IOV fast but less flexible
```

# Jak navazuje další téma

Další lekce je shrnutí ke státnicím. Virtualizace uzavírá performance část: i když je kód správný, výkon může pokazit host scheduler, cgroups, storage, síť nebo noisy neighbor.
