# Design Patterns and Antipatterns

> **Zkouškový fokus:** umět vysvětlit, co je design pattern, proč se používá, jaké jsou GoF a enterprise patterns, a proč existují antipatterns.

## 1. Co je design pattern

**Design pattern** je obecně použitelné řešení opakujícího se problému v návrhu softwaru.

Není to hotový kód, který se jen zkopíruje.

Je to spíš:

```text
pojmenované řešení
osvědčený návrhový princip
komunikační zkratka mezi vývojáři
šablona, kterou je nutné přizpůsobit kontextu
```

Příklad:

```text
Strategy pattern neříká přesně, jaký kód napsat.
Říká, že algoritmus lze oddělit za společné rozhraní
a konkrétní implementace lze měnit.
```

---

## 2. Proč design patterns vznikly

Design patterns řeší problémy, které se v objektově orientovaném a enterprise vývoji opakují.

Typické problémy:

```text
jak vytvářet objekty flexibilně
jak oddělit rozhraní od implementace
jak měnit algoritmus za běhu
jak skrýt složitost externího systému
jak snížit coupling
jak zvýšit reuse
jak organizovat komunikaci mezi objekty
```

---

## 3. Proč je důležité znát design patterns

Design patterns jsou důležité, protože:

```text
jsou proven best practices
zlepšují komunikaci mezi vývojáři
pomáhají dokumentovat návrh
zlepšují strukturu kódu
pomáhají vyhnout se opakovaným chybám
usnadňují refactoring
```

Příklad komunikace:

```text
Použijeme Strategy pro výpočet ceny.
```

Tato jedna věta vývojářům rychle řekne:

```text
bude společné rozhraní
bude více implementací algoritmu
klient bude používat abstrakci
konkrétní algoritmus bude vyměnitelný
```

---

## 4. Struktura design patternu

Klasicky se pattern popisuje pomocí:

```text
Pattern name
Problem
Solution
Consequences
```

### 4.1 Pattern name

Název slouží jako komunikační zkratka.

Příklad:

```text
Factory
Strategy
Observer
Adapter
Repository
```

### 4.2 Problem

Popisuje problém a kontext.

Příklad:

```text
Potřebujeme podporovat více platebních metod bez velkého if/else v jedné třídě.
```

### 4.3 Solution

Popisuje návrhové řešení.

Příklad:

```text
Definujeme PaymentStrategy interface a konkrétní implementace pro card, PayPal, bank transfer.
```

### 4.4 Consequences

Popisuje trade-offs.

Příklad:

```text
+ nové strategie lze přidat bez změny klientského kódu
+ lepší testovatelnost
- více tříd
- pro jednoduchý případ může být zbytečné
```

---

## 5. Design pattern vs architectural pattern

### Design pattern

Typicky řeší problém na úrovni:

```text
class
object
interface
method
collaboration between objects
```

Příklady:

```text
Strategy
Factory
Singleton
Adapter
Observer
```

### Architectural pattern

Řeší problém na úrovni systému nebo subsystému.

Příklady:

```text
API Gateway
Saga
CQRS
Circuit Breaker
Database per Service
Event Sourcing
```

### Zkoušková formulace

> Design patterns are usually more fine-grained than architectural patterns. Design patterns solve recurring implementation and object collaboration problems, while architectural patterns solve broader system-level problems.

## 7. Creational patterns

Creational patterns řeší vytváření objektů.

Cíl:

```text
oddělit klientský kód od konkrétní konstrukce objektů
zvýšit flexibilitu vytváření objektů
skrýt složitou inicializaci
```

Typické GoF creational patterns:

```text
Factory Method
Abstract Factory
Builder
Prototype
Singleton
```

## 8. Factory Method

## 8.1 Problém

Klient potřebuje vytvořit objekt, ale nechceme, aby byl pevně závislý na konkrétní třídě.

Špatně:

```java
PaymentProcessor processor = new CardPaymentProcessor();
```

Problém:

```text
klient zná konkrétní implementaci
změna implementace vyžaduje změnu klienta
těžší testování
```

---

## 8.2 Řešení

Vytvoření objektu přes factory metodu.

```java
interface PaymentProcessor {
    void pay(int amount);
}

class CardPaymentProcessor implements PaymentProcessor {
    public void pay(int amount) {
        // card payment
    }
}

class PaymentProcessorFactory {
    PaymentProcessor create(String type) {
        if (type.equals("card")) {
            return new CardPaymentProcessor();
        }
        throw new IllegalArgumentException("Unknown payment type");
    }
}
```

---

## 8.3 Výhody

```text
klient není přímo závislý na konstrukci objektu
vytváření je centralizované
snazší změna implementace
```

## 8.4 Nevýhody

```text
více tříd / více abstrakcí
factory může sama narůst do složitého objektu
```

---

## 9. Abstract Factory

## 9.1 Problém

Potřebujeme vytvářet rodiny souvisejících objektů.

Příklad:

```text
UI components for Windows
UI components for macOS
UI components for Linux
```

Nechceme míchat komponenty z různých rodin.

---

## 9.2 Řešení

Factory interface pro celou rodinu objektů.

```text
UIFactory
  createButton()
  createCheckbox()

WindowsUIFactory
MacUIFactory
LinuxUIFactory
```

---

## 9.3 Výhody

```text
konzistentní vytváření souvisejících objektů
klient nezná konkrétní třídy
snadnější výměna celé rodiny implementací
```

## 9.4 Nevýhody

```text
složitější struktura
přidání nového typu produktu může vyžadovat změnu všech factories
```

---

## 10. Builder

## 10.1 Problém

Objekt má mnoho parametrů nebo složitou konstrukci.

Špatně:

```java
new User("john", "john@example.com", true, false, 10, null, "admin", ...)
```

Problém:

```text
nečitelné
snadno se zamění parametry
konstruktor je příliš dlouhý
```

---

## 10.2 Řešení

Builder vytváří objekt krok za krokem.

```java
User user = User.builder()
    .username("john")
    .email("john@example.com")
    .active(true)
    .role("admin")
    .build();
```

---

## 10.3 Výhody

```text
čitelnější konstrukce objektu
dobré pro immutable objects
snazší práce s optional parameters
```

## 10.4 Nevýhody

```text
více kódu
pro jednoduché objekty zbytečné
```

---

## 11. Singleton

## 11.1 Problém

Chceme zajistit, že existuje jen jedna instance určité třídy.

Příklad:

```text
configuration manager
application context
logger
```

---

## 11.2 Řešení

Třída kontroluje vlastní instanci.

```java
class AppConfig {
    private static final AppConfig INSTANCE = new AppConfig();

    private AppConfig() {}

    public static AppConfig getInstance() {
        return INSTANCE;
    }
}
```

---

## 11.3 Výhody

```text
globálně dostupná jediná instance
kontrola vytvoření objektu
```

## 11.4 Nevýhody

```text
globální stav
těžší testování
skryté závislosti
problémy s paralelismem u špatné implementace
```

Důležité:

> Singleton je často nadužívaný. V moderních aplikacích je často lepší použít dependency injection a nechat lifecycle objektu řídit frameworkem.

## 13. Adapter

## 13.1 Problém

Máme existující třídu nebo externí API, ale její rozhraní neodpovídá tomu, co náš kód očekává.

Příklad:

```text
Our system expects PaymentGateway interface.
External provider has StripeClient with different methods.
```

---

## 13.2 Řešení

Adapter převede jedno rozhraní na jiné.

```java
interface PaymentGateway {
    void charge(int amount);
}

class StripeClient {
    void createCharge(int cents) {
        // external API call
    }
}

class StripePaymentAdapter implements PaymentGateway {
    private final StripeClient stripeClient;

    StripePaymentAdapter(StripeClient stripeClient) {
        this.stripeClient = stripeClient;
    }

    public void charge(int amount) {
        stripeClient.createCharge(amount);
    }
}
```

---

## 13.3 Výhody

```text
oddělení interního kódu od externí knihovny
snazší výměna externího systému
lepší testovatelnost
```

## 13.4 Nevýhody

```text
další vrstva nepřímé komunikace
příliš mnoho adapterů může zvyšovat složitost
```

---

## 14. Composite

## 14.1 Problém

Chceme pracovat stejně s jednotlivým objektem i se skupinou objektů.

Příklad:

```text
file system:
file
directory containing files and directories
```

---

## 14.2 Řešení

Společné rozhraní pro leaf i composite objekty.

```text
Component
  File
  Directory
```

Directory obsahuje kolekci Component.

---

## 14.3 Výhody

```text
jednotné zacházení s jednotlivci i skupinami
přirozené pro stromové struktury
```

## 14.4 Nevýhody

```text
může být těžší omezit, které operace dávají smysl pro leaf a composite
```

---

## 15. Facade

## 15.1 Problém

Subsystem je složitý a klient by musel volat mnoho tříd.

Příklad:

```text
Order creation requires:
- validate cart
- check inventory
- calculate price
- create order
- start payment
- send notification
```

---

## 15.2 Řešení

Facade poskytuje jednoduché rozhraní k celému subsystému.

```java
class CheckoutFacade {
    void checkout(User user, Cart cart) {
        // coordinates many internal components
    }
}
```

---

## 15.3 Výhody

```text
zjednodušuje použití složitého subsystému
skrývá interní detaily
snižuje coupling klienta
```

## 15.4 Nevýhody

```text
facade může vyrůst v God Object
může skrýt příliš mnoho detailů
```

## 18. Strategy

## 18.1 Problém

Máme více variant algoritmu a chceme je měnit bez velkého if/else.

Příklad:

```text
different discount calculation
different payment methods
different sorting strategies
different validation policies
```

Špatně:

```java
if (type.equals("student")) {
    // student discount
} else if (type.equals("vip")) {
    // vip discount
} else if (type.equals("seasonal")) {
    // seasonal discount
}
```

---

## 18.2 Řešení

Algoritmus oddělíme za společné rozhraní.

```java
interface DiscountStrategy {
    int calculateDiscount(Order order);
}

class StudentDiscount implements DiscountStrategy {
    public int calculateDiscount(Order order) {
        return 10;
    }
}

class VipDiscount implements DiscountStrategy {
    public int calculateDiscount(Order order) {
        return 20;
    }
}
```

---

## 18.3 Výhody

```text
nový algoritmus lze přidat bez změny klienta
lepší testovatelnost
nižší množství if/else
dodržuje Open-Closed Principle
```

## 18.4 Nevýhody

```text
více tříd
klient nebo factory musí vybrat správnou strategii
pro jednoduché případy může být zbytečné
```

---

## 19. Observer

## 19.1 Problém

Více objektů potřebuje reagovat na změnu jednoho objektu.

Příklad:

```text
user registered
order status changed
file changed
button clicked
domain event occurred
```

---

## 19.2 Řešení

Subject informuje observers.

```text
Subject → notify observers
Observer A reacts
Observer B reacts
Observer C reacts
```

---

## 19.3 Výhody

```text
subject nemusí znát konkrétní observers
snadné přidání nového observeru
podporuje event-like komunikaci
```

## 19.4 Nevýhody

```text
může být těžší sledovat flow
neočekávané side effects
pořadí observerů může být problém
```

---

```java
interface Command {
```

## 21. State

## 21.1 Problém

Objekt mění chování podle svého stavu.

Příklad objednávky:

```text
Created
Paid
Shipped
Cancelled
```

Špatně:

```java
if (status == CREATED) { ... }
else if (status == PAID) { ... }
else if (status == SHIPPED) { ... }
```

---

## 21.2 Řešení

Každý stav je vlastní objekt s vlastním chováním.

```text
OrderState
  CreatedState
  PaidState
  ShippedState
  CancelledState
```

---

## 21.3 Výhody

```text
stavová logika je oddělená
méně složitých if/else
snazší přidat nový stav
```

## 21.4 Nevýhody

```text
více tříd
přehnané pro jednoduchý stavový model
```

## 22. Template Method

## 22.1 Problém

Máme algoritmus s pevnou strukturou, ale některé kroky se liší.

Příklad:

```text
import file:
1. open file
2. parse file
3. validate data
4. save data
5. report result
```

CSV a XML import se liší hlavně parsingem.

---

## 22.2 Řešení

Base class definuje skeleton algoritmu, subclasses mění konkrétní kroky.

```java
abstract class FileImporter {
    public final void importFile() {
        open();
        parse();
        validate();
        save();
    }

    protected abstract void parse();
}
```

---

## 22.3 Výhody

```text
reuse společného flow
konzistentní pořadí kroků
```

## 22.4 Nevýhody

```text
dědičnost může zvýšit coupling
méně flexibilní než composition
```

## 24. DTO — Data Transfer Object

## 24.1 Problém

Nechceme přes API posílat interní entity nebo příliš mnoho dat.

Příklad špatně:

```text
REST API returns JPA UserEntity with passwordHash, internal flags and database fields.
```

---

## 24.2 Řešení

DTO je objekt určený pro přenos dat.

```java
class UserDto {
    public String username;
    public String email;
}
```

---

## 24.3 Výhody

```text
oddělení API contractu od interní entity
lepší bezpečnost
menší response payload
stabilnější API
lepší kontrola serializace
```

## 24.4 Nevýhody

```text
mapping mezi entity a DTO
více tříd
možná duplicita struktur
```

---

## 25. DAO — Data Access Object

## 25.1 Problém

Business logic by neměla znát detaily přístupu k datům.

Špatně:

```text
Service contains SQL queries directly.
```

---

## 25.2 Řešení

DAO zapouzdří přístup k datovému zdroji.

```java
interface UserDao {
    User findById(Long id);
    void save(User user);
}
```

Data source může být:

```text
RDBMS
NoSQL database
external service
linked data repository
file
```

---

## 25.3 Výhody

```text
oddělení persistence od business logiky
snazší testování
snazší změna datového zdroje
lepší organizace SQL/queries
```

## 25.4 Nevýhody

```text
více vrstev
může být zbytečné u velmi jednoduché aplikace
```

## 26. Repository

Repository je podobné DAO, ale často pracuje více na doménové úrovni.

DAO je typicky blíže databázovým operacím.

Repository se tváří jako kolekce doménových objektů.

Příklad:

```java
interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);
}
```

Rozdíl zjednodušeně:

```text
DAO = data access focused
Repository = domain collection focused
```

V praxi se tyto pojmy často používají podobně.

## 27. Unit of Work

## 27.1 Problém

V jedné business transakci změníme více objektů.

Potřebujeme koordinovat zápis změn.

Příklad:

```text

update customer statistics
reserve inventory

```

---

## 27.2 Řešení

Unit of Work sleduje změněné objekty a na konci je zapíše.

ORM frameworky jako JPA/Hibernate tento pattern často používají interně.

---

## 27.3 Výhody

```text
koordinace změn v transakci
méně ručního ukládání
lepší práce s concurrency
```

## 27.4 Nevýhody

```text
skryté chování ORM
lazy loading problémy
neočekávané queries
těžší debugging persistence contextu
```

## 28. Lazy Load

## 28.1 Problém

Objekt má data, která jsou drahá nebo zbytečná načíst hned.

Příklad:

```text
User has thousands of orders.
Product has large image.
Document has large binary content.
```

---

## 28.2 Řešení

Data se načtou až při prvním použití.

```text
user.getOrders()
```

spustí načtení orders.

---

## 28.3 Výhody

```text
lepší performance při nepoužití dat
menší memory usage
rychlejší initial load
```

## 28.4 Nevýhody

```text
N+1 query problem
skryté databázové volání
LazyInitializationException
těžší odhad performance
```

## 29. Optimistic and pessimistic locking

## 29.1 Problém

Více uživatelů nebo procesů mění stejná data.

Příklad:

```text
two admins edit the same product
two users reserve the last ticket
```

---

## 29.2 Optimistic locking

Předpokládá, že konflikty jsou vzácné.

Používá verzi záznamu.

```text
Product version = 5
User A saves with version 5 → success, version becomes 6
User B saves with version 5 → conflict
```

Výhody:

```text
dobré pro méně časté konflikty
neblokuje čtení
```

Nevýhody:

```text
konflikt se objeví až při zápisu
uživatel musí někdy opakovat změnu
```

---

## 29.3 Pessimistic locking

Předpokládá, že konflikt je pravděpodobný.

Záznam se zamkne.

Výhody:

```text
zabraňuje konfliktu předem
vhodné pro kritické operace
```

Nevýhody:

```text
blokování
nižší paralelismus
riziko deadlocku
```

---

## 31. Inversion of Control

## 31.1 Princip

**Inversion of Control** znamená, že tok řízení nepřebírá aplikace sama, ale framework.

Normálně:

```text
our code calls framework/library
```

IoC:

```text
framework calls our code
```

Známé jako:

```text
Hollywood Principle:
Don't call us, we'll call you.
```

---

## 31.2 Příklad

Ve Spring aplikaci:

```java
@RestController
class UserController {
    @GetMapping("/users")
    List<UserDto> users() {
        ...
    }
}
```

Vývojář nevolá ručně web server.

Framework:

```text
přijme HTTP request
najde controller
zavolá metodu
serializuje response
```

---

## 31.3 Výhody

```text
framework řeší lifecycle
méně boilerplate
standardizovaná struktura aplikace
lepší integrace cross-cutting concerns
```

## 31.4 Nevýhody

```text
framework magic
těžší pochopení pro začátečníky
skryté lifecycle chování
```

---

## 32. Dependency Injection

## 32.1 Princip

**Dependency Injection** je forma IoC.

Objekt si nevytváří závislosti sám. Dostane je zvenku.

Špatně:

```java
class OrderService {
    private PaymentGateway paymentGateway = new StripePaymentGateway();
}
```

Dobře:

```java
class OrderService {
    private final PaymentGateway paymentGateway;

    OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
```

---

## 32.2 Výhody

```text
loose coupling
snazší testování
snazší výměna implementace
závislost je explicitní
podporuje Dependency Inversion Principle
```

---

## 32.3 Nevýhody

```text
více konfigurace
u velkých aplikací složitý dependency graph
při nadužívání může být těžké sledovat, odkud co přichází
```

---

## 33. SOLID principles

SOLID nejsou patterny, ale design principles.

```text
S - Single Responsibility Principle
O - Open/Closed Principle
L - Liskov Substitution Principle
I - Interface Segregation Principle
D - Dependency Inversion Principle
```

---

## 34. Single Responsibility Principle

Třída nebo komponenta by měla mít jednu hlavní odpovědnost.

Špatně:

```text
UserService:
- validates user
- sends emails
- writes audit logs
- exports reports
- handles payments
```

Lépe:

```text
UserService
EmailService
AuditService
ReportService
PaymentService
```

---

## 35. Open/Closed Principle

Software entity by měly být:

```text
open for extension
closed for modification
```

Příklad:

```text
Strategy pattern allows adding new discount strategy
without changing existing discount calculation client.
```

---

## 36. Liskov Substitution Principle

Subclass musí být použitelná místo parent class bez rozbití správnosti programu.

Špatný příklad:

```text
Square extends Rectangle
```

pokud změna width u square automaticky mění height a porušuje očekávání Rectangle.

---

## 37. Interface Segregation Principle

Lepší je více malých rozhraní než jedno velké.

Špatně:

```java
interface Worker {
    void work();
    void eat();
}
```

Robot worker neumí eat.

Lépe:

```java
interface Workable {
    void work();
}

interface Eatable {
    void eat();
}
```

---

## 38. Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions.

Špatně:

```text
OrderService depends directly on StripeClient.
```

Dobře:

```text
OrderService depends on PaymentGateway interface.
StripePaymentAdapter implements PaymentGateway.
```

# Antipatterns

## 39. Co je antipattern

**Antipattern** je opakující se špatné řešení problému.

Na první pohled může vypadat prakticky nebo rychle, ale dlouhodobě způsobuje problémy.

Antipattern má často dvě části:

```text
bad solution
better alternative
```

Příklad:

```text
Antipattern:
God Object

Problem:
One class does too many things.

Better alternative:
Split responsibilities according to cohesion and clear boundaries.
```

---

## 40. Proč znát antipatterns

Antipatterns pomáhají:

```text
rozpoznat špatnou strukturu
pojmenovat problém
komunikovat technický dluh
vyhnout se opakovaným chybám
navrhnout refactoring
```

---

## 41. Big Ball of Mud

## 41.1 Popis

Systém nemá jasnou architekturu.

Symptomy:

```text
všechno závisí na všem
neexistují jasné vrstvy
neexistují jasné moduly
business logic je všude
změny jsou nebezpečné
noví vývojáři se těžko orientují
```

---

## 41.2 Důsledky

```text
těžká údržba
těžké testování
vysoký technický dluh
pomalý vývoj
strach ze změn
```

---

## 41.3 Lepší alternativa

```text
layered architecture
modular monolith
clear module boundaries
refactoring
architecture rules
tests
documentation
```

---

## 42. God Object / God Class / God Service

## 42.1 Popis

Jedna třída nebo služba dělá příliš mnoho věcí.

Příklad:

```text
ApplicationService:
- users
- orders
- payments
- reports
- notifications
- permissions
```

---

## 42.2 Problém

```text
nízká cohesion
vysoký coupling
těžké testování
těžký refactoring
časté merge konflikty
```

---

## 42.3 Lepší alternativa

```text
Single Responsibility Principle
split by business capability
separate services/classes
clear interfaces
```

---

## 43. Spaghetti Code

## 43.1 Popis

Kód má chaotický control flow.

Symptomy:

```text
dlouhé metody
mnoho vnořených if/else
kopírovaná logika
nejasné vedlejší efekty
globální proměnné
```

---

## 43.2 Lepší alternativa

```text
extract methods
introduce strategies
separate responsibilities
write tests before refactoring
simplify control flow
```

---

## 44. Golden Hammer

## 44.1 Popis

Tým používá jednu oblíbenou technologii nebo pattern na všechny problémy.

Příklad:

```text
Všude použijeme microservices.
Všude použijeme Kafka.
Všude použijeme inheritance.
Všechno bude hexagonal architecture.
```

---

## 44.2 Problém

```text
řešení neodpovídá kontextu
zbytečná komplexita
špatné trade-offs
technologie se používá kvůli hype, ne kvůli požadavkům
```

---

## 44.3 Lepší alternativa

```text
choose design according to requirements
evaluate trade-offs
prefer simplest sufficient solution
```

---

## 45. Lava Flow

## 45.1 Popis

V systému zůstává starý, mrtvý nebo experimentální kód, protože se ho nikdo nebojí odstranit.

Symptomy:

```text
nepoužívané třídy
staré experimenty
mrtvé větve
nejasný účel modulů
komentáře typu "do not remove"
```

---

## 45.2 Problém

```text
zvyšuje složitost
mate vývojáře
zhoršuje maintainability
může obsahovat bezpečnostní chyby
```

---

## 45.3 Lepší alternativa

```text
delete dead code
use version control
add tests
document active modules
perform regular cleanup
```

---

## 46. Copy-Paste Programming

## 46.1 Popis

Vývojář kopíruje podobný kód místo vytvoření sdílené abstrakce.

Symptomy:

```text
stejná validace na mnoha místech
stejný SQL dotaz v různých třídách
stejná business rule v několika services
```

---

## 46.2 Problém

```text
změna se musí udělat na více místech
snadno vznikne nekonzistence
bug fix se zapomene v jedné kopii
```

---

## 46.3 Lepší alternativa

```text
extract method
extract class
shared domain logic
template method
strategy
utility only when appropriate
```

Pozor:

```text
V microservices není vždy správné vytvořit sdílenou knihovnu pro všechno.
Někdy je menší duplicita lepší než silný coupling mezi službami.
```

---

## 47. Premature Optimization

## 47.1 Popis

Tým optimalizuje dříve, než ví, kde je skutečný problém.

Příklad:

```text
zavedení komplexního cache systému bez měření
ruční optimalizace SQL bez evidence bottlenecku
použití low-level technik bez potřeby
```

---

## 47.2 Problém

```text
zvyšuje složitost
může zavést chyby
řeší špatný problém
zhoršuje čitelnost
```

---

## 47.3 Lepší alternativa

```text
measure first
profile
identify bottleneck
optimize critical path
verify improvement
```

---

## 48. Overengineering

## 48.1 Popis

Řešení je složitější, než problém vyžaduje.

Příklad:

```text
malá CRUD aplikace s microservices, Kubernetes, Kafka, CQRS, Event Sourcing a service mesh
```

---

## 48.2 Problém

```text
vyšší náklady
delší vývoj
složitější provoz
větší riziko chyb
horší onboarding
```

---

## 48.3 Lepší alternativa

```text
KISS
YAGNI
start simple
add complexity only when justified
```

## 49. Anemic Domain Model

## 49.1 Popis

Doménové objekty obsahují jen data a žádné chování.

Veškerá business logic je v services.

Příklad:

```java
class Order {
    Long id;
    String status;
    BigDecimal totalPrice;
}
```

a všechny operace jsou v:

```text
OrderService
```

---

## 49.2 Kdy je to problém

U složité domény to vede k:

```text
velkým service třídám
duplicitní business logic
slabému modelování domény
horší maintainability
```

---

## 49.3 Kdy to nemusí být problém

U jednoduchých CRUD aplikací může být anemic model přijatelný.

Bezpečná formulace:

> Anemic domain model is more problematic in complex domain systems than in simple CRUD applications.

## 50. Shotgun Surgery

## 50.1 Popis

Malá změna vyžaduje úpravu mnoha různých míst.


## 50.2 Problém

```text
změny jsou pomalé
snadno se na něco zapomene
```

## 50.3 Lepší alternativa

```text
better encapsulation
module boundaries
DTO mapping in one place
reduce duplication
```

## 51. Tight Coupling

## 51.2 Problém

```text
těžší testování
```

## 52. Antipatterns in microservices

Microservices mají vlastní typické antipatterns.

### 52.1 Distributed monolith

Služby jsou fyzicky oddělené, ale logicky silně závislé.

Symptomy:

```text
služby se musí deployovat spolu
každý request volá dlouhý chain služeb
změna jedné služby vyžaduje změnu ostatních
výpadek jedné služby zastaví celý systém
```

Lepší alternativa:

```text
clear service boundaries
asynchronous communication where useful
database per service
backward-compatible APIs
```

---

### 52.2 Shared Persistence

Více služeb sdílí jednu databázi a přímo čte nebo mění stejné tabulky.

Problém:

```text
silný coupling
nejasné data ownership
těžké změny schématu
služby nejsou autonomní
```

Lepší alternativa:

```text
database per service
API access
events for data propagation
```

---

### 52.3 Wrong Cuts

Služby jsou špatně rozdělené.

Špatně podle technických vrstev:

```text
UserControllerService
UserBusinessService
UserRepositoryService
```

Lépe podle business capabilities:

```text
User Service
Order Service
Payment Service
Inventory Service
```

---

### 52.4 Cyclic Dependency

Služby tvoří cyklus.

Příklad:

```text
A calls B
B calls C
C calls A
```

Problém:

```text
těžké pochopit
těžké deployovat
vyšší riziko cascading failures
```

---

### 52.5 Megaservice

Jedna služba je příliš velká a chová se jako malý monolit.

Symptomy:

```text
velká codebase
mnoho business capabilities
časté změny od různých týmů
těžké testování
```

---

### 52.6 No API Gateway

Klienti volají přímo interní služby.

Problémy:

```text
klient zná interní topologii
těžší security
těžší změny služeb
duplicitní cross-cutting concerns
```

---

### 52.7 Too Many Technologies

Každá služba má jiný jazyk, framework, databázi a build system bez dobrého důvodu.

Problém:

```text
provozní chaos
těžší monitoring
těžší hiring
těžší incident response
```

Lepší alternativa:

```text
controlled technology diversity
team standards
approved technology stack
```

---

### 52.8 Microservice Greedy

Tým vytváří microservice pro každou malou feature.

Problém:

```text
příliš mnoho služeb
vyšší deployment overhead
více síťové komunikace
složitější monitoring
```

---

### 52.9 No DevOps Tools

Microservices bez CI/CD, monitoringu a automatizovaného deploymentu.

Problém:

```text
manuální deployment
pomalé release
více chyb
špatná observability
```

Microservices bez DevOps maturity jsou velmi rizikové.

## 58. Zkoušková odpověď: design pattern

A design pattern is a named, reusable solution to a recurring software design problem. It is not a ready-made implementation, but a general template that must be adapted to a concrete context.

Design patterns are useful because they capture proven best practices, improve communication between developers and help structure code. A typical pattern description contains a name, the problem, the solution and the consequences or trade-offs.

Design patterns are often divided into creational, structural and behavioral patterns. Creational patterns, such as Factory or Builder, deal with object creation. Structural patterns, such as Adapter or Composite, deal with object composition. Behavioral patterns, such as Strategy or Observer, deal with communication and behavior of objects.

It is also important to know antipatterns, because patterns can be overused or misused. For example, using many patterns in a simple system can lead to overengineering.

---

## 59. Zkoušková odpověď: types of design patterns

Design patterns are commonly divided into three groups.

Creational patterns solve problems related to object creation. Examples are Factory Method, Abstract Factory, Builder and Singleton.

Structural patterns solve problems related to composition of classes and objects. Examples are Adapter, Composite, Facade and Proxy.

Behavioral patterns solve problems related to object behavior and communication. Examples are Strategy, Observer, Command and State.

In enterprise applications, there are also enterprise patterns such as DTO, DAO, Repository, Unit of Work and Lazy Load. These patterns solve common problems with persistence, transactions, data transfer and integration.

---

## 60. Zkoušková odpověď: antipatterns

An antipattern is a commonly occurring bad solution to a recurring problem. It can look useful in the short term, but it creates long-term problems such as high coupling, low maintainability, difficult testing or technical debt.

Examples of general antipatterns are Big Ball of Mud, God Object, Spaghetti Code, Golden Hammer, Lava Flow, Copy-Paste Programming and Overengineering.

In microservices, common antipatterns include Distributed Monolith, Shared Persistence, Wrong Cuts, Cyclic Dependency, Megaservice, No API Gateway, Too Many Technologies and No DevOps Tools.

Knowing antipatterns is important because it helps developers recognize bad design early and communicate technical debt clearly.
