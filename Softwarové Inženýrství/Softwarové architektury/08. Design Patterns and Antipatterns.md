> **Zkouškový fokus:** umět vysvětlit, co je design pattern, proč vznikl, jak se liší od architectural patternu, znát hlavní GoF kategorie a umět popsat typické antipatterns.

## 1. Co je design pattern

**Design pattern** je opakovaně použitelné řešení typického návrhového problému na úrovni tříd, objektů nebo menších modulů.

Pattern není hotový kód. Je to pojmenovaný návrhový princip, který říká:

- jaký problém řeší
- v jakém kontextu se hodí
- jaké objekty nebo třídy spolupracují
- jaké výhody přináší
- jaké trade-offs vytváří

Příklad:

- Strategy řeší výběr algoritmu za běhu.
- Adapter umožní použít nekompatibilní rozhraní.
- Observer řeší upozorňování více objektů na změnu stavu.

> [!note] Důležité
> Pattern není povinnost. Pokud problém není přítomný, pattern může z jednoduchého kódu udělat zbytečně složitý kód.

---

## 2. Proč design patterns vznikly

Design patterns vznikly proto, že vývojáři opakovaně naráželi na podobné problémy:

- jak oddělit tvorbu objektů od jejich použití
- jak měnit algoritmus bez změny klientského kódu
- jak zabalit složitý subsystém do jednoduššího rozhraní
- jak reagovat na změnu stavu
- jak skládat objekty do stromových struktur
- jak omezit coupling mezi třídami

Přínos patternů:

- dávají společný jazyk týmu
- zrychlují komunikaci návrhu
- pomáhají oddělit odpovědnosti
- podporují maintainability
- ukazují známé trade-offs

Příklad komunikace:

- "Použijeme Strategy pro výpočet ceny."

Tým zhruba ví, že bude existovat rozhraní pro algoritmus a několik implementací.

---

## 3. Struktura design patternu

Typický popis patternu obsahuje:

- **Name:** název patternu
- **Problem:** jaký problém řeší
- **Context:** kdy se problém objevuje
- **Solution:** návrhová struktura řešení
- **Consequences:** výhody, nevýhody a trade-offs
- **Examples:** typické použití v praxi

> [!tip] Jak pattern hodnotit
> U zkoušky nestačí vyjmenovat název. Důležité je říct problém, princip řešení a cenu řešení.

---

## 4. Design pattern vs architectural pattern

**Design pattern** je jemnější úroveň.

Řeší:

- třídy
- objekty
- rozhraní
- menší moduly
- lokální implementační problém

Příklady:

- Factory Method
- Strategy
- Observer
- Adapter
- Repository

**Architectural pattern** je vyšší úroveň.

Řeší:

- komponenty
- služby
- vrstvy
- deployment
- komunikaci mezi většími částmi systému

Příklady:

- API Gateway
- CQRS
- Saga
- Layered architecture
- Microservices

> [!note] Bezpečná formulace
> Design pattern solves a recurring design problem at class or object level. Architectural pattern solves a recurring architectural problem at system or component level.

---

## 5. GoF design patterns

GoF patterns se tradičně dělí na tři skupiny:

- **Creational patterns:** tvorba objektů
- **Structural patterns:** skládání objektů a tříd
- **Behavioral patterns:** komunikace a chování objektů

Nejdůležitější není znát všech 23 nazpaměť, ale umět vysvětlit typické zástupce a proč se používají.

---

## 6. Creational patterns

Creational patterns řeší, jak vytvářet objekty tak, aby klientský kód nebyl zbytečně svázaný s konkrétní implementací.

### 6.1 Factory Method

**Problem:** klientský kód nechce znát konkrétní třídu objektu, který vytváří.

**Solution:** tvorba objektu se přesune do factory metody.

Příklad:

- `PaymentFactory.create("card")` vrátí `CardPayment`.
- `PaymentFactory.create("paypal")` vrátí `PayPalPayment`.

Výhody:

- klient není závislý na konkrétní třídě
- jednodušší přidání nové implementace
- centralizace tvorby objektů

Nevýhody:

- více tříd nebo metod
- může skrývat příliš mnoho rozhodování

### 6.2 Abstract Factory

**Problem:** systém potřebuje vytvářet rodiny souvisejících objektů.

**Solution:** vytvoříme factory interface pro celou rodinu objektů.

Příklad:

- `WindowsUIFactory` vytváří Windows button a Windows dialog.
- `MacUIFactory` vytváří Mac button a Mac dialog.

Výhody:

- konzistentní rodina objektů
- klient nezná konkrétní třídy
- snadnější výměna celé varianty

Nevýhody:

- složitější struktura
- přidání nového typu produktu může být pracné

### 6.3 Builder

**Problem:** objekt má mnoho parametrů nebo složitý proces konstrukce.

**Solution:** konstrukce se rozdělí do kroků.

Příklad:

- `OrderBuilder.withCustomer(...).withItems(...).withShipping(...).build()`

Výhody:

- čitelnější tvorba složitých objektů
- méně dlouhých konstruktorů
- možnost validace před `build()`

Nevýhody:

- další třída navíc
- overkill pro jednoduché objekty

### 6.4 Singleton

**Problem:** systém chce mít právě jednu instanci určité třídy.

**Solution:** třída kontroluje tvorbu své instance.

Příklady:

- configuration registry
- application-wide logger
- shared resource manager

Výhody:

- kontrola počtu instancí
- jednoduchý globální přístup

Nevýhody:

- globální stav
- horší testovatelnost
- skryté dependencies
- v moderním kódu často lepší použít dependency injection

> [!warning] Pozor na Singleton
> Singleton je často nadužívaný. Pokud jde jen o sdílenou závislost, dependency injection je většinou čistší řešení.

## 7. Structural patterns

Structural patterns řeší, jak skládat objekty a třídy do větších struktur.

### 7.1 Adapter

**Problem:** existující třída má rozhraní, které klient neumí použít.

**Solution:** adapter převede jedno rozhraní na jiné.

Příklad:

- aplikace očekává `PaymentGateway`
- externí knihovna poskytuje `StripeClient`
- `StripePaymentAdapter` implementuje `PaymentGateway` a uvnitř používá `StripeClient`

Výhody:

- znovupoužití existujícího kódu
- izolace externí knihovny
- nižší coupling klienta na vendor API

Nevýhody:

- další vrstva
- příliš mnoho adapterů může znepřehlednit systém

### 7.2 Composite

**Problem:** klient chce pracovat stejně s jedním objektem i se skupinou objektů.

**Solution:** objekty se skládají do stromové struktury se společným rozhraním.

Příklad:

- file system
  - file
  - folder
  - nested folder

Výhody:

- jednotné zacházení s leaf i composite objekty
- vhodné pro stromové struktury

Nevýhody:

- rozhraní může být příliš obecné
- může být těžké omezit validní operace pro leaf vs composite

### 7.3 Facade

**Problem:** subsystém má složité rozhraní.

**Solution:** facade poskytne jednodušší vstupní rozhraní.

Příklad:

- `OrderFacade.createOrder()` uvnitř volá inventory, payment, invoice a notification.

Výhody:

- jednodušší použití subsystému
- izolace klienta od detailů
- snížení coupling

Nevýhody:

- facade může vyrůst do God Object
- může skrývat důležité detaily chování

### 7.4 Proxy

**Problem:** přístup k objektu musí být kontrolovaný nebo odložený.

**Solution:** proxy objekt zastupuje skutečný objekt.

Příklady:

- lazy loading proxy
- remote proxy
- security proxy
- caching proxy

Výhody:

- kontrola přístupu
- lazy loading
- caching
- logging

Nevýhody:

- nepřímé volání
- debugging může být těžší
- proxy může skrývat nákladnou operaci

## 8. Behavioral patterns

Behavioral patterns řeší chování objektů a komunikaci mezi nimi.

### 8.1 Strategy

**Problem:** systém potřebuje měnit algoritmus bez změny klientského kódu.

**Solution:** algoritmus se zabalí do samostatné strategie.

Příklad:

- `DiscountStrategy`
  - `StudentDiscount`
  - `VipDiscount`
  - `SeasonalDiscount`

Výhody:

- snadná výměna algoritmu
- odstranění velkých `if/else`
- lepší testovatelnost algoritmů

Nevýhody:

- více tříd
- klient nebo context musí strategii vybrat

### 8.2 Observer

**Problem:** více objektů musí reagovat na změnu stavu jiného objektu.

**Solution:** subject publikuje změnu a observers se přihlásí k odběru.

Příklad:

- order changes state
- email notification reacts
- audit log reacts
- analytics reacts

Výhody:

- loose coupling mezi subject a observers
- snadné přidání nového observeru

Nevýhody:

- složitější tracing
- nejasné pořadí reakcí
- riziko memory leaks, pokud se observers neodregistrují

### 8.3 Command

**Problem:** akci chceme reprezentovat jako objekt.

**Solution:** command objekt zapouzdří požadavek.

Příklady:

- undo/redo
- queue of jobs
- scheduled tasks
- audit of operations

Výhody:

- akce lze ukládat, předávat a opakovat
- podporuje undo/redo
- odděluje invoker od receiveru

Nevýhody:

- více tříd
- jednoduché akce mohou být zbytečně zabalené

### 8.4 State

**Problem:** objekt mění chování podle svého stavu.

**Solution:** stav se reprezentuje samostatnými třídami.

Příklad:

Order states:

- Created
- Paid
- Shipped
- Cancelled

Výhody:

- odstranění složitých stavových `if/else`
- chování pro stav je na jednom místě
- jasnější validní přechody

Nevýhody:

- více tříd
- změny stavového modelu mohou být rozsáhlé

### 8.5 Template Method

**Problem:** algoritmus má pevnou kostru, ale některé kroky se liší.

**Solution:** base class definuje skeleton algoritmu a subclasses implementují konkrétní kroky.

Příklad:

Import file flow:

1. open file
2. parse rows
3. validate rows
4. save data

Výhody:

- reuse společné části algoritmu
- jasná struktura procesu

Nevýhody:

- inheritance coupling
- menší flexibilita než composition

### 8.6 Iterator

**Problem:** klient chce procházet kolekci bez znalosti její interní struktury.

**Solution:** iterator poskytne jednotné rozhraní pro postupné procházení.

Příklady:

- list iterator
- tree traversal
- result set cursor

Výhody:

- skrývá interní strukturu kolekce
- podporuje různé způsoby průchodu

Nevýhody:

- pro jednoduché kolekce není potřeba řešit explicitně

## 9. Enterprise design patterns

Enterprise patterns jsou praktické patterns často používané ve webových a enterprise systémech.

### 9.1 Repository

Repository zapouzdří přístup k datům.

Výhody:

- business logic nezná SQL/ORM detaily
- lepší testovatelnost
- centralizace persistence operací

Riziko:

- příliš obecné repository může být jen tenká vrstva nad ORM bez jasné hodnoty

### 9.2 DAO

DAO řeší přístup k databázi na nižší úrovni.

Používá se hlavně pro:

- SQL queries
- persistence details
- mapping mezi tabulkami a objekty

### 9.3 DTO

DTO přenáší data mezi vrstvami nebo přes API.

Výhody:

- API neodhaluje interní entity
- lze validovat vstup
- lze vracet jen potřebná data

Riziko:

- příliš mnoho mappingu
- DTO bez jasného důvodu může přidat boilerplate

### 9.4 Service Layer

Service layer organizuje use cases a business workflow.

Typicky řeší:

- transakce
- orchestrace repositories
- volání externích služeb
- authorization na úrovni use case

### 9.5 Unit of Work

Unit of Work sleduje změny objektů a uloží je jako jednu transakci.

Používá se hlavně v ORM.

Příklad:

- změna objednávky
- změna položek objednávky
- změna skladové rezervace
- commit všeho najednou

## 10. SOLID principles

SOLID nejsou design patterns, ale návrhové principy.

- **Single Responsibility Principle:** třída má mít jeden důvod ke změně.
- **Open/Closed Principle:** kód má být otevřený rozšíření, ale uzavřený modifikaci.
- **Liskov Substitution Principle:** subtype musí být použitelný místo base typu.
- **Interface Segregation Principle:** klient nemá záviset na metodách, které nepoužívá.
- **Dependency Inversion Principle:** high-level modules nemají záviset na low-level detailech, ale na abstrakcích.

> [!note] Prakticky
> SOLID není checklist pro maximalizaci abstrakcí. Smyslem je snížit coupling a zvýšit srozumitelnost změn.

## 11. Antipatterns

**Antipattern** je opakovaný špatný návrh, který vypadá jako řešení, ale dlouhodobě vytváří problémy.

Struktura antipatternu:

- **Antipattern:** název špatného řešení
- **Problem:** proč je špatné
- **Better alternative:** lepší přístup

### 11.1 God Object / God Service

Jedna třída nebo service dělá příliš mnoho věcí.

Příklad:

- `ApplicationService` řeší users, orders, payments, notifications, reports i permissions.

Problémy:

- nízká cohesion
- vysoký coupling
- těžké testování
- změna je riziková

Lepší alternativa:

- rozdělit odpovědnosti podle use cases nebo domény

### 11.2 Spaghetti Code

Kód nemá jasný flow.

Symptomy:

- mnoho větví bez struktury
- kopírovaná logika
- nejasné dependencies
- těžké čtení

Lepší alternativa:

- jasné use cases
- menší funkce
- oddělené odpovědnosti
- vhodné patterns jen tam, kde řeší reálný problém

### 11.3 Lava Flow

Starý kód zůstává v systému, protože nikdo neví, jestli se ještě používá.

Symptomy:

- dead code
- staré experimenty
- nepoužívané moduly
- komentáře typu "do not remove"

Lepší alternativa:

- observability
- test coverage
- postupné odstraňování mrtvého kódu
- dokumentované rozhodnutí

### 11.4 Golden Hammer

Tým používá jeden oblíbený pattern na všechno.

Příklad:

- všechno se řeší přes Strategy
- všude se používá Singleton
- každá třída má vlastní Factory

Lepší alternativa:

- vybírat pattern podle problému, ne podle obliby

### 11.5 Copy-Paste Programming

Logika se kopíruje místo abstrahování.

Problémy:

- bug fix se musí udělat na více místech
- kopie se časem liší
- obtížnější změny

Lepší alternativa:

- extrahovat společnou logiku
- použít composition
- vytvořit sdílenou doménovou službu, pokud dává smysl

### 11.6 Overengineering

Kód používá příliš mnoho patterns a abstrakcí pro jednoduchý problém.

Příklad:

- jednoduchý CRUD endpoint má factory, strategy, command, facade a několik mapperů bez reálné potřeby

Lepší alternativa:

- začít jednoduše
- přidat pattern až ve chvíli, kdy řeší konkrétní opakovaný problém

## 12. Jak vybrat pattern

Před použitím patternu se ptej:

- Jaký problém pattern řeší?
- Opravdu tento problém mám?
- Sníží pattern coupling nebo jen přidá abstrakce?
- Bude kód čitelnější pro tým?
- Jaké nevýhody pattern přináší?
- Lze problém vyřešit jednodušeji?

> [!tip] Zkoušková věta
> Design patterns improve communication and maintainability when they solve a real recurring problem. If they are used mechanically, they can create unnecessary complexity.

## 13. Comparison table

| Pattern | Category | Main idea | Good for | Risk |
|---|---|---|---|---|
| Factory Method | Creational | object creation through method | choosing implementation | hidden complexity |
| Abstract Factory | Creational | families of related objects | UI/toolkit variants | many interfaces |
| Builder | Creational | step-by-step construction | complex objects | overkill |
| Singleton | Creational | one shared instance | controlled shared resource | global state |
| Adapter | Structural | compatible wrapper | external APIs | extra layer |
| Composite | Structural | tree structure | file systems, menus | too general interface |
| Facade | Structural | simple API over subsystem | hiding complexity | God facade |
| Proxy | Structural | controlled access | caching, security, remote access | hidden cost |
| Strategy | Behavioral | interchangeable algorithm | pricing, validation | many small classes |
| Observer | Behavioral | notification of changes | events, UI, domain reactions | hard tracing |
| Command | Behavioral | action as object | queues, undo, jobs | boilerplate |
| State | Behavioral | behavior by state | workflows, lifecycle | many state classes |

---

## 14. Krátké shrnutí

- **Design pattern:** reusable solution to recurring design problem at class/object level.
- **Architectural pattern:** reusable solution at system/component level.
- **GoF categories:** creational, structural, behavioral.
- **Creational:** Factory Method, Abstract Factory, Builder, Singleton.
- **Structural:** Adapter, Composite, Facade, Proxy.
- **Behavioral:** Strategy, Observer, Command, State, Template Method, Iterator.
- **Enterprise patterns:** Repository, DAO, DTO, Service Layer, Unit of Work.
- **Antipattern:** repeated bad solution that creates long-term problems.
