# Architecture Evaluation and ATAM

> **Zkouškový fokus:** umět říct, proč architekturu nehodnotíme absolutně, jak fungují quality attribute scenarios a jaké výstupy dává ATAM.

## 1. Proč architekturu vyhodnocovat

Softwarová architektura není sama o sobě automaticky dobrá nebo špatná.

Architektura je dobrá tehdy, když v daném kontextu splňuje:

```text
funkční požadavky
kvalitativní požadavky
business cíle
technická omezení
organizační omezení
provozní omezení
```

Bez vyhodnocení architektury může tým zjistit příliš pozdě, že systém:

```text
nejde dobře škálovat
je příliš těžké ho měnit
má slabou dostupnost
není bezpečný
je moc složitý na provoz
má špatně zvolenou komunikaci mezi komponentami
```

Cílem vyhodnocení architektury tedy není říct pouze:

```text
tato architektura je dobrá
tato architektura je špatná
```

ale přesněji:

```text
tato architektura splňuje / nesplňuje konkrétní požadavky
tato architektura má tato rizika
tato rozhodnutí mají tyto trade-offs
tato místa jsou citlivá na změnu
```

## 2. Good architecture vs bad architecture

Bezpečná zkoušková formulace:

> Architecture is not evaluated as inherently good or bad. It must be evaluated according to the requirements, quality attributes, business goals and stakeholder concerns of a concrete system.

Například microservices nejsou automaticky lepší než monolit.

Microservices mohou být vhodné pro:

```text
velký systém
více autonomních týmů
nezávislé deploymenty
nezávislé škálování částí systému
různé technologie pro různé služby
```

Ale mohou být špatná volba pro:

```text
malou aplikaci
malý tým
rychlý MVP projekt
tým bez DevOps zkušeností
systém, kde distribuovaná komplexita nepřináší hodnotu
```

Naopak monolit může být velmi dobrá architektura, pokud je:

```text
dobře modulární
jednoduchý na deployment
dobře testovatelný
dostatečný pro aktuální rozsah systému
```

## 3. Kvalita architektury

Kvalita architektury se měří přes **quality attributes**.

Příklady:

```text
availability
performance
scalability
security
maintainability
modifiability
testability
usability
interoperability
reliability
recoverability
```

Tyto atributy musí být formulovány měřitelně.

Špatně:

```text
System must be fast.
System must be secure.
System must be reliable.
```

Lépe:

```text
95 % requests must finish under 200 ms.
System must reject unauthenticated access to admin endpoints.
System must recover from service restart within 30 seconds.
System must be available 99.9 % per month.
```

## 4. Quality attribute scenario

**Quality attribute scenario** je strukturovaný způsob, jak převést obecný kvalitativní požadavek na konkrétní měřitelný scénář.

Obecná struktura:

```text
stimulus source
stimulus
environment
artifact
response
response measure
```

### 4.1 Stimulus source

Zdroj události.

Příklady:

```text
end user
external system
administrator
attacker
internal subsystem
monitoring system
CI/CD pipeline
```

### 4.2 Stimulus

Událost nebo podmínka, na kterou musí systém reagovat.

Příklady:

```text
high request volume
invalid input
database outage
service crash
unauthorized request
deployment of a new version
network latency increase
```

### 4.3 Environment

Stav systému v okamžiku, kdy stimulus nastane.

Příklady:

```text
normal operation
peak load
startup
shutdown
recovery mode
degraded network
maintenance window
```

### 4.4 Artifact

Část systému, která je ovlivněna.

Příklady:

```text
web server
database
API gateway
authentication service
payment service
message broker
frontend application
```

### 4.5 Response

Jak má systém reagovat.

Příklady:

```text
reject request
return error message
log security event
switch to fallback
retry operation
scale additional instance
notify administrator
continue processing with degraded functionality
```

### 4.6 Response measure

Objektivní metrika, podle které se pozná, jestli systém scénář splnil.

Příklady:

```text
response time < 200 ms
recovery time < 30 seconds
error rate < 1 %
availability 99.9 %
no unauthorized data exposure
maximum data loss < 5 seconds
```

## 5. Příklad quality attribute scenario

### Performance scenario

```text
Quality attribute:
Performance

Stimulus source:
End user

Stimulus:
User sends a search request.

Environment:
Normal operation with 500 concurrent users.

Artifact:
Search API and database.

Response:
System returns search results.

Response measure:
95 % of requests finish under 300 ms.
```

### Availability scenario

```text
Quality attribute:
Availability

Stimulus source:
Database server

Stimulus:
Primary database becomes unavailable.

Environment:
Normal production operation.

Artifact:
Backend service.

Response:
System switches to read-only mode and informs users that write operations are temporarily unavailable.

Response measure:
Read operations remain available.
Recovery time is under 2 minutes.
No committed data is lost.
```

### Security scenario

```text
Quality attribute:
Security

Stimulus source:
Unauthenticated user

Stimulus:
User tries to access admin endpoint.

Environment:
Normal operation.

Artifact:
Authentication and authorization layer.

Response:
System rejects the request, returns 401 or 403, and logs the event.

Response measure:
No protected data is returned.
Security event is logged within 1 second.
```

## 6. General vs concrete scenarios

Existují dva typy scénářů:

```text
general scenarios
concrete scenarios
```

### General scenario

Obecný scénář popisuje typickou situaci, která může platit pro mnoho systémů.

Příklad:

```text
Under heavy load, the system should continue to process requests.
```

### Concrete scenario

Konkrétní scénář je přizpůsobený jednomu systému.

Příklad:

```text
During ticket sale peak, the ticket reservation API must process 2000 purchase requests per minute and 95 % of successful requests must finish under 1 second.
```

Ke zkoušce je dobré říct:

> General scenarios are reusable templates. Concrete scenarios are specific to one system and include concrete artifacts, environment and response measures.

## 7. Metody hodnocení quality attributes

Architekturu lze hodnotit několika způsoby.

### 7.1 Scenario-based evaluation

Hodnocení pomocí scénářů.

Postup:

```text
1. vybereme důležité quality attributes
2. vytvoříme konkrétní scénáře
3. zkontrolujeme, jestli architektura scénáře podporuje
4. identifikujeme risks, non-risks, trade-offs a sensitivity points
```

Příklad:

```text
Scénář:
Service A is unavailable.

Otázka:
Má architektura fallback, retry, circuit breaker nebo graceful degradation?
```

### 7.2 Simulation / prototyping

Část systému se implementuje nebo simuluje.

Používá se, když nestačí pouze teoretická analýza.

Příklad:

```text
load test prototype
proof of concept
prototype of message broker communication
prototype of database sharding
```

### 7.3 Mathematical modeling

Používá se tam, kde lze systém formálně analyzovat.

Příklad:

```text
deadlock analysis
queueing model
capacity planning
throughput estimation
availability calculation
```

### 7.4 Experience-based assessment

Hodnocení podle zkušeností architektů nebo senior engineers.

Výhoda:

```text
rychlé
praktické
vhodné v rané fázi návrhu
```

Nevýhoda:

```text
subjektivní
závisí na zkušenosti hodnotitelů
může přehlédnout méně očividná rizika
```

## 8. ATAM

![[Pasted image 20260522133935.png]]

**ATAM** znamená **Architecture Trade-off Analysis Method**.

**ATAM** je metoda pro **analýzu a hodnocení softwarové architektury**.

Používá se hlavně k tomu, aby tým zjistil:
- jestli architektura podporuje cíle projektu,
- kde jsou rizika,
- jaké kompromisy architektura obsahuje,
- jestli systém zvládne požadované vlastnosti jako výkon, bezpečnost nebo dostupnost.
## Jednoduše řečeno

**ATAM pomáhá ověřit, zda je navržená architektura dobrá pro konkrétní potřeby systému.**

Neřeší jen to, jestli systém „funguje“, ale hlavně jestli bude fungovat dobře v důležitých situacích.

Například: Systém má být rychlý, bezpečný a snadno rozšiřitelný.  
ATAM pomůže zjistit, jestli zvolená architektura tyto požadavky opravdu podporuje, nebo jestli mezi nimi vznikají problémy.

## Hlavní vstupy

- **Business drivers** - obchodní cíle systému. Například: rychlé uvedení na trh, nízké náklady, podpora velkého počtu uživatelů.
- **Quality attributes** - kvalitativní vlastnosti systému. Například: výkon, bezpečnost, dostupnost, škálovatelnost, udržovatelnost.
- **Scenarios** - konkrétní situace, podle kterých se architektura testuje. Například: „Co se stane, když se připojí 10 000 uživatelů najednou?“
- **Software architecture** - aktuální nebo navržená architektura systému.
- **Architectural approach** - obecný architektonický přístup nebo způsob řešení, který se používá k dosažení určitých vlastností systému, například výkonu, škálovatelnosti nebo dostupnosti.
- **Architectural decisions** - konkrétní architektonická rozhodnutí. Například: použití mikroslužeb, databázové replikace, cache nebo message queue.
## Co se při ATAM dělá

Tým vezme obchodní cíle, požadavky na kvalitu a architektonická rozhodnutí.

Potom analyzuje, jestli daná architektura tyto cíle podporuje.

Zjednodušeně:

```text
business goals
+ quality attributes
+ architecture decisions
+ scenarios
= analysis of risks and trade-offs
```

## Výstupy ATAM

- **Risks** - rizika v architektuře. Například: databáze může být úzké hrdlo systému.
- **Non-risks** - části architektury, které nejsou problémové.
- **Sensitivity points** - místa, kde malá změna může mít velký dopad. Například: velikost cache výrazně ovlivňuje výkon systému.
- **Trade-offs** - kompromisy mezi různými vlastnostmi systému. Například: vyšší bezpečnost může znamenat nižší výkon.
- **Risk themes** - skupiny souvisejících rizik. Například: problémy se škálovatelností nebo dostupností.

## Příklad

Máme e-shop, který musí zvládnout velkou návštěvnost během Black Friday.

Pomocí ATAM se ptáme:
- zvládne architektura vysoký počet uživatelů?
- co se stane, když vypadne databáze?
- zpomalí bezpečnostní kontroly celý systém?
- je systém snadno rozšiřitelný?
- kde jsou největší rizika?

## 10. ATAM process

ATAM má typicky 9 kroků:

```text
1. Present the ATAM
2. Present the business drivers
3. Present the architecture
4. Identify the architectural approaches
5. Create a quality attribute tree
6. Analyze the architectural approaches
7. Brainstorm and prioritize scenarios
8. Re-analyze the architectural approaches
9. Present the results
```

---

## 11. Kroky ATAM detailně

### 11.1 Present the ATAM

Evaluation team vysvětlí:

```text
cíl hodnocení
proces
role účastníků
očekávané výstupy
pravidla diskuze
```

Smysl:

```text
všichni rozumí, proč se hodnocení dělá a co z něj má vzniknout
```

### 11.2 Present the business drivers

Decision makers představí business kontext.

Typicky:

```text
business goals
hlavní features
constraints
scope
deadline
budget
regulatory requirements
expected users
critical risks
```

Business drivers jsou důležité, protože z nich vznikají architecturally significant requirements.

### 11.3 Present the architecture

Architect nebo design team představí architekturu.

Typicky:

```text
hlavní komponenty
deployment
communication
data storage
integration points
technologies
known constraints
architectural decisions
```

### 11.4 Identify architectural approaches

Tým identifikuje použité styly, vzory a technická rozhodnutí.

Příklady:

```text
layered architecture
microservices
event-driven architecture
REST API
CQRS
caching
load balancing
database replication
message broker
circuit breaker
```

Smysl:

```text
zjistit, jaké architektonické přístupy mají vliv na quality attributes
```

### 11.5 Create a quality attribute tree

**Quality attribute tree** rozkládá obecnou kvalitu systému na konkrétní měřitelné požadavky.

Struktura:

```text
utility
  → quality attribute
    → attribute refinement
      → architecturally significant requirement
```

Příklad:

```text
Utility
  Performance
    Latency
      95 % API requests under 200 ms [High]
    Throughput
      system processes 1000 requests/minute [Medium]

  Security
    Authentication
      all admin users must authenticate with strong credentials [High]
    Authorization
      only admins can access admin API [High]

  Availability
    Recovery
      system recovers from backend crash within 30 seconds [High]
```

Priority mohou být například:

```text
H = high
M = medium
L = low
```

### 11.6 Analyze the architectural approaches

Tým kontroluje, jak architektura podporuje vybrané quality attributes.

Příklad:

```text
Requirement:
System must recover from service failure within 30 seconds.

Architecture:
Kubernetes deployment with readiness/liveness probes and multiple replicas.

Analysis:
This supports automatic restart and failover, but database failure is still a risk.
```

Výstupy:

```text
risks
non-risks
sensitivity points
trade-offs
```

### 11.7 Brainstorm and prioritize scenarios

Stakeholdeři navrhují scénáře, které jsou pro ně důležité.

Příklady:

```text
What happens when database is down?
What happens under peak load?
Can we add a new payment provider?
Can attackers access private data?
Can we deploy without downtime?
Can the system recover after a failed deployment?
```

Scénáře se sloučí, pokud jsou podobné, a potom se prioritizují.

### 11.8 Re-analyze architectural approaches

Nejdůležitější scénáře se analyzují znovu hlouběji.

Cíl:

```text
ověřit, jestli architektura opravdu podporuje prioritní scénáře
zjistit konkrétní rizika
najít trade-offs
najít citlivá rozhodnutí
```

### 11.9 Present the results

Na konci se prezentují výsledky.

Typické výstupy:

```text
architecture documents
quality attribute trees
risk scenarios
non-risk scenarios
sensitivity points
trade-offs
risk themes
recommendations
```

## 12. Hlavní výstupy ATAM

### 12.1 Risks

**Risk** je architektonické rozhodnutí nebo chybějící rozhodnutí, které může způsobit nesplnění požadavku.

Příklad:

```text
Risk:
System uses a single database instance without failover.

Affected quality attribute:
Availability

Consequence:
Database failure can make the whole system unavailable.
```

### 12.2 Non-risks

**Non-risk** je rozhodnutí, které podporuje požadavky a nepředstavuje problém v daném kontextu.

Příklad:

```text
Non-risk:
Static files are served through CDN.

Affected quality attribute:
Performance and availability

Reason:
This reduces load on backend and improves response times for users in different regions.
```

### 12.3 Sensitivity points

**Sensitivity point** je místo, kde malá změna rozhodnutí může výrazně ovlivnit quality attribute.

Příklad:

```text
Sensitivity point:
Cache TTL.

If TTL is too low:
performance benefit is weak.

If TTL is too high:
users may see stale data.
```

Další příklady:

```text
number of service replicas
database connection pool size
message queue retry configuration
timeout values
rate limit configuration
sharding key
```

### 12.4 Trade-offs

**Trade-off** je situace, kdy jedno rozhodnutí zlepší jeden quality attribute, ale zhorší jiný.

Příklady:

```text
Caching:
+ improves performance
- can reduce data freshness

Microservices:
+ improves independent deployment and scalability
- increases operational complexity and testing difficulty

Strong consistency:
+ simpler reasoning about data correctness
- can reduce availability and performance in distributed systems

High security:
+ protects sensitive data
- can reduce usability and increase implementation complexity
```

Ke zkoušce:

> Architecture evaluation is mainly about discovering and documenting trade-offs, because architectural decisions usually improve some qualities while making others worse.

### 12.5 Risk themes

**Risk theme** je skupina souvisejících rizik.

Příklad:

```text
Risk theme:
Single points of failure

Risks:
- one database instance
- one message broker
- no redundant API gateway
- no backup strategy
```

Další příklad:

```text
Risk theme:
Poor maintainability

Risks:
- unclear module boundaries
- business logic duplicated across layers
- no architecture documentation
- no automated tests
```

## 13. Příklad ATAM analýzy

### System

Online ticket selling system.

### Business drivers

```text
Users must buy tickets during peak sales.
System must handle high load.
System must protect payments and personal data.
System must be available during important events.
```

### Quality attribute tree

```text
Utility
  Performance
    Throughput
      process 5000 purchase requests per minute [H]
    Latency
      95 % successful purchase requests under 1 second [H]

  Availability
    Failure recovery
      backend instance failure must not stop sales [H]
    Database availability
      database outage must not cause data corruption [H]

  Security
    Payment protection
      only authorized payment callbacks are accepted [H]
    Personal data protection
      personal data is visible only to authorized users [H]

  Maintainability
    Provider replacement
      payment provider can be replaced within 2 developer-days [M]
```

### Architectural approaches

```text
load balancer
multiple backend instances
PostgreSQL database
message queue for async processing
payment provider integration
centralized logging
monitoring
```

### Possible risks

```text
Single database instance is a single point of failure.
Payment provider integration is tightly coupled to business logic.
No rate limiting can allow traffic spikes to overload the system.
No idempotency key can cause duplicate payments.
```

### Possible trade-offs

```text
Async processing improves scalability, but makes user feedback and debugging harder.
Caching improves performance, but can return stale data.
Strict payment consistency improves correctness, but can increase latency.
```

### Possible sensitivity points

```text
database connection pool size
message retry policy
payment callback timeout
number of backend replicas
cache TTL
```

## 14. Difference: ATAM vs normal review

### Normal architecture review

Může být méně strukturovaný.

Typicky:

```text
architekt ukáže diagramy
tým diskutuje problémy
někdo navrhne změny
```

### ATAM

ATAM je systematičtější.

Má:

```text
jasný proces
quality attribute scenarios
stakeholder involvement
utility tree
risk analysis
trade-off analysis
documented results
```

ATAM je vhodný hlavně u větších nebo kritických systémů, kde architektura ovlivňuje mnoho stakeholderů a quality attributes.

## 15. Jak odpovědět na otázku: Can one architecture be better than another?

Krátká odpověď:

> One architecture can be better than another only with respect to a specific context and specific quality attributes. Architecture is not universally good or bad. It must be evaluated against functional requirements, quality requirements, business goals, stakeholder concerns and constraints.

Rozvedení:

```text
For a small application, a monolith can be better because it is simpler to develop, test and deploy.
For a large system with many teams and independent scaling needs, microservices can be better.
For high-throughput event processing, event-driven architecture can be more suitable.
For a simple CRUD application, event-driven architecture can be unnecessary overengineering.
```

Důležité:

```text
better architecture = better fit for given requirements
not more modern architecture
not more complex architecture
not more distributed architecture
```

## 17. Časté chyby při hodnocení architektury

### 17.1 Hodnocení podle popularity

Špatně:

```text
Microservices are modern, so they are better.
Kubernetes is industry standard, so we must use it.
```

Správně:

```text
We choose architecture according to requirements, constraints and quality attributes.
```

### 17.2 Ignorování trade-offs

Každé rozhodnutí má důsledky.

Příklad:

```text
Adding a message broker can improve decoupling,
but it also adds operational complexity and harder debugging.
```

### 17.3 Neměřitelné quality attributes

Špatně:

```text
System should be scalable.
```

Lépe:

```text
System must support 5000 concurrent users with 95 % requests under 300 ms.
```

### 17.4 Ignorování stakeholderů

Architektura navržená jen z pohledu vývojářů může ignorovat:

```text
users
operations
security
business
support
testers
```

### 17.5 Overengineering

Použití složité architektury bez důvodu.

Příklad:

```text
Small CRUD application with 15 microservices, Kafka, service mesh and Kubernetes.
```

## 18. Zkoušková odpověď: architecture evaluation

Software architecture should not be judged as universally good or bad. It should be evaluated in relation to concrete requirements, quality attributes, business drivers, constraints and stakeholder concerns.

Quality attributes such as performance, availability, security, maintainability, modifiability and testability should be expressed as measurable quality requirements. A useful way to evaluate them is through quality attribute scenarios. A scenario contains a stimulus source, stimulus, environment, artifact, response and response measure.

Architecture can be evaluated by scenario-based evaluation, simulation or prototyping, mathematical modeling and experience-based assessment. One common method is ATAM, the Architecture Trade-off Analysis Method. ATAM analyzes the architecture through business drivers, architectural approaches, quality attribute scenarios and stakeholder priorities. Its outputs include risks, non-risks, sensitivity points, trade-offs and risk themes.

The main idea is that architectural decisions usually involve trade-offs. For example, microservices can improve independent deployment and scalability, but increase operational and testing complexity. Therefore, the best architecture is the one that provides the best fit for the given system context.
