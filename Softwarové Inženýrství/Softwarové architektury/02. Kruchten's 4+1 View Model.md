> **Zkouškový fokus:** umět bezpečně popsat logical, process, development, physical view a scenarios, včetně vazby na UML diagramy.

## 1. Proč existuje 4+1 View Model

![[Assets/SWA/Pasted image 20260601222051.png]]

U větších softwarových systémů nestačí popsat architekturu jedním diagramem.
Různí stakeholdeři potřebují vidět systém z různých perspektiv.

Například:
- uživatele zajímá, jaké funkce systém poskytuje
- vývojáře zajímá, jak je systém rozdělen do modulů a balíčků
- DevOps tým zajímá, kde systém běží a jak je nasazený
- architekta zajímá komunikace, závislosti, výkon, škálování a rizika
- manažera zajímá rozdělení práce, náklady a rizika

Jedna perspektiva obvykle nestačí, protože zvýrazní jen jednu část reality.
Například class diagram může dobře popsat doménové objekty, ale neukáže deployment.
Deployment diagram ukáže servery a kontejnery, ale neukáže detailní chování use casu.

> [!NOTE]
> **Kruchten's 4+1 View Model** proto popisuje software architecture pomocí několika doplňujících se pohledů:
> 1. Logical view
> 2. Process view
> 3. Development view
> 4. Physical view
> 5. Scenarios jako „+1“

Scenarios tvoří „+1“, protože propojují ostatní čtyři pohledy a ověřují, že architektura opravdu podporuje důležité use cases.

Bezpečná zkoušková formulace:

> Kruchten's 4+1 View Model is an architectural model that describes a software system from multiple perspectives. The four main views describe functionality, runtime behavior, implementation structure and deployment. The additional scenario view connects and validates the other views using important use cases.

---

## 2. Základní idea modelu

Model není jeden konkrétní diagram.
Je to způsob, jak organizovat architektonickou dokumentaci.

Každý view odpovídá na jinou otázku:

| View | Hlavní otázka |
|---|---|
| Logical view | Co systém dělá? |
| Process view | Jak systém běží v runtime? |
| Development view | Jak je systém organizován v kódu? |
| Physical view | Kde systém běží? |
| Scenarios | Jak views spolupracují na konkrétních use cases? |

Důležité je, že views nejsou izolované.
Stejný prvek systému může být vidět v několika views.

Příklad:
- Order Service
  - **Logical view:** odpovídá za objednávky.
  - **Process view:** zpracovává requesty, volá payment service, publikuje eventy.
  - **Development view:** je implementován jako package/module/service v repository.
  - **Physical view:** běží jako container v Kubernetes nebo jako část backend aplikace.
  - **Scenarios:** účastní se scénáře "customer creates order".

> [!note] Jak si model pamatovat
> Jeden systémový prvek se v různých views popisuje jiným jazykem. Logical view řeší význam, process view běh, development view kód, physical view infrastrukturu a scenarios ukazují konkrétní průchod systémem.

---

## 3. Logical View

### 3.1 Co popisuje

**Logical view** se zaměřuje na funkční požadavky systému.
Popisuje, co systém dělá z pohledu domény a hlavních abstrakcí.

Řeší hlavně:
- hlavní doménové objekty
- jejich odpovědnosti
- vztahy mezi objekty
- funkcionalitu systému
- business logiku
- klíčové abstrakce
- terminologii systému

Typicky odpovídá na otázky:
- Jaké hlavní objekty nebo komponenty systém obsahuje?
- Jaké jsou jejich odpovědnosti?
- Jak spolu souvisí?
- Jaká je doménová struktura systému?
- Jaké funkce systém poskytuje uživatelům?

Logical view je blízký tomu, co by pochopil doménový expert nebo analytik.

---

### 3.2 Typické UML diagramy

Pro logical view se hodí hlavně:
- class diagram
- state diagram
- component diagram
- object diagram

Nejdůležitější je obvykle **class diagram**, protože ukazuje hlavní třídy, jejich atributy, metody a vztahy.

**State diagram** se hodí, pokud má objekt důležité stavy.

Příklad pro objednávku:
- Created → Paid → Shipped → Delivered
- Created → Cancelled
- Paid → Refunded

---

### 3.3 Příklad logical view pro e-shop

Logical view může obsahovat například tyto doménové objekty:
- Customer
- Product
- Cart
- Order
- OrderItem
- Payment
- Shipment
- Invoice

Vztahy:
- Customer creates Order
- Order contains OrderItems
- OrderItem references Product
- Order has Payment
- Order has Shipment

Tento pohled ještě nemusí říkat, jestli systém bude monolit, microservices nebo serverless.
Popisuje hlavně logickou doménu a funkcionalitu.

---

## 4. Process View

### 4.1 Co popisuje

**Process view** se zaměřuje na runtime chování systému.
Popisuje, jak části systému spolupracují při běhu.

Řeší hlavně nefunkční požadavky jako:
- performance
- scalability
- availability
- concurrency
- synchronization
- communication
- fault tolerance
- throughput
- latency

Typické otázky:
- Jaké procesy, služby nebo vlákna běží?
- Jak spolu komunikují?
- Je komunikace synchronní nebo asynchronní?
- Kde mohou vzniknout bottlenecks?
- Jak systém reaguje na vysokou zátěž?
- Jak systém zvládá chyby?

Process view není jen business process.
Jde hlavně o runtime strukturu a dynamické chování systému.

---

### 4.2 Typické UML diagramy

Pro process view se hodí:
- sequence diagram
- activity diagram
- communication diagram
- state diagram

**Sequence diagram** ukazuje pořadí komunikace mezi objekty nebo službami.
**Activity diagram** ukazuje tok aktivit, rozhodování, paralelizaci a workflow.

---

### 4.3 Příklad process view pro e-shop

Scénář: customer creates order.
1. Customer odešle checkout request.
2. Frontend zavolá Order API.
3. Order Service validuje košík.
4. Order Service zavolá Payment Service.
5. Payment Service kontaktuje payment gateway.
6. Order Service vytvoří objednávku.
7. Order Service publikuje OrderCreated event.
8. Inventory Service sníží skladové množství.
9. Notification Service odešle potvrzení zákazníkovi.

Tento pohled pomáhá diskutovat například:
- Co se stane, když payment gateway neodpovídá?
- Co se stane, když inventory update selže?
- Je checkout synchronní nebo asynchronní?
- Jak dlouho může zákazník čekat?
- Kde má být retry?
- Kde má být timeout?

---

## 5. Development View

### 5.1 Co popisuje

**Development view** popisuje implementační organizaci systému.
Zaměřuje se na to, jak je systém strukturován z pohledu vývojářů.

Řeší například:
- moduly
- balíčky
- vrstvy
- repository strukturu
- knihovny
- frameworky
- build systém
- dependencies
- team ownership
- source code organization

Typické otázky:
- Jak je projekt rozdělen v kódu?
- Kde se nachází business logic?
- Kde jsou controllery?
- Kde jsou repositories?
- Jaké moduly na sobě závisí?
- Jaký tým vlastní kterou část?
- Jak probíhá build a deployment pipeline?

Development view je důležitý hlavně pro vývojáře a projektové řízení.
Pomáhá novým členům týmu rychle pochopit strukturu projektu.

---

### 5.2 UML alignment

V původním výkladu nemá development view vždy jeden přesný standardní UML diagram.
V praxi se ale často používají:
- package diagram
- component diagram
- module diagram
- class diagram na vyšší úrovni

Důležité není vybrat „dokonalý“ diagram, ale jasně ukázat implementační strukturu.

---

### 5.3 Příklad development view pro layered backend

Typická struktura backendu:

```
- src/
  - controllers/
  - services/
  - repositories/
  - models/
  - dto/
  - config/
  - security/
  - migrations/
  - tests/
```

Závislosti:

```
Controller → Service → Repository → Database
```

Architektonické pravidlo:

- Controller nesmí přímo přistupovat do databáze.
- Business logic nesmí být v repository.
- Repository neřeší HTTP requesty.

---

### 5.4 Příklad development view pro microservices

V microservice architektuře může development view řešit například:
```
order-service/
payment-service/
inventory-service/
notification-service/
api-gateway/
shared-contracts/
deployment/
```

Důležité otázky:
- Má každá service vlastní repository?
- Nebo je použit monorepo?
- Které knihovny jsou sdílené?
- Jak se spravují API contracts?
- Který tým vlastní kterou service?
- Jak se verzují API?

Development view tedy neřeší jen kód, ale i organizaci vývoje.

---

## 6. Physical View

### 6.1 Co popisuje

**Physical view** popisuje deployment systému.
Řeší, kde a jak systém běží.

Zaměřuje se na:
- servery
- kontejnery
- cloud resources
- network
- load balancers
- databáze
- message brokers
- object storage
- firewally
- external systems
- runtime nodes

Typické otázky:
- Na jakých nodech systém běží?
- Kolik instancí služby existuje?
- Kde je databáze?
- Kde je cache?
- Jak je řešen load balancing?
- Jak služby komunikují přes síť?
- Jaké části jsou v cloudu a jaké on-premise?

Physical view je důležitý pro DevOps, operations, security a infrastrukturu.

---

### 6.2 Typické UML diagramy

Pro physical view se nejvíce hodí:
- deployment diagram
- infrastructure diagram
- network diagram
- container diagram

V UML je nejtypičtější **deployment diagram**.
Ukazuje mapping softwarových komponent na fyzické nebo virtuální nody.

---

### 6.3 Příklad physical view pro e-shop

Příklad deploymentu:

```
Client browser
  ↓ HTTPS
Load balancer
  ↓
Frontend container
  ↓ REST
Backend API containers
  ↓
PostgreSQL database
Redis cache
Message broker
External payment gateway
```

Tento pohled umožňuje řešit:

- kde je single point of failure
- jak systém škálovat
- jak řešit monitoring
- jak řešit síťovou bezpečnost
- jak zálohovat databázi

---

## 7. Scenarios View (+1)

### 7.1 Co popisuje

**Scenarios** jsou konkrétní use cases nebo user tasks, které ukazují, jak systém funguje napříč ostatními views.

Scenarios tvoří „+1“, protože:
- ověřují architekturu
- propojují logical, process, development a physical view
- ukazují chování systému na konkrétních případech
- pomáhají odhalit chybějící části návrhu
- pomáhají komunikovat se stakeholdery

Scenarios mohou být:
- hlavní business use cases
- kritické quality attribute scenarios
- rizikové scénáře
- failure scenarios
- performance scenarios
- security scenarios

---

### 7.2 Proč jsou scenarios důležité

Bez scenarios může být architektura jen statický popis.
Scenarios ukazují, jestli statická struktura opravdu funguje pro reálné požadavky.

Příklad:
- Máme class diagram, deployment diagram a module diagram.
- Ale dokud neprojdeme scénář "customer creates order",
- nevíme, jestli všechny části opravdu spolupracují správně.

Scenarios tedy slouží jako validace architektury.

---

### 7.3 Příklad scenario: customer creates order

Scenario:
- Customer creates an order and pays online.

Logical view:
- Customer, Cart, Order, Payment, Product

Process view:
- Frontend → Order Service → Payment Service → Payment Gateway
- Order Service → Inventory Service
- Order Service → Notification Service

Development view:
- order module
- payment module
- inventory module
- notification module
- API clients
- DTOs
- repositories

Physical view:
- frontend container
- backend service containers
- PostgreSQL
- message broker
- external payment gateway

Tím jeden scénář propojí všechny views.

---

## 8. UML alignment

Kruchten's 4+1 není totéž co UML.
Je to model pohledů na architekturu.
UML se ale často používá jako jazyk pro vyjádření jednotlivých views.

| Kruchten view    | Co popisuje                                           | Typické UML diagramy                                      |
| ---------------- | ----------------------------------------------------- | --------------------------------------------------------- |
| Logical view     | Funkcionalita, doménové objekty, vztahy               | Class diagram, State diagram, Object diagram              |
| Process view     | Runtime chování, komunikace, concurrency, performance | Sequence diagram, Activity diagram, Communication diagram |
| Development view | Implementační struktura, moduly, balíčky              | Package diagram, Component diagram                        |
| Physical view    | Deployment, nodes, infrastructure                     | Deployment diagram                                        |
| Scenarios        | Use cases propojující views                           | Use-case diagram, Sequence diagram, Activity diagram      |

Důležité:
- UML diagramy jsou nástroje.
- 4+1 View Model je organizační rámec pro architektonickou dokumentaci.

> [!note] Jak to číst
> Nejde o pět oddělených dokumentů. Views se překrývají a společně popisují jeden systém: stejná komponenta může mít doménový význam, runtime chování, implementační umístění i deployment.

## 9. Jak model zachycuje complete behavior systému

4+1 model zachycuje systém z více pohledů, protože komplexní systém nelze plně pochopit jen jedním pohledem.

### Logical view

Ukazuje, co systém dělá a jaké má hlavní doménové koncepty.

### Process view

Ukazuje, jak systém funguje při běhu, jak komponenty komunikují a jak systém splňuje runtime quality attributes.

### Development view

Ukazuje, jak je systém implementačně organizován, aby ho vývojáři mohli vyvíjet, udržovat a rozšiřovat.

### Physical view

Ukazuje, jak je systém nasazený na infrastruktuře.

### Scenarios

Ukazují konkrétní průchody systémem a ověřují, že všechny views dohromady dávají smysl.

Proto lze říct:

> The 4+1 model captures the complete architecture by combining static structure, dynamic behavior, implementation organization, deployment structure and concrete scenarios that validate the architecture.

## 10. Vztah k quality attributes

4+1 model není jen dokumentační šablona.
Pomáhá také uvažovat o kvalitě architektury.

Příklad:

- **Performance:** nejvíce se projeví v process view a physical view.
- **Maintainability:** nejvíce se projeví v development view a logical view.
- **Security:** projeví se ve všech views.
- **Scalability:** process view + physical view.
- **Testability:** development view + scenarios.
- **Usability:** logical view + scenarios.

Scenarios jsou zvlášť důležité pro quality attributes, protože kvalita musí být ověřitelná na konkrétních situacích.

Příklad quality scenario:

- **Stimulus:** 1000 users try to buy tickets within one minute.
- **Environment:** system is under high load.
- **Artifact:** reservation service and database.
- **Response:** system accepts valid requests and prevents double booking.
- **Response measure:** 95 % requests finish under 2 seconds, no seat is sold twice.
