> **Zkouškový fokus:** umět vysvětlit distributed architecture, client-server, REST, SOA, orchestration/choreography, event-driven architecture a základ microservices. Důležité je chápat, že distribuovanost přináší škálovatelnost a autonomii, ale také síťové chyby, latenci, consistency problémy a vyšší provozní nároky.

## 1. Co je distributed architecture

**Distributed architecture** znamená, že systém je rozdělen na více částí, které běží v různých procesech, kontejnerech, serverech nebo uzlech a komunikují přes síť.

Příklady:

- frontend běží v browseru
- backend běží na serveru
- databáze běží na jiném serveru
- microservices běží v kontejnerech
- message broker běží jako samostatná infrastruktura
- externí payment provider je volán přes API

Distribuovaný systém není jen více tříd nebo modulů v jedné aplikaci. Důležité je, že komunikace mezi částmi není lokální method call, ale síťové volání.

> [!note] Hlavní rozdíl
> V monolitu se části systému typicky volají v jednom procesu. V distribuovaném systému se části volají přes síť, a proto musíme řešit timeouty, retry, partial failures, latenci, monitoring a security mezi službami.

---

## 2. Proč distributed architecture vzniká

Distribuovaná architektura se používá hlavně kvůli:

- scalability
- availability
- fault isolation
- team autonomy
- independent deployment
- integration with external systems
- geographical distribution
- technology flexibility

Příklad organizačního rozdělení:

- Frontend team vyvíjí web UI.
- Backend team vyvíjí API.
- Payment team vlastní payment service.
- DevOps tým spravuje deployment, monitoring a incident response.

To může dávat smysl u velkého systému, ale u malé aplikace může stejný přístup vytvořit zbytečnou komplexitu.

---

## 3. Proč je distributed architecture těžší

Distribuovaná architektura přidává problémy, které v monolitu často nejsou tak výrazné.

Typické problémy:

- network latency
- network failures
- partial failures
- timeouts
- retries
- duplicate messages
- message ordering
- distributed transactions
- eventual consistency
- monitoring across services
- log correlation
- deployment coordination
- API versioning
- security between services

> [!tip] Zkoušková věta
> A distributed system is harder mainly because calls between components are no longer local method calls. They are network calls and can fail independently.

---

## 4. Fallacies of distributed computing

Při návrhu distributed systems je nebezpečné předpokládat:

- network is reliable
- latency is zero
- bandwidth is infinite
- network is secure
- topology does not change
- there is one administrator
- transport cost is zero
- network is homogeneous

Tyto předpoklady jsou chybné.

Praktický dopad:

- každé síťové volání musí počítat s timeoutem
- každá operace může být provedena vícekrát
- služba může odpovědět pomalu nebo vůbec
- data mezi službami nemusí být okamžitě konzistentní
- síťové volání je dražší než lokální volání
- tracing a log correlation jsou nutné pro debugging

## 5. Client-server architecture

### 5.1 Princip

**Client-server architecture** odděluje klienty a server.

Klient:

- posílá request
- zobrazuje response
- řeší interakci s uživatelem
- drží UI state nebo lokální cache

Server:

- zpracovává requesty
- obsahuje business logic nebo přístup k datům
- vrací response
- centralizuje data a pravidla

Typické příklady:

- browser -> web server -> database
- mobile app -> backend API -> database
- desktop client -> file server

### 5.2 Komunikace

Komunikace bývá často request-response.

Příklady protokolů:

- HTTP / HTTPS
- REST
- GraphQL
- gRPC
- WebSocket
- SQL protocol

Příklad REST komunikace:

- `GET /api/products`
- `POST /api/orders`
- `DELETE /api/users/{id}`

### 5.3 Výhody

- jasné rozdělení klienta a serveru
- centralizovaná správa dat
- server lze měnit bez instalace nové aplikace u každého uživatele
- klient a server lze škálovat odděleně
- dobře známý styl
- vhodný pro webové a mobilní aplikace

### 5.4 Nevýhody

- server může být single point of failure
- server může být bottleneck
- síťová latence ovlivňuje uživatele
- nutnost řešit autentizaci a autorizaci
- riziko DoS / DDoS útoků
- riziko Man-in-the-Middle bez správného TLS

### 5.5 Kdy použít client-server

Vhodné pro:

- web applications
- mobile applications
- enterprise applications
- centralized information systems
- systems with many clients and one central data source

---

## 6. N-tier architecture

Client-server se často rozšiřuje do **n-tier architecture**.

Typické vrstvy:

- client / presentation tier
- application tier
- database tier

Příklad:

- Browser
- Frontend / Web server
- Backend API
- Database

Výhody:

- každý tier lze spravovat a škálovat jinak
- lepší separation of concerns
- jednodušší izolace UI, business logic a persistence

Nevýhody:

- více síťových hopů
- vyšší deployment complexity
- vyšší monitoring complexity
- chyby mohou vznikat mezi vrstvami

---

## 7. RESTful distributed systems

REST je velmi častý způsob komunikace v distributed architectures.

REST API používá:

- resources
- URIs
- HTTP methods
- HTTP status codes
- representations, usually JSON
- stateless communication

Příklad:

- `GET /orders/123`
- `POST /orders`
- `PUT /orders/123`
- `DELETE /orders/123`

REST není jen "JSON přes HTTP". REST je architectural style s konkrétními constraints.

---

## 8. REST constraints

REST constraints:

- client-server
- stateless
- cacheable
- uniform interface
- layered system
- code on demand optional

### 8.1 Client-server

Klient a server mají oddělené odpovědnosti.

- **client:** UI / user interaction
- **server:** data / business processing

### 8.2 Stateless

Každý request obsahuje všechny informace potřebné ke zpracování.

Výhody:

- lepší scalability
- jednodušší load balancing
- jednodušší restart serveru

Nevýhody:

- více dat v requestu
- session state musí být řešen tokenem, klientem nebo externím storem

### 8.3 Cacheable

Response může říct, jestli je cacheovatelná.

Příklady:

- `Cache-Control`
- `ETag`
- `Last-Modified`

Caching zlepšuje performance, ale musí se hlídat freshness dat.

### 8.4 Uniform interface

API má používat jednotný způsob práce s resources.

Příklad:

- resources jsou reprezentované přes URI
- HTTP metody mají sémantiku
- status codes mají význam
- representations jsou oddělené od interní implementace

### 8.5 Layered system

Klient nemusí vědět, jestli komunikuje přímo se serverem, nebo přes proxy, gateway, cache nebo load balancer.

### 8.6 Code on demand

Server může klientovi poslat spustitelný kód. V REST je to optional constraint a v běžných API se často neřeší.

## 9. Richardson Maturity Model

Richardson Maturity Model popisuje, jak moc API využívá principy REST.

### 9.1 Level 0: RPC over HTTP

HTTP se používá jen jako transport.

Příklad:

- `POST /doSomething`
- `POST /getOrder`
- `POST /deleteUser`

Typické znaky:

- všechno je `POST`
- URI nepopisují resources
- HTTP metody nemají význam
- API připomíná remote procedure calls

### 9.2 Level 1: Resources

API začne rozlišovat resources.

Příklad:

- `/orders`
- `/orders/123`
- `/users/15`

Je to lepší než Level 0, ale ještě nemusí správně používat HTTP metody.

### 9.3 Level 2: HTTP methods

API používá HTTP metody podle jejich významu.

Příklad:

- `GET /orders/123` - read order
- `POST /orders` - create order
- `PUT /orders/123` - replace order
- `PATCH /orders/123` - partial update
- `DELETE /orders/123` - delete order

Toto je úroveň většiny běžných REST API.

### 9.4 Level 3: Hypermedia controls / HATEOAS

Response obsahuje odkazy na možné další akce.

Příklad:

- order response obsahuje link na payment
- user response obsahuje link na orders
- API vede klienta přes dostupné akce

V praxi je Level 3 méně častý, ale důležitý pro teoretické pochopení REST.

> [!note] Ke zkoušce
> Většina praktických REST API je hlavně Level 2: resources plus správné HTTP methods. HATEOAS je nejvíc REST-pure varianta, ale v běžných enterprise API není vždy použitá.

---

## 10. REST API design rules

Dobré REST API by mělo:

- používat nouns pro resources, ne verbs
- používat plural nouns
- používat HTTP methods podle sémantiky
- vracet správné status codes
- být stateless
- mít konzistentní error format
- podporovat pagination u kolekcí
- verzovat API kontrolovaně
- dokumentovat contract

Příklady:

- `GET /orders`
- `GET /orders/123`
- `POST /orders`
- `PATCH /orders/123`
- `DELETE /orders/123`

Méně vhodné:

- `POST /getOrders`
- `POST /createOrder`
- `GET /deleteOrder/123`

## 11. REST security

U REST API je potřeba řešit:

- HTTPS / TLS
- authentication
- authorization
- input validation
- rate limiting
- CORS
- CSRF podle typu klienta
- secure error messages
- token expiration
- audit logging

Příklady:

- admin endpoint vyžaduje admin role
- public endpoint má rate limiting
- access token má omezenou životnost
- sensitive data se nelogují

## 12. OpenAPI / Swagger

**OpenAPI** je strojově čitelný popis REST API contractu.

Popisuje:

- endpoints
- HTTP methods
- request schemas
- response schemas
- status codes
- authentication
- examples

Výhody:

- dokumentace API
- generování klientů
- generování server stubs
- contract testing
- lepší komunikace mezi týmy
- jednodušší API review

> [!tip] Praktický význam
> OpenAPI pomáhá hlavně tam, kde frontend, backend a externí integrace potřebují přesný contract. Bez contractu se týmy často rozbijí na detailech payloadu, status codes nebo error formátu.

---

## 13. GraphQL

### 13.1 Princip

**GraphQL** je query language pro API. Klient si říká, jaká data přesně chce.

REST typicky vystavuje více endpointů:

- `/users/1`
- `/users/1/orders`
- `/orders/50/items`

GraphQL typicky používá jeden endpoint:

- `POST /graphql`

Klient v query určí požadovaný tvar dat.

### 13.2 Výhody

- klient dostane přesně data, která potřebuje
- omezuje over-fetching
- omezuje under-fetching
- vhodné pro více různých klientů
- silný schema contract
- dobré pro komplexní datové grafy

**Over-fetching** znamená, že server vrátí více dat, než klient potřebuje.

**Under-fetching** znamená, že klient musí volat více endpointů, aby získal všechna potřebná data.

### 13.3 Nevýhody

- složitější server implementation
- složitější caching než u REST
- riziko drahých queries
- nutnost řešit query depth / complexity limits
- authorization může být jemnější a složitější
- monitoring výkonu může být těžší

## 14. Service-Oriented Architecture / SOA

### 14.1 Princip

**SOA** organizuje systém jako sadu služeb, které poskytují business capabilities přes standardizované contracts.

Typické principy:

- standardized service contract
- loose coupling
- abstraction
- reusability
- autonomy
- discoverability
- composability

SOA se často používá ve velkých enterprise systémech, kde je potřeba integrovat mnoho aplikací.

### 14.2 Typické prvky SOA

- business services
- application services
- infrastructure services
- message bus
- orchestrator
- Enterprise Service Bus
- service contracts
- service registry

### 14.3 Standardized service contract

Služba má jasně definovaný contract.

Contract říká:

- jaké operace služba poskytuje
- jaký request očekává
- jaký response vrací
- jaké chyby mohou nastat
- jaké security požadavky platí

Bez contractu se služby těžko znovupoužívají a integrují.

### 14.4 Loose coupling

Služby by se neměly znát přes interní implementaci. Mají komunikovat přes contract.

Špatně:

- jedna služba přímo čte interní tabulky jiné služby

Správně:

- služba používá public API nebo message contract jiné služby

### 14.5 Abstraction

Služba skrývá interní implementaci.

Klient ví:

- co služba umí
- jak ji zavolat
- jaký contract platí

Klient neví:

- jak je služba implementovaná
- jakou databázi používá
- jaké interní moduly má

### 14.6 Reusability

SOA často zdůrazňuje znovupoužití služeb napříč enterprise prostředím.

Příklad:

- Customer service může používat e-shop, billing i support systém.

### 14.7 Composability

Služby lze skládat do business procesů.

Příklad process order:

- validate customer
- reserve inventory
- create invoice
- process payment
- send confirmation

## 15. Enterprise Service Bus / ESB

**ESB** je integrační vrstva, která propojuje služby.

Může řešit:

- routing
- protocol transformation
- message transformation
- orchestration
- security
- monitoring
- integration with legacy systems

Výhoda:

- centralizovaná integrace enterprise systémů

Riziko:

- ESB se může stát bottleneckem
- příliš mnoho logiky v ESB vede k centralizované komplexitě
- týmy mohou ztratit autonomii

---

## 16. SOA vs microservices

| Kritérium | SOA | Microservices |
|---|---|---|
| Velikost služeb | často větší enterprise services | menší služby kolem business capabilities |
| Governance | více centralizovaná | více decentralizovaná |
| Integrace | často ESB / orchestrator | API, events, lightweight messaging |
| Data | často sdílené enterprise zdroje | ideálně database per service |
| Reuse | silný důraz na service reuse | důraz na autonomii a bounded context |
| Deployment | nemusí být plně nezávislý | nezávislý deployment je klíčový |

SOA a microservices jsou příbuzné, ale microservices kladou větší důraz na malé autonomní služby, nezávislý deployment a decentralizaci.

## 17. Orchestration

### 17.1 Princip

**Orchestration** znamená, že jeden centrální orchestrator řídí celý proces.

Příklad:

Order Orchestrator řídí flow:

1. call Payment Service
2. call Inventory Service
3. call Shipping Service
4. send confirmation

Orchestrator ví, jaký je celý business flow.

### 17.2 Výhody

- proces je na jednom místě
- snazší pochopení flow
- jednodušší řízení chyb
- jednodušší audit procesu
- vhodné pro workflow s jasným vlastníkem

### 17.3 Nevýhody

- orchestrator může být bottleneck
- vyšší coupling na centrální komponentu
- riziko distributed monolith
- změny procesu často znamenají změny orchestratoru

---

## 18. Choreography

### 18.1 Princip

**Choreography** znamená, že služby reagují na události bez centrálního řídicího prvku.

Příklad:

- Order Service publishes `OrderCreated`.
- Payment Service reacts and publishes `PaymentCompleted`.
- Inventory Service reacts and publishes `InventoryReserved`.
- Notification Service reacts and sends email.

Každá služba zná pouze události, které odebírá a publikuje.

### 18.2 Výhody

- looser coupling
- lepší autonomie služeb
- lepší škálovatelnost
- není jeden centrální orchestrator
- snadnější přidání nového consumeru

### 18.3 Nevýhody

- složitější pochopení celého flow
- složitější debugging
- eventual consistency
- riziko skrytých závislostí přes eventy
- těžší audit procesu

### 18.4 Orchestration vs choreography

| Kritérium | Orchestration | Choreography |
|---|---|---|
| Řízení procesu | centrální orchestrator | služby reagují na eventy |
| Čitelnost flow | lepší | horší |
| Coupling | vyšší na orchestrator | nižší |
| Autonomie služeb | nižší | vyšší |
| Debugging | jednodušší | těžší |
| Riziko | bottleneck / distributed monolith | skrytý event flow |

> [!note] Bezpečná formulace
> Orchestration uses a central controller to coordinate services. Choreography uses events, where each service reacts independently. Orchestration is easier to understand, but can create coupling. Choreography improves autonomy and loose coupling, but makes the global process harder to trace.

## 19. Event-driven architecture

### 19.1 Princip

**Event-driven architecture** je styl, kde komponenty komunikují pomocí událostí.

Základní pojmy:

- event
- producer
- consumer
- event broker / event bus
- topic / queue
- subscriber

Producer publikuje událost:

- `OrderCreated`
- `PaymentCompleted`
- `UserRegistered`
- `InventoryUpdated`

Consumer na událost reaguje:

- send email
- update read model
- start payment process
- reserve inventory

### 19.2 Event

**Event** říká, že se něco stalo.

Dobré názvy eventů:

- `OrderCreated`
- `PaymentFailed`
- `UserRegistered`
- `InvoiceIssued`

Méně vhodné názvy:

- `CreateOrder`
- `DoPayment`
- `SendEmail`

Ty druhé spíš vypadají jako commands.

### 19.3 Event vs command

**Command** je žádost, aby někdo něco udělal.

Příklad:

- `CreateOrder`
- `ReserveInventory`
- `SendEmail`

Command má typicky konkrétního adresáta.

**Event** je informace, že se něco stalo.

Příklad:

- `OrderCreated`
- `InventoryReserved`
- `EmailSent`

Event může mít více consumerů a producer nemusí vědět, kdo na něj zareaguje.

### 19.4 Event broker

Event broker zprostředkovává komunikaci.

Příklady:

- Kafka
- RabbitMQ
- ActiveMQ
- cloud pub/sub services

Broker řeší:

- receiving messages
- storing messages
- routing messages
- delivering messages
- retries
- consumer groups podle technologie

### 19.5 Publish-subscribe

Producer publikuje event do topicu.

Consumers se přihlásí k odběru.

Příklad:

- Order Service publishes `OrderCreated`.
- Payment Service subscribes and starts payment.
- Inventory Service subscribes and reserves stock.
- Notification Service subscribes and sends email.

### 19.6 Výhody

- loose coupling mezi producers a consumers
- dobrá škálovatelnost
- asynchronní zpracování
- snadnější přidání nového consumeru
- vhodné pro real-time a high-volume systémy
- dobré pro integration workflows

### 19.7 Nevýhody

- vyšší komplexita
- eventual consistency
- složitější debugging
- těžší sledování flow systému
- problémy s orderingem událostí
- nutnost řešit duplicity a idempotency
- potřeba dobré observability

### 19.8 Idempotency

**Idempotency** znamená, že opakované zpracování stejné zprávy nezmění výsledek špatným způsobem.

Proč je důležitá:

- broker může doručit zprávu vícekrát
- retry může opakovat operaci
- consumer může spadnout po částečném zpracování

Příklad:

- payment callback se zpracuje dvakrát, ale platba se nezapočítá dvakrát

### 19.9 Ordering

**Ordering** řeší pořadí zpráv.

Problém:

- `OrderCancelled` může dorazit dříve než `OrderCreated`
- více eventů pro stejný order může být zpracováno ve špatném pořadí

Možná řešení:

- partitioning by aggregate id
- sequence numbers
- versioning
- idempotent consumers
- conflict handling

### 19.10 Dead-letter queue

**Dead-letter queue** ukládá zprávy, které se nepodařilo zpracovat.

Používá se, když:

- zpráva má špatný formát
- consumer opakovaně selže
- externí služba je dlouho nedostupná
- retry limit byl vyčerpán

DLQ pomáhá, aby jedna špatná zpráva nezablokovala celý tok zpracování.

## 20. Microservices architecture

### 20.1 Princip

**Microservices architecture** strukturuje aplikaci jako sadu malých, nezávisle nasaditelných služeb.

Služby jsou typicky:

- loosely coupled
- independently deployable
- organized around business capabilities
- owned by small teams
- independently scalable
- responsible for their own data

Příklad:

- User Service
- Order Service
- Payment Service
- Inventory Service
- Notification Service

### 20.2 Business capability

Microservice by měla být orientovaná kolem business capability, ne kolem technické vrstvy.

Dobře:

- Order Service
- Payment Service
- Inventory Service

Špatně:

- Controller Service
- Repository Service
- Database Service

Služby podle technických vrstev často vedou k distributed monolithu.

### 20.3 Database per service

Každá služba má vlastnit svá data.

Výhody:

- jasný ownership
- nezávislost služby
- menší coupling
- možnost zvolit vhodnou databázi pro službu

Nevýhody:

- složitější reporting
- složitější queries přes více služeb
- eventual consistency
- potřeba řešit integraci přes API, events nebo read models

### 20.4 Výhody

- nezávislý deployment
- nezávislé škálování
- lepší fault isolation
- autonomie týmů
- možnost různých technologií
- rychlejší změny ve velkých systémech
- lepší alignment s Conway's Law

### 20.5 Nevýhody

- distribuovaná komplexita
- síťové chyby
- latence
- těžší testování
- těžší debugging
- data consistency problems
- složitější deployment
- potřeba DevOps maturity
- vyšší nároky na observability

> [!warning] Důležité
> Microservices are not a silver bullet. They solve some problems of large monoliths, but introduce distributed system complexity.

### 20.6 Conway's Law

**Conway's Law** říká, že architektura systému často kopíruje komunikační strukturu organizace.

Praktický dopad:

- pokud má tým jasný ownership služby, microservice může fungovat dobře
- pokud všichni mění všechno, microservices nepřinesou autonomii
- špatně rozdělené týmy často vytvoří špatně rozdělené služby

## 21. Service discovery

V microservices se instance služeb mohou dynamicky měnit.

Problém:

- Order Service potřebuje zavolat Payment Service.
- Payment Service může běžet ve více instancích.
- Instance mohou vznikat a zanikat.

**Service discovery** pomáhá najít aktuální dostupné instance služby.

Typy:

- client-side discovery
- server-side discovery
- service registry
- DNS-based discovery

Příklady technologií:

- Kubernetes Service
- Consul
- Eureka
- cloud load balancers

---

## 22. API Gateway

**API Gateway** je vstupní bod pro klienty.

Může řešit:

- routing
- authentication
- authorization
- rate limiting
- request aggregation
- protocol translation
- logging
- TLS termination

Výhody:

- klient nemusí znát všechny služby
- centralizace cross-cutting concerns na hraně systému
- jednodušší evoluce interních služeb

Rizika:

- gateway může být bottleneck
- gateway může obsahovat příliš mnoho business logic
- špatně navržená gateway se stane mini-monolitem

---

## 23. Service mesh

**Service mesh** řeší komunikaci mezi službami na infrastrukturní úrovni.

Typicky poskytuje:

- traffic routing
- retries
- timeouts
- mTLS
- observability
- circuit breaking
- policy enforcement

Často se realizuje přes sidecar proxy.

Výhoda:

- aplikační služby nemusí implementovat všechen networking samy

Nevýhoda:

- vyšší provozní komplexita
- potřeba zkušeností s platformou
- složitější debugging infrastruktury

---

## 24. Container orchestration and Kubernetes

Microservices se často nasazují v kontejnerech.

Kubernetes řeší:

- scheduling containers
- service discovery
- scaling
- rolling updates
- health checks
- self-healing
- configuration
- secrets
- load balancing

Kubernetes ale není důvod pro microservices. Je to nástroj pro provoz kontejnerizovaných aplikací.

> [!note] Častá chyba
> Kubernetes neřeší špatné hranice služeb, špatný domain model ani chybějící observability. Jen provozuje kontejnery.

---

## 25. Design for failure

V distribuovaném systému musíme počítat s tím, že něco selže.

Typické principy:

- timeout
- retry
- circuit breaker
- bulkhead
- graceful degradation
- fallback
- idempotency
- observability

Bez těchto principů může jedno pomalé síťové volání zastavit velkou část systému.

---

## 26. Timeout

**Timeout** omezuje, jak dlouho čekáme na odpověď.

Proč je důležitý:

- služba může být pomalá
- síť může mít problém
- bez timeoutu se requesty mohou hromadit

Příklad:

- Payment Service musí odpovědět do 2 sekund, jinak request selže kontrolovaně.

Timeout musí být nastaven rozumně. Příliš krátký timeout způsobí falešná selhání, příliš dlouhý timeout blokuje resources.

---

## 27. Retry

**Retry** opakuje operaci po selhání.

Hodí se pro:

- dočasné síťové chyby
- krátký výpadek služby
- transient errors

Rizika:

- retry může přetížit už tak problémovou službu
- retry může způsobit duplicitní operace
- bez backoffu může vzniknout retry storm

Dobrá praxe:

- retry with exponential backoff
- jitter
- retry jen pro safe nebo idempotent operations
- limit počtu pokusů

---

## 28. Circuit breaker

**Circuit breaker** zastaví volání služby, která opakovaně selhává.

Stavy:

- closed - volání prochází
- open - volání se blokuje a vrací fallback/error
- half-open - zkouší se, jestli se služba zotavila

Výhoda:

- chrání systém před kaskádovým selháním
- dává selhávající službě čas se zotavit

---

## 29. Bulkhead

**Bulkhead** izoluje resources tak, aby selhání jedné části nepotopilo celý systém.

Příklad:

- zvláštní thread pool pro payment calls
- zvláštní connection pool pro reporting
- limitované fronty pro externí integrace

Když payment provider zpomalí, nemá spotřebovat všechny resources celé aplikace.

---

## 30. Graceful degradation

**Graceful degradation** znamená, že systém při problému funguje omezeně, ale nepadne celý.

Příklady:

- search funguje, ale bez doporučení
- produktová stránka se zobrazí bez recenzí
- systém dovolí read-only režim při problému s write databází
- checkout dočasně vypne některé platební metody

---

## 31. Eventual consistency

**Eventual consistency** znamená, že data nemusí být konzistentní okamžitě, ale časem se do konzistentního stavu dostanou.

Příklad:

- Order Service vytvoří objednávku.
- Payment Service později potvrdí platbu.
- Inventory Service později rezervuje sklad.

Mezi těmito kroky může existovat dočasný mezistav.

Výhoda:

- lepší availability a scalability

Nevýhoda:

- složitější reasoning
- uživatel může chvíli vidět neúplný stav
- je potřeba řešit kompenzace a konflikty

---

## 32. Distributed transactions

V monolitu lze často použít jednu databázovou transakci.

V microservices je transakce přes více služeb těžká, protože každá služba může mít vlastní databázi.

Možnosti:

- two-phase commit
- Saga pattern
- eventual consistency
- compensating actions

**Two-phase commit** poskytuje silnější konzistenci, ale je složitý a může zhoršit availability.

**Saga** rozděluje proces na kroky a při chybě spouští kompenzační akce.

Příklad:

- create order
- reserve inventory
- charge payment
- pokud payment selže, release inventory a cancel order

---

## 33. Observability

**Observability** znamená schopnost pochopit stav systému podle výstupů, které produkuje.

Typické pilíře:

- logs
- metrics
- distributed tracing

V distribuovaném systému je observability nutná, protože jeden uživatelský request může projít mnoha službami.

---

## 34. Logs

Logs zachycují události v systému.

Dobré logy obsahují:

- timestamp
- service name
- log level
- correlation ID / trace ID
- user/request context podle bezpečnostních pravidel
- error details

Pozor:

- nelogovat hesla, tokens, platební data nebo citlivé osobní údaje

---

## 35. Metrics

Metrics jsou číselné hodnoty sledované v čase.

Příklady:

- request rate
- error rate
- latency
- CPU / memory
- queue length
- database connections
- retry count
- circuit breaker state

Metrics pomáhají odhalit degradaci dříve, než uživatelé nahlásí incident.

---

## 36. Distributed tracing

Distributed tracing sleduje jeden request napříč službami.

Pomáhá zjistit:

- který request volal jaké služby
- kde vznikla latence
- kde nastala chyba
- jak dlouho trvaly jednotlivé části flow

Klíčový pojem:

- correlation ID / trace ID

Bez trace ID je debugging microservices výrazně těžší.

---

## 37. Deployment challenges

Distribuovaný systém má složitější deployment.

Problémy:

- více služeb
- kompatibilita API verzí
- rolling updates
- database migrations
- backward compatibility
- feature flags
- configuration management
- secrets management

Dobrá praxe:

- CI/CD
- automated tests
- canary deployments
- blue-green deployments
- monitoring after deploy
- rollback strategy

---

## 38. API versioning

API se musí vyvíjet bez rozbití klientů.

Možnosti versioningu:

- URL versioning: `/v1/orders`
- header versioning
- media type versioning
- backward-compatible evolution bez explicitní verze

Dobrá praxe:

- nepřejmenovávat pole bez důvodu
- nepřestat vracet pole bez deprekační fáze
- přidávat optional fields místo breaking changes
- dokumentovat deprecation
- testovat contract mezi službami

---

## 39. Comparison of distributed styles

| Style | Main idea | Strengths | Weaknesses | Typical use |
|---|---|---|---|---|
| Client-server | clients call central server | simple, clear split | server bottleneck, latency | web/mobile apps |
| N-tier | separated presentation/app/data tiers | separation, independent tier scaling | more hops, more deployment complexity | enterprise systems |
| REST | resources over HTTP | simple, cacheable, widely supported | over/under-fetching, versioning | public/internal APIs |
| GraphQL | client asks for exact data shape | flexible for clients | complex caching/security | multiple clients, complex data graphs |
| SOA | enterprise services with contracts | integration, reuse | ESB/governance complexity | enterprise integration |
| Event-driven | async communication by events | loose coupling, scalability | debugging, eventual consistency | async workflows, real-time systems |
| Microservices | independent business services | independent deploy/scale, team autonomy | distributed complexity | large systems, many teams |

## 40. Common antipatterns

### 40.1 Distributed monolith

Služby jsou fyzicky oddělené, ale musí se deployovat a měnit společně.

Symptomy:

- silné synchronní závislosti
- shared database
- změna jedné služby vyžaduje změnu mnoha dalších
- žádná reálná týmová autonomie

### 40.2 Shared database between services

Více služeb zapisuje do stejných tabulek.

Problémy:

- nejasný ownership dat
- coupling přes databázi
- těžký refactoring
- obcházení business pravidel služby

### 40.3 Chatty services

Služby si posílají příliš mnoho malých requestů.

Problémy:

- vysoká latency
- vyšší riziko failure
- složitější tracing
- horší performance

Možná řešení:

- coarse-grained APIs
- batching
- API composition
- async events
- read models

### 40.4 No API Gateway

Klient musí znát mnoho interních služeb.

Problémy:

- složitý klient
- duplicita authentication logic
- těžká změna interní struktury služeb

### 40.5 Too many technologies

Každá služba používá jiný jazyk, framework a databázi bez silného důvodu.

Problémy:

- horší maintenance
- horší hiring
- složitější operations
- složitější debugging

### 40.6 Microservice per feature

Tým vytvoří příliš mnoho malých služeb.

Problémy:

- overhead komunikace
- overhead deploymentu
- mnoho API contractů
- složitější monitoring

Správně:

- služba má reprezentovat smysluplnou business capability, ne každou malou feature.
