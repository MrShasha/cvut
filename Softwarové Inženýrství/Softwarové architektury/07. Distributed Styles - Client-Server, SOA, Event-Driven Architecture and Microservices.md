# Distributed Styles - Client-Server, SOA, Event-Driven Architecture and Microservices

> **Zkouškový fokus:** umět vysvětlit distributed architecture, client-server, REST, SOA, orchestration/choreography, event-driven architecture a základ microservices.

## 1. Co je distributed architecture

**Distributed architecture** znamená, že systém je rozdělen na více částí, které běží v různých procesech, na různých serverech, kontejnerech nebo uzlech a komunikují přes síť.

Příklady:

```text
frontend běží v browseru
backend běží na serveru
databáze běží na jiném serveru
microservices běží v kontejnerech
message broker běží jako samostatná infrastruktura
```

Distribuovaný systém není jen “více tříd v aplikaci”. Důležité je, že komunikace probíhá přes síť.

---

## 2. Proč distributed architecture vzniká

Distribuovaná architektura se používá hlavně kvůli:

```text
scalability
availability
fault isolation
team autonomy
independent deployment
integration with external systems
geographical distribution
technology flexibility
```

Příklad:

```text
Frontend team vyvíjí web UI.
Backend team vyvíjí API.
Payment team vlastní payment service.
DevOps tým spravuje deployment a monitoring.
```

---

## 3. Proč je distributed architecture těžší

Distribuovaná architektura přidává problémy, které v monolitu často nejsou tak výrazné.

Typické problémy:

```text
network latency
network failures
partial failures
timeouts
retries
duplicate messages
message ordering
distributed transactions
eventual consistency
monitoring across services
log correlation
deployment coordination
API versioning
security between services
```

Důležitá zkoušková věta:

> A distributed system is harder mainly because calls between components are no longer local method calls. They are network calls and can fail independently.

---

## 4. Fallacies of distributed computing

Při návrhu distributed systems je nebezpečné předpokládat:

```text
network is reliable
latency is zero
bandwidth is infinite
network is secure
topology does not change
there is one administrator
transport cost is zero
network is homogeneous
```

Tyto předpoklady jsou chybné.

Praktický dopad:

```text
každé síťové volání musí počítat s timeoutem
každá operace může být provedena vícekrát
služba může odpovědět pomalu nebo vůbec
data mezi službami nemusí být okamžitě konzistentní
```

## 5. Client-server architecture

## 5.1 Princip

**Client-server architecture** odděluje klienty a server.

Klient:

```text
posílá request
zobrazuje response
řeší interakci s uživatelem
```

Server:

```text
zpracovává requesty
obsahuje business logic nebo přístup k datům
vrací response
```

Typický příklad:

```text
browser → web server → database
mobile app → backend API → database
desktop client → file server
```

---

## 5.2 Typická komunikace

Komunikace bývá request-response.

Příklady protokolů:

```text
HTTP / HTTPS
REST
GraphQL
gRPC
WebSocket
SQL protocol
```

Příklad REST komunikace:

```text
GET /api/products
POST /api/orders
DELETE /api/users/{id}
```

---

## 5.3 Výhody client-server

```text
jasné rozdělení klienta a serveru
centralizovaná správa dat
server lze měnit bez instalace nové aplikace u každého uživatele
klient a server lze škálovat odděleně
dobře známý styl
vhodný pro webové a mobilní aplikace
```

---

## 5.4 Nevýhody client-server

```text
server může být single point of failure
server může být bottleneck
síťová latence ovlivňuje uživatele
nutnost řešit autentizaci a autorizaci
riziko DoS / DDoS útoků
riziko Man-in-the-Middle bez správného TLS
```

---

## 5.5 Kdy použít client-server

Vhodné pro:

```text
web applications
mobile applications
enterprise applications
centralized information systems
systems with many clients and one central data source
```

---

## 6. N-tier architecture

Client-server se často rozšiřuje do **n-tier architecture**.

Typické vrstvy:

```text
client / presentation tier
application tier
database tier
```

Příklad:

```text
Browser
  ↓
Frontend / Web server
  ↓
Backend API
  ↓
Database
```

Výhoda:

```text
každý tier lze spravovat a škálovat jinak
lepší separation of concerns
```

Nevýhoda:

```text
více síťových hopů
vyšší deployment a monitoring complexity
```

Příklad:


## 8. REST constraints

REST je architectural style, ne pouze JSON přes HTTP.

REST constraints:

```text
client-server
stateless
cacheable
uniform interface
layered system
code on demand optional
```

### 8.1 Client-server

Klient a server mají oddělené odpovědnosti.

```text
client = UI / user interaction
server = data / business processing
```

### 8.2 Stateless

Každý request obsahuje všechny informace potřebné ke zpracování.

Server nemusí držet session state mezi requesty.

Výhoda:

```text
lepší scalability
jednodušší load balancing
```

Nevýhoda:

```text
více dat v každém requestu
nutnost řešit autentizaci tokenem nebo podobným mechanismem
```

### 8.3 Cacheable

Response může být označena jako cacheable nebo non-cacheable.

Výhoda:

```text
lepší performance
nižší load na server
```

### 8.4 Uniform interface

REST používá jednotné rozhraní:

```text
resources
HTTP methods
representations
self-descriptive messages
hypermedia links
```

### 8.5 Layered system

Klient nemusí vědět, jestli komunikuje přímo se serverem, nebo přes proxy, gateway, cache nebo load balancer.

### 8.6 Code on demand

Volitelné. Server může poslat klientovi spustitelný kód, například JavaScript.

## Level 0: RPC over HTTP

Na úrovni 0 API používá HTTP pouze jako transportní mechanismus. Typicky existuje jeden endpoint, na který se posílají různé operace v těle požadavku.

Příklad:

```http
POST /api
```

Tělo požadavku může obsahovat například:

```json
{
  "operation": "createOrder",
  "data": {
    "productId": 10,
    "quantity": 2
  }
}
```

V tomto případě URL nepopisuje konkrétní resource. Server rozhoduje, co má udělat, podle hodnoty `operation`.

Takové API se podobá spíše vzdálenému volání funkcí než REST API.

## Level 1: Resources

Na úrovni 1 API začíná pracovat s resources. Místo jednoho obecného endpointu používá různé URL pro různé typy objektů.

Příklady resources:

```http
/orders
/users
/products
```

Každá URL reprezentuje určitou kolekci nebo konkrétní objekt.

Například:

```http
/orders
```

reprezentuje objednávky, zatímco:

```http
/orders/123
```

reprezentuje konkrétní objednávku s ID `123`.

API je už lépe strukturované, ale nemusí ještě správně používat HTTP metody.

## Level 2: HTTP Methods

Na úrovni 2 API používá HTTP metody podle jejich významu. Stejná resource může podporovat různé operace podle použité metody.

Příklady:

```http
GET /orders/123
```

Získání detailu objednávky.

```http
POST /orders
```

Vytvoření nové objednávky.

```http
DELETE /orders/123
```

Smazání objednávky.

Na této úrovni API využívá běžné HTTP principy, například:

- `GET` pro čtení dat
- `POST` pro vytvoření nového resource
- `PUT` nebo `PATCH` pro úpravu existujícího resource
- `DELETE` pro odstranění resource

Toto je úroveň, na které se nachází většina běžných REST API.

## Level 3: Hypermedia Controls / HATEOAS

Na úrovni 3 API kromě dat vrací také odkazy na další možné akce. Klient se tedy nemusí spoléhat jen na pevně naprogramované URL, ale může se řídit odkazy obsaženými v odpovědi serveru.

Tomuto principu se říká **HATEOAS** — _Hypermedia as the Engine of Application State_.

Příklad odpovědi:

```json
{
  "id": 123,
  "status": "created",
  "links": [
    { "rel": "self", "href": "/orders/123" },
    { "rel": "cancel", "href": "/orders/123/cancel" },
    { "rel": "payment", "href": "/orders/123/payment" }
  ]
}
```

Tato odpověď neobsahuje pouze informace o objednávce, ale také říká klientovi, co může udělat dál.

Například:
- `self` odkazuje na samotnou objednávku
- `cancel` umožňuje objednávku zrušit
- `payment` vede na platbu objednávky

Díky tomu je API flexibilnější, protože server může klientovi dynamicky říkat, jaké akce jsou v daném stavu dostupné.

Například pokud už je objednávka zaplacená, server nemusí vrátit odkaz `cancel`, protože zrušení už není možné.

## 10. REST API design rules

Základní pravidla dobrého REST API:

- Resources by měly být pojmenované jako **podstatná jména**, ne jako slovesa.
- Pokud je to možné, používají se **množná čísla**.
- HTTP metody se používají podle jejich významu.
- API vrací správné HTTP status kódy.
- URI by měly být hierarchické a předvídatelné.
- API kontrakty by měly používat DTOs.
- API by mělo být dokumentované pomocí OpenAPI.
- Verze API se přidává tehdy, když je potřeba řešit breaking changes.

Dobře:

```text
GET /customers/123/orders
POST /customers/123/orders
GET /orders/456
DELETE /orders/456
```

Špatně:

```text
GET /updateCustomer?id=123
POST /deleteOrder
GET /services?op=createOrder
```

REST API musí řešit hlavně:

- HTTPS
- authentication
- authorization
- input validation
- rate limiting
- CORS
- CSRF tam, kde je relevantní
- security headers
- data exposure
- object-level authorization

Časté mechanismy:

```text
JWT
OAuth2
OpenID Connect
Basic Auth for simple internal integrations
mTLS for service-to-service communication
```

Důležitý problém:

```text
Nestačí zabezpečit UI.
Každá server-side operace musí kontrolovat permissions.
```

## 12. OpenAPI / Swagger

**OpenAPI** je standardní způsob, jak popsat REST API ve strojově čitelné podobě. Dříve se často používal název **Swagger**, dnes Swagger označuje hlavně sadu nástrojů kolem OpenAPI.

OpenAPI dokumentace popisuje, jaké endpointy API nabízí, jak se volají a jaké requesty a response používají.

OpenAPI může popisovat:

- endpointy
- HTTP metody
- path parametry
- query parametry
- request body
- response body
- status kódy
- datová schémata
- autentizaci a autorizaci

### Výhody OpenAPI

OpenAPI má několik praktických výhod:

- automatická dokumentace API
- generování klientských knihoven
- generování server skeletonu
- testování API
- validace requestů a response
- kontrola kompatibility API
- lepší komunikace mezi frontendem a backendem

Například frontend tým může podle OpenAPI specifikace přesně vidět, jaký request má poslat a jakou response může očekávat.

Příklad:

```yaml
paths:
  /orders/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
      responses:
        "200":
          description: OK
```

## 13. GraphQL

## 13.1 Princip

**GraphQL** je query language pro API.

Klient se ptá přesně na data, která chce.

Příklad query:

```graphql
{
  user(id: "123") {
    name
    orders {
      id
      totalPrice
    }
  }
}
```

Response obsahuje jen požadovaná pole.

## 13.2 Výhody GraphQL

GraphQL je užitečný hlavně tam, kde mají klienti složité datové požadavky nebo kde jedno API používá více různých typů klientů.

Hlavní výhody:

- klient si vybere přesná data
- omezuje over-fetching
- omezuje under-fetching
- je vhodný pro komplexní UI
- jedno API může sloužit různým klientům
- silně typované schema zlepšuje kontrakt mezi frontendem a backendem
### Over-fetching

REST endpoint vrací více dat, než klient potřebuje.
### Under-fetching

Klient musí zavolat více endpointů, aby získal potřebná data.

---

## 13.3 Nevýhody GraphQL

GraphQL ale není automaticky lepší než REST. Přináší vlastní složitost a problémy, které je potřeba řešit.

Hlavní nevýhody:

- složitější caching
- složitější authorization na úrovni polí
- riziko drahých queries
- nutnost řešit query depth limits
- nutnost řešit query complexity limits
- složitější monitoring než u jednoduchého REST API
- vyšší nároky na návrh schématu

## 14. Service-Oriented Architecture / SOA

## 14.1 Princip

**Service-Oriented Architecture** organizuje systém jako sadu služeb.

Služba poskytuje business capability přes jasně definovaný contract.

Typické principy SOA:

```text
standardized service contract
loose coupling
service abstraction
service reusability
service autonomy
service discoverability
service composability
```

---

## 14.2 Typické prvky SOA

```text
business services
application services
infrastructure services
service contracts
message bus
Enterprise Service Bus
orchestration engine
service registry
```

SOA je často spojena s enterprise integration.

Příklad:

```text
HR system
finance system
CRM
ERP
billing system
reporting system
```

Tyto systémy komunikují přes služby a integrační middleware.

---

## 14.3 Standardized service contract

Služba má jasný contract.

Contract popisuje:

```text
operations
input
output
data formats
error responses
security requirements
```

Příklad:

```text
CreateInvoice(customerId, items) → InvoiceId
```

Výhoda:

```text
klient nemusí znát interní implementaci služby
```

---

## 14.4 Loose coupling

Služby by měly minimalizovat závislosti.

Dobře:

```text
Order service calls Payment service through stable API contract.
```

Špatně:

```text
Order service directly reads internal payment database tables.
```

---

## 14.5 Abstraction

Služba skrývá interní logiku.

Klient ví:

```text
co služba poskytuje
jak ji zavolat
jaký výsledek dostane
```

Klient neví:

```text
jaká databáze je uvnitř
jaké třídy služba používá
jak přesně se výsledek počítá
```

---

## 14.6 Reusability

SOA často klade důraz na znovupoužití služeb.

Příklad:

```text
CustomerService může používat e-shop, CRM i billing system.
```

Výhoda:

```text
méně duplicity
centrální správa business capability
```

Riziko:

```text
příliš sdílené služby se mohou stát bottleneckem a zdrojem coupling
```

---

## 14.7 Composability

Služby lze skládat do větších business procesů.

Příklad:

```text
Process order:
1. validate customer
2. reserve inventory
3. create invoice
4. process payment
5. arrange shipping
```

V SOA to často řídí orchestrator nebo process engine.

---

## 15. Enterprise Service Bus / ESB

**Enterprise Service Bus** je integrační middleware.

Může řešit:

```text
routing
message transformation
protocol conversion
service orchestration
monitoring
security
retries
```

Příklad:

```text
SOAP service → ESB → REST service
XML → ESB transformation → JSON
```

---

## 16. Výhody SOA

```text
dobrá integrace enterprise systémů
service reuse
standardized contracts
možnost skládat služby do business procesů
platform independence
lepší oddělení systémů než přímé point-to-point integrace
```

---

## 17. Nevýhody SOA

```text
vyšší počáteční investice
komplexní service governance
ESB může být bottleneck
ESB může vytvořit centralizovanou závislost
vyšší overhead komunikace
složitější management velkého množství služeb
```

Antipattern:

```text
Smart ESB, dumb services
```

To znamená, že příliš mnoho business logiky je v ESB místo ve službách.

---

## 18. SOA vs Microservices

SOA a microservices jsou podobné v tom, že oba přístupy pracují se službami.

Rozdíly:

| Kritérium | SOA | Microservices |
|---|---|---|
| Service size | často větší enterprise services | menší služby kolem business capability |
| Communication | často ESB / SOAP / enterprise middleware | REST, gRPC, messaging |
| Governance | centralizovanější | decentralizovanější |
| Data ownership | méně striktní | často database per service |
| Deployment | nemusí být vždy nezávislý | nezávislý deployment je klíčový |
| Team model | enterprise integration | small autonomous teams |
| Goal | reuse and integration | independent delivery and scalability |

Bezpečná formulace:

> Microservices can be seen as a more lightweight and decentralized evolution of service-oriented ideas, but with stronger emphasis on independent deployment, team autonomy and decentralized data ownership.

## 19. Orchestration

## 19.1 Princip

**Orchestration** znamená, že centrální komponenta řídí business proces.

Příklad:

```text
Order Orchestrator:
1. call Customer Service
2. call Payment Service
3. call Inventory Service
4. call Shipping Service
5. send confirmation
```

Orchestrator ví, jaký je celý workflow.

---

## 19.2 Výhody orchestrace

```text
workflow je explicitní
snadnější pochopení procesu
snadnější audit business procesu
centralizovaná kontrola chyb
vhodné pro složité business procesy
```

---

## 19.3 Nevýhody orchestrace

```text
orchestrator může být bottleneck
služby mohou být silně závislé na orchestratoru
centrální komponenta může být single point of failure
riziko distributed monolith
```

Distributed monolith vznikne, když služby sice běží odděleně, ale jsou tak silně synchronně provázané, že se musí deployovat, měnit nebo provozovat skoro jako jeden celek.

---

## 20. Choreography

## 20.1 Princip

**Choreography** znamená, že není centrální orchestrator.

Služby reagují na události.

Příklad:

```text
Order Service publishes OrderCreated.
Payment Service receives OrderCreated and processes payment.
Payment Service publishes PaymentCompleted.
Inventory Service receives PaymentCompleted and reserves items.
Shipping Service receives InventoryReserved and creates shipment.
Notification Service sends email.
```

---

## 20.2 Výhody choreography

```text
loose coupling
vyšší autonomie služeb
lepší škálovatelnost
lepší fault isolation
snadnější přidání nového consumeru
```

---

## 20.3 Nevýhody choreography

```text
globální workflow je méně viditelný
těžší debugging
eventual consistency
složitější error handling
těžší testování celého procesu
```

---

## 21. Orchestration vs choreography

| Kritérium | Orchestration | Choreography |
|---|---|---|
| Control | centrální orchestrator | služby reagují na eventy |
| Visibility | workflow jasně viditelný | workflow rozptýlený |
| Coupling | vyšší | nižší |
| Debugging | jednodušší | těžší |
| Scalability | může mít bottleneck | lepší škálovatelnost |
| Failure handling | centrální | distribuované |
| Typical communication | sync calls / commands | async events |

Zkoušková věta:

> Orchestration is easier to understand, but can increase coupling. Choreography improves loose coupling and autonomy, but makes the global workflow harder to observe and debug.

## 22. Event-Driven Architecture

## 22.1 Princip

**Event-driven architecture** používá události jako hlavní mechanismus komunikace.

Základní prvky:

```text
event producer
event consumer
event broker / event bus
event channel / topic / queue
event message
```

Producer publikuje event.

Consumer event zpracuje.

Producer nemusí vědět, kdo event zpracuje.

---

## 22.2 Event

Event je záznam, že se něco stalo.

Dobré názvy eventů:

```text
OrderCreated
PaymentAuthorized
UserRegistered
InvoiceGenerated
ProductStockChanged
```

Špatné názvy:

```text
CreateOrder
AuthorizePayment
RegisterUser
```

Proč?

```text
Event should describe something that already happened.
Command describes something that should happen.
```

---

## 22.3 Event vs command

### Command

Command říká:

```text
do something
```

Příklad:

```text
CreateOrder
CancelOrder
SendEmail
```

### Event

Event říká:

```text
something happened
```

Příklad:

```text
OrderCreated
OrderCancelled
EmailSent
```

Důležité:

```text
Command má obvykle jednoho intended receivera.
Event může mít mnoho consumerů.
```

---

## 22.4 Event broker

Event broker předává eventy mezi producers a consumers.

Příklady technologií:

```text
Kafka
RabbitMQ
ActiveMQ
NATS
AWS SNS/SQS
Google Pub/Sub
Azure Service Bus
```

Broker může poskytovat:

```text
queues
topics
durability
acknowledgement
retry
dead-letter queue
ordering guarantees
consumer groups
```

---

## 22.5 Publish-subscribe

V pub-sub modelu producer publikuje event do topicu.

Více consumerů může tento event zpracovat nezávisle.

Příklad:

```text
Topic: order-events

Order Service publishes OrderCreated.

Consumers:
- Payment Service
- Notification Service
- Analytics Service
- Fraud Detection Service
```

Výhoda:

```text
přidání Analytics Service nevyžaduje změnu Order Service
```

---

## 22.6 Výhody event-driven architecture

```text
loose coupling
asynchronous processing
lepší scalability
lepší elasticity
snadné přidání nových consumerů
dobré pro high-volume data
dobré pro integraci služeb
dobré pro audit log / event history
```

---

## 22.7 Nevýhody event-driven architecture

```text
složitější debugging
eventual consistency
možné duplicitní eventy
problémy s orderingem
složitější error handling
složitější monitoring
těžší pochopení end-to-end flow
```

---

## 22.8 Idempotency

V event-driven systémech je důležité, aby consumer zvládl zpracovat stejný event vícekrát.

**Idempotentní operace** znamená:

```text
opakované provedení stejné operace vede ke stejnému výslednému stavu
```

Příklad:

```text
PaymentCompleted event přijde dvakrát.
Order must be marked as paid only once.
```

Řešení:

```text
event id
processed events table
idempotency key
unique constraint
deduplication
```

---

## 22.9 Ordering

Někdy záleží na pořadí eventů.

Příklad:

```text
OrderCreated
OrderPaid
OrderShipped
```

Problém:

```text
consumer dostane OrderShipped před OrderPaid
```

Možná řešení:

```text
partitioning by aggregate id
sequence numbers
versioning
consumer-side buffering
design tolerant to reordering
```

---

## 22.10 Dead-letter queue

Pokud event nelze zpracovat ani po retry, může skončit v **dead-letter queue**.

Použití:

```text
manual investigation
later reprocessing
alerting
debugging failed messages
```

## 23. Microservices Architecture

## 23.1 Princip

**Microservices architecture** strukturuje aplikaci jako sadu malých služeb.

Každá služba je:

```text
independently deployable
loosely coupled
organized around business capability
owned by small team
independently scalable
```

Příklad:

```text
User Service
Order Service
Payment Service
Inventory Service
Notification Service
```

---

## 23.2 Business capability

Microservice by měla být organizovaná kolem business capability, ne kolem technické vrstvy.

Dobře:

```text
Order Service
Payment Service
Shipping Service
Customer Service
```

Špatně:

```text
Controller Service
Repository Service
Database Service
Validation Service
```

To by byla distribuovaná layered architecture a často antipattern.

---

## 23.3 Database per service

Důležité pravidlo v microservices:

```text
each service owns its data
```

To znamená:

```text
Order Service owns order data.
Payment Service owns payment data.
Inventory Service owns stock data.
```

Jiná služba nesmí přímo měnit interní databázi jiné služby.

Správně:

```text
Payment Service asks Order Service through API or consumes OrderCreated event.
```

Špatně:

```text
Payment Service directly updates order table.
```

---

## 23.4 Výhody microservices

```text
independent deployment
independent scaling
fault isolation
team autonomy
technology flexibility
smaller codebases
faster delivery in large organizations
easier replacement of individual services
```

---

## 23.5 Nevýhody microservices

```text
distributed complexity
network failures
higher latency
harder debugging
harder testing
data consistency problems
API versioning
deployment complexity
observability requirements
DevOps maturity required
```

Důležitá věta:

> Microservices solve organizational and scalability problems, but introduce distributed system problems.

---

## 23.6 Microservices and Conway’s Law

**Conway’s Law** říká, že architektura systému často kopíruje komunikační strukturu organizace.

Jinými slovy: systém obvykle vypadá podobně jako týmy, které ho vytvářejí.

Pokud jsou týmy rozdělené podle **business capabilities**, například:

```text
Orders team
Payments team
Shipping team
Customer team
```

pak mohou microservices přirozeně odpovídat těmto oblastem:

```text
Order Service
Payment Service
Shipping Service
Customer Service
```

To je pro microservices vhodné, protože každý tým vlastní konkrétní business oblast end-to-end.

Pokud je ale organizace rozdělená technicky:

```text
frontend team
backend team
database team
QA team
operations team
```

může vzniknout systém se špatnými hranicemi služeb. Služby pak často nejsou skutečně autonomní, protože každá změna vyžaduje koordinaci napříč mnoha týmy.

Výsledek může být spíše **distributed monolith** než dobře navržená microservices architektura.

## 29. Timeout

```text

```

```text

```

## 30. Retry

Retry opakuje operaci po dočasné chybě.

```text

```

```text

```

## 31. Circuit breaker

Circuit breaker chrání systém před opakovaným voláním služby, která selhává.

Stavy:

```text

```

Princip:

```text
pokud služba často selhává, circuit breaker se otevře
další requesty se rychle odmítnou nebo použijí fallback
po čase se zkusí testovací request
```

Výhoda:

```text

```

## 32. Bulkhead

Bulkhead izoluje části systému, aby chyba jedné části nepotopila celý systém.

Příklad:

```text

separate service instances
separate resource limits
```

Příklad:

```text
Slow reporting API should not consume all threads needed for checkout.
```

---

## 33. Graceful degradation

Systém při chybě poskytuje omezenou funkcionalitu místo úplného výpadku.

Příklad:

```text
Recommendation Service is down.
E-shop still allows browsing and purchasing.
Only personalized recommendations are hidden.
```

## 34. Eventual consistency

V distributed systems často nelze mít okamžitou konzistenci všude.

**Eventual consistency** znamená:

```text
data may be temporarily inconsistent,
but if no new updates occur,
all replicas/services eventually converge to consistent state
```

Příklad:

```text
Order Service marks order as created.
Payment Service processes payment later.
Inventory Service reserves items after event.
```

Mezitím může být stav:

```text
order created, payment pending, inventory not yet reserved
```

To musí UI a business proces umět zobrazit.

## 42. Comparison of distributed styles

| Style | Main idea | Strengths | Weaknesses | Typical use |
|---|---|---|---|---|
| Client-server | clients request services from server | simple, known, centralized data | server bottleneck/failure | web/mobile apps |
| N-tier | separate presentation/app/data tiers | separation, independent tier scaling | more network hops | enterprise systems |
| REST | resource-based HTTP API | simple, interoperable, stateless | over/under-fetching, versioning | public/internal APIs |
| GraphQL | client asks for exact data | flexible for UI | query complexity, caching | complex frontends |
| SOA | enterprise services with contracts | reuse, integration | ESB/governance complexity | enterprise integration |
| Orchestration | central process controller | clear workflow | coupling, bottleneck | business processes |
| Choreography | services react to events | loose coupling | harder tracing | async workflows |
| Event-driven | event producers/consumers | scalable, decoupled | eventual consistency | real-time/integration |
| Microservices | independent business services | deploy/scale/team autonomy | distributed complexity | large systems |

## 43. Common antipatterns

### 43.1 Distributed monolith

Služby jsou síťově oddělené, ale logicky silně svázané.

Symptomy:

```text
každá změna vyžaduje změnu více služeb
služby se musí deployovat společně
synchronní chain volání je dlouhý
výpadek jedné služby zastaví celý systém
```

---

### 43.2 Shared database between services

Více služeb přímo používá stejné tabulky.

Problém:

```text
silné coupling
nejasné ownership
těžké změny schématu
porušení encapsulation služby
```

---

### 43.3 Chatty services

Služby spolu komunikují příliš často a příliš jemně.

Příklad:

```text
Order Service calls Customer Service 50 times while processing one request.
```

Problém:

```text
latency
network overhead
fragility
```

---

### 43.4 No API Gateway

Klient komunikuje přímo s mnoha interními službami.

Problém:

```text
klient zná interní strukturu systému
těžší security
těžší změny služeb
```

---

### 43.5 Too many technologies

Každý tým používá jiný jazyk, framework a databázi bez důvodu.

Problém:

```text
vyšší provozní komplexita
těžší hiring
těžší monitoring
těžší sdílení znalostí
```

---

### 43.6 Microservice per feature

Každá malá feature se stane microservice.

Problém:

```text
příliš jemná granularita
moc deploymentů
moc síťové komunikace
vyšší komplexita než hodnota
```

## 44. Zkoušková odpověď: distributed architecture

Distributed architecture splits a system into multiple components that run in separate processes or nodes and communicate over a network. Examples include client-server systems, service-oriented architecture, event-driven systems and microservices.

The main benefits are scalability, availability, fault isolation, independent deployment, integration flexibility and team autonomy. However, distributed systems are harder than monolithic systems because network communication can fail, latency is not zero, services can be unavailable independently and data consistency becomes more difficult.

Therefore, distributed architecture must be designed for failure. It usually needs timeouts, retries, circuit breakers, monitoring, logging, tracing, health checks, API versioning and careful data ownership. A distributed architecture should be chosen only when its benefits justify the additional complexity.

---

## 45. Zkoušková odpověď: SOA

Service-Oriented Architecture organizes a system as a set of services with standardized contracts. Services are designed to be loosely coupled, reusable, autonomous, discoverable and composable. SOA is often used in enterprise integration, where multiple systems need to communicate through stable service contracts.

SOA can use an Enterprise Service Bus for routing, transformation, protocol conversion and orchestration. Its advantages are service reuse, integration of heterogeneous systems and standardized communication. Its disadvantages are higher complexity, governance overhead, possible ESB bottleneck and high initial investment.

---

## 46. Zkoušková odpověď: event-driven architecture

Event-driven architecture is based on communication through events. Producers publish events and consumers subscribe to them, usually through an event broker or event bus. Producers do not need to know which consumers process the events.

This improves loose coupling, scalability and extensibility, because new consumers can be added without changing producers. It is suitable for asynchronous workflows, real-time processing, high-volume systems and integration between services. The disadvantages are higher complexity, eventual consistency, harder debugging, message ordering problems and the need for idempotent consumers.

---

## 47. Zkoušková odpověď: microservices

Microservices architecture structures an application as a collection of small, loosely coupled and independently deployable services. Services are organized around business capabilities and are usually owned by small autonomous teams.

The advantages are independent deployment, independent scaling, better fault isolation, team autonomy and technology flexibility. The disadvantages are distributed system complexity, network failures, harder testing and debugging, data consistency problems, API versioning and higher DevOps requirements.

Microservices are not a silver bullet. They are useful for large and complex systems where the benefits of independent delivery and scalability justify the operational and architectural complexity.
