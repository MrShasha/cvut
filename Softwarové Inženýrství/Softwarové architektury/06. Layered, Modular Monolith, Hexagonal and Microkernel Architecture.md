# Layered, Modular Monolith, Hexagonal and Microkernel Architecture

> **Zkouškový fokus:** umět detailně popsat layered architecture, modular monolith, hexagonal architecture a microkernel, včetně výhod, nevýhod a typických pastí.

## 1. Proč tyto styly řešit zvlášť

Tento blok pokrývá hlavní **monolithic / in-process** architektonické styly a vzory, které se často používají v běžných enterprise aplikacích.

Patří sem:

```text
layered architecture
modular monolith
hexagonal architecture / ports and adapters
microkernel architecture
```

Nejsou to nutně zastaralé styly. Naopak, často jsou vhodnější než microservices, pokud systém nepotřebuje distribuovanou komplexitu.

Důležitá zkoušková myšlenka:

> Monolith is not automatically bad. A badly structured monolith is bad. A modular monolith or a well-layered system can be a very good architecture.

---

## 2. Layered Architecture

## 2.1 Základní princip

**Layered architecture** rozděluje systém do horizontálních vrstev podle technické odpovědnosti.

Typické vrstvy:

```text
presentation layer
application layer
business logic layer
data access layer
database layer
```

V běžné backend aplikaci to často vypadá takto:

```text
Controller
  ↓
Service
  ↓
Repository / DAO
  ↓
Database
```

Každá vrstva má vlastní odpovědnost.

---

## 2.2 Příklad ve webové aplikaci

Příklad požadavku:

```text
User creates an order.
```

Možné vrstvy:

```text
OrderController
- přijme HTTP request
- validuje základní vstup
- zavolá OrderService
- vrátí HTTP response

OrderService
- obsahuje business logic
- zkontroluje stav košíku
- spočítá cenu
- vytvoří objednávku
- zavolá repository

OrderRepository
- ukládá objednávku do databáze
- načítá objednávky z databáze

Database
- fyzicky ukládá data
```

---

## 2.3 Strict vs relaxed layering

### Strict layering

V strict layering může vrstva komunikovat pouze s bezprostředně nižší vrstvou.

```text
Controller → Service → Repository → Database
```

Controller nemůže přeskočit Service a volat Repository přímo.

Výhoda:

```text
čistá struktura
dobrá kontrola závislostí
business logic zůstává ve správné vrstvě
```

Nevýhoda:

```text
více boilerplate
někdy zbytečné předávání dat
```

### Relaxed layering

V relaxed layering může vrstva přeskočit některé mezivrstvy.

Příklad:

```text
Controller → Repository
```

To může být rychlejší pro jednoduché read-only operace, ale může to rozbít jasnou strukturu.

Riziko:

```text
business logic se začne objevovat v controlleru
vrstvy ztratí smysl
systém se stane méně udržovatelný
```

Bezpečná formulace:

> Strict layering improves architectural discipline, while relaxed layering can reduce boilerplate but increases the risk of broken separation of concerns.

---

## 2.4 Odpovědnosti vrstev

### Presentation / Controller Layer

Řeší komunikaci s uživatelem nebo externím klientem.

Typicky:

```text
HTTP request / response
routing
basic input validation
DTO mapping
status codes
authentication context
```

Neměla by obsahovat hlavní business logic.

Špatně:

```text
Controller directly calculates discounts, updates database, sends emails and handles payment rules.
```

Lépe:

```text
Controller receives request and delegates business operation to service.
```

---

### Application / Service Layer

Řeší aplikační use cases.

Typicky:

```text
business workflow
transaction boundary
calling repositories
calling external services
authorization at use-case level
coordination of domain objects
```

Příklad:

```text
createOrder()
cancelOrder()
approvePayment()
registerUser()
```

Service layer často odpovídá tomu, co systém umí dělat.

---

### Domain / Business Layer

Obsahuje doménová pravidla.

Příklad:

```text
Order cannot be cancelled after shipment.
Discount cannot be greater than total price.
User cannot approve his own request.
```

U jednodušších aplikací je business layer často spojená se service layer.

U složitějších domén je lepší mít čistější domain model.

---

### Data Access Layer

Řeší persistence.

Typicky:

```text
SQL queries
ORM mapping
repositories
DAO
transactions support
database-specific details
```

Repository nebo DAO schovává technické detaily databáze před business logikou.

---

## 2.5 Výhody Layered Architecture

```text
jednoduchá na pochopení
přirozená pro webové a enterprise aplikace
jasné rozdělení odpovědností
dobrá testovatelnost vrstev
snadné onboarding nových vývojářů
dobrá podpora ve frameworcích
```

Příklad:

```text
Spring Boot aplikace s Controller-Service-Repository strukturou.
```

Vývojář rychle ví, kam má napsat nový endpoint, kam business logic a kam database query.

---

## 2.6 Nevýhody Layered Architecture

```text
může vést k boilerplate kódu
může vzniknout anemic domain model
příliš mnoho vrstev může zhoršit performance
změna funkcionality často prochází všemi vrstvami
cross-cutting concerns jdou napříč vrstvami
deployment je typicky jeden celek
omezené nezávislé škálování částí systému
```

### Anemic domain model

Business pravidla nejsou v doménových objektech, ale jen v services.

Příklad:

```text
Order je pouze datová struktura.
Všechna logika je v OrderService.
```

To není vždy špatně, ale u složité domény to může zhoršit maintainability.

---

## 2.7 Cross-cutting concerns

Cross-cutting concerns jsou věci, které procházejí napříč vrstvami.

Příklady:

```text
logging
security
transactions
validation
monitoring
configuration
error handling
caching
internationalization
privacy
```

V layered architecture se často řeší pomocí:

```text
middleware
interceptors
filters
aspects / AOP
framework configuration
annotations
```

Příklad:

```text
@Transactional
@PreAuthorize
logging filter
exception handler
```

---

## 2.8 Typické chyby v layered architecture

### Business logic in controller

Špatně:

```text
Controller validates business rules, updates database and sends notifications.
```

Problém:

```text
těžké testování
duplicita logiky
controller je příliš velký
```

Správně:

```text
Controller delegates to service.
```

---

### Repository called from everywhere

Špatně:

```text
Controller → Repository
Service → Repository
Helper → Repository
```

Problém:

```text
nejasné transaction boundaries
business rules se obcházejí
těžší kontrola konzistence
```

---

### God Service

Špatně:

```text
ApplicationService has 5000 lines and handles users, orders, payments and notifications.
```

Problém:

```text
nízká cohesion
vysoký coupling
těžké testování
```

---

## 2.9 Kdy použít layered architecture

Dobrá volba pro:

```text
CRUD aplikace
enterprise informační systémy
backend API
administrativní systémy
menší a střední aplikace
týmy používající Spring / Jakarta EE / .NET
```

Méně vhodná pro:

```text
extrémně složité domény bez dalších struktur
systémy s velmi vysokou potřebou nezávislého škálování
velké systémy s mnoha autonomními týmy bez modulárních hranic
```

---

## 3. Modular Monolith

## 3.1 Problém klasického monolitu

Monolit není problém sám o sobě.

Problém je, když se z něj stane:

```text
Big Ball of Mud
```

Typické symptomy:

```text
všechno závisí na všem
není jasné, kam patří nová funkcionalita
business logic je všude
moduly nemají hranice
změna jedné části rozbije jinou část
testy jsou pomalé a křehké
```

**Modular monolith** řeší tento problém tak, že monolit rozdělí na jasně oddělené moduly.

---

## 3.2 Základní princip

Modular monolith je jedna aplikace, ale s jasnou interní modularitou.

```text
one codebase
one deployable application
clear internal modules
explicit module boundaries
controlled dependencies
```

Příklad e-shopu:

```text
Product Module
Basket Module
Order Module
Payment Module
User Module
Notification Module
```

Každý modul má vlastní odpovědnost.

---

## 3.3 Struktura modulu

Jeden modul může obsahovat:

```text
API / public interface
application services
domain logic
repositories
database schema / tables
tests
```

Příklad:

```text
order/
  api/
  application/
  domain/
  infrastructure/
  tests/
```

Důležité je, že ostatní moduly nelezou do interních tříd modulu.

---

## 3.4 Public interface modulu

Modul by měl mít jasné veřejné rozhraní.

Příklad:

```text
OrderModule.createOrder(...)
OrderModule.cancelOrder(...)
OrderModule.getOrderStatus(...)
```

Ostatní moduly by neměly přímo používat:

```text
OrderRepository
OrderEntity internals
internal helper classes
private database tables
```

---

## 3.5 Module boundaries

Hranice modulů jsou klíčové.

Správně:

```text
Payment Module asks Order Module through public API.
```

Špatně:

```text
Payment Module directly reads order tables and modifies order status.
```

Problém špatného přístupu:

```text
silné coupling
porušení ownership
těžší refactoring
riziko skrytých dependencies
```

---

## 3.6 Database in modular monolith

Existuje více možností.

### Shared database with separated schemas

```text
order_schema
payment_schema
user_schema
```

Výhoda:

```text
lepší oddělení dat
jasnější ownership
```

Nevýhoda:

```text
pořád jedna databáze
možné obcházení hranic přes SQL
```

### Shared database with separated tables

```text
orders
order_items
payments
users
```

Jednodušší, ale tým musí disciplinovaně hlídat ownership tabulek.

### Database per module

Někdy lze mít modulárně oddělená úložiště i v monolitu.

To usnadňuje případný přechod na microservices, ale zvyšuje komplexitu.

---

## 3.7 Výhody modular monolith

```text
jednodušší provoz než microservices
jeden deployment
jednodušší debugging
jednodušší transakce
jasnější boundaries než klasický monolit
lepší maintainability
snadnější refactoring
dobrý krok před microservices
```

Prakticky:

```text
Můžeš mít většinu výhod dobré modularity bez síťové a DevOps komplexity microservices.
```

---

## 3.8 Nevýhody modular monolith

```text
stále jeden deployable unit
škálování je většinou pro celou aplikaci
potřeba disciplíny v týmu
hranice nejsou fyzicky vynucené sítí
může degenerovat do Big Ball of Mud
```

Pokud tým ignoruje boundaries, modular monolith se rychle změní na obyčejný špatný monolit.

---

## 3.9 Modular monolith vs microservices

| Kritérium | Modular monolith | Microservices |
|---|---|---|
| Deployment | jeden celek | nezávislý deployment služeb |
| Communication | in-process calls | síťová komunikace |
| Transactions | jednodušší | složitější |
| Debugging | jednodušší | těžší |
| Scaling | typicky celý systém | jednotlivé služby |
| Team autonomy | střední | vysoká |
| Operational complexity | nižší | vysoká |
| Data consistency | jednodušší | eventual consistency / Saga často nutná |

Důležitá věta:

> Modular monolith is often a better starting point than microservices, because it preserves simplicity while enforcing better internal structure.

## 4. Hexagonal Architecture / Ports and Adapters

## 4.1 Základní princip

**Hexagonal architecture**, také **Ports and Adapters**, odděluje business logiku od externích technologií.

Cíl:

```text
business logic should not depend on UI, database, framework or external services
```

Jádro systému je uprostřed.

Okolo jsou adaptéry.

```text
External world → Adapter → Port → Application / Domain Core → Port → Adapter → External system
```

---

## 4.2 Core

Core obsahuje:

```text
domain model
business rules
application services
use cases
domain services
```

Core by neměl záviset na:

```text
REST framework
database implementation
message broker
file system
external API client
UI
```

---

## 4.3 Ports

**Port** je rozhraní.

Existují dva typické směry.

### Driving / primary ports

Používají se pro vstup do aplikace.

Příklad:

```text
CreateOrderUseCase
CancelOrderUseCase
RegisterUserUseCase
```

Volá je například:

```text
REST controller
GraphQL resolver
CLI command
message consumer
```

### Driven / secondary ports

Používají se, když core potřebuje něco zvenku.

Příklad:

```text
OrderRepository
PaymentGateway
EmailSender
FileStorage
Clock
```

Core zná pouze interface, ne konkrétní technologii.

---

## 4.4 Adapters

**Adapter** je konkrétní implementace portu.

Příklady inbound adapters:

```text
REST controller
GraphQL resolver
CLI adapter
message listener
```

Příklady outbound adapters:

```text
PostgresOrderRepository
StripePaymentGateway
SmtpEmailSender
S3FileStorage
SystemClock
```

---

## 4.5 Příklad

Požadavek:

```text
Create order.
```

Core:

```text
CreateOrderUseCase
Order
OrderRepository interface
PaymentGateway interface
```

Adapters:

```text
RestOrderController
PostgresOrderRepository
StripePaymentGateway
```

Závislosti:

```text
RestOrderController → CreateOrderUseCase
CreateOrderUseCase → OrderRepository interface
CreateOrderUseCase → PaymentGateway interface
PostgresOrderRepository implements OrderRepository
StripePaymentGateway implements PaymentGateway
```

Důležité:

```text
CreateOrderUseCase neví, že repository je PostgreSQL.
CreateOrderUseCase neví, že payment gateway je Stripe.
```

---

## 4.6 Dependency direction

Nejdůležitější pravidlo:

```text
Dependencies point inward.
```

To znamená:

```text
infrastructure depends on core
core does not depend on infrastructure
```

Špatně:

```text
OrderService imports Spring Controller.
Order entity imports JPA repository.
Domain logic directly calls HTTP client.
```

Dobře:

```text
OrderService depends on PaymentGateway interface.
StripePaymentGateway implements PaymentGateway.
```

---

## 4.7 Výhody hexagonal architecture

```text
dobrá testovatelnost business logic
business logic je oddělená od frameworků
snazší výměna databáze nebo externí služby
snazší mockování v testech
lepší maintainability
lepší separation of concerns
vhodné pro složitější domény
```

Příklad testu:

```text
CreateOrderUseCase can be tested with fake OrderRepository and fake PaymentGateway.
```

Není potřeba spouštět:

```text
HTTP server
real database
real payment provider
```

---

## 4.8 Nevýhody hexagonal architecture

```text
vyšší počáteční komplexita
více interfaces
více mappingu mezi vrstvami
může být overengineering pro jednoduchý CRUD
vyžaduje disciplínu v dependency direction
```

Pro jednoduchou aplikaci:

```text
GET /products
POST /products
```

může být plná hexagonal architecture zbytečně složitá.

---

## 4.9 Hexagonal vs layered architecture

| Kritérium | Layered architecture | Hexagonal architecture |
|---|---|---|
| Hlavní princip | technické vrstvy | core oddělený od externích adapterů |
| Dependency direction | typicky shora dolů | dovnitř ke core |
| Business logic | service/domain layer | application/domain core |
| Database | spodní vrstva | externí adapter |
| API | horní vrstva | inbound adapter |
| Testability | dobrá | velmi dobrá pro core |
| Complexity | nižší | vyšší |

Důležitá formulace:

> Layered architecture separates technical responsibilities into layers. Hexagonal architecture protects the business core from external technologies using ports and adapters.

---

## 4.10 Kdy použít hexagonal architecture

Vhodná pro:

```text
složitější business doménu
systémy s dlouhou životností
systémy s více externími integracemi
systémy, kde je důležitá testovatelnost
systémy, kde se může měnit infrastruktura
```

Méně vhodná pro:

```text
jednoduchý CRUD
rychlý prototyp
malý projekt bez složité business logiky
```

---

## 5. Microkernel Architecture

## 5.1 Základní princip

**Microkernel architecture** rozděluje systém na:

```text
core system
plug-in modules
```

Core obsahuje minimální základní funkcionalitu.

Pluginy přidávají konkrétní rozšíření.

Příklad:

```text
VS Code:
core editor
plugin for Python
plugin for Java
plugin for Docker
plugin for Git
```

Nebo:

```text
web browser:
core browsing engine
ad blocker extension
password manager extension
developer tools extension
```

---

## 5.2 Core system

Core by měl být stabilní a malý.

Obsahuje:

```text
základní runtime
plugin registry
plugin lifecycle
core API
shared services
basic configuration
```

Core by neměl obsahovat každou specializovanou funkci.

---

## 5.3 Plug-in modules

Pluginy poskytují rozšíření.

Příklad:

```text
syntax highlighting plugin
payment provider plugin
report generator plugin
export plugin
authentication provider plugin
```

Plugin komunikuje s core přes jasné plugin API.

---

## 5.4 Plugin registry

Systém často potřebuje registr pluginů.

Registry řeší:

```text
které pluginy jsou nainstalované
které pluginy jsou aktivní
jakou verzi plugin má
jaké capability plugin poskytuje
jak plugin spustit
```

---

## 5.5 Výhody microkernel architecture

```text
dobrá rozšiřitelnost
core zůstává stabilní
pluginy lze přidávat nebo odebírat
dobré pro produktové platformy
dobré pro systémy s variabilní funkcionalitou
možnost třetích stran vytvářet rozšíření
```

Příklad:

```text
IDE nemusí mít všechny funkce v core.
Nové jazyky a nástroje lze přidat jako pluginy.
```

---

## 5.6 Nevýhody microkernel architecture

```text
složitý návrh plugin API
contract versioning
kompatibilita pluginů
testování kombinací pluginů
lifecycle management pluginů
bezpečnost pluginů
výkon kvůli nepřímým voláním
```

Velký problém:

```text
Pluginy samostatně fungují, ale v kombinaci mohou způsobit chyby.
```

---

## 5.7 Kdy použít microkernel

Vhodné pro:

```text
IDE
text editors
web browsers
workflow engines
product platforms
systems with optional features
systems with third-party extensions
```

Méně vhodné pro:

```text
běžný CRUD backend
jednoduchou webovou aplikaci
systém bez požadavku na rozšiřitelnost pluginy
```

---

## 6. Comparison

| Style | Main idea | Strengths | Weaknesses | Typical use |
|---|---|---|---|---|
| Layered | Technical layers | Simple, clear, common | Boilerplate, layer coupling | Web/enterprise apps |
| Modular monolith | One app with modules | Low ops complexity, good boundaries | One deployment, discipline needed | Growing business apps |
| Hexagonal | Core + ports/adapters | Testability, framework independence | More abstractions | Complex domain apps |
| Microkernel | Core + plugins | Extensibility | Plugin API complexity | IDEs, browsers, platforms |

---

## 7. Vztah k quality attributes

### Maintainability

Podporují:

```text
layered architecture through separation of concerns
modular monolith through module boundaries
hexagonal architecture through isolated core
microkernel through stable core and isolated plugins
```

Rizika:

```text
poor boundaries
business logic in wrong places
too many dependencies
unclear plugin contracts
```

---

### Testability

Layered architecture:

```text
testování controllerů, services, repositories zvlášť
```

Modular monolith:

```text
testování modulů jako relativně samostatných částí
```

Hexagonal architecture:

```text
velmi dobrá testovatelnost core přes fake adapters
```

Microkernel:

```text
pluginy lze testovat samostatně, ale kombinace pluginů jsou těžké
```

---

### Scalability

Layered architecture:

```text
typicky škáluje celý deployable unit
```

Modular monolith:

```text
také typicky škáluje celý systém
```

Hexagonal architecture:

```text
sama o sobě neřeší scaling, ale umožňuje lepší výměnu infrastruktury
```

Microkernel:

```text
škálování záleží na implementaci core a pluginů
```

---

### Flexibility / Modifiability

Modular monolith:

```text
změny uvnitř modulu jsou jednodušší, pokud jsou boundaries dodrženy
```

Hexagonal:

```text
výměna externí technologie je jednodušší díky portům
```

Microkernel:

```text
přidání nové funkcionality přes plugin je hlavní výhoda
```

---

## 8. Typické antipatterny

## 8.1 Big Ball of Mud

Systém nemá jasnou strukturu.

Symptomy:

```text
všechno závisí na všem
žádné vrstvy nebo moduly
nejasné odpovědnosti
změny jsou nebezpečné
```

Vzniká často ze špatného monolitu bez modularity.

---

## 8.2 God Object / God Service

Jedna třída nebo service dělá příliš mnoho věcí.

Příklad:

```text
ApplicationService handles users, orders, payments, notifications, reports and permissions.
```

Problém:

```text
nízká cohesion
vysoký coupling
těžké testování
těžké změny
```

---

## 8.3 Spaghetti Code

Chaotická logika bez jasného flow.

Symptomy:

```text
hodně if/else bez struktury
kopírovaná logika
nejasné dependencies
těžké čtení
```

---

## 8.4 Lava Flow

Starý kód zůstává v systému, protože se ho nikdo bojí odstranit.

Symptomy:

```text
nepoužívané moduly
staré experimenty
dead code
nikdo neví, jestli se to ještě používá
```

---

## 8.5 Golden Hammer

Tým používá jeden oblíbený přístup na všechny problémy.

Příklad:

```text
Všechno musí být layered architecture.
Všechno musí být hexagonal architecture.
Všechno musí být microservices.
```

Správně:

```text
Styl se vybírá podle kontextu a quality attributes.
```

---

## 9. Mini example: choosing architecture

### Scenario

Malá aplikace pro správu rezervací.

Requirements:

```text
CRUD reservations
login
admin interface
email notifications
expected users: hundreds
small team
fast delivery
```

Dobrá volba:

```text
layered modular monolith
```

Proč:

```text
jednoduchý deployment
jasná struktura
rychlý vývoj
nízká operational complexity
dostatečné pro daný load
```

Zbytečně složité:

```text
microservices with Kubernetes, service mesh and distributed transactions
```

---

### Scenario 2

Platforma pro pluginy třetích stran.

Requirements:

```text
stable core
third-party extensions
optional functionality
plugin lifecycle
versioned extension API
```

Dobrá volba:

```text
microkernel architecture
```

Proč:

```text
core zůstává stabilní
funkce lze přidávat pluginy
```

## 10. Zkoušková odpověď: layered architecture

Layered architecture organizes a system into horizontal layers, where each layer has a specific technical responsibility. A typical web application has a presentation layer, application or service layer, business logic layer, data access layer and database layer.

The main advantage is separation of concerns. Controllers handle requests and responses, services implement use cases and business workflows, repositories handle persistence. This makes the system easier to understand, test and maintain.

The main disadvantages are possible boilerplate, performance overhead caused by passing requests through many layers, and coupling between layers. If the architecture is not followed strictly, business logic can leak into controllers or repositories. Layered architecture is suitable for CRUD, web and enterprise applications, but it may be insufficient for very large systems without additional modular boundaries.

---

## 11. Zkoušková odpověď: modular monolith

A modular monolith is a monolithic application divided into clear internal modules. It has one codebase and one deployment unit, but modules have explicit boundaries and responsibilities.

It combines the operational simplicity of a monolith with better maintainability and organization. Each module can represent a business capability, such as orders, payments or users. Modules should communicate through public interfaces and should not directly access each other's internal implementation or database tables.

The main advantage is lower operational complexity compared to microservices. Debugging, deployment and transactions are simpler. The main disadvantage is that all modules are still deployed together and independent scaling is limited. It also requires discipline, because module boundaries are not physically enforced by the network.

---

## 12. Zkoušková odpověď: hexagonal architecture

Hexagonal architecture, also called ports and adapters, separates the business core of an application from external technologies such as databases, web frameworks, message brokers and external APIs.

The core contains domain logic and application use cases. Ports are interfaces that define how the core communicates with the outside world. Adapters are concrete implementations for specific technologies, for example REST controllers, PostgreSQL repositories or payment provider clients.

The key rule is that dependencies point inward. The business core depends on abstractions, not on infrastructure. This improves testability, maintainability and flexibility. The disadvantage is higher initial complexity and more abstractions, so it can be overengineering for simple CRUD applications.

---

## 13. Zkoušková odpověď: microkernel architecture

Microkernel architecture splits the system into a minimal core and plug-in modules. The core provides basic functionality, plugin lifecycle and extension points. Plugins add optional or specialized functionality.

This architecture is suitable for systems that must be extensible, such as IDEs, text editors, browsers or product platforms. New functionality can be added without changing the core system.

The main advantages are extensibility, stable core and independent plugin development. The main disadvantages are complexity of plugin API design, versioning, compatibility, security and testing of plugin combinations.
