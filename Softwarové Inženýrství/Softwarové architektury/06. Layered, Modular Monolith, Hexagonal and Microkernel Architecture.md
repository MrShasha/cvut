> **Zkouškový fokus:** umět detailně vysvětlit layered architecture, modular monolith, hexagonal architecture a microkernel. Důležité je znát princip, typické části, výhody, nevýhody, vztah ke quality attributes a nejčastější chyby.

## 1. Proč tyto styly řešit zvlášť

Tento blok pokrývá hlavní **monolithic / in-process** styly. Jsou důležité, protože velká část reálných enterprise systémů nezačíná jako microservices, ale jako monolit, vrstvená aplikace nebo modulární aplikace.

Patří sem:

- layered architecture
- modular monolith
- hexagonal architecture / ports and adapters
- microkernel architecture

Tyto styly nejsou zastaralé. Často jsou praktičtější než microservices, protože zachovávají jednodušší deployment, jednodušší debugging a menší provozní komplexitu.

> [!note] Hlavní myšlenka
> Monolith není automaticky špatně. Špatně je neřízený monolit bez hranic, kde všechno závisí na všem. Dobře navržený layered nebo modular monolith může být velmi dobrá architektura.

## 2. Layered architecture

### 2.1 Princip

**Layered architecture** rozděluje systém do horizontálních vrstev podle technické odpovědnosti.

Typické vrstvy:

- **presentation layer:** komunikace s uživatelem nebo externím klientem
- **application / service layer:** use cases, workflow, transakční hranice
- **domain / business layer:** doménová pravidla
- **data access layer:** persistence, repositories, DAO
- **database layer:** fyzické uložení dat

V běžné backend aplikaci:

- Controller
- Service
- Repository / DAO
- Database

Každá vrstva má mít jasnou odpovědnost. Smyslem není vytvořit co nejvíce vrstev, ale oddělit části systému, které se mění z jiných důvodů.

### 2.2 Příklad průchodu requestu

Požadavek: **User creates an order.**

- **OrderController**
  - přijme HTTP request
  - provede základní validaci formátu vstupu
  - převede request na DTO nebo command
  - zavolá `OrderService`
  - vrátí HTTP response
- **OrderService**
  - provede use case `createOrder`
  - ověří business pravidla
  - spočítá cenu
  - vytvoří objednávku
  - řídí transakci
  - zavolá repository a případně externí služby
- **OrderRepository**
  - ukládá objednávku do databáze
  - načítá objednávky z databáze
  - skrývá SQL/ORM detaily
- **Database**
  - fyzicky ukládá data

> [!tip] Praktické pravidlo
> Controller by měl být tenký. Hlavní business rozhodnutí patří do service nebo domain vrstvy, ne do HTTP handleru.

### 2.3 Strict vs relaxed layering

**Strict layering** znamená, že vrstva smí komunikovat pouze s bezprostředně nižší vrstvou.

Příklad:

- Controller -> Service -> Repository -> Database

Výhody:

- čistá struktura
- dobrá kontrola závislostí
- business logic zůstává ve správné vrstvě
- jednodušší architektonická kontrola

Nevýhody:

- více boilerplate
- někdy zbytečné předávání dat
- jednoduché read-only operace mohou být zbytečně dlouhé

**Relaxed layering** dovoluje některé vrstvy přeskočit.

Příklad:

- Controller -> Repository

To může být přijatelné pro jednoduchý read-only endpoint, ale je to rizikové, pokud se v controlleru začne objevovat business logic.

> [!note] Zkoušková formulace
> Strict layering improves architectural discipline, while relaxed layering can reduce boilerplate but increases the risk of broken separation of concerns.

### 2.4 Odpovědnosti vrstev

**Presentation / Controller layer** řeší:

- routing
- HTTP request / response
- status codes
- basic input validation
- DTO mapping
- authentication context

Neměla by řešit:

- výpočet ceny
- rozhodování o business pravidlech
- přímé ukládání do databáze
- odesílání více typů side effects bez service vrstvy

**Application / Service layer** řeší:

- use cases
- business workflow
- transaction boundary
- volání repositories
- volání externích služeb
- authorization na úrovni use case
- koordinaci doménových objektů

Příklady metod:

- `createOrder()`
- `cancelOrder()`
- `approvePayment()`
- `registerUser()`

**Domain / Business layer** řeší:

- doménová pravidla
- invariants
- stavové přechody
- výpočty patřící do domény

Příklady pravidel:

- Order cannot be cancelled after shipment.
- Discount cannot be greater than total price.
- User cannot approve his own request.

**Data access layer** řeší:

- SQL queries
- ORM mapping
- repositories
- DAO
- database-specific details
- podporu transakcí

### 2.5 Cross-cutting concerns

**Cross-cutting concerns** jsou věci, které procházejí napříč vrstvami.

Příklady:

- logging
- security
- transactions
- validation
- monitoring
- configuration
- error handling
- caching
- internationalization
- privacy

V layered architecture se často řeší přes:

- middleware
- interceptors
- filters
- aspects / AOP
- framework configuration
- annotations

Příklady:

- `@Transactional`
- `@PreAuthorize`
- logging filter
- exception handler

### 2.6 Výhody

- jednoduchá na pochopení
- přirozená pro webové a enterprise aplikace
- jasné rozdělení odpovědností
- dobrá testovatelnost vrstev
- snadný onboarding nových vývojářů
- dobrá podpora ve frameworcích
- vhodná pro CRUD a administrativní systémy

### 2.7 Nevýhody

- může vést k boilerplate kódu
- může vzniknout anemic domain model
- změna funkcionality často prochází více vrstvami
- příliš mnoho vrstev může zhoršit performance
- cross-cutting concerns se řeší napříč celou aplikací
- deployment je typicky jeden celek
- omezené nezávislé škálování částí systému

**Anemic domain model** znamená, že doménové objekty jsou jen datové struktury a všechna business logika je v services. U jednoduché aplikace to nemusí vadit, ale u složité domény to může zhoršit maintainability.

### 2.8 Typické chyby

- **Business logic in controller:** controller počítá slevy, mění stav objednávky, ukládá data a posílá emaily.
- **Repository called from everywhere:** controller, helper i service volají repository přímo a obcházejí transaction boundary.
- **God Service:** jedna service řeší users, orders, payments, notifications i reports.
- **Layering only by folder names:** projekt má složky `controller`, `service`, `repository`, ale odpovědnosti nejsou reálně oddělené.

### 2.9 Kdy použít layered architecture

Dobrá volba pro:

- CRUD aplikace
- enterprise informační systémy
- backend API
- administrativní systémy
- menší a střední aplikace
- týmy používající Spring, Jakarta EE nebo .NET

Méně vhodná pro:

- velmi složité domény bez dalších struktur
- systémy s potřebou nezávislého škálování business částí
- velké systémy s mnoha autonomními týmy bez modulárních hranic

## 3. Modular monolith

### 3.1 Problém klasického monolitu

Monolit není problém sám o sobě. Problém vzniká, když se z něj stane **Big Ball of Mud**.

Typické symptomy:

- všechno závisí na všem
- není jasné, kam patří nová funkcionalita
- business logic je rozptýlená po celé aplikaci
- části systému nemají ownership
- změna jedné části rozbíjí jiné části
- testy jsou pomalé a křehké

**Modular monolith** řeší tento problém tím, že jedna aplikace má jasné interní moduly a kontrolované závislosti.

### 3.2 Princip

Modular monolith má:

- one codebase
- one deployable application
- clear internal modules
- explicit module boundaries
- controlled dependencies

Příklad e-shopu:

- Product module
- Basket module
- Order module
- Payment module
- User module
- Notification module

Každý modul reprezentuje business oblast, ne jen technickou vrstvu.

> [!note] Rozdíl proti obyčejnému monolitu
> Obyčejný monolit může mít jen technické složky. Modular monolith má business moduly s jasnými hranicemi a veřejným rozhraním.

### 3.3 Struktura modulu

Jeden modul může obsahovat:

- public API / interface
- application services
- domain logic
- repositories
- database schema nebo vlastní tabulky
- tests

Příklad:

- `order/`
  - `api/`
  - `application/`
  - `domain/`
  - `infrastructure/`
  - `tests/`

Ostatní moduly by neměly používat interní třídy modulu. Mají používat jeho public API.

### 3.4 Public interface modulu

Modul by měl vystavit omezené veřejné rozhraní.

Příklad:

- `OrderModule.createOrder(...)`
- `OrderModule.cancelOrder(...)`
- `OrderModule.getOrderStatus(...)`

Ostatní moduly by neměly přímo používat:

- `OrderRepository`
- interní entity objednávky
- private helper classes
- private database tables

Tím se chrání možnost modul refaktorovat bez rozbití zbytku systému.

### 3.5 Module boundaries

Hranice modulů jsou nejdůležitější část modular monolithu.

Správně:

- Payment module asks Order module through public API.

Špatně:

- Payment module directly reads order tables and modifies order status.

Problémy špatného přístupu:

- silný coupling
- porušení ownership
- těžší refactoring
- skryté dependencies
- business pravidla lze obejít

Hranice lze kontrolovat pomocí:

- code reviews
- package visibility
- dependency rules
- architecture tests
- jasné dokumentace public API

### 3.6 Database in modular monolith

Existuje více možností.

**Shared database with separated schemas**

- `order_schema`
- `payment_schema`
- `user_schema`

Výhoda:

- lepší oddělení dat
- jasnější ownership
- snazší případná extrakce modulu

Nevýhoda:

- pořád jedna databáze
- možné obcházení hranic přes SQL

**Shared database with separated tables**

- `orders`
- `order_items`
- `payments`
- `users`

Je jednodušší, ale tým musí disciplinovaně hlídat ownership tabulek.

**Database per module**

Někdy lze mít modulárně oddělená úložiště i v monolitu. To usnadňuje budoucí přechod na microservices, ale zvyšuje komplexitu transakcí a datové integrace.

### 3.7 Výhody

- jednodušší provoz než microservices
- jeden deployment
- jednodušší debugging
- jednodušší transakce
- jasnější boundaries než klasický monolit
- lepší maintainability
- snadnější refactoring
- dobrý mezikrok před microservices

### 3.8 Nevýhody

- stále jeden deployable unit
- škálování je většinou pro celou aplikaci
- potřeba disciplíny v týmu
- hranice nejsou fyzicky vynucené sítí
- špatně hlídané moduly degenerují do Big Ball of Mud

### 3.9 Modular monolith vs microservices

| Kritérium | Modular monolith | Microservices |
|---|---|---|
| Deployment | jeden celek | nezávislý deployment služeb |
| Communication | in-process calls | síťová komunikace |
| Transactions | jednodušší | složitější |
| Debugging | jednodušší | těžší |
| Scaling | typicky celý systém | jednotlivé služby |
| Team autonomy | střední | vysoká |
| Operational complexity | nižší | vysoká |
| Data consistency | jednodušší | často eventual consistency / Saga |

> [!tip] Zkoušková věta
> Modular monolith is often a better starting point than microservices, because it preserves simplicity while enforcing better internal structure.

## 4. Hexagonal architecture / Ports and Adapters

### 4.1 Princip

**Hexagonal architecture**, také **Ports and Adapters**, odděluje business logiku od externích technologií.

Cíl:

- business logic should not depend on UI, database, framework or external services

Jádro systému je uprostřed. Okolo jsou adaptéry.

Zjednodušený tok:

- External world -> Adapter -> Port -> Application / Domain Core -> Port -> Adapter -> External system

### 4.2 Core

Core obsahuje:

- domain model
- business rules
- application services
- use cases
- domain services

Core by neměl záviset na:

- REST framework
- database implementation
- message broker
- file system
- external API client
- UI

Smysl je chránit business logiku před technickými detaily. Framework, databáze nebo payment provider se mohou změnit, ale core by kvůli tomu neměl být přepsán.

### 4.3 Ports

**Port** je rozhraní, přes které core komunikuje s okolím.

**Driving / primary ports** jsou vstupy do aplikace.

Příklady:

- `CreateOrderUseCase`
- `CancelOrderUseCase`
- `RegisterUserUseCase`

Volá je například:

- REST controller
- GraphQL resolver
- CLI command
- message consumer

**Driven / secondary ports** jsou rozhraní, která core potřebuje pro komunikaci ven.

Příklady:

- `OrderRepository`
- `PaymentGateway`
- `EmailSender`
- `FileStorage`
- `Clock`

Core zná pouze interface, ne konkrétní technologii.

### 4.4 Adapters

**Adapter** je konkrétní implementace portu.

Inbound adapters:

- REST controller
- GraphQL resolver
- CLI adapter
- message listener

Outbound adapters:

- `PostgresOrderRepository`
- `StripePaymentGateway`
- `SmtpEmailSender`
- `S3FileStorage`
- `SystemClock`

### 4.5 Příklad

Požadavek: **Create order.**

Core:

- `CreateOrderUseCase`
- `Order`
- `OrderRepository` interface
- `PaymentGateway` interface

Adapters:

- `RestOrderController`
- `PostgresOrderRepository`
- `StripePaymentGateway`

Závislosti:

- `RestOrderController` -> `CreateOrderUseCase`
- `CreateOrderUseCase` -> `OrderRepository` interface
- `CreateOrderUseCase` -> `PaymentGateway` interface
- `PostgresOrderRepository` implements `OrderRepository`
- `StripePaymentGateway` implements `PaymentGateway`

Důležité:

- `CreateOrderUseCase` neví, že repository je PostgreSQL.
- `CreateOrderUseCase` neví, že payment gateway je Stripe.

### 4.6 Dependency direction

Nejdůležitější pravidlo:

- **Dependencies point inward.**

To znamená:

- infrastructure depends on core
- core does not depend on infrastructure

Špatně:

- OrderService imports Spring Controller.
- Order entity imports JPA repository.
- Domain logic directly calls HTTP client.

Dobře:

- OrderService depends on PaymentGateway interface.
- StripePaymentGateway implements PaymentGateway.

### 4.7 Výhody

- dobrá testovatelnost business logic
- business logic je oddělená od frameworků
- snazší výměna databáze nebo externí služby
- snazší mockování v testech
- lepší maintainability
- lepší separation of concerns
- vhodné pro složitější domény

Příklad testu:

- `CreateOrderUseCase` lze testovat s fake `OrderRepository` a fake `PaymentGateway`.

Není potřeba spouštět:

- HTTP server
- real database
- real payment provider

### 4.8 Nevýhody

- vyšší počáteční komplexita
- více interfaces
- více mappingu mezi vrstvami
- může být overengineering pro jednoduchý CRUD
- vyžaduje disciplínu v dependency direction

Pro jednoduchou aplikaci typu `GET /products` a `POST /products` může být plná hexagonal architecture zbytečně složitá.

### 4.9 Hexagonal vs layered architecture

| Kritérium | Layered architecture | Hexagonal architecture |
|---|---|---|
| Hlavní princip | technické vrstvy | core oddělený od externích adapterů |
| Dependency direction | typicky shora dolů | dovnitř ke core |
| Business logic | service/domain layer | application/domain core |
| Database | spodní vrstva | externí adapter |
| API | horní vrstva | inbound adapter |
| Testability | dobrá | velmi dobrá pro core |
| Complexity | nižší | vyšší |

> [!note] Bezpečná formulace
> Layered architecture separates technical responsibilities into layers. Hexagonal architecture protects the business core from external technologies using ports and adapters.

### 4.10 Kdy použít hexagonal architecture

Vhodná pro:

- složitější business doménu
- systémy s dlouhou životností
- systémy s více externími integracemi
- systémy, kde je důležitá testovatelnost
- systémy, kde se může měnit infrastruktura

Méně vhodná pro:

- jednoduchý CRUD
- rychlý prototyp
- malý projekt bez složité business logiky

## 5. Microkernel architecture

### 5.1 Princip

**Microkernel architecture** rozděluje systém na:

- core system
- plug-in modules

Core obsahuje minimální základní funkcionalitu. Pluginy přidávají konkrétní rozšíření.

Příklad IDE:

- core editor
- plugin for Python
- plugin for Java
- plugin for Docker
- plugin for Git

Příklad webového prohlížeče:

- core browsing engine
- ad blocker extension
- password manager extension
- developer tools extension

### 5.2 Core system

Core by měl být stabilní a malý.

Obsahuje:

- základní runtime
- plugin registry
- plugin lifecycle
- core API
- shared services
- basic configuration

Core by neměl obsahovat každou specializovanou funkci. Pokud se core začne plnit volitelnými funkcemi, microkernel ztrácí smysl.

### 5.3 Plug-in modules

Pluginy poskytují rozšíření.

Příklady:

- syntax highlighting plugin
- payment provider plugin
- report generator plugin
- export plugin
- authentication provider plugin

Plugin komunikuje s core přes jasné plugin API. Toto API musí být stabilní, dobře dokumentované a verzované.

### 5.4 Plugin registry a lifecycle

Systém často potřebuje registry pluginů.

Registry řeší:

- které pluginy jsou nainstalované
- které pluginy jsou aktivní
- jakou verzi plugin má
- jaké capability plugin poskytuje
- jak plugin spustit

Lifecycle pluginu typicky řeší:

- installation
- activation
- deactivation
- update
- compatibility check
- uninstall

### 5.5 Výhody

- dobrá rozšiřitelnost
- core zůstává stabilní
- pluginy lze přidávat nebo odebírat
- dobré pro produktové platformy
- dobré pro systémy s variabilní funkcionalitou
- možnost třetích stran vytvářet rozšíření

### 5.6 Nevýhody

- složitý návrh plugin API
- contract versioning
- kompatibilita pluginů
- testování kombinací pluginů
- lifecycle management pluginů
- bezpečnost pluginů
- výkon kvůli nepřímým voláním

Velký problém:

- Pluginy mohou samostatně fungovat, ale v kombinaci způsobit chyby.

### 5.7 Kdy použít microkernel

Vhodné pro:

- IDE
- text editors
- web browsers
- workflow engines
- product platforms
- systémy s optional features
- systémy s third-party extensions

Méně vhodné pro:

- běžný CRUD backend
- jednoduchou webovou aplikaci
- systém bez požadavku na rozšiřitelnost pluginy

## 6. Comparison

| Style | Main idea | Strengths | Weaknesses | Typical use |
|---|---|---|---|---|
| Layered | Technical layers | Simple, clear, common | Boilerplate, layer coupling | Web/enterprise apps |
| Modular monolith | One app with modules | Low ops complexity, good boundaries | One deployment, discipline needed | Growing business apps |
| Hexagonal | Core + ports/adapters | Testability, framework independence | More abstractions | Complex domain apps |
| Microkernel | Core + plugins | Extensibility | Plugin API complexity | IDEs, browsers, platforms |

## 7. Vztah ke quality attributes

### 7.1 Maintainability

Podporují:

- layered architecture přes separation of concerns
- modular monolith přes module boundaries
- hexagonal architecture přes isolated core
- microkernel přes stable core a isolated plugins

Rizika:

- poor boundaries
- business logic in wrong places
- too many dependencies
- unclear plugin contracts

### 7.2 Testability

- **Layered architecture:** testování controllerů, services a repositories zvlášť.
- **Modular monolith:** testování modulů jako relativně samostatných částí.
- **Hexagonal architecture:** velmi dobrá testovatelnost core přes fake adapters.
- **Microkernel:** pluginy lze testovat samostatně, ale kombinace pluginů jsou těžké.

### 7.3 Scalability

- **Layered architecture:** typicky škáluje celý deployable unit.
- **Modular monolith:** také typicky škáluje celý systém.
- **Hexagonal architecture:** sama o sobě neřeší scaling, ale umožňuje lepší výměnu infrastruktury.
- **Microkernel:** škálování záleží na implementaci core a pluginů.

### 7.4 Flexibility / Modifiability

- **Modular monolith:** změny uvnitř modulu jsou jednodušší, pokud jsou boundaries dodrženy.
- **Hexagonal architecture:** výměna externí technologie je jednodušší díky portům.
- **Microkernel:** přidání nové funkcionality přes plugin je hlavní výhoda.
- **Layered architecture:** jednoduché změny jsou přehledné, ale větší use case často prochází více vrstvami.

> [!note] Důležité
> Žádný styl maximalizuje všechny quality attributes zároveň. Výběr stylu je vždy trade-off mezi jednoduchostí, testovatelností, škálovatelností, modifikovatelností a provozní komplexitou.

## 8. Typické antipatterny

### 8.1 Big Ball of Mud

Systém nemá jasnou strukturu.

Symptomy:

- všechno závisí na všem
- žádné vrstvy nebo moduly
- nejasné odpovědnosti
- změny jsou nebezpečné

Vzniká často ze špatného monolitu bez modularity.

### 8.2 God Object / God Service

Jedna třída nebo service dělá příliš mnoho věcí.

Příklad:

- ApplicationService handles users, orders, payments, notifications, reports and permissions.

Problém:

- nízká cohesion
- vysoký coupling
- těžké testování
- těžké změny

### 8.3 Spaghetti Code

Chaotická logika bez jasného flow.

Symptomy:

- mnoho `if/else` bez struktury
- kopírovaná logika
- nejasné dependencies
- těžké čtení

### 8.4 Lava Flow

Starý kód zůstává v systému, protože se ho nikdo nebojí upravit nebo odstranit.

Symptomy:

- nepoužívané moduly
- staré experimenty
- dead code
- nikdo neví, jestli se část systému ještě používá

### 8.5 Golden Hammer

Tým používá jeden oblíbený přístup na všechny problémy.

Příklad:

- Všechno musí být layered architecture.
- Všechno musí být hexagonal architecture.
- Všechno musí být microservices.

Správně:

- Styl se vybírá podle kontextu, constraints a quality attributes.

## 9. Mini examples: choosing architecture

### 9.1 Malá aplikace pro správu rezervací

Requirements:

- CRUD reservations
- login
- admin interface
- email notifications
- expected users: hundreds
- small team
- fast delivery

Dobrá volba:

- layered modular monolith

Proč:

- jednoduchý deployment
- jasná struktura
- rychlý vývoj
- nízká operational complexity
- dostatečné pro daný load

Zbytečně složité:

- microservices with Kubernetes, service mesh and distributed transactions

### 9.2 Platforma pro pluginy třetích stran

Requirements:

- stable core
- third-party extensions
- optional functionality
- plugin lifecycle
- versioned extension API

Dobrá volba:

- microkernel architecture

Proč:

- core zůstává stabilní
- funkce lze přidávat pluginy
- dobrá rozšiřitelnost

### 9.3 Systém se složitou doménou a mnoha externími integracemi

Requirements:

- complex business rules
- multiple payment providers
- database can change
- high testability required
- long-term maintainability

Dobrá volba:

- hexagonal architecture

Proč:

- business logic je chráněná před externími technologiemi
- payment provider lze vyměnit přes adapter
- core lze testovat bez reálné infrastruktury

---

## 10. Zkoušková odpověď: layered architecture

Layered architecture organizes a system into horizontal layers, where each layer has a specific technical responsibility. A typical web application has a presentation layer, application or service layer, business logic layer, data access layer and database layer.

The main advantage is separation of concerns. Controllers handle requests and responses, services implement use cases and business workflows, repositories handle persistence. This makes the system easier to understand, test and maintain.

The main disadvantages are possible boilerplate, performance overhead caused by passing requests through many layers, and coupling between layers. If the architecture is not followed strictly, business logic can leak into controllers or repositories. Layered architecture is suitable for CRUD, web and enterprise applications, but it may be insufficient for very large systems without additional modular boundaries.

---

## 11. Zkoušková odpověď: modular monolith

A modular monolith is a monolithic application divided into clear internal modules. It has one codebase and one deployment unit, but modules have explicit boundaries and responsibilities.

It combines the operational simplicity of a monolith with better maintainability and organization. Each module can represent a business capability, such as orders, payments or users. Modules should communicate through public interfaces and should not directly access each other's internal implementation or database tables.

The main advantage is lower operational complexity compared to microservices. Debugging, deployment and transactions are simpler. The main disadvantage is that all modules are still deployed together and independent scaling is limited. It also requires discipline, because module boundaries are not physically enforced by the network.

---

## 12. Zkoušková odpověď: hexagonal architecture

Hexagonal architecture, also called ports and adapters, separates the business core of an application from external technologies such as databases, web frameworks, message brokers and external APIs.

The core contains domain logic and application use cases. Ports are interfaces that define how the core communicates with the outside world. Adapters are concrete implementations for specific technologies, for example REST controllers, PostgreSQL repositories or payment provider clients.

The key rule is that dependencies point inward. The business core depends on abstractions, not on infrastructure. This improves testability, maintainability and flexibility. The disadvantage is higher initial complexity and more abstractions, so it can be overengineering for simple CRUD applications.

---

## 13. Zkoušková odpověď: microkernel architecture

Microkernel architecture splits the system into a minimal core and plug-in modules. The core provides basic functionality, plugin lifecycle and extension points. Plugins add optional or specialized functionality.

This architecture is suitable for systems that must be extensible, such as IDEs, text editors, browsers or product platforms. New functionality can be added without changing the core system.

The main advantages are extensibility, stable core and independent plugin development. The main disadvantages are complexity of plugin API design, versioning, compatibility, security and testing of plugin combinations.

---

## 14. Krátké shrnutí

- **Layered architecture:** technical layers, controller/service/repository, simple and common, good for enterprise CRUD apps.
- **Modular monolith:** one application with clear business modules, good alternative to premature microservices, requires discipline.
- **Hexagonal architecture:** core business logic in center, ports are interfaces, adapters are technology-specific implementations, dependencies point inward.
- **Microkernel:** minimal core, plugins add functionality, good for extensible platforms.
- **Main exam idea:** these styles are not outdated. They are often better than microservices when the system does not need distributed complexity.
