# Microservices Antipatterns

> **Zkouškový fokus:** umět poznat distributed monolith, shared database, wrong cuts, chatty services, no API versioning, no observability a organizační antipatterns.

## 1. Co je antipattern

**Antipattern** je opakující se špatné řešení opakujícího se problému.

Na první pohled může vypadat logicky, rychle nebo moderně, ale dlouhodobě způsobuje:

```text
vyšší coupling
nižší maintainability
horší testování
složitější deployment
nižší reliability
vyšší technický dluh
```

V microservices jsou antipatterns obzvlášť nebezpečné, protože chyba v návrhu se násobí distribuovanou komplexitou.

Důležitá zkoušková věta:

> Microservices do not remove bad design. They often amplify it by adding network, deployment and data consistency complexity.

---

## 2. Proč microservices antipatterns vznikají

Typické příčiny:

```text
microservices are adopted because of hype
domain boundaries are unclear
team has no DevOps maturity
services are split too early
services are split by technical layers
database ownership is not respected
API compatibility is ignored
observability is missing
organization keeps monolithic processes
```

Častá chyba:

```text
Tým vezme špatný monolit, rozdělí ho mechanicky na služby
a vznikne ještě horší distributed monolith.
```

---

## 3. Hlavní kategorie antipatterns

Microservices antipatterns lze rozdělit na:

```text
adoption antipatterns
technical antipatterns
data antipatterns
communication antipatterns
organizational antipatterns
operational antipatterns
```

# **Adoption antipatterns**

## 4. Microservices as the Goal

## 4.1 Popis

Tým považuje počet microservices za cíl.

Špatné myšlení:

```text
We need to have microservices.
The more services we have, the more modern our architecture is.
Success = number of services.
```

Správné myšlení:

```text
Goal is faster delivery, scalability, reliability or team autonomy.
Microservices are only one possible tool.
```

---

## 4.2 Proč je to problém

Pokud jsou microservices cílem samy o sobě, tým může vytvořit služby bez reálného důvodu.

Důsledky:

```text
too many services
unnecessary network communication
deployment overhead
harder testing
higher infrastructure cost
low business value
```

---

## 4.3 Lepší alternativa

```text
start from business goals
identify quality attributes
evaluate trade-offs
use modular monolith if sufficient
extract microservices only when there is a real need
```

Zkoušková věta:

> Microservices should be a means to achieve business and architectural goals, not the goal itself.

---

## 5. Microservices Magic Pixie Dust

## 5.1 Popis

Tým věří, že microservices automaticky vyřeší problémy systému.

Typické tvrzení:

```text
Our monolith is messy, so microservices will fix it.
Microservices will make us faster.
Microservices will make the system scalable.
```

---

## 5.2 Proč je to problém

Pokud tým neumí navrhnout dobrý monolit, často neumí navrhnout ani dobré microservices.

Výsledek:

```text
bad modularity becomes bad service boundaries
bad coupling becomes distributed coupling
bad data model becomes shared database
bad testing becomes worse testing
```

---

## 5.3 Lepší alternativa

Nejdřív opravit základní engineering practices:

```text
clean code
automated tests
CI/CD
modular design
clear ownership
monitoring
domain understanding
```

Až potom řešit microservices.

---

## 6.1 Popis


Microservices jsou pokročilá architektura, ne náhrada za základní disciplínu.

# **Technical service decomposition antipatterns**

## 9. Distributed Monolith

## 9.1 Popis

**Distributed monolith** je systém, který je fyzicky rozdělen na služby, ale logicky se chová jako jeden silně provázaný monolit.

Symptomy:

```text
services must be deployed together
a small change requires changes in many services
long synchronous call chains
shared database
cyclic dependencies
services cannot be tested independently
failure of one service breaks the whole system
```

---

## 9.2 Příklad

```text
Order Service calls Pricing Service.
Pricing Service calls Customer Service.
Customer Service calls Discount Service.
Discount Service calls Order Service.
```

Výsledkem je síťový chaos.

---

## 9.3 Proč je to problém

Distributed monolith má nevýhody obou světů:

```text
monolith-like coupling
microservice-like operational complexity
```

Tedy:

```text
těžký deployment
těžké testování
síťová latence
nízká autonomie týmů
žádné skutečné independent deployment
```

---

## 9.4 Lepší alternativa

```text
redesign service boundaries
decompose by business capability
reduce synchronous chains
use events where appropriate
remove shared database
define clear API contracts
make services independently deployable
```

Zkoušková věta:

> A distributed monolith has the complexity of microservices without their benefits.

---

## 10. Services by Technical Layer

## 10.1 Popis

Služby jsou rozděleny podle technických vrstev místo business capabilities.

Špatně:

```text
Controller Service
Business Logic Service
Repository Service
Database Service
Validation Service
```

---

## 10.2 Proč je to problém

Každý use case musí projít přes mnoho služeb.

Příklad:

```text
Client → Controller Service → Business Service → Repository Service → Database Service
```

To přidává:

```text
latency
network failure points
deployment coupling
distributed transaction problems
```

Ve skutečnosti je to layered monolith přes síť.

---

## 10.3 Lepší alternativa

Rozdělit podle business schopností:

```text
Order Service
Payment Service
Inventory Service
Customer Service
Shipping Service
```

Každá služba obsahuje vlastní:

```text
API
business logic
data access
data ownership
```

---

## 11. Microservice per Entity

## 11.1 Popis

Každá databázová entita dostane vlastní microservice.

Příklad:

```text
User Service
Address Service
Email Service
Phone Service
Role Service
Permission Service
```

---

## 11.2 Proč je to problém

Business use case často potřebuje mnoho entit.

Vzniká:

```text
chatty communication
too many services
too many joins through APIs
low cohesion
high coupling
```

---

## 11.3 Lepší alternativa

Služba má odpovídat business capability nebo bounded contextu, ne jedné tabulce.

Například:

```text
Customer Service
```

může vlastnit:

```text
customer
address
contact preferences
customer status
```

---

## 12. Microservice per Feature

## 12.1 Popis

Každá malá feature se stane samostatnou službou.

Příklad:

```text
CreateOrderService
CancelOrderService
UpdateOrderStatusService
OrderHistoryService
OrderEmailService
```

---

## 12.2 Proč je to problém

Služby jsou příliš jemné.

Důsledky:

```text
too many deployments
too many APIs
too many network calls
harder monitoring
low cohesion
high operational overhead
```

---

## 12.3 Lepší alternativa

Spojit související behavior do jedné business služby.

```text
Order Service
```

obsahuje:

```text
create order
cancel order
update order status
order history
```

---

## 13.1 Popis

Jedna microservice je příliš velká a obsahuje mnoho business capabilities.

Příklad:

```text
Commerce Service:
- products
- orders
- payments
- inventory
- shipping
- customers
- reports
```

## 13.2 Proč je to problém

Megaservice se chová jako monolith uvnitř microservice architecture.

Důsledky:

```text

too many responsibilities
multiple teams changing same service
slow tests
hard deployment
low cohesion
```

---

## 13.3 Lepší alternativa

Rozdělit podle business capabilities nebo bounded contexts:

```text
Product Catalog Service
Order Service
Payment Service
Inventory Service
Shipping Service
```

Pozor:

```text
nerozdělovat mechanicky
nejdřív pochopit doménové hranice
```

## 14.1 Popis

Služby jsou rozděleny podle špatných hranic.

Příklady špatných hranic:

```text
UI screens

team preferences instead of domain
```

---

## 14.2 Symptomy

```text
frequent cross-service transactions
services constantly call each other
many changes affect multiple services
duplicated business rules
unclear data ownership
```

---

## 14.3 Lepší alternativa

Použít:

```text
business capability analysis
DDD bounded contexts
event storming
domain expert collaboration
use case analysis
service responsibility mapping
```

# **Data antipatterns**

## 15. Shared Database / Shared Persistence

## 15.1 Popis

Více služeb přímo používá stejnou databázi nebo stejné tabulky.

Příklad:

```text
Order Service writes orders table.
Payment Service also writes orders table.
Reporting Service directly reads all production tables.
Inventory Service updates order_status column.
```

---

## 15.2 Proč je to problém

```text
hidden coupling
unclear ownership
schema changes become dangerous
services cannot evolve independently
independent deployment is broken
business rules can be bypassed
```

---

## 15.3 Lepší alternativa

```text
database per service
schema per service
strict table ownership
access through service API
domain events for data propagation
CQRS read models for queries
```

Zkoušková věta:

> Shared persistence is an antipattern because it couples services through the database and destroys service autonomy.

---

## 16. Data Ownership Confusion

## 16.1 Popis

Není jasné, která služba vlastní jaká data.

Příklad:

```text
Customer address is changed in Customer Service,
but Shipping Service also stores and modifies address.
```

---

## 16.2 Důsledky

```text
conflicting updates
inconsistent data
unclear source of truth
hard debugging
business rule duplication
```

---

## 16.3 Lepší alternativa

Pro každý datový koncept určit:

```text
owner service
source of truth
read-only replicas if needed
event propagation rules
update rules
```

Příklad:

```text
Customer Service is source of truth for customer profile.
Shipping Service may keep delivery address snapshot for shipment.
```

Důležité:

```text
snapshot není totéž jako ownership
```

---

## 17. Distributed Transactions Everywhere

## 17.1 Popis

Tým se snaží zachovat stejný model transakcí jako v monolitu a chce ACID transakce přes více služeb.

Příklad:

```text
one transaction across Order Service, Payment Service and Inventory Service
```

---

## 17.2 Proč je to problém

Distribuované transakce:

```text
increase coupling
reduce availability
are hard to operate
can block resources
do not fit many cloud-native systems
```

---

## 17.3 Lepší alternativa

Použít:

```text
Saga pattern
eventual consistency
compensating transactions
outbox pattern
idempotent operations
business process redesign
```

Někdy lepší otázka:

```text
Are service boundaries wrong if every operation requires distributed transaction?
```

---

## 18. Reporting Through Production Databases

## 18.1 Popis

Reporting nebo analytics přímo čte databáze všech služeb.

Problém:

```text
read load affects production
schema coupling
reporting breaks when services change schema
security risks
```

---

## 18.2 Lepší alternativa

```text
data warehouse
event-driven read model
CQRS projections
replicated reporting database
analytics pipeline
```

# **Communication antipatterns**

## 19. Chatty Services

## 19.1 Popis

Služby spolu komunikují příliš často a příliš jemně.

Příklad:

```text
Order Service calls Customer Service for each order item.
Order Service calls Product Service 50 times in one request.
```

---

## 19.2 Proč je to problém

```text
high latency
network overhead
more failure points
harder debugging
poor performance
```

---

## 19.3 Lepší alternativa

```text
coarser APIs
batch endpoints
local read models
API composition with limits
data replication through events
rethink service boundaries
```

---

## 20. Long Synchronous Call Chain

## 20.1 Popis

Jeden request synchronně volá mnoho služeb za sebou.

Příklad:

```text
Client
→ API Gateway
→ Order Service
→ Customer Service
→ Payment Service
→ Fraud Service
→ Inventory Service
→ Shipping Service
```

---

## 20.2 Proč je to problém

Celková availability klesá, protože request závisí na všech službách v řetězci.

Důsledky:

```text
high latency
cascading failures
timeouts
harder tracing
bad user experience
```

---

## 20.3 Lepší alternativa

```text
reduce chain length
use asynchronous workflow
use Saga
cache or replicate read data
combine strongly related responsibilities
use fallback where safe
```

---

## 21. No Timeouts

## 21.1 Popis

Služba volá jinou službu bez timeoutu.

Problém:

```text
caller waits indefinitely
threads/connections are exhausted
failure propagates
system becomes unavailable
```

---

## 21.2 Lepší alternativa

Každé síťové volání musí mít:

```text
timeout
retry policy if appropriate
circuit breaker for unstable dependency
fallback if possible
```

---

## 22. Retry Storm

## 22.1 Popis

Při chybě služby mnoho callerů začne agresivně retryovat.

Příklad:

```text
Payment Service is slow.
100 services retry immediately every 100 ms.
Payment Service becomes even more overloaded.
```

---

## 22.2 Lepší alternativa

```text
limited retries
exponential backoff
jitter
circuit breaker
rate limiting
retry only idempotent operations
```

---

## 23. Ignoring Idempotency

## 23.1 Popis

Služba neumí bezpečně zpracovat stejný request nebo event vícekrát.

Příklad:

```text
Payment event arrives twice.
System charges customer twice.
```

---

## 23.2 Lepší alternativa

```text
idempotency keys
unique business operation IDs
processed message table
deduplication
safe state transitions
```

Příklad:

```text
PaymentCaptured with event_id=123 is processed once.
Second delivery is ignored.
```

---

## 24. Event Soup

## 24.1 Popis

Systém má mnoho eventů bez jasné struktury, ownership a dokumentace.

Symptomy:

```text
nobody knows who consumes which event
event names are inconsistent
event schemas are undocumented
breaking changes in events
duplicate events with similar meaning
```

---

## 24.2 Proč je to problém

```text
hard debugging
hidden coupling
consumer breakage
inconsistent business reactions
```

---

## 24.3 Lepší alternativa

```text
event catalog
schema registry
event versioning
clear event ownership
consistent naming
consumer documentation
compatibility rules
```

---

## 25. Command/Event Confusion

## 25.1 Popis

Tým míchá commands a events.

Špatně:

```text
event: CreateOrder
event: SendEmail
event: ReserveInventory
```

To jsou commands, ne events.

Events by měly být fakta:

```text
OrderCreated
EmailSent
InventoryReserved
```

---

## 25.2 Proč je to problém

```text
unclear semantics
wrong coupling
harder workflow reasoning
consumers misunderstand message meaning
```

---

## 25.3 Lepší alternativa

```text
Command = request to do something
Event = fact that something happened
```

---

# **API and contract antipatterns**

## 26. Static Contract Pitfall / No API Versioning

## 26.1 Popis

API se mění bez semantického verzování, deprecation policy nebo compatibility rules.

Příklad:

```text
remove field from response
rename JSON property
change enum value
change Protobuf field meaning
```

Consumer se rozbije.

---

## 26.2 Proč je to problém

```text
services cannot be deployed independently
hidden runtime failures
coordination overhead
loss of trust in API
```

---

## 26.3 Lepší alternativa

```text
backward-compatible API evolution
OpenAPI / Protobuf contracts
contract testing
semantic versioning where suitable
deprecation period
consumer communication
```

---

## 27. Breaking Changes Without Coordination

## 27.1 Popis

Provider změní API a nasadí ho bez kontroly dopadu na consumery.

Důsledky:

```text
frontend breaks
other services fail
pipeline failures
production incidents
```

---

## 27.2 Lepší alternativa

```text
consumer-driven contract tests
API compatibility checks in CI
deprecation policy
communication with consumers
versioned APIs
feature flags for rollout
```

---

## 28. Leaky Service Abstraction

## 28.1 Popis

Služba odhaluje interní implementační detaily.

Příklad:

```text
API returns internal database IDs that should not be public.
API exposes internal table structure.
API requires clients to know internal status transitions.
```

---

## 28.2 Proč je to problém

```text
clients become coupled to internals
refactoring becomes hard
security risks
API becomes unstable
```

---

## 28.3 Lepší alternativa

```text
stable DTOs
public domain language
hide internal persistence model
clear API contract
```

---

## 29. Too Generic API

## 29.1 Popis

Služba nabízí příliš generické API místo business operations.

Špatně:

```text
POST /execute
POST /query
POST /updateEntity
```

Nebo:

```text
GenericDataService with arbitrary table and field names
```

---

## 29.2 Proč je to problém

```text
no clear contract
hard to validate
hard to secure
business meaning hidden
clients depend on internal data model
```

---

## 29.3 Lepší alternativa

Business-oriented APIs:

```text
POST /orders
POST /orders/{id}/cancel
POST /payments/{id}/capture
GET /customers/{id}/orders
```

# **Organizational antipatterns**

## 30. Common Ownership

## 30.1 Popis

Jedna centrální skupina vlastní všechny microservices.

Nebo nikdo přesně neví, kdo co vlastní.

---

## 30.2 Proč je to problém

Microservices mají podporovat team autonomy.

Pokud jeden tým vlastní vše:

```text
no real autonomy
bottleneck team
unclear responsibility
slow changes
low accountability
```

---

## 30.3 Lepší alternativa

```text
clear service ownership
team owns code, data, deployment, monitoring and incidents
documentation of ownership
on-call or support responsibility
```

---

## 31. Legacy Organization / Red Flag Law

## 31.1 Popis

Organizace zavede microservices, ale ponechá stejné procesy jako u monolitu.

Příklad:

```text
separate development team
separate QA team
separate operations team
central release board
manual deployment
long approval cycles
```

---

## 31.2 Proč je to problém

Microservices vyžadují:

```text
autonomous teams
DevOps responsibility
fast CI/CD
service ownership
automated testing
```

Pokud organizace zůstane monolitická, architektura bude také špatně fungovat.

---

## 31.3 Lepší alternativa

```text
cross-functional teams
you build it, you run it
automated delivery
clear ownership
product/service teams
```

---

## 32. No DevOps Tools

## 32.1 Popis

Organizace zavede microservices bez DevOps automatizace.

Chybí:

```text
CI/CD
automated tests
container registry
deployment automation
monitoring
logging
alerting
rollback
```

---

## 32.2 Proč je to problém

U jednoho monolitu lze někdy manuální deployment přežít.

U desítek služeb je to katastrofa.

Důsledky:

```text
slow releases
manual errors
inconsistent environments
hard rollback
low reliability
```

---

## 32.3 Lepší alternativa

Před microservices mít:

```text
automated build
automated tests
automated deployment
centralized logging
metrics
tracing
alerting
infrastructure as code
```

---

## 33. Too Many Technologies

## 33.1 Popis

Každý tým používá jiné technologie bez dobrého důvodu.

Příklad:

```text
10 services:
- Java Spring
- Node.js Express
- Python FastAPI
- Go
- Kotlin
- Ruby
- PostgreSQL
- MongoDB
- Cassandra
- Redis as primary DB
```

---

## 33.2 Proč je to problém

```text
harder operations
harder hiring
harder debugging
inconsistent monitoring

knowledge fragmentation
```

---

## 33.3 Lepší alternativa

```text
controlled technology diversity
golden path / paved road
approved stack
exceptions must be justified
shared platform support
```

Důležité:

```text
Polyglot persistence and polyglot programming can be useful,
but without governance it becomes chaos.
```

---

## 34.1 Popis

Každý tým vytváří službu od nuly.

Výsledek:

```text
different security setup
different CI/CD
```

## 34.2 Lepší alternativa

```text
metrics
health checks
security baseline

testing setup
API documentation
```

Výhoda:

```text

konzistentní provoz
méně chyb
```

# How to detect antipatterns

## 44. Questions to ask

Při revizi microservice architecture se ptát:

```text
Can each service be deployed independently?
Can each service be tested independently?
Does each service own its data?
Are service boundaries aligned with business capabilities?
Are there long synchronous call chains?
Are services sharing database tables?
Do we have clear API contracts?
Do we have contract tests?
Do we have logs, metrics and traces?
Does every service have an owner?
Can the system tolerate failure of one service?
```

Pokud je mnoho odpovědí “no”, pravděpodobně existují antipatterns.

## 48. Exam answer: microservices antipatterns

Microservices antipatterns are recurring bad solutions that appear when microservices are adopted or designed incorrectly. They are dangerous because microservices add distributed system complexity, so bad design becomes harder to operate, test and debug.

A common antipattern is the distributed monolith. In this case, services are physically separated, but they are logically tightly coupled. They must be deployed together, use long synchronous call chains or share the same database. This gives the system the complexity of microservices without independent deployment or team autonomy.

Another common antipattern is shared persistence, where several services directly access the same database tables. This breaks data ownership and makes independent evolution impossible. Other antipatterns include wrong service cuts, megaservice, microservice per feature, no API versioning, no DevOps tools, too many technologies and missing observability.

The solution is to design services around business capabilities or bounded contexts, give each service clear ownership of its data, use explicit API contracts, automate deployment, monitor services properly and design the system for failure.

---

## 49. Exam answer: distributed monolith

A distributed monolith is a system that is split into multiple services, but the services are so tightly coupled that they behave like one monolithic application. Typical symptoms are shared databases, long synchronous call chains, cyclic dependencies and the need to deploy many services together.

It is an antipattern because it combines disadvantages of both monoliths and microservices. It has the coupling of a monolith, but also the network, deployment and operational complexity of microservices.

To fix it, service boundaries should be redesigned around business capabilities, shared persistence should be removed, APIs should be made explicit and backward-compatible, and services should become independently deployable and observable.

---

## 50. Exam answer: shared persistence

Shared persistence is a microservice antipattern where multiple services directly access the same database tables. It creates hidden coupling between services, makes schema evolution dangerous and breaks the principle that each service owns its data.

The better approach is database per service or at least strict logical ownership of database schemas or tables. Other services should access the data through the owning service’s API or receive updates through events. For queries across multiple services, API Composition, CQRS read models or data replication through events can be used.

---

## 51. Exam answer: organizational antipatterns

Microservices require not only technical changes, but also organizational changes. An organizational antipattern appears when a company keeps monolithic processes while adopting microservices.

Examples include common ownership of all services by one team, no DevOps tools, manual deployment, no clear service ownership and too many technologies without governance. These problems prevent independent delivery and make microservices slow and unreliable.

A better approach is to use cross-functional teams, clear service ownership, CI/CD automation, shared platform standards and consistent observability and security practices.
