# 1. Web Services

## 1.1 Co je web service

**Web service** je softwarové rozhraní dostupné přes síť, které umožňuje komunikaci mezi aplikacemi.

Typicky:

```text
client sends request
service processes request
service returns response
```

Web services se používají pro:

```text
system integration
communication between frontend and backend
communication between microservices
integration with external providers
public APIs
enterprise systems
```

Příklady:

```text
payment API
shipping API
authentication API
weather API
banking API
school information system API
```

---

## 1.2 Hlavní přístupy k web services

Typické přístupy:

```text
SOAP web services
REST APIs
GraphQL APIs
gRPC APIs
Linked Data APIs
```

Ve starších enterprise systémech je běžný SOAP.

V moderních webových a microservice systémech je velmi běžný REST.

GraphQL se často používá pro komplexní frontendové dotazy.

gRPC se často používá pro efektivní service-to-service komunikaci.

# 2. SOAP

## 2.1 Co je SOAP

**SOAP** znamená **Simple Object Access Protocol**.

Je to protokol pro výměnu strukturovaných zpráv, typicky ve formátu XML.

SOAP zpráva je obvykle posílána přes HTTP, ale teoreticky může používat i jiné transporty.

SOAP je často spojován s enterprise systémy.

---

## 2.2 SOAP message structure

SOAP zpráva má typicky:

```text
Envelope
Header
Body
Fault
```

### Envelope

Kořenový element SOAP zprávy.

Říká, že zpráva je SOAP message.

### Header

Volitelná část pro metadata.

Může obsahovat:

```text
authentication
transaction information
routing
security metadata
```

### Body

Hlavní obsah zprávy.

Obsahuje request nebo response data.

### Fault

Chybová odpověď.

Používá se, když operace selže.

---

## 2.3 SOAP vlastnosti

SOAP je:

```text
XML-based
strictly structured
contract-oriented
enterprise-friendly
often used with WSDL
often used with WS-* standards
```

SOAP může podporovat rozšířené enterprise požadavky:

```text
security
transactions
reliable messaging
formal contracts
```

---

## 2.4 Výhody SOAP

```text
formal contract through WSDL
strong typing
standardized error format
enterprise features
tooling for client generation
good for strict integrations
```

---

## 2.5 Nevýhody SOAP

```text
verbose XML
higher overhead
less human-readable than simple REST JSON
more complex tooling
less popular for modern web/mobile APIs
```

---

# 3. WSDL and UDDI

## 3.1 WSDL

**WSDL** znamená **Web Services Description Language**.

Popisuje SOAP web service.

WSDL definuje:

```text
available operations
input messages
output messages
data types
service endpoint
binding / protocol details
```

Příklad významu:

```text
Client can generate code from WSDL and know how to call the service.
```

---

## 3.2 UDDI

**UDDI** znamená **Universal Description, Discovery and Integration**.

Je to registry pro publikaci a hledání web services.

Myšlenka:

```text
service provider publishes service
service consumer discovers service
consumer uses service description to call it
```

V praxi se UDDI používá méně často než původně očekáváno.

---

## 3.3 SOAP / WSDL / UDDI together

Zjednodušený model:

```text
SOAP = message protocol
WSDL = service contract / description
UDDI = service registry / discovery
```

# 4. REST

## 4.1 Co je REST

**REST** znamená **Representational State Transfer**.

Je to architektonický styl pro návrh webových API.

Důležité:

```text
REST is not just JSON over HTTP.
REST is an architectural style with constraints.
```

REST typicky pracuje s resources.

Příklad resources:

```text
/users
/orders
/products
/payments
```

---

## 4.2 REST constraints

REST constraints:

```text
client-server
stateless
cacheable
uniform interface
layered system
code on demand optional
```

### Client-server

Oddělení klienta a serveru.

```text
client = user interface / consumer
server = data and business logic provider
```

### Stateless

Každý request obsahuje všechny informace potřebné ke zpracování.

Server nemusí držet session state mezi requesty.

Výhoda:

```text
better scalability
simpler load balancing
```

### Cacheable

Response může být cacheovatelná.

Výhoda:

```text
better performance
lower server load
```

### Uniform interface

REST má jednotné rozhraní založené na:

```text
resources
HTTP methods
representations
status codes
links if HATEOAS is used
```

### Layered system

Klient nemusí vědět, jestli komunikuje přímo se serverem, nebo přes proxy, cache, API gateway nebo load balancer.

### Code on demand

Volitelné. Server může poslat klientovi spustitelný kód, například JavaScript.

---

## 4.3 HTTP methods

Typické REST operace:

```text
GET     read resource
POST    create resource or execute non-idempotent operation
PUT     replace resource
PATCH   partially update resource
DELETE  delete resource
```

Příklady:

```text
GET /orders/123
POST /orders
PUT /users/42
PATCH /orders/123/status
DELETE /products/10
```

---

## 4.4 Idempotency

**Idempotentní operace** znamená, že opakované provedení má stejný výsledný efekt.

Typicky idempotentní:

```text
GET
PUT
DELETE
```

Typicky ne-idempotentní:

```text
POST
```

Příklad:

```text
DELETE /orders/123
```

Pokud se zavolá dvakrát, výsledek je pořád:

```text
order does not exist
```

---

## 4.5 HTTP status codes

Důležité status codes:

```text
200 OK
201 Created
204 No Content
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Entity
500 Internal Server Error
503 Service Unavailable
```

Příklad:

```text
POST /orders returns 201 Created when order is created.
GET /orders/999 returns 404 Not Found if order does not exist.
POST /orders with invalid input returns 400 or 422.
```

---

## 4.6 REST resource naming

Dobré:

```text
GET /customers/123/orders
POST /orders
GET /orders/456
DELETE /orders/456
```

Špatné:

```text
GET /getOrder?id=456
POST /deleteOrder
POST /doPaymentThing
```

Doporučení:

```text
use nouns, not verbs
use plural resources
use HTTP methods for actions
use predictable URI structure
```

# 5. HATEOAS

## 5.1 Co je HATEOAS

**HATEOAS** znamená **Hypermedia As The Engine Of Application State**.

Myšlenka:

```text
response contains links to possible next actions
```

Příklad:

```json
{
  "id": 123,
  "status": "CREATED",
  "links": [
    { "rel": "self", "href": "/orders/123" },
    { "rel": "cancel", "href": "/orders/123/cancel" },
    { "rel": "payment", "href": "/orders/123/payment" }
  ]
}
```

---

## 5.2 Výhody HATEOAS

```text
API is more discoverable
client can follow links
server can guide allowed transitions
less hardcoded client knowledge
```

---

## 5.3 Nevýhody HATEOAS

```text
more complex implementation
not always used in practice
frontend clients often hardcode flows anyway
```

Ke zkoušce stačí vědět:

```text
HATEOAS is part of mature REST, but many practical APIs use only lower REST maturity levels.
```

# 6. Richardson Maturity Model

Richardson Maturity Model popisuje úroveň REST API.

```text
Level 0: HTTP as transport only
Level 1: resources
Level 2: HTTP methods
Level 3: hypermedia / HATEOAS
```

## 6.1 Level 0

Jedno endpoint API.

```text
POST /api
```

Body říká, co se má stát.

Je to spíš RPC over HTTP.

## 6.2 Level 1

API používá resources.

```text
/orders
/customers
/products
```

## 6.3 Level 2

API používá HTTP methods správně.

```text
GET /orders/123
POST /orders
DELETE /orders/123
```

## 6.4 Level 3

API používá hypermedia links.

Response obsahuje odkazy na další možné akce.

# 7. Content Negotiation and DTO

## 7.1 Content negotiation

HTTP umožňuje dohodnout representation format.

Headers:

```text
Accept
Content-Type
```

Příklad:

```text
Accept: application/json
Content-Type: application/json
```

Někdy API může podporovat více formátů:

```text
application/json
application/xml
text/csv
```

---

## 7.2 DTO in REST APIs

**DTO** znamená **Data Transfer Object**.

DTO odděluje API contract od interní entity.

Špatně:

```text
REST API returns database entity directly.
```

Problém:

```text
leaks internal fields
security risk
unstable API
coupling between persistence and API
```

Dobře:

```text
UserEntity is internal.
UserDto is returned by API.
```

Výhody:

```text
stable API contract
better security
control over serialized fields
clear request/response models
```

```text

```

## 8.2 Proč je OpenAPI důležité v architektuře

OpenAPI pomáhá:

```text
document APIs
generate clients

test APIs
validate requests/responses
check backward compatibility
communicate between frontend and backend
```

V microservices je OpenAPI důležité jako service contract.

---

## 8.3 Příklad OpenAPI fragmentu

```yaml

  /orders/{id}:
    get:
      summary: Get order by id
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        "200":
          description: Order found
        "404":
          description: Order not found
```

# 9. API Versioning

## 9.1 Proč verzovat API

API se vyvíjí.

Breaking change může rozbít klienty.

Breaking changes:

```text
remove endpoint
remove response field
rename field
change field type
make optional field required
change operation semantics
remove enum value
```

---

## 9.2 Typy versioningu

```text
URL versioning: /api/v1/orders
header versioning: API-Version: 1
media type versioning: application/vnd.company.v1+json
event schema versioning
```

---

## 9.3 Best practice

Nejlepší je preferovat backward-compatible changes.

Safe changes:

```text
add optional response field
add new endpoint
add optional request field
add new event type
```

Pokud breaking change nejde obejít:

```text
introduce new version
deprecate old version
give migration time
communicate with consumers
```

# 10. GraphQL

## 10.1 Co je GraphQL

**GraphQL** je query language pro API.

Klient si vybere přesně data, která potřebuje.

Příklad:

```graphql
{
  user(id: "123") {
    name
    email
    orders {
      id
      totalPrice
    }
  }
}
```

---

## 10.2 Problémy REST, které GraphQL řeší

### Over-fetching

REST endpoint vrátí více dat, než klient potřebuje.

### Under-fetching

Klient musí zavolat více endpointů, aby získal všechna data.

GraphQL umožňuje jeden přesný dotaz.

---

## 10.3 Výhody GraphQL

```text
client specifies needed fields
good for complex UI
reduces over-fetching and under-fetching
single endpoint
strong schema
good developer tooling
```

---

## 10.4 Nevýhody GraphQL

```text
complex caching
query complexity control needed
authorization at field level can be hard
risk of expensive queries
monitoring is less straightforward than REST endpoints
```

---

## 10.5 Kdy použít GraphQL

Vhodné:

```text
complex frontend
many different clients
client needs flexible data shape
data comes from many backend sources
```

Méně vhodné:

```text
simple CRUD API
strictly resource-oriented public API
team lacks experience
```

# 11. Web API Security

## 11.1 Základní témata

Web API security řeší:

```text
authentication
authorization
HTTPS/TLS
input validation
output encoding
rate limiting
CORS
CSRF where relevant
audit logging
secrets management
```

---

## 11.2 Authentication vs authorization

Authentication:

```text
Who are you?
```

Authorization:

```text
What are you allowed to do?
```

Příklad:

```text
User is authenticated with JWT.
Only admin can delete users.
```

---

## 11.3 Common mechanisms

```text
Basic Auth
API keys
JWT
OAuth2
OpenID Connect
mTLS
session cookies
```

### JWT

JWT je token obsahující claims.

Příklad claims:

```text
user id
roles
expiration
issuer
audience
```

Pozor:

```text
JWT must be validated:
signature, expiration, issuer, audience.
```

### OAuth2 / OpenID Connect

OAuth2 řeší autorizaci přístupu k resources.

OpenID Connect přidává identity layer nad OAuth2.

---

## 11.4 API Gateway security

API Gateway může řešit:

```text
TLS termination
token validation
rate limiting
routing
basic authorization checks
```

Ale:

```text
critical authorization should also be enforced in services.
```

Jinak může interní call obejít gateway.

Framework obvykle řeší:

```text
request handling
dependency injection
configuration

transactions
serialization
validation
testing support
```

Příklady:

```text

Jakarta EE
ASP.NET

```

---

## 12.2 Library vs framework

Library:

```text
your code calls library
```

Framework:

```text
framework calls your code
```

To souvisí s Inversion of Control.

Příklad:

```text
In Spring, framework creates controllers and services and calls them when HTTP request arrives.
```

---

## 12.3 Výhody frameworků

```text
faster development
standard structure
less boilerplate
security support
transaction support
integration support
testing utilities
community and ecosystem
```

---

## 12.4 Nevýhody frameworků

```text
framework lock-in
learning curve
hidden magic
version upgrade problems
performance overhead
architecture may be shaped by framework too much
```

Důležité:

```text
Architecture should not be only a consequence of framework defaults.
```

# 14. JPA, ORM and Transactions

## 14.1 JPA

**JPA** znamená **Java Persistence API**.

Je to standard pro mapování objektů na relační databázi.

Typické pojmy:

```text
Entity
EntityManager
Repository
Persistence Context
Transaction
Lazy Loading
JPQL
```

---

## 14.2 ORM

**ORM** znamená **Object-Relational Mapping**.

Mapuje:

```text
Java object ↔ database table row
class ↔ table
field ↔ column
relationship ↔ foreign key
```

Výhody:

```text
less SQL boilerplate
object-oriented data access
transaction integration
```

Nevýhody:

```text
N+1 query problem
lazy loading surprises
hidden SQL
performance tuning can be hard
object-relational impedance mismatch
```

---

## 14.3 Transactions

Transaction zajišťuje ACID vlastnosti:

```text
Atomicity
Consistency
Isolation
Durability
```

V monolitu s jednou DB jsou transakce jednodušší.

V microservices jsou transakce přes více služeb složité a často se používá:

```text
Saga
eventual consistency
compensating transactions
Outbox Pattern
```

# 17. Database Migrations: Flyway and Liquibase

## 17.1 Proč database migrations

Database schema se vyvíjí spolu s aplikací.

Bez migration toolu vzniká problém:

```text
manual SQL changes
different environments have different schema
hard rollback
no history of changes
```

---

## 17.2 Flyway

Flyway používá versioned migration scripts.

Příklad:

```text
V1__create_users_table.sql
V2__add_email_to_users.sql
V3__create_orders_table.sql
```

Flyway aplikuje migrace v pořadí.

---

## 17.3 Liquibase

Liquibase používá changelogs.

Mohou být ve formátu:

```text
XML
YAML
JSON
SQL
```

Podporuje:

```text
change sets
rollback metadata
database-independent changes
```

---

## 17.4 Architecture relevance

Database migrations jsou důležité pro:

```text
repeatable deployments
CI/CD
environment consistency
rollback planning
schema evolution
```

V microservices platí:

```text
each service should own and migrate its own schema
```

# 20. Semantic Web

## 20.1 Co je Semantic Web

**Semantic Web** je rozšíření webu, kde informace mají dobře definovaný význam, aby s nimi mohly lépe pracovat počítače i lidé.

Zjednodušeně:

```text
Web of documents → Web of data
```

Klasický web propojuje dokumenty.

Semantic Web propojuje věci a jejich významy.

---

## 20.2 Proč Semantic Web

Cíl:

```text
machine-readable meaning
data integration
shared vocabularies
reasoning over data
interoperability between datasets
```

Příklad:

```text
Instead of just a page about Prague,
data says:
Prague is a city.
Prague is capital of Czech Republic.
Czech Republic is a country.
```

# 22. RDF

## 22.1 Co je RDF

**RDF** znamená **Resource Description Framework**.

Je to model pro popis dat ve formě triples.

Triple:

```text
subject predicate object
```

Příklad:

```text
MonaLisa creator LeonardoDaVinci
Prague capitalOf CzechRepublic
Artur studiesAt CTU
```

---

## 22.2 RDF triple example

```text
subject:   wd:Q12418
predicate: dcterms:title
object:    "Mona Lisa"
```

## 28.3 MapReduce

MapReduce je programovací model pro distribuované zpracování dat.

Má dvě hlavní fáze:

```text

```

### Map

Map vezme input a vytvoří key-value pairs.

Příklad word count:

```text

world → 1
```

```text
map(file, text):
    for each word in text:
        emit(word, 1)

    emit(word, sum(counts))
```

# 33. Exam-style answer: Web services

Web services are network-accessible interfaces that allow applications to communicate. They are used for system integration, frontend-backend communication, microservices and external APIs. Common approaches include SOAP, REST, GraphQL and gRPC.

SOAP is an XML-based protocol with formal contracts described by WSDL. It is common in enterprise systems and supports strict contracts and WS-* standards, but it is verbose and more complex.

REST is an architectural style based on resources, HTTP methods and constraints such as client-server, stateless communication, cacheability, uniform interface and layered system. REST APIs are commonly documented using OpenAPI.

GraphQL allows clients to request exactly the data they need, which reduces over-fetching and under-fetching, but it adds complexity in caching, authorization and query control.

---

# 34. Exam-style answer: REST and OpenAPI

REST is an architectural style for web APIs. It models the system as resources identified by URIs and uses HTTP methods such as GET, POST, PUT, PATCH and DELETE. REST is based on constraints such as client-server, stateless communication, cacheability, uniform interface and layered system.

OpenAPI is a standard for describing REST APIs. It documents endpoints, parameters, request and response schemas, status codes and security requirements. It is useful for API documentation, client generation, testing and compatibility checking.

A good REST API uses resource-oriented URIs, correct HTTP methods, appropriate status codes, DTOs for stable API contracts and versioning or backward-compatible evolution when the API changes.

---

# 35. Exam-style answer: Frameworks

A framework is a software platform that provides structure and reusable mechanisms for application development. Unlike a library, where application code calls the library, a framework often controls the application flow and calls user code. This is related to Inversion of Control.

Frameworks such as Spring or Jakarta EE support common architectural concerns: dependency injection, web request handling, persistence, transactions, security, messaging, validation and testing. They improve productivity and standardization, but can also introduce framework lock-in, hidden complexity and upgrade problems.

From an architectural perspective, frameworks are useful tools, but the architecture should not be blindly dictated by framework defaults. Important architectural decisions should still be explicit.

---

# 36. Exam-style answer: Semantic Web and Linked Data

Semantic Web is an extension of the web where information has well-defined meaning, making it easier for computers and people to cooperate. It uses technologies such as RDF, OWL and ontologies.

RDF represents knowledge as triples: subject, predicate and object. OWL is used to define ontologies with classes, properties and logical relationships. Ontologies provide a shared conceptual model of a domain.

Linked Data is a method for publishing structured and interlinked data on the web. Its principles are to use URIs as names for things, use HTTP URIs, provide useful information using standards such as RDF and SPARQL, and include links to other URIs.

These technologies are relevant for semantic interoperability, knowledge representation, reasoning and integration of heterogeneous datasets.

---

# 37. Exam-style answer: Big Data

Big Data refers to data that is too large, fast or diverse for traditional processing approaches. It is often described using the 5V model: volume, velocity, variety, veracity and value.

Big Data systems must solve challenges such as data capture, storage, transmission, curation, analysis and visualization. Techniques include statistics, data mining, machine learning, optimization, visualization and stream processing.

Big Data platforms can be based on batch processing, stream processing or interactive analysis. Hadoop and MapReduce are examples of batch processing. MapReduce processes data using map and reduce phases. Apache Storm is an example of stream processing, where topologies of spouts and bolts process continuous data streams.

From an architecture perspective, Big Data systems require distributed storage, distributed computation, fault tolerance and coordination between processing and data units.
