## 1. Web Services

Web service je síťově dostupné rozhraní, přes které spolu komunikují aplikace.

Použití:

- frontend komunikuje s backendem;
- microservices komunikují mezi sebou;
- firma integruje externí systémy;
- veřejné API poskytuje data nebo operace;
- enterprise systémy propojují starší aplikace.

Web services jsou architektonicky důležité proto, že určují hranici mezi systémy. Jakmile aplikace komunikuje přes síťové API, začínají být podstatné contracty, verzování, bezpečnost, dokumentace a kompatibilita.

Typické přístupy:

- **SOAP:** formální XML protokol, často enterprise integrace.
- **REST:** architektonický styl nad resources a HTTP.
- **GraphQL:** klient si určuje přesný tvar dat.
- **gRPC:** efektivní service-to-service komunikace přes Protobuf.
- **Linked Data APIs:** publikování propojených dat s významem.

## 2. SOAP

SOAP znamená **Simple Object Access Protocol**. Je to protokol pro výměnu strukturovaných zpráv, typicky ve formátu XML.

SOAP zpráva má:

- **Envelope:** kořen zprávy;
- **Header:** metadata, například security nebo routing;
- **Body:** request nebo response data;
- **Fault:** standardizovaná chyba.

Vlastnosti SOAP:

- XML-based;
- silně strukturovaný;
- contract-oriented;
- často používá WSDL;
- dobře zapadá do enterprise integrací;
- může využívat WS-* standardy pro security, transactions nebo reliable messaging.

SOAP je vhodné chápat jako velmi formální integrační styl. Jeho síla je v přesně definovaném contractu a standardech, jeho slabina v těžkopádnosti pro jednodušší webová API.

Výhody:

- formální contract - WSDL přesně popisuje operace, zprávy a datové typy;
- strong typing - kontrakt jasně říká, jaká data služba očekává a vrací;
- tooling pro generování klientů - z contractu lze generovat klientské knihovny;
- standardní error handling - SOAP má formální mechanismus pro chyby;
- dobré pro přísné enterprise integrace - hodí se tam, kde jsou důležité standardy, governance a stabilní kontrakty.

Nevýhody:

- verbose XML - zprávy jsou větší a hůř čitelné než běžný JSON;
- vyšší overhead - parsing, obálky a standardy zvyšují náklady komunikace;
- složitější tooling - integrace je formálnější a těžší na rychlé prototypování;
- méně přirozené pro moderní web/mobile API - pro jednoduchá API bývá REST nebo GraphQL praktičtější.

> [!NOTE]
> SOAP není „špatný REST“. Je to jiný integrační styl: formálnější, těžší, ale vhodný tam, kde je potřeba silný contract a enterprise standardy.

## 3. WSDL and UDDI

**WSDL** znamená **Web Services Description Language**. Popisuje SOAP službu.

WSDL definuje:

- operations;
- input/output messages;
- data types;
- endpoint;
- binding a protocol details.

**UDDI** znamená **Universal Description, Discovery and Integration**. Je to registry pro publikaci a hledání web services. V praxi se používá méně, než se původně očekávalo.

Zjednodušeně:

| Pojem | Smysl |
|---|---|
| SOAP | message protocol |
| WSDL | service contract |
| UDDI | service registry |

## 4. REST

REST znamená **Representational State Transfer**. Je to architektonický styl pro webová API.

REST není jen “JSON over HTTP”. Důležité jsou constraints:

- **Client-server:** klient a server mají oddělené odpovědnosti.
- **Stateless:** každý request obsahuje vše potřebné.
- **Cacheable:** odpovědi mohou být cacheované.
- **Uniform interface:** resources, HTTP methods, representations, status codes.
- **Layered system:** klient nemusí vědět, jestli mluví přímo se serverem nebo přes gateway/proxy.
- **Code on demand:** volitelné, například JavaScript poslaný serverem.

Resources jsou typicky nouns:

- `/orders`;
- `/customers/123`;
- `/products/42/reviews`.

HTTP methods:

| Method | Typický význam |
|---|---|
| GET | čtení resource |
| POST | vytvoření nebo ne-idempotentní akce |
| PUT | nahrazení resource |
| PATCH | částečná změna |
| DELETE | odstranění |

Status codes:

- `200 OK`;
- `201 Created`;
- `204 No Content`;
- `400 Bad Request`;
- `401 Unauthorized`;
- `403 Forbidden`;
- `404 Not Found`;
- `409 Conflict`;
- `422 Unprocessable Entity`;
- `500 Internal Server Error`;
- `503 Service Unavailable`.

Dobré REST API používá resource-oriented URL, správné HTTP methods, DTOs, jasné status codes a dokumentovaný contract.

## 5. HATEOAS and Richardson Maturity Model

**HATEOAS** znamená **Hypermedia As The Engine Of Application State**. Response obsahuje odkazy na další možné akce.

Příklad významu:

- objednávka je `CREATED`;
- response obsahuje link na cancel a payment;
- klient nemusí hardcodovat všechny přechody.

V praxi mnoho REST API HATEOAS nepoužívá plně, ale zkouškově je dobré vědět, že patří k vyšší zralosti REST.

Richardson Maturity Model:

| Level | Význam |
|---|---|
| 0 | HTTP jako transport, jedno obecné endpoint API |
| 1 | resources |
| 2 | správné HTTP methods |
| 3 | hypermedia / HATEOAS |

## 6. DTO, Content Negotiation and OpenAPI

### DTO

DTO znamená **Data Transfer Object**. Odděluje API contract od interní entity.

Špatně:

- REST API vrací přímo database entity.

Problém:

- leak interních fieldů;
- security risk;
- nestabilní API;
- coupling mezi persistence a API.

Dobře:

- `UserEntity` je interní model;
- `UserDto` je veřejný API model.

### Content negotiation

HTTP headers:

- `Accept`;
- `Content-Type`.

Příklad:

- klient chce `application/json`;
- server odpoví JSON reprezentací.

### OpenAPI / Swagger

OpenAPI je standard pro popis REST API.

Popisuje:

- endpoints;
- HTTP methods;
- path/query parameters;
- request/response bodies;
- schemas;
- status codes;
- security requirements.

Architektonický význam:

- API dokumentace;
- generování klientů;
- compatibility checking;
- contract mezi týmy;
- testování API.

## 7. API Versioning

API se vyvíjí a breaking changes mohou rozbít klienty.

Breaking changes:

- odstranění endpointu;
- odstranění response fieldu;
- přejmenování fieldu;
- změna typu;
- povinný field místo volitelného;
- změna významu operace.

Možnosti versioningu:

- URL: `/api/v1/orders`;
- header: `API-Version: 1`;
- media type: `application/vnd.company.v1+json`;
- schema version u eventů.

Best practice:

- preferovat backward-compatible changes;
- verzi zavést, když breaking change nejde obejít;
- starou verzi deprecovat s migračním obdobím.

## 8. GraphQL

GraphQL je query language pro API. Klient si vybere přesně data, která potřebuje.

Řeší:

- **Over-fetching:** REST endpoint vrací víc dat, než klient potřebuje.
- **Under-fetching:** klient musí volat mnoho endpointů pro jednu obrazovku.

Výhody:

- flexibilní tvar odpovědi;
- dobré pro komplexní UI;
- strong schema;
- dobré developer tooling.

Nevýhody:

- složitější cache;
- nutnost kontrolovat query complexity;
- field-level authorization může být těžká;
- monitoring není tak přímočarý jako u REST endpointů.

Kdy použít:

- mnoho různých klientů;
- komplexní frontend;
- data z více backend zdrojů.

Kdy spíš ne:

- jednoduché CRUD API;
- veřejné resource-oriented API;
- tým bez zkušeností s GraphQL.

## 9. Web API Security

Základní pojmy:

- **Authentication:** kdo jsi?
- **Authorization:** co smíš dělat?

Mechanismy:

- Basic Auth;
- API keys;
- session cookies;
- JWT;
- OAuth2;
- OpenID Connect;
- mTLS.

Důležité oblasti:

- HTTPS/TLS;
- input validation;
- output encoding;
- rate limiting;
- CORS;
- CSRF u cookie-based aplikací;
- audit logging;
- secrets management.

API Gateway může řešit TLS termination, token validation, rate limiting a routing. U citlivých operací ale nemá být jedinou autorizační vrstvou. Služby musí chránit kritickou business logiku samy.

## 10. Frameworks in Software Architecture

Framework je softwarová platforma, která dává aplikaci strukturu a poskytuje hotové mechanismy.

Framework typicky řeší:

- request handling;
- dependency injection;
- configuration;
- security;
- data access;
- transactions;
- serialization;
- validation;
- testing support.

Library vs framework:

| Library | Framework |
|---|---|
| aplikace volá knihovnu | framework volá aplikační kód |
| větší kontrola v aplikaci | Inversion of Control |
| menší strukturální vliv | větší architektonický vliv |

Výhody frameworků:

- rychlejší vývoj;
- standardní struktura;
- méně boilerplate;
- security a transaction support;
- ekosystém a tooling.

Nevýhody:

- framework lock-in;
- hidden magic;
- learning curve;
- upgrade problémy;
- riziko, že architektura slepě kopíruje framework defaults.

> **Důležitá věta:** Framework supports architecture, but should not replace architectural thinking.

## 12. JPA, ORM and Transactions

**JPA** znamená **Java Persistence API**. Je to standard pro mapování objektů na relační databázi.

Typické pojmy:

- Entity;
- EntityManager;
- Repository;
- Persistence Context;
- Transaction;
- Lazy Loading;
- JPQL.

**ORM** znamená **Object-Relational Mapping**.

Mapuje:

- class na table;
- object na row;
- field na column;
- relationship na foreign key.

Výhody ORM:

- méně SQL boilerplate;
- object-oriented data access;
- integrace s transakcemi.

Nevýhody ORM:

- N+1 query problem;
- lazy loading surprises;
- hidden SQL;
- performance tuning;
- object-relational impedance mismatch.

Transakce zajišťuje ACID:

- Atomicity;
- Consistency;
- Isolation;
- Durability.

V monolitu s jednou databází jsou transakce jednodušší. V microservices se často používá Saga, eventual consistency, compensating transactions a Outbox.

## 13. Messaging and Integration

Messaging umožňuje asynchronous communication.

JMS znamená **Java Message Service**. Je to Java API pro queues, topics a publish-subscribe integraci.

Queue vs topic:

| Typ | Význam |
|---|---|
| Queue | zprávu zpracuje jeden consumer |
| Topic | zprávu může zpracovat více subscriberů |

Výhody messagingu:

- loose coupling;
- asynchronous processing;
- load leveling;
- lepší resilience;
- enterprise integration.

Nevýhody:

- eventual consistency;
- složitější debugging;
- message ordering;
- duplicate messages;
- potřeba idempotent consumers.

## 14. Database Migrations

Database schema se vyvíjí spolu s aplikací. Bez migration toolu vznikají rozdíly mezi dev, test a production prostředím.

### Flyway

Používá versioned SQL migrations:

- `V1__create_users_table.sql`;
- `V2__add_email_to_users.sql`;
- `V3__create_orders_table.sql`.

### Liquibase

Používá changelogs ve formátu XML, YAML, JSON nebo SQL. Podporuje change sets a rollback metadata.

Architektonický význam:

- repeatable deployments;
- audit historie změn;
- CI/CD;
- konzistence prostředí;
- rollback planning.

V microservices platí: každá služba migruje vlastní schema.

## 17. Semantic Web

Semantic Web je rozšíření webu, kde informace mají dobře definovaný význam.

Zjednodušeně:

## 18. Ontologies

Ontology je explicitní popis sdíleného významu v doméně.

Popisuje:

- concepts;
- classes;
- relations;
- properties;
- constraints;
- význam termínů.

Příklad univerzitní domény:

- Student;
- Course;
- Teacher;
- University;
- enrolledIn;
- teaches.

Typy:

- **Top ontology:** obecné pojmy jako entity, event, object, process.
- **Domain ontology:** pojmy pro konkrétní doménu, například medicína nebo education.

Ontologie pomáhají při integraci dat, reasoning a sjednocení slovníku mezi systémy.

## 19. RDF and OWL

### RDF

RDF znamená **Resource Description Framework**. Data reprezentuje jako triples:

- subject;
- predicate;
- object.

Příklady:

- Prague capitalOf CzechRepublic;
- Student enrolledIn Course;
- MonaLisa creator LeonardoDaVinci.

RDF je vhodné pro knowledge graphs, propojení dat a semantic queries.

### OWL

OWL znamená **Web Ontology Language**. Umožňuje bohatší popis ontologií než základní RDF.

Může definovat:

- classes;
- properties;
- equivalent classes;
- restrictions;
- logical relationships.

OWL je důležité pro reasoning. Například systém může odvodit, že člověk s dítětem je parent, pokud to ontology definuje.

## 21. Linked Data

Linked Data je metoda publikování strukturovaných a propojených dat na webu.

Staví na:

- URI;
- HTTP;
- RDF;
- SPARQL.

Principy:

1. Používat URI jako jména věcí.
2. Používat HTTP URI, aby je šlo dohledat.
3. Při dohledání URI poskytnout užitečné informace pomocí RDF/SPARQL.
4. Přidávat odkazy na další URI.

Příklady Linked Open Data:

- Wikidata;
- DBpedia;
- government open data;
- geografická data.

Architektura Linked Data aplikace může obsahovat data acquisition, integration, cleansing, vocabulary mapping, triple store, SPARQL endpoint a visualization.

## 24. Hadoop and MapReduce

Apache Hadoop je platforma pro distribuované ukládání a zpracování velkých dat.

Typické části:

- **HDFS:** distributed file system;
- **MapReduce:** batch processing model;
- **YARN:** resource management;
- **HBase:** NoSQL součást Hadoop ecosystem.

HDFS vlastnosti:

- data se dělí na bloky;
- bloky se replikují mezi nodes;
- systém je fault tolerant;
- hodí se pro velké soubory.

MapReduce má fáze:

- **Map:** input se převede na key-value pairs.
- **Shuffle and sort:** hodnoty se seskupí podle klíče.
- **Reduce:** hodnoty se agregují.

Příklad word count:

- map vytvoří `word -> 1`;
- shuffle seskupí stejné words;
- reduce sečte počty.

Výhody:

- distributed processing;
- fault tolerance;
- dobré pro velké batch jobs.

Nevýhody:

- vysoká latence;
- nevhodné pro real-time processing;
- rigidní model pro některé úlohy.

## 25. Apache Storm

Apache Storm je systém pro stream processing. Zpracovává data kontinuálně.

Použití:

- real-time analytics;
- event processing;
- monitoring;
- stream transformations.

Typické prvky:

- **Nimbus:** master node, koordinuje topology.
- **Supervisor:** běží na worker nodes.
- **Worker:** proces zpracovávající část topology.
- **ZooKeeper:** koordinace clusteru.
- **Topology:** graf výpočtu běžící kontinuálně.
- **Spout:** zdroj streamu.
- **Bolt:** zpracování streamu.

Spout může číst například Kafka topic. Bolt může filtrovat, transformovat, agregovat, joinovat nebo zapisovat do databáze.

## 26. Principles of Big Data Architecture

Neexistuje jedna Big Data architektura pro všechny případy. Volba závisí na objemu dat, latenci, typu dat, consistency requirements, nákladech a schopnostech týmu.

Důležité principy:

- **Bring computation to data:** u velkých dat je drahé přesouvat data.
- **Distributed storage and processing:** škálování přes více uzlů.
- **Fault tolerance:** výpadek uzlu nesmí zastavit celý systém.
- **Partitioning:** data i výpočet se rozdělí.
- **Batch vs stream:** historická analýza vs reakce v reálném čase.

## 28. Krátké shrnutí

- SOAP je XML protokol s formálním WSDL contractem.
- REST je architektonický styl založený na resources, HTTP methods a stateless komunikaci.
- OpenAPI dokumentuje REST API a podporuje contracts mezi týmy.
- GraphQL řeší flexibilní dotazy pro komplexní UI, ale komplikuje cache a authorization.
- Frameworky dávají aplikaci strukturu a podporují DI, security, persistence, transactions a testing.
- JPA/ORM zjednodušuje persistence, ale může skrývat SQL a způsobit N+1 problém.
- Messaging podporuje asynchronous communication, ale vyžaduje idempotency a monitoring.
- Semantic Web pracuje s významem dat pomocí RDF, OWL a ontologií.
- Linked Data publikuje propojená data přes URI, HTTP, RDF a SPARQL.
- Big Data řeší škálu: volume, velocity, variety, veracity a value.
