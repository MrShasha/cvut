# 2. Nejkratší záchytný souhrn před zkouškou

## 2.1 Co je software architecture

→ Detaily: [[1. Software Architecture Basics#Co je software architecture]]

**Software architecture** je vysokourovňová struktura systému: hlavní části, jejich odpovědnosti, vztahy, komunikace, nasazení a způsob, jak systém plní funkční i kvalitativní požadavky.

Bezpečná odpověď:

> Software architecture describes the high-level structure of a system: its main components, their responsibilities, communication, deployment and the architectural decisions that support required quality attributes.

**Lidský překlad:** Architektura není „jak přesně napíšu metodu“, ale „jak systém jako celek drží pohromadě“.

**Co nezapomenout:**
- architektura je most mezi requirements a code,
- nejvíc ovlivňuje quality attributes,
- vždy je o trade-offs,
- není univerzálně dobrá/špatná bez kontextu.

> [!tip] Tip ke zkoušce
> U definice rovnou přidej příklad: „U e-shopu architektura říká, že frontend volá backend přes REST, backend je layered/modular, data jsou v DB, soubory v object storage a deployment běží v kontejnerech.“

---

## 2.2 Architecture vs Design

→ Detaily: [[1. Software Architecture Basics#Architecture vs Design]]

| Architecture | Design |
|---|---|
| komponenty, služby, vrstvy, deployment | třídy, metody, rozhraní |
| mění se pomaleji | mění se častěji |
| má velký dopad na quality attributes | řeší lokální implementační problém |
| příklad: microservices, layered, message broker | příklad: Strategy, Factory, Repository |

Bezpečná odpověď:

> Architecture is about high-level structure and decisions with system-wide impact. Design is more detailed and focuses on classes, interfaces, methods and local implementation patterns. The boundary is not always sharp, but architecture usually has stronger impact on quality attributes and long-term evolution.

> [!warning] Častá chyba
> Neříkej, že architecture je „jen diagram“ a design je „jen kód“. Obojí jsou rozhodnutí, liší se hlavně **úrovní dopadu**.

## 2.3 Quality attributes a quality requirements

→ Detaily: [[03. Quality Attributes and Architecture Metrics]]

**Quality attribute** je kvalitativní vlastnost systému: performance, scalability, availability, security, maintainability, testability, modifiability, usability, interoperability.

**Quality requirement** je konkrétní měřitelný požadavek:

- Špatně: `System must be fast.`
- Dobře: `95 % of search requests must finish under 300 ms under 500 concurrent users.`

**Struktura dobrého quality attribute scenario:**

| Část | Význam | Příklad |
|---|---|---|
| Stimulus source | kdo/odkud událost přijde | end user |
| Stimulus | co se stane | user sends search request |
| Environment | za jakých podmínek | normal operation, 500 concurrent users |
| Artifact | ovlivněná část systému | Search API and database |
| Response | jak má systém reagovat | returns results |
| Response measure | jak změříme úspěch | 95 % under 300 ms |

> [!tip] Tip ke zkoušce
> Když se tě zeptají na kvalitu architektury, nezačni „microservices jsou lepší“. Začni: „Kvalita se hodnotí vůči quality attributes v konkrétním kontextu.“

## 2.4 ATAM a hodnocení architektury

→ Detaily: [[04. Architecture Evaluation and ATAM]]

**ATAM = Architecture Trade-off Analysis Method.**

Smysl:
- spojit business drivers,
- quality attributes,
- scénáře,
- architektonická rozhodnutí,
- rizika a trade-offs.

Výstupy ATAM:

| Výstup | Co znamená |
|---|---|
| Risks | rozhodnutí může ohrozit požadovaný atribut |
| Non-risks | rozhodnutí je pro daný scénář v pořádku |
| Sensitivity points | místo, kde malá změna silně ovlivní kvalitu |
| Trade-off points | rozhodnutí zlepšuje jeden atribut a zhoršuje jiný |
| Prioritized scenarios | nejdůležitější scénáře podle stakeholderů |

Bezpečná odpověď:

> ATAM is a scenario-based method for evaluating whether architecture supports important quality attributes and business goals. It identifies risks, non-risks, sensitivity points and trade-off points.

**Příklad trade-offu:** caching zlepší performance, ale může zhoršit consistency a zvýšit složitost invalidace.

## 2.5 Kruchten's 4+1 View Model

→ Detaily: [[02. Kruchten's 4+1 View Model]]

| View | Otázka | Typicky zajímá | Diagramy |
|---|---|---|---|
| Logical | Co systém dělá? | analytik, doménový expert | class/component/state |
| Process | Jak běží v runtime? | architekt, DevOps | sequence/activity/communication |
| Development | Jak je organizovaný kód? | vývojáři | package/component |
| Physical | Kde systém běží? | DevOps, infrastruktura | deployment diagram |
| Scenarios | Jak to funguje na use case? | všichni | sequence/use case |

Bezpečná odpověď:

> 4+1 View Model describes architecture from several complementary perspectives: logical, process, development and physical view. The +1 scenario view validates and connects the other views using important use cases.

> [!tip] Jak si to pamatovat
> Logical = význam, Process = běh, Development = kód, Physical = infrastruktura, Scenarios = průchod use casem.

## 2.6 Architectural style, architectural pattern, design pattern

→ Detaily: [[05. Architectural Styles Overview#Architectural style vs architectural pattern vs design pattern]]

| Pojem | Úroveň | Příklady |
|---|---|---|
| Architectural style | tvar celého systému | layered, microservices, client-server, event-driven |
| Architectural pattern | řešení architektonického problému | API Gateway, CQRS, Saga, Circuit Breaker |
| Design pattern | řešení na úrovni tříd/objektů | Factory, Strategy, Adapter, Observer |

Bezpečná odpověď:

> Architectural style defines the overall structural organization of the system. Architectural pattern is a reusable solution to a recurring architectural problem. Design pattern solves recurring implementation problems at class or object level.

## 2.7 Layered architecture

→ Detaily: [[06. Layered, Modular Monolith, Hexagonal and Microkernel Architecture#Layered architecture]]

**Princip:** systém je rozdělen do horizontálních vrstev podle technické odpovědnosti.

Typicky:

```text
Controller -> Service -> Repository -> Database
```

**Výhody:** jednoduchost, známý styl, dobrá separace odpovědností, vhodné pro CRUD/enterprise, snadný onboarding.

**Nevýhody:** boilerplate, anemic domain model, změny často procházejí více vrstvami, omezené nezávislé škálování, cross-cutting concerns.

**Strict layering:** vrstva smí volat jen bezprostředně nižší.

**Relaxed layering:** lze přeskočit vrstvu, ale roste riziko porušení odpovědností.

> [!warning] Častá chyba
> Layered architecture není automaticky čistá. Pokud controller obsahuje business logiku a service jen přeposílá data, máš vrstvy jen podle názvů složek.

---

## 2.8 Modular monolith

→ Detaily: [[06. Layered, Modular Monolith, Hexagonal and Microkernel Architecture#Modular Monolith]]

**Modular monolith** je jedna aplikace a jeden deployment, ale s jasnými interními business moduly.

Příklad:

```text
Order module
Payment module
Inventory module
Customer module
Notification module
```

Každý modul má vlastní public API, business logiku, data access a testy.

**Smysl:** dostaneš jednoduchost monolitu, ale lepší hranice než u chaotického monolitu.

**Výhody:** jednoduchý deployment, jednodušší debugging, nižší provozní komplexita, lepší maintainability než Big Ball of Mud.

**Nevýhody:** stále jeden deployable unit, nutná disciplína, omezené nezávislé škálování.

> [!tip] Dobrá věta
> Modular monolith is often a better starting point than microservices because it preserves simple deployment while enforcing clear business boundaries.

---

## 2.9 Hexagonal architecture / Ports and Adapters

→ Detaily: [[06. Layered, Modular Monolith, Hexagonal and Microkernel Architecture#Hexagonal Architecture / Ports and Adapters]]

**Princip:** doména je uprostřed a okolní technologie jsou připojené přes porty a adaptéry.

- **Port** = rozhraní, které doména potřebuje nebo poskytuje.
- **Adapter** = konkrétní napojení technologie: REST controller, database adapter, message broker adapter, payment gateway adapter.

Směr závislostí:

```text
Adapters -> Ports -> Application/Domain core
```

**Výhody:** dobrá testovatelnost, izolace domény od frameworků, snadnější výměna DB/API/message brokeru.

**Nevýhody:** více abstrakcí, overkill pro jednoduché CRUD, vyžaduje disciplínu.

> [!tip] Příklad
> Payment service v doméně nezná Stripe SDK. Zná jen `PaymentGatewayPort`. `StripePaymentAdapter` je detail infrastruktury.

---

## 2.10 Microkernel architecture

→ Detaily: [[06. Layered, Modular Monolith, Hexagonal and Microkernel Architecture#Microkernel Architecture]]

**Microkernel** má malé jádro a rozšiřitelné pluginy.

Příklad:
- IDE,
- browser,
- workflow engine,
- enterprise produkt s custom moduly.

**Výhody:** vysoká rozšiřitelnost, plugin ecosystem, izolace core funkcí.

**Nevýhody:** složitost plugin API, versioning pluginů, bezpečnost pluginů, kompatibilita.

Bezpečná odpověď:

> Microkernel architecture separates a minimal core system from plug-in modules. It is useful when the system must be extensible and customizable, but it requires stable plugin contracts and careful versioning.

---

## 2.11 Distributed architecture

→ Detaily: [[07. Distributed Styles - Client-Server, SOA, Event-Driven Architecture and Microservices]]

**Distributed architecture** znamená, že části systému běží v různých procesech/uzlech a komunikují přes síť.

Přínosy:
- independent scalability,
- independent deployment,
- fault isolation,
- team autonomy,
- technology flexibility.

Cena:
- latency,
- partial failures,
- timeouts,
- retries,
- eventual consistency,
- distributed tracing,
- API versioning,
- security between services.

> [!warning] Klíčová věta
> V monolitu je volání metoda. V distribuovaném systému je volání síťová operace, která může selhat, trvat dlouho nebo proběhnout vícekrát.

---

## 2.12 REST, SOAP, GraphQL a OpenAPI

→ Detaily: [[07. Distributed Styles - Client-Server, SOA, Event-Driven Architecture and Microservices#RESTful distributed systems]] a [[12. Supporting Topics - Web Services, Frameworks, Semantic Web and Big Data]]

| Přístup | Princip | Kdy se hodí | Slabiny |
|---|---|---|---|
| SOAP | formální XML protokol, WSDL, WS-* | enterprise integrace, silné contracty | verbose, těžkopádnější |
| REST | resources + HTTP methods + stateless | běžná web/mobile API | někdy over/under-fetching |
| GraphQL | klient si řekne přesný tvar dat | komplexní UI, více klientů | složitější cache, query complexity |
| OpenAPI | strojově čitelný popis REST API | dokumentace, contract testing, generování klientů | není architektura sama o sobě |

**REST constraints:** client-server, stateless, cacheable, uniform interface, layered system, code on demand optional.

**Richardson Maturity Model:**

| Level | Význam |
|---|---|
| 0 | RPC over HTTP |
| 1 | resources |
| 2 | HTTP methods |
| 3 | HATEOAS |

## 2.13 Event-driven architecture

→ Detaily: [[07. Distributed Styles - Client-Server, SOA, Event-Driven Architecture and Microservices#Event-Driven Architecture]]

**Princip:** komponenty nevolají přímo jedna druhou, ale publikují a konzumují události.

Příklad:

```text
Order Service -> OrderCreated event -> Payment / Inventory / Notification
```

**Výhody:** loose coupling, asynchronní zpracování, škálovatelnost, dobré pro integrace.

**Nevýhody:** eventual consistency, složitější debugging, ordering, duplicate messages, idempotence, monitoring.

**Choreography:** služby reagují na eventy bez centrálního řídicího procesu.

**Orchestration:** centrální orchestrator řídí workflow.

> [!tip] Komise ráda slyší
> Event-driven architecture zlepšuje loose coupling, ale komplikuje konzistenci a pozorovatelnost systému.

## 2.14 Microservices vs Monolith

→ Detaily: [[09. Microservices vs Monolith]]

| Kritérium | Monolith | Microservices |
|---|---|---|
| Deployment | jednoduchý, jeden artifact | nezávislý deployment služeb |
| Debugging | jednodušší stack trace | distributed tracing, correlation IDs |
| Testing | jednodušší E2E | unit + integration + contract + E2E |
| Transactions | jednodušší ACID | Saga, eventual consistency |
| Scaling | typicky celý systém | jednotlivé služby |
| Team autonomy | horší u velkých týmů | lepší při dobrých boundaries |
| Operational complexity | nižší | vyšší |

**Microservice premium:** microservices dávají smysl až tehdy, když přínos nezávislého deploymentu/škálování/team ownership převýší distribuovanou komplexitu.

Bezpečná odpověď:

> Microservices are not automatically better than monoliths. They are useful when independent deployment, scalability and team autonomy are worth the cost of distributed systems complexity.

## 2.15 Microservices patterns

→ Detaily: [[10. Microservices Patterns and Best Practices]]

| Pattern | Co řeší | Jedna věta ke zkoušce |
|---|---|---|
| Database per Service | data ownership | každá služba vlastní svá data a ostatní k nim jdou přes API/eventy |
| Saga | business transakce přes více služeb | série lokálních transakcí + kompenzace |
| Outbox | atomické DB změny + event | event se uloží do outbox tabulky ve stejné DB transakci |
| CQRS | oddělení write/read modelu | command side mění stav, query side má read model |
| Event Sourcing | stav jako historie eventů | aktuální stav se rekonstruuje z událostí |
| API Gateway | jednotný vstup | routing, auth, rate limiting, agregace |
| Circuit Breaker | ochrana před závislostí | po selhání dependency se volání dočasně zastaví |
| Bulkhead | izolace selhání | oddělené resources pro různé části systému |
| Service Discovery | nalezení služby | klient/gateway zjistí aktuální instance služby |
| Contract Testing | kompatibilita API | ověření, že provider a consumer si rozumí |

## 2.16 Microservices antipatterns

→ Detaily: [[11. Microservices Antipatterns]]

| Antipattern | Jak poznat | Proč je problém | Lepší řešení |
|---|---|---|---|
| Distributed monolith | služby se musí deployovat společně | komplexita microservices bez benefitů | přemapovat boundaries, některé služby sloučit |
| Shared database | více služeb zapisuje do stejných tabulek | skrytý coupling, rozbité ownership | database/schema per service, API, events |
| Services by technical layer | Controller Service, Repository Service | layered monolith přes síť | služby podle business capability |
| Chatty services | mnoho malých requestů | latency, failure points | batch API, read model, coarse-grained API |
| Long sync chain | request jde přes mnoho služeb | sčítání latence, nízká availability | async workflow, Saga, cache/read model |
| Retry storm | všichni retryují při výpadku | dependency se přetíží ještě víc | backoff, jitter, circuit breaker |
| No observability | nikdo neví, kde chyba vznikla | nemožný provoz a debugging | logs, metrics, traces, correlation IDs |

> [!warning] Silná věta
> Microservices do not fix bad design. They often amplify it.

## 2.17 Design patterns a antipatterns

→ Detaily: [[08. Design Patterns and Antipatterns]]

**Design pattern** není hotový kód, ale pojmenované opakovatelné řešení.

| Kategorie | Řeší | Příklady |
|---|---|---|
| Creational | tvorba objektů | Factory Method, Abstract Factory, Builder, Singleton |
| Structural | skládání objektů | Adapter, Facade, Composite, Proxy |
| Behavioral | chování/komunikace | Strategy, Observer, Command, Template Method |

**Jak pattern popsat:** problem → context → solution → consequences → example.

**Antipattern:** opakující se špatné řešení, které se tváří jako řešení, ale dlouhodobě škodí.

Příklady:
- Big Ball of Mud,
- God Object,
- Spaghetti Code,
- Golden Hammer,
- Lava Flow,
- Singleton abuse.

## 2.18 Frameworks, Spring/Jakarta EE, persistence, messaging

→ Detaily: [[12. Supporting Topics - Web Services, Frameworks, Semantic Web and Big Data]]

**Framework** dává aplikaci strukturu a často používá inversion of control.

| Téma | Co říct |
|---|---|
| Library vs framework | library volá aplikace, framework volá aplikační kód |
| DI/IoC | framework spravuje závislosti a lifecycle objektů |
| Spring | ecosystem: IoC, Boot, MVC, Data, Security, Cloud |
| Jakarta EE | standardizovaná enterprise platforma |
| ORM/JPA | mapování objektů na relační DB, persistence context, transactions |
| Messaging | asynchronní komunikace, queue/topic, broker, producer/consumer |

> [!tip] Důležitá věta
> Framework supports architecture, but should not replace architectural thinking.

## 2.19 Semantic Web, Linked Data, Big Data

→ Detaily: [[12. Supporting Topics - Web Services, Frameworks, Semantic Web and Big Data]]

**Semantic Web:** data mají strojově zpracovatelný význam.

Základní pojmy:
- RDF triple: subject-predicate-object,
- URI identifikuje resource,
- ontology popisuje pojmy a vztahy,
- SPARQL dotazuje grafová RDF data,
- Linked Data propojují data přes URI.

**Big Data:** data s velkým objemem/rychlostí/různorodostí, kde běžné přístupy nestačí.

Pojmy:
- Volume, Velocity, Variety,
- distributed storage,
- replication,
- partitioning/sharding,
- batch vs stream processing,
- MapReduce/Hadoop/Spark jako příklady zpracování.

# 4. Jednotlivé otázky s odpověďmi a tipy

## Q1. Microservices: výhody, nevýhody a rozdíl ve vývoji

→ Detaily: [[09. Microservices vs Monolith]], [[10. Microservices Patterns and Best Practices]], [[11. Microservices Antipatterns]]

### Bezpečná odpověď

Microservices architecture rozděluje systém na malé, nezávisle nasaditelné služby organizované kolem business capabilities. Každá služba má jasnou odpovědnost, vlastní API, vlastní ownership a ideálně vlastní data.

Oproti monolitu nejsou části systému oddělené jen v kódu, ale i procesem, deploymentem, síťovým rozhraním a často databází.

### Výhody

- **Independent deployment:** změnu jedné služby lze nasadit bez release celého systému.
- **Independent scalability:** každou službu lze škálovat podle její zátěže.
- **Team autonomy:** tým vlastní službu end-to-end.
- **Fault isolation:** chyba jedné služby nemusí shodit celý systém, pokud jsou správně navržené timeouts, circuit breakers a graceful degradation.
- **Technology flexibility:** služba může použít jinou technologii, pokud to dává smysl.

### Nevýhody

- **Distributed complexity:** síťová volání, latence, partial failures.
- **Harder testing:** unit, integration, contract, E2E, test environments.
- **Harder debugging:** request prochází více službami, potřebuješ correlation ID a tracing.
- **Data consistency:** každá služba vlastní data, takže běžná ACID transakce přes celý systém není jednoduchá.
- **Operational overhead:** CI/CD, monitoring, service discovery, containers, orchestration, secrets, logs.

### Jak se liší vývoj

Vývoj microservices vyžaduje:
- jasné service boundaries podle business capabilities,
- explicitní API/event contracty,
- contract testing,
- automatizovaný deployment,
- observability,
- resiliency patterns,
- práci s eventual consistency,
- DevOps odpovědnost týmu.

### Co říct navíc pro lepší známku

Microservices dávají smysl jen tehdy, když přínos nezávislosti převáží cenu distribuovaného systému. Pro malý tým a nejasnou doménu je často lepší modular monolith.

### Typické doptání

**Na jakých úrovních se microservices testují?**

- unit tests uvnitř služby,
- integration tests se závislostmi,
- contract tests mezi consumer/provider,
- end-to-end tests přes několik služeb,
- resilience/load tests pro provozní chování.

**Co je potřeba pro tooling/deployment?**

- CI/CD,
- kontejnery,
- orchestration například Kubernetes,
- monitoring/logging/tracing,
- API Gateway,
- service discovery,
- secrets/config management,
- rollback/canary/blue-green deployment.

### Tip ke zkoušce

U historické otázky Mareček podle záznamu ocenil škálovatelnost, ale doptával se i na testování, tooling a deployment. Nezůstaň tedy jen u „microservices se dobře škálují“. Dotáhni odpověď až do praktického vývoje a provozu.

## Q2. Co je software architecture a architecture vs design

→ Detaily: [[1. Software Architecture Basics]]

### Bezpečná odpověď

Software architecture je vysokourovňová struktura systému. Popisuje hlavní komponenty, jejich odpovědnosti, komunikaci, nasazení a rozhodnutí, která podporují požadované quality attributes.

Architecture řeší hlavní části systému a rozhodnutí s velkým dopadem. Design řeší detailnější návrh tříd, rozhraní, metod a lokálních patternů.

### Příklad

Architektura:
- systém bude modular monolith,
- backend bude layered,
- platby půjdou přes externí provider,
- eventy se budou publikovat do message brokeru.

Design:
- použijeme Strategy pro výběr platební metody,
- repository bude za rozhraním,
- DTO mapper bude oddělený od entity.

### Tip

Důležité je říct, že hranice mezi architecture a design není vždy ostrá. Praktický test: když změna ovlivní deployment, komunikaci komponent, data ownership nebo quality attributes, je to spíš architektura.

## Q3. Jak měřit kvalitu architektury

→ Detaily: [[03. Quality Attributes and Architecture Metrics]], [[04. Architecture Evaluation and ATAM]]

### Bezpečná odpověď

Architekturu nelze hodnotit absolutně. Hodnotí se vůči požadavkům, quality attributes, business goals, stakeholder concerns a constraints konkrétního systému.

Kvalita se měří přes quality attributes:
- performance,
- scalability,
- availability,
- reliability,
- security,
- maintainability,
- modifiability,
- testability,
- usability,
- interoperability.

### Perspektivy

| Perspektiva | Co ji zajímá | Příklad metrik |
|---|---|---|
| User | rychlost, dostupnost, použitelnost | p95 latency, uptime, task completion rate |
| Developer | změnitelnost, testovatelnost | files changed, test time, lead time |
| DevOps | provoz, recovery, observability | MTTR, error rate, deployment frequency |
| Business | cena, time-to-market, riziko | cost of change, release cadence |
| Security | ochrana dat a přístupů | vulnerabilities, audit logs, unauthorized attempts |

### Tip

Nikdy neříkej „lepší architektura je microservices“. Řekni: „lepší je ta, která v daném kontextu lépe splní prioritní quality attributes za přijatelnou cenu.“

## Q4. ATAM a quality attribute scenarios

→ Detaily: [[04. Architecture Evaluation and ATAM]]

### Bezpečná odpověď

ATAM je metoda pro hodnocení architektury pomocí scénářů. Cílem je zjistit, jestli architektura podporuje důležité quality attributes a business goals, a identifikovat risks, non-risks, sensitivity points a trade-offs.

### Quality attribute scenario

Příklad performance scénáře:

- **Stimulus source:** end user
- **Stimulus:** sends search request
- **Environment:** normal operation, 500 concurrent users
- **Artifact:** Search API and database
- **Response:** returns results
- **Response measure:** 95 % under 300 ms

### ATAM výstupy

- **Risk:** rozhodnutí může ohrozit požadavek.
- **Non-risk:** rozhodnutí je v daném scénáři v pořádku.
- **Sensitivity point:** parametr, na kterém hodně záleží.
- **Trade-off point:** rozhodnutí zlepšuje jednu kvalitu a zhoršuje jinou.

### Tip

Když mluvíš o trade-offu, vždy dej konkrétní příklad: caching, microservices, shared library, synchronous communication, event-driven komunikace.

## Q5. Kruchten's 4+1 View Model

→ Detaily: [[02. Kruchten's 4+1 View Model]]

### Bezpečná odpověď

Kruchten's 4+1 View Model organizuje architektonickou dokumentaci do několika pohledů, protože jeden diagram nestačí pro všechny stakeholdery.

- **Logical view:** doménové objekty, funkcionalita, odpovědnosti.
- **Process view:** runtime chování, procesy, komunikace, concurrency, performance.
- **Development view:** moduly, packages, vrstvy, repository struktura, dependencies.
- **Physical view:** deployment, servery, kontejnery, infrastruktura.
- **Scenarios view:** důležité use cases, které propojují a validují ostatní views.

### Tip

Neříkej jen výčet. U každého view řekni otázku:
- Logical: co systém dělá?
- Process: jak běží?
- Development: jak je v kódu?
- Physical: kde běží?
- Scenarios: jak to projde use casem?

## Q6. Architectural style vs architectural pattern vs design pattern

→ Detaily: [[05. Architectural Styles Overview]], [[08. Design Patterns and Antipatterns]]

### Bezpečná odpověď

Architectural style je nejvyšší úroveň organizace systému. Architectural pattern je opakovatelné řešení architektonického problému. Design pattern je jemnější řešení na úrovni tříd a objektů.

### Příklady

- **Style:** microservices, layered, client-server.
- **Architectural pattern:** API Gateway, CQRS, Saga, Circuit Breaker.
- **Design pattern:** Factory, Strategy, Observer, Adapter.

### Tip

Komise může zkoušet záměny. Řekni: „Layered architecture může být styl, ale Repository je spíš design/enterprise pattern. API Gateway je architektonický pattern, protože ovlivňuje komunikaci a deployment.“

## Q7. Layered, modular monolith, hexagonal a microkernel

→ Detaily: [[06. Layered, Modular Monolith, Hexagonal and Microkernel Architecture]]

### Bezpečná odpověď

Tyto styly řeší, jak udržet systém přehledný uvnitř jednoho procesu nebo jednoho deploymentu.

### Layered architecture

Rozdělení podle technické odpovědnosti:

```text
Controller -> Service -> Repository -> Database
```

Dobré pro CRUD a enterprise aplikace. Riziko: business logika v controlleru, God Service, anemic domain model.

### Modular monolith

Jedna aplikace, ale rozdělená podle business modulů:

```text
Order / Payment / Inventory / Customer
```

Dobrá volba, když chceš jednoduchost deploymentu, ale nechceš Big Ball of Mud.

### Hexagonal architecture

Doména je izolovaná od technologií přes porty a adaptéry.

Dobré pro testability a modifiability. Riziko: moc abstrakcí pro jednoduchý systém.

### Microkernel

Core + pluginy. Hodí se pro rozšiřitelné produkty, IDE, workflow systémy.

### Tip

U této otázky komise pravděpodobně ocení, když řekneš, že monolith není automaticky špatně. Špatně je neřízený monolith bez hranic.

## Q8. Distributed architecture a fallacies

→ Detaily: [[07. Distributed Styles - Client-Server, SOA, Event-Driven Architecture and Microservices]]

### Bezpečná odpověď

Distributed architecture rozděluje systém na části, které běží v různých procesech/uzlech a komunikují přes síť.

### Výhody

- nezávislé škálování,
- nezávislý deployment,
- fault isolation,
- týmová autonomie,
- integrace externích systémů.

### Nevýhody

- latency,
- partial failures,
- timeouts,
- retries,
- duplicate messages,
- eventual consistency,
- monitoring a tracing,
- API versioning,
- security.

### Fallacies of distributed computing

Nebezpečné předpoklady:

- network is reliable,
- latency is zero,
- bandwidth is infinite,
- network is secure,
- topology does not change,
- transport cost is zero.

### Tip

Řekni: „Distribuovanost není jen rozdělení tříd. Je to přesun hranic do sítě.“ To je přesně architektonická pointa.

## Q9. REST, SOAP, GraphQL, OpenAPI

→ Detaily: [[12. Supporting Topics - Web Services, Frameworks, Semantic Web and Big Data]]

### Bezpečná odpověď

Web service je síťově dostupné rozhraní mezi aplikacemi. Architektonicky je důležité, protože vytváří contract mezi systémy.

### SOAP

Formální XML protokol, WSDL contract, enterprise integrace, WS-* standardy. Silné contracty, ale vysoký overhead.

### REST

Architectural style nad resources a HTTP. Důležité constraints: client-server, stateless, cacheable, uniform interface, layered system.

### GraphQL

Query language pro API. Klient si řekne přesný tvar dat. Řeší over-fetching a under-fetching, ale komplikuje cache, autorizaci a query complexity.

### OpenAPI

Strojově čitelný popis REST API contractu. Pomáhá dokumentaci, generování klientů a contract testingu.

### Tip

U RESTu neříkej „JSON přes HTTP“. Řekni „resources, HTTP methods, statelessness, representations, status codes, uniform interface“.

---

## Q10. SOA, event-driven architecture, orchestration/choreography

→ Detaily: [[07. Distributed Styles - Client-Server, SOA, Event-Driven Architecture and Microservices]]

### Bezpečná odpověď

SOA organizuje systém jako sadu služeb poskytujících business capabilities přes standardizované contracts. Event-driven architecture organizuje komunikaci kolem událostí, které producenti publikují a konzumenti zpracovávají.

### SOA

Typicky důraz na standardizovaný contract, loose coupling, reusability a enterprise integraci. Historicky často s ESB/SOAP, ale princip služby je širší.

### Event-driven architecture

Producer publikuje event a neví přesně, kdo ho zpracuje. Consumers reagují asynchronně.

### Orchestration vs choreography

| Přístup | Princip | Výhoda | Nevýhoda |
|---|---|---|---|
| Orchestration | centrální orchestrator řídí workflow | přehledný proces | centralizace logiky |
| Choreography | služby reagují na eventy | loose coupling | horší čitelnost procesu |

### Tip

Když mluvíš o eventech, vždy zmiň idempotenci, duplicate messages, ordering a observability.

## Q11. Microservices patterns

→ Detaily: [[10. Microservices Patterns and Best Practices]]

### Bezpečná odpověď

Microservices patterns nejsou dekorace. Jsou to techniky, jak zvládnout distribuovanou komplexitu.

### Hlavní patterns

**Database per Service:** každá služba vlastní svá data. Jiná služba nechodí přímo do jejích tabulek.

**Saga:** business transakce přes více služeb jako série lokálních transakcí. Při selhání se spustí kompenzace.

**Outbox:** služba zapíše business změnu i event do outbox tabulky ve stejné DB transakci. Publisher event později odešle.

**CQRS:** oddělení command side a query side. Read model může být denormalizovaný.

**Event Sourcing:** stav se ukládá jako posloupnost doménových eventů.

**API Gateway:** jednotný vstup, routing, auth, rate limiting, agregace.

**Circuit Breaker:** chrání systém před opakovaným voláním selhávající služby.

**Observability:** logs, metrics, traces, correlation IDs.

### Tip

U každého patternu řekni nejen „co to je“, ale i „jaký problém řeší“. Například Outbox řeší problém: DB commit proběhne, ale event se nepodaří publikovat.

## Q12. Microservices antipatterns

→ Detaily: [[11. Microservices Antipatterns]]

### Bezpečná odpověď

Antipattern je opakující se špatné řešení. V microservices je nebezpečné, protože špatné hranice se násobí latencí, deploymentem, datovou konzistencí a provozní složitostí.

### Hlavní antipatterns

- **Distributed monolith:** fyzicky služby, logicky jeden provázaný systém.
- **Shared database:** více služeb přímo sdílí tabulky.
- **Services by technical layer:** Controller Service, Repository Service.
- **Chatty services:** moc malých síťových volání.
- **Long synchronous call chain:** jeden request čeká na mnoho služeb.
- **Retry storm:** agresivní retry zhorší výpadek.
- **No observability:** žádné traces, metrics, correlation IDs.

### Tip

Silná věta ke zkoušce:

> A distributed monolith has the complexity of microservices without their benefits.

---

## Q13. Design patterns a antipatterns

→ Detaily: [[08. Design Patterns and Antipatterns]]

### Bezpečná odpověď

Design pattern je pojmenované opakovatelné řešení typického návrhového problému na úrovni tříd, objektů nebo menších modulů.

### GoF kategorie

- **Creational:** Factory Method, Abstract Factory, Builder, Singleton.
- **Structural:** Adapter, Facade, Composite, Proxy.
- **Behavioral:** Strategy, Observer, Command, Template Method.

### Příklad Strategy

Problem: potřebujeme měnit algoritmus za běhu.

Solution: definujeme interface `PricingStrategy` a konkrétní implementace `RegularPricing`, `DiscountPricing`, `VipPricing`.

Consequences: méně `if/else`, lepší rozšiřitelnost, ale více tříd.

### Antipatterns

- God Object,
- Big Ball of Mud,
- Spaghetti Code,
- Golden Hammer,
- Lava Flow,
- Singleton abuse.

### Tip

Nauč se u každého patternu říct: problém → princip → trade-off. Samotný název nestačí.

## Q14. Frameworks, DI/IoC, persistence a transactions

→ Detaily: [[12. Supporting Topics - Web Services, Frameworks, Semantic Web and Big Data]]

### Bezpečná odpověď

Framework je platforma, která dává aplikaci strukturu a poskytuje mechanismy jako request handling, dependency injection, configuration, security, persistence, transactions a testing support.

### Library vs framework

- Library: aplikace volá knihovnu.
- Framework: framework volá aplikační kód.

To je inversion of control.

### DI/IoC

Dependency Injection znamená, že objekt si závislosti nevytváří sám, ale dostane je zvenku. IoC container spravuje lifecycle objektů a wiring závislostí.

### Spring / Jakarta EE

- Spring: ekosystém, Spring Boot, MVC, Data, Security, Cloud.
- Jakarta EE: standardizovaná enterprise platforma, servlets, REST, DI, persistence, transactions, messaging, security.

### Persistence a transactions

ORM/JPA mapuje objekty na relační databázi. Transakce určují atomický blok změn. Architektonicky je důležité, kde leží transaction boundary — typicky v service/application layer.

### Tip

Framework není architektura. Framework může architekturu podporovat, ale nemá nahradit architektonické myšlení.

---

## Q15. Semantic Web, Linked Data a Big Data

→ Detaily: [[12. Supporting Topics - Web Services, Frameworks, Semantic Web and Big Data]]

### Bezpečná odpověď

Semantic Web se snaží, aby data na webu měla strojově zpracovatelný význam. Linked Data propojují data přes globální identifikátory a vztahy.

### Pojmy

- **RDF:** data jako triple `subject-predicate-object`.
- **URI:** identifikátor resource.
- **Ontology:** formální popis pojmů a vztahů.
- **SPARQL:** dotazovací jazyk nad RDF grafem.
- **Linked Data:** publikování a propojování dat přes URI.

### Big Data

Big Data řeší data, která jsou příliš velká, rychlá nebo různorodá pro jednoduché centralizované zpracování.

Pojmy:
- Volume,
- Velocity,
- Variety,
- distributed storage,
- replication,
- partitioning,
- batch processing,
- stream processing.

### Tip

Pro SWA je důležité říct, že nejde jen o technologie, ale o architektonické dopady: data management, integrace, škálování, interoperability a provozní složitost.
