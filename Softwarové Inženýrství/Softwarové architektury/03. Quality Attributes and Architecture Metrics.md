# Quality Attributes and Architecture Metrics

> **Zkouškový fokus:** umět vysvětlit quality attribute, quality requirement, měřitelnost, ISO/IEC 25010 a typické metriky z různých perspektiv.

## 1. Proč se architektura nehodnotí jako „dobrá“ nebo „špatná“ absolutně

Softwarová architektura není sama o sobě univerzálně dobrá nebo špatná.
Vždy se hodnotí vůči konkrétnímu kontextu:

```text
business cíle
funkční požadavky
nefunkční požadavky
velikost systému
velikost týmu
technické constraints
budget
čas
provozní prostředí
rizika
```

Stejná architektura může být výborná pro jeden systém a špatná pro jiný.

Příklad:

```text
Microservices mohou být dobrá volba pro velký systém s více týmy,
nezávislým deployem a různými doménami.

Ale pro malou CRUD aplikaci mohou být zbytečně složité,
drahé a těžké na provoz.
```

Bezpečná formulace ke zkoušce:

> We cannot say that one architecture is universally better than another. We must evaluate whether the architecture satisfies the required quality attributes and stakeholder concerns in a specific context.

---

## 2. Quality attribute

**Quality attribute** je měřitelná nebo testovatelná vlastnost systému, která říká, jak dobře systém splňuje potřeby stakeholderů.

Příklady quality attributes:

```text
availability
reliability
performance
scalability
security
maintainability
modifiability
testability
usability
interoperability
portability
recoverability
```

Quality attributes se často označují jako **non-functional requirements**, ale u architektury je lepší mluvit přesněji o kvalitativních vlastnostech systému.

---

## 3. Quality requirement

**Quality requirement** je konkrétní požadavek na hodnotu určitého quality attribute.

Rozdíl:

```text
Quality attribute:
System availability.

Quality requirement:
The system must be available 99.9 % of the time per month.
```

Další příklady:

```text
Performance attribute:
latency

Quality requirement:
95 % of requests must complete within 200 ms under normal load.
```

```text
Security attribute:
authentication

Quality requirement:
All administrative endpoints must require multi-factor authentication.
```

```text
Modifiability attribute:
change effort

Quality requirement:
Adding a new payment provider should require changes only in the payment module and should take less than two developer-days.
```

---

## 4. Jak má vypadat dobrý quality requirement

Dobrý quality requirement má být:

```text
not subjective
specific
measurable or testable
with clear context
with expected value
```

Špatně:

```text
System must be fast.
```

Lépe:

```text
For 95 % of search requests, the system must return results within 300 ms
under a load of 500 concurrent users.
```

Špatně:

```text
System must be secure.
```

Lépe:

```text
Only users with the ADMIN role can access user management endpoints,
and all access attempts must be logged.
```

## 5. Functional vs non-functional requirements

### Functional requirements

Funkční požadavky říkají, **co systém dělá**.

Příklad:

```text
User can create an account.
User can log in.
User can create an order.
Admin can manage products.
```

### Non-functional requirements / quality attributes

Nefunkční požadavky říkají, **jak dobře systém funguje**.

Příklad:

```text
Login must complete within 1 second.
The system must be available 99.9 % of the time.
Passwords must be stored as salted hashes.
The system must support 1000 concurrent users.
```

### Proč je to důležité pro architekturu

Funkční požadavky lze často implementovat různými způsoby.
Quality attributes ale často zásadně určují architekturu.

Příklad:

```text
Requirement:
User can upload files.

Possible simple implementation:
Store files directly on local disk.

But if quality attributes include scalability, availability and cloud deployment,
then architecture may require object storage, CDN, metadata database,
replication and access control.
```

## 6. Perspektivy hodnocení kvality

Quality attributes lze hodnotit z různých perspektiv.

## 6.1 Design and system perspective

Tato perspektiva řeší vnitřní strukturu systému.

Typické atributy:

```text
maintainability
reusability
flexibility
```

### Maintainability

Maintainability znamená, jak snadno lze systém udržovat a měnit během jeho životního cyklu.

Otázky:

```text
Je jasné, kam patří nový kód?
Je systém rozdělený na rozumné moduly?
Jsou závislosti kontrolované?
Lze opravit chybu bez rizika rozbití celého systému?
```

Možné metriky:

```text
time needed to implement a change
number of components affected by a change
code complexity
coupling between modules
technical debt
number of defects after change
```

### Reusability

Reusability znamená, do jaké míry lze části systému použít znovu.

Příklad:

```text
Shared authentication module can be reused by multiple applications.
A validation library can be reused by multiple services.
```

Pozor:

```text
Reusability is useful, but too much sharing can increase coupling.
```

To je důležité hlavně u microservices, kde sdílené knihovny mohou služby příliš svázat.

### Flexibility

Flexibility znamená schopnost systému přizpůsobit se budoucím změnám požadavků.

Příklad:

```text
System supports adding another payment provider without rewriting order logic.
```

---

## 6.2 Developer perspective

Tato perspektiva řeší, jak dobře se se systémem pracuje vývojářům.

Typické atributy:

```text
modifiability
testability
conceptual integrity
```

### Modifiability

Modifiability znamená, jak snadno lze přidat, změnit nebo odebrat funkcionalitu.

Příklad dobré modifiability:

```text
Business rules are isolated in service layer.
Adding a new rule does not require changing UI, database schema and API at the same time.
```

Možné metriky:

```text
change effort
number of files changed
number of modules touched
lead time for change
risk of regression
```

### Testability

Testability znamená, jak snadno lze systém testovat a dokazovat chyby pomocí automatizovaných testů.

Dobrá testability:

```text
business logic can be tested without UI
database can be mocked or replaced by test container
external services are behind interfaces
tests are deterministic
```

Možné metriky:

```text
test coverage
test execution time
number of flaky tests
time needed to set up test environment
defect detection rate
```

### Conceptual integrity

Conceptual integrity znamená konzistenci celého systému.

Příklad:

```text
consistent naming
consistent API style
consistent error handling
consistent module boundaries
consistent coding conventions
```

Nízká conceptual integrity:

```text
Each team uses different naming, error format, authentication style and folder structure.
```

## 6.3 User perspective

Tato perspektiva řeší kvalitu z pohledu uživatelů a provozu.

Typické atributy:

```text
availability
interoperability
security
performance
usability
```

### Availability

Availability znamená, jak dlouho je systém dostupný a schopný obsluhovat požadavky.

Příklad:

```text
The system must be available 99.9 % per month.
```

Možné metriky:

```text
uptime percentage
MTBF - mean time between failures
MTTR - mean time to repair
number of outages
downtime per month
```

### Interoperability

Interoperability znamená schopnost systému komunikovat s jinými systémy.

Zahrnuje:

```text
communication protocols
data formats
API contracts
authentication methods
versioning
compatibility
```

Příklad:

```text
System exposes REST API documented using OpenAPI.
System consumes events from Kafka in JSON format.
System integrates with external payment provider through HTTPS API.
```

### Security

Security znamená ochranu dat a funkcí před neautorizovaným nebo neautentizovaným použitím.

Zahrnuje:

```text
authentication
authorization
confidentiality
integrity
auditability
non-repudiation
secure communication
secure storage
```

Možné metriky:

```text
number of vulnerabilities
number of unauthorized access attempts
patch time
percentage of endpoints protected by authorization
time to detect suspicious activity
```

### Performance

Performance popisuje, jak rychle systém reaguje a jaký objem práce zvládne.

Hlavní pojmy:

```text
latency - time to respond
throughput - amount of work per time unit
resource utilization - CPU, memory, disk, network
capacity - maximum supported load
```

Příklad metrik:

```text
average response time
p95 latency
p99 latency
requests per second
CPU utilization
memory usage
queue length
```

### Usability

Usability znamená, jak snadno se systém používá.

Zahrnuje:

```text
learnability
operability
user error protection
accessibility
feedback to the user
```

Možné metriky:

```text
task completion rate
number of user errors
time to complete task
user satisfaction score
support ticket count
```

## 7. ISO/IEC 25010 quality model

ISO/IEC 25010 je standardní model kvality softwarového produktu.

Hlavní charakteristiky:

```text
Functional suitability
Performance efficiency
Compatibility
Usability
Reliability
Security
Maintainability
Portability
```

## 7.1 Functional suitability

Systém poskytuje funkce, které odpovídají požadavkům.

Subattributes:

```text
functional completeness
functional correctness
functional appropriateness
```

## 7.2 Performance efficiency

Systém využívá zdroje efektivně a reaguje v požadovaném čase.

Subattributes:

```text
time behaviour
resource utilization
capacity
```

## 7.3 Compatibility

Systém může koexistovat nebo spolupracovat s jinými systémy.

Subattributes:

```text
co-existence
interoperability
```

## 7.4 Usability

Systém je pro uživatele pochopitelný a použitelný.

Subattributes:

```text
appropriateness recognizability
learnability
operability
user error protection
user interface aesthetics
accessibility
```

## 7.5 Reliability

Systém funguje správně za daných podmínek po určitou dobu.

Subattributes:

```text
maturity
availability
fault tolerance
recoverability
```

## 7.6 Security

Systém chrání data a funkce.

Subattributes:

```text
confidentiality
integrity
non-repudiation
accountability
authenticity
```

## 7.7 Maintainability

Systém lze analyzovat, měnit a testovat.

Subattributes:

```text
modularity
reusability
analysability
modifiability
testability
```

## 7.8 Portability

Systém lze přenést do jiného prostředí.

Subattributes:

```text
adaptability
installability
replaceability
```

## 8. Quality attribute scenarios

Quality attribute scenario je strukturovaný způsob, jak měřit nebo testovat kvalitu architektury.

Každý scénář obsahuje:

```text
stimulus source
stimulus
environment
artifact
response
response measure
```

## 8.1 Stimulus source

Kdo nebo co vyvolá událost.

Příklad:

```text
end user
administrator
external system
internal subsystem
attacker
monitoring system
```

## 8.2 Stimulus

Událost nebo podmínka, na kterou systém reaguje.

Příklad:

```text
high request volume
incorrect input
server failure
unauthorized request
database unavailable
new business rule requested
```

## 8.3 Environment

V jakém režimu systém je.

Příklad:

```text
normal operation
peak load
startup
shutdown
recovery mode
maintenance mode
```

## 8.4 Artifact

Část systému, která je stimulusem ovlivněna.

Příklad:

```text
web server
database
API gateway
authentication service
order module
message broker
```

## 8.5 Response

Jak má systém reagovat.

Příklad:

```text
reject invalid request
return error response
scale out
retry operation
write audit log
switch to backup instance
notify administrator
```

## 8.6 Response measure

Objektivní měření odpovědi.

Příklad:

```text
response time under 200 ms
recovery within 30 seconds
error rate below 0.1 %
99.9 % availability
no data loss
```

## 9. Examples of quality attribute scenarios

## 9.1 Availability scenario

```text
Stimulus source:
External user

Stimulus:
User sends a request while the system is under heavy load.

Environment:
Peak load operation.

Artifact:
Web service.

Response:
System accepts the request or returns a controlled message that the service is busy.

Response measure:
95 % of requests are accepted within 500 ms,
and rejected requests receive a response within 1 second.
```

## 9.2 Performance scenario

```text
Stimulus source:
User

Stimulus:
User opens product search.

Environment:
Normal load with 500 concurrent users.

Artifact:
Search API.

Response:
System returns search results.

Response measure:
95 % of responses complete within 300 ms.
```

## 9.3 Security scenario

```text
Stimulus source:
Unauthenticated user

Stimulus:
User attempts to access admin endpoint.

Environment:
Normal operation.

Artifact:
Backend API.

Response:
System rejects the request and logs the attempt.

Response measure:
100 % of unauthorized admin requests return 401 or 403,
and every attempt is written to the audit log.
```

## 9.4 Modifiability scenario

```text
Stimulus source:
Business stakeholder

Stimulus:
New payment provider must be added.

Environment:
Development phase.

Artifact:
Payment module.

Response:
Developer adds a new provider implementation without changing order logic.

Response measure:
Change is implemented within two developer-days
and affects only the payment module and configuration.
```

## 9.5 Recoverability scenario

```text
Stimulus source:
Database server

Stimulus:
Primary database becomes unavailable.

Environment:
Production operation.

Artifact:
Persistence layer.

Response:
System switches to read-only mode or backup database.

Response measure:
System restores basic operation within 60 seconds
and no committed transaction is lost.
```

## 10. Typical architecture metrics

## 10.1 Performance metrics

```text
Latency - doba zpoždění mezi odesláním požadavku a začátkem odpovědi systému.
Average response time - průměrná doba, za kterou systém zpracuje požadavek a vrátí odpověď.
P95 response time - hodnota, pod kterou se vejde 95 % všech dob odpovědi; ukazuje pomalejší část provozu.
P99 response time - hodnota, pod kterou se vejde 99 % všech dob odpovědi; pomáhá odhalit extrémně pomalé odpovědi.
Throughput - množství práce, které systém zvládne zpracovat za jednotku času.
Requests per second - počet požadavků zpracovaných systémem za jednu sekundu.
Transactions per second - počet dokončených transakcí za jednu sekundu.
CPU utilization - procentuální využití procesoru systémem nebo aplikací.
Memory utilization - využití operační paměti systémem nebo aplikací.
I/O wait - čas, kdy procesor čeká na dokončení vstupně-výstupních operací, například práce s diskem.
Network bandwidth - množství dat, které lze přenést přes síť za jednotku času.
Queue length - počet požadavků nebo úloh čekajících ve frontě na zpracování.
```

## 10.2 Availability and reliability metrics

```text
uptime percentage - procento času, kdy je systém dostupný a funguje správně.  
downtime per month - celková doba za měsíc, kdy je systém nedostupný nebo nefunkční.  
MTBF - průměrná doba mezi dvěma poruchami systému.  
MTTR - průměrná doba potřebná k opravě systému po poruše.  
failure rate - frekvence, s jakou dochází k poruchám systému.  
error rate - podíl požadavků nebo operací, které skončí chybou.  
successful request ratio - podíl požadavků, které byly úspěšně zpracovány.  
number of incidents - počet zaznamenaných incidentů za dané období.  
recovery time objective - RTO - maximální přijatelná doba, za kterou musí být služba obnovena po výpadku.  
recovery point objective - RPO - maximální přijatelná ztráta dat vyjádřená časem od poslední obnovitelné zálohy.
```

## 10.3 Maintainability metrics

```text
change lead time - doba od zahájení změny do jejího nasazení nebo dokončení.  
number of components touched by change - počet komponent, které byly změnou upraveny nebo ovlivněny.  
cyclomatic complexity - míra složitosti kódu podle počtu nezávislých cest v programu.  
code duplication - množství opakujícího se nebo zkopírovaného kódu v systému.  
coupling - míra závislosti mezi jednotlivými komponentami nebo moduly.  
cohesion - míra, do jaké spolu prvky uvnitř jedné komponenty logicky souvisejí.  
technical debt - nahromaděné kompromisy v kódu nebo architektuře, které ztěžují další vývoj.  
number of defects introduced by change - počet chyb, které vznikly v důsledku konkrétní změny.  
build time - doba potřebná k sestavení aplikace nebo systému.
```

## 10.4 Testability metrics

```text
test coverage - procento kódu nebo funkcionality pokryté testy.  
test execution time - doba potřebná ke spuštění a dokončení testů.  
flaky test ratio - podíl testů, které někdy selžou a někdy projdou bez změny kódu.  
number of automated tests - počet testů, které se spouštějí automaticky bez ručního zásahu.  
setup time for test environment - doba potřebná k přípravě testovacího prostředí.  
defect detection rate - míra, s jakou testy nebo kontrolní procesy odhalují chyby.
```

## 10.5 Security metrics

```text
number of known vulnerabilities - počet známých zranitelností v systému, aplikaci nebo infrastruktuře.  
time to patch vulnerability - doba potřebná k opravě nebo záplatování zjištěné zranitelnosti.  
number of unauthorized access attempts - počet pokusů o neoprávněný přístup k systému nebo datům.  
percentage of encrypted communication - procento síťové komunikace chráněné šifrováním. 
percentage of protected endpoints - procento koncových zařízení nebo služeb chráněných bezpečnostními mechanismy.  
security incident count - počet bezpečnostních incidentů za dané období.
```

## 10.6 Usability metrics

```text
task completion rate - procento úloh, které uživatelé úspěšně dokončí.  
time to complete task - doba, kterou uživatel potřebuje k dokončení konkrétní úlohy.  
user error rate - podíl chyb, kterých se uživatelé dopustí při práci se systémem.  
number of support requests - počet požadavků uživatelů na podporu nebo pomoc.  
user satisfaction - míra spokojenosti uživatelů se systémem nebo službou.  
accessibility issues - počet nebo typ problémů, které brání používání systému lidem se specifickými potřebami.
```

## 11. Trade-offs between quality attributes

Quality attributes často stojí proti sobě.
Architektura je proto vždy o trade-offs.

## 11.1 Performance vs maintainability

Vysoce optimalizovaný kód může být těžší na pochopení a údržbu.

```text
+ faster execution
- more complex code
- harder debugging
- harder future changes
```

## 11.2 Security vs usability

Silnější bezpečnost může zhoršit pohodlí uživatele.

```text
MFA improves security,
but login becomes slower and less convenient.
```

## 11.3 Availability vs consistency

V distribuovaných systémech může být těžké maximalizovat dostupnost i silnou konzistenci zároveň.

```text
If a network partition occurs,
system may choose availability with eventual consistency,
or strict consistency with temporary unavailability.
```

## 11.4 Scalability vs simplicity

Microservices nebo event-driven architecture mohou zlepšit škálovatelnost, ale zvyšují složitost.

```text
+ independent scaling
+ better team autonomy
- distributed debugging
- harder testing
- harder data consistency
```

## 11.5 Flexibility vs cost

Flexibilní architektura často vyžaduje více abstrakcí a návrhové práce.

```text
+ easier future changes
- higher initial cost
- more complex design
```

## 13. Is one architecture better than another?

Nelze říct, že jedna architektura je obecně lepší než druhá.

Lze ale říct, že jedna architektura je vhodnější pro konkrétní systém a požadavky.

Příklad:

```text
Small startup MVP:
modular monolith may be better.

Large system with many teams and independent release cycles:
microservices may be better.

Data processing pipeline:
pipes and filters may be better.

Plugin-based IDE:
microkernel may be better.
```

Architektura se hodnotí podle toho, jak dobře plní požadavky a quality attributes.

---

## 14. Example comparison: monolith vs microservices by quality attributes

| Quality attribute | Monolith | Microservices |
|---|---|---|
| Simplicity | usually better | worse |
| Deployment | simple single deployment | complex independent deployments |
| Scalability | whole application scales together | individual services can scale separately |
| Testability | easier end-to-end testing | harder distributed testing |
| Maintainability | good if modular, bad if too large | good boundaries, but more operational complexity |
| Performance | no network overhead inside app | network calls between services |
| Reliability | one failure can affect whole app | better fault isolation, but more failure points |
| Data consistency | easier transactions | distributed consistency is hard |
| Team autonomy | limited in large codebase | better for independent teams |

Závěr:

```text
Neither is universally better.
The better choice depends on system size, team structure,
quality attributes, deployment needs and operational maturity.
```

## 15. Časté chyby při práci s quality attributes

## 15.1 Subjective requirements

Špatně:

```text
System should be user-friendly.
System should be fast.
System should be secure.
```

Lépe:

```text
New users should be able to complete registration in less than 2 minutes.
95 % of API requests should finish within 200 ms.
All admin actions must require authentication and be logged.
```

## 15.2 Ignoring context

Metrika bez kontextu je často nepoužitelná.

Špatně:

```text
Response time must be 200 ms.
```

Lépe:

```text
95 % of product detail requests must complete within 200 ms
under normal load of 1000 concurrent users.
```

## 15.3 Maximizing everything

Nelze chtít maximální výkon, maximální flexibilitu, nulové náklady, jednoduchost a 100% dostupnost zároveň.

Architektura musí prioritizovat.

## 15.4 Measuring only code metrics

Code metrics jsou užitečné, ale architektonická kvalita není jen kód.

Je nutné měřit i:

```text
deployment
runtime behaviour
failure recovery
integration
security
usability
business risks
```

## 16. Zkoušková odpověď: How can you measure the quality of an architecture?

The quality of a software architecture can be measured by evaluating whether it satisfies the required quality attributes of the system. Architecture is not inherently good or bad. It is good only in relation to concrete requirements, stakeholder concerns and business constraints.

Quality attributes are measurable or testable properties such as availability, performance, security, maintainability, modifiability, testability, usability, interoperability and reliability. Each quality attribute should be expressed as a concrete quality requirement with a measurable value and context. For example, instead of saying that the system must be fast, we can say that 95 % of requests must complete within 200 ms under a load of 500 concurrent users.

Architecture quality can be measured using quality attribute scenarios. A scenario defines a stimulus source, stimulus, environment, affected artifact, expected response and response measure. This makes the quality attribute concrete and testable.

Quality can also be evaluated from different perspectives. Users care mainly about usability, performance and availability. Developers care about maintainability, modifiability and testability. Operations teams care about deployability, monitoring, scalability and recoverability. Business stakeholders care about cost, risk and ability to evolve the system.

Therefore, one architecture cannot be called universally better than another. The better architecture is the one that satisfies the most important quality attributes and trade-offs in the given context.
