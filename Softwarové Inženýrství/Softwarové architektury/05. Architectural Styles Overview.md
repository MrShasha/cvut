> **Zkouškový fokus:** umět odlišit architectural style, architectural pattern a design pattern a znát hlavní monolitické i distribuované styly.

## 1. Co je architectural style

**Architectural style** je obecný způsob organizace softwarového systému na vysoké úrovni.

Určuje hlavně:

- jaké typy komponent systém má
- jak jsou komponenty uspořádané
- jak spolu komunikují
- jaké vztahy a omezení mezi nimi platí
- jaké quality attributes tento styl typicky podporuje nebo zhoršuje

Jednoduše:

> Architectural style is a high-level structural organization of a system.

> [!note] Jak si to pamatovat
> Styl říká, jak systém vypadá jako celek: jaké má hlavní části, jak mezi nimi teče komunikace a jaké typické trade-offs tím vznikají.

Příklady architektonických stylů:

- layered architecture
- client-server architecture
- event-driven architecture
- microservices
- service-oriented architecture
- pipes and filters
- microkernel
- peer-to-peer
- space-based architecture

---

## 2. Architectural style vs architectural pattern vs design pattern

Tyto pojmy se často pletou.

### 2.1 Architectural style

Styl je nejvyšší úroveň organizace systému.

Příklad:

- layered architecture
- microservices
- event-driven architecture
- client-server

Říká, jak je systém celkově uspořádán.

### 2.2 Architectural pattern

Architectural pattern je opakovatelná řešení architektonického problému.

Příklad:

- API Gateway
- CQRS
- Saga
- Circuit Breaker
- Bulkhead
- Sidecar
- Database per Service

Pattern může být použit uvnitř určitého stylu.

Například v microservices se často používají:

- API Gateway
- Service Discovery
- Database per Service
- Saga
- Circuit Breaker
- CQRS

### 2.3 Design pattern

Design pattern je nižší úroveň, typicky na úrovni tříd a objektů.

Příklad:

- Factory
- Singleton
- Strategy
- Observer
- Adapter
- Repository
- DAO

Design pattern řeší implementační problém, ne celou strukturu systému.

### 2.4 Bezpečná zkoušková formulace

> Architectural style defines the overall structural organization of a system. Architectural pattern is a reusable solution to a recurring architectural problem. Design pattern is more fine-grained and usually solves recurring implementation problems at class or object level.

> [!tip] Rychlé rozlišení
> **Style** je tvar celé architektury. **Architectural pattern** je opakované řešení architektonického problému uvnitř architektury. **Design pattern** je implementační řešení na úrovni tříd, objektů nebo modulů.

---

## 3. Proč znát architectural styles

Architectural styles pomáhají:

- rychleji navrhovat systém
- komunikovat architekturu s týmem
- používat osvědčené přístupy
- chápat trade-offs
- odhadovat dopad na quality attributes
- vyhnout se známým problémům

Například když řekneme:

- The system uses layered architecture.

tým zhruba chápe:

- existuje presentation/controller layer
- existuje business/service layer
- existuje persistence/repository layer
- závislosti typicky směřují shora dolů

Když řekneme:

- The system uses event-driven architecture.

tým chápe:

- komponenty komunikují přes události
- komunikace je často asynchronní
- producers a consumers jsou oddělení
- debugging a consistency mohou být složitější

---

## 4. Základní dělení stylů

Architektonické styly lze dělit různě. Praktické dělení ke zkoušce:

- monolithic styles
- distributed styles
- data-flow styles
- event-based styles
- plugin-based styles
- decentralized styles

### 4.1 Monolithic styles

Systém je většinou nasazen jako jedna aplikace nebo jeden hlavní deployable unit.

Příklady:

- traditional monolith
- layered architecture
- modular monolith
- microkernel
- hexagonal architecture
- pipes and filters inside one process

Výhody:

- jednodušší vývoj
- jednodušší debugging
- jednodušší deployment
- jednodušší transakce
- nižší operační komplexita

Nevýhody:

- horší nezávislé škálování částí systému
- větší riziko růstu komplexity
- těžší paralelní vývoj ve velkém týmu
- deployment celé aplikace při změně jedné části

Monolitické styly tedy kupují jednoduchost provozu a vývoje za cenu menší nezávislosti částí systému. Dobře fungují hlavně tehdy, když tým dokáže udržet jasné vnitřní hranice a systém zatím nepotřebuje samostatně škálovat nebo nasazovat jednotlivé části.

### 4.2 Distributed styles

Systém je rozdělen na více síťově komunikujících částí.

Příklady:

- client-server
- service-oriented architecture
- microservices
- event-driven architecture
- peer-to-peer
- space-based architecture

Výhody:

- nezávislé škálování
- nezávislé deploymenty
- lepší fault isolation
- možnost různých technologií
- lepší podpora velkých týmů

Nevýhody:

- síťová komunikace
- latence
- partial failures
- složitější monitoring
- složitější debugging
- složitější testování
- problémy s konzistencí dat
- vyšší DevOps nároky

Distribuované styly dávají smysl ve chvíli, kdy přínos nezávislého škálování, deploymentu nebo týmové autonomie převáží cenu síťové komunikace. Pokud tuto cenu tým neumí zaplatit monitoringem, testy, automatizací a jasnými contracty, distribuovanost spíš přidá problémy.

## 5.1 Princip

**Monolithic architecture** znamená, že aplikace je postavena jako jeden celek.

Typicky:

- jedna codebase
- jeden deployable artifact
- jedna hlavní databáze
- funkce jsou uvnitř jedné aplikace

Příklad:

- E-shop jako jedna Spring Boot aplikace:
  - users
  - products
  - cart
  - orders
  - payments
  - admin

Vše je v jedné aplikaci, ale může být vnitřně rozděleno do balíčků, vrstev nebo modulů.

### 5.2 Kdy se hodí

Monolit se hodí pro:

- malé a střední aplikace
- MVP
- malý tým
- jednodušší business doménu
- rychlý start projektu
- systémy bez potřeby nezávislého škálování částí

### 5.3 Výhody

- jednoduchý deployment
- jednoduchý lokální vývoj
- jednodušší debugging
- jednodušší testování end-to-end
- jednodušší databázové transakce
- nižší provozní komplexita

### 5.4 Nevýhody

- s růstem může být těžko pochopitelný
- silné coupling mezi částmi
- jedna změna může ovlivnit celý systém
- škáluje se obvykle celý systém, ne jednotlivé části
- větší tým si může překážet v jedné codebase
- technologická změna může být obtížná

### 5.5 Zkoušková formulace

> Monolithic architecture is not automatically bad. It is often a good choice for small or medium systems, MVPs and teams without strong DevOps maturity. The main problem appears when the monolith grows without clear modular boundaries and becomes hard to maintain.

### 6.1 Princip

**Layered architecture** rozděluje systém do horizontálních vrstev podle technické odpovědnosti.

Smyslem vrstvení je oddělit různé druhy práce v systému. Uživatelské rozhraní nemá řešit databázové detaily, persistence nemá obsahovat business pravidla a business logika nemá být závislá na konkrétním webovém frameworku.

Typické vrstvy:

- presentation layer
- application / service layer
- business logic layer
- data access layer
- database layer

V běžné webové aplikaci:

- Controller
- Service
- Repository / DAO
- Database

Seznam vrstev je proto potřeba chápat jako způsob řízení závislostí. Každá vrstva má jasnou odpovědnost a změna v jedné oblasti by měla co nejméně zasahovat ostatní části systému.

### 6.2 Komunikace

Typicky platí:

- vyšší vrstva volá nižší vrstvu
- nižší vrstva nevolá vyšší vrstvu

Toto pravidlo drží architekturu čitelnou. Jakmile nižší vrstva začne volat vyšší, vznikají kruhové závislosti a systém se postupně mění v těžko udržovatelnou spleť.

Příklad:

- Controller → Service → Repository → Database

### 6.3 Výhody

- jednoduché pochopení
- dobrá separace odpovědností
- vhodné pro CRUD a enterprise aplikace
- snazší testování jednotlivých vrstev
- přirozený styl pro mnoho frameworků

### 6.4 Nevýhody

- může vzniknout zbytečné předávání dat přes mnoho vrstev
- špatně navržené vrstvy mohou být silně provázané
- změna může vyžadovat zásah do více vrstev
- omezené nezávislé škálování
- cross-cutting concerns procházejí napříč vrstvami (něco co najednou ovlivňuje všechny části systému)

### 6.5 Typické cross-cutting concerns

- logging
- security
- transactions
- validation
- configuration
- monitoring
- i18n / l10n
- privacy

> [!note] Častá past
> Layered architecture není automaticky čistá architektura. Pokud všechny vrstvy jen mechanicky přeposílají data a business pravidla jsou rozlezlá všude, vznikne sice vrstvený, ale špatně udržovatelný systém.

### 7.1 Princip

**Modular monolith** je monolit, který má jasné interní moduly.

Není to chaos v jedné aplikaci. Je to monolit s dobrými boundaries.

Příklad modulů:

- User module
- Order module
- Payment module
- Inventory module
- Notification module

Každý modul má vlastní:

- business logic
- API / interface
- data access
- tests

### 7.2 Výhody

- jednodušší deployment než microservices
- lepší organizace než klasický monolit
- jasnější ownership částí systému
- snazší refactoring
- nižší operační komplexita
- může být dobrý mezikrok před microservices

### 7.3 Nevýhody

- stále jeden deployable unit
- škálování je obvykle pro celou aplikaci
- tým musí disciplinovaně držet boundaries
- bez kontroly závislostí se může změnit v Big Ball of Mud

### 7.4 Důležitá myšlenka

Modular monolith může být lepší volba než microservices, pokud tým ještě nepotřebuje nezávislé deploymenty a nechce distribuovanou komplexitu.

### 8.1 Princip

**Hexagonal architecture** odděluje business logic od externích technologií.

Jádro systému:

- domain model
- business rules
- application logic

Externí části:

- REST API
- database
- message broker
- file system
- external services
- UI

Komunikace probíhá přes:

- ports = interfaces
- adapters = konkrétní implementace pro externí technologii

### 8.2 Příklad

Business logic nechce vědět, jestli se data ukládají do PostgreSQL nebo MongoDB.

- OrderService depends on OrderRepository interface.
- PostgresOrderRepository implements OrderRepository.

### 8.3 Výhody

- dobrá testovatelnost business logic
- nižší coupling na frameworky a databáze
- snazší výměna externích technologií
- čistší doménový model
- lepší maintainability

### 8.4 Nevýhody

- vyšší počáteční komplexita
- více abstrakcí
- potřeba disciplíny
- může být overkill pro jednoduchý CRUD

### 10.1 Princip

**Client-server architecture** odděluje klienty a server.

Klient:

- posílá requesty
- zobrazuje data
- interaguje s uživatelem

Server:

- zpracovává requesty
- obsahuje business logic nebo data access
- vrací response

Příklady:

- web browser → web server
- mobile app → backend API
- desktop app → database server

### 10.2 Komunikace

Typické protokoly:

- HTTP
- HTTPS
- REST
- GraphQL
- gRPC
- SQL
- WebSocket

### 10.3 Výhody

- jasné rozdělení odpovědností
- centralizovaná správa dat
- klienti a server se mohou vyvíjet odděleně
- server lze škálovat nezávisle na klientech

### 10.4 Nevýhody

- server může být single point of failure
- síťová latence
- bezpečnostní rizika komunikace
- DoS/DDoS útoky
- potřeba řešit autentizaci a autorizaci

### 11.1 Princip

**Service-oriented architecture** organizuje systém jako sadu služeb, které poskytují business capabilities.

Typické principy:

- standardized service contract
- loose coupling
- abstraction
- reusability
- autonomy
- discoverability
- composability

SOA byla často používána ve velkých enterprise systémech.

### 11.2 Typické prvky

- business services
- application services
- infrastructure services
- message bus
- orchestrator
- Enterprise Service Bus
- service contracts

### 11.3 Výhody

- reusability služeb
- integrace enterprise systémů
- platform independence
- možnost skládání business procesů
- lepší organizace velkých systémů

### 11.4 Nevýhody

- vyšší overhead
- komplexní service management
- ESB se může stát bottleneckem
- vysoká počáteční investice
- riziko příliš centralizované orchestrace

### 11.5 SOA vs microservices

SOA a microservices jsou příbuzné, ale nejsou stejné.

SOA často:

- používá větší enterprise services
- má centrální orchestraci nebo ESB
- klade důraz na service reuse v enterprise prostředí

Microservices typicky:

- mají menší služby
- jsou organizované kolem business capabilities
- mají nezávislý deployment
- preferují decentralizované řízení
- často mají vlastní databázi na službu

### 12.1 Princip

**Event-driven architecture** je styl, kde komponenty komunikují pomocí událostí.

Základní pojmy:

- event
- producer
- consumer
- event broker / event bus
- topic / queue
- subscriber

Producer publikuje událost:

- OrderCreated
- PaymentCompleted
- UserRegistered
- InventoryUpdated

Consumer na událost reaguje:

- send email
- update read model
- start payment process
- reserve inventory

### 12.2 Výhody

- loose coupling mezi producers a consumers
- dobrá škálovatelnost
- asynchronní zpracování
- snadnější přidání nového consumeru
- vhodné pro real-time a high-volume systémy

### 12.3 Nevýhody

- vyšší komplexita
- eventual consistency
- složitější debugging
- těžší sledování flow systému
- problémy s orderingem událostí
- nutnost řešit duplicity a idempotency

### 12.4 Kdy se hodí

- více subsystémů reaguje na stejné události
- real-time processing
- IoT
- stream processing
- notification systems
- audit log
- integration between services

### 14.1 Princip

**Pipes and filters** rozkládají zpracování dat na sekvenci nezávislých kroků.

- input → filter 1 → filter 2 → filter 3 → output

Pipe předává data mezi filtry.

Filter provádí transformaci, validaci nebo výpočet.

Styl se hodí tam, kde je práce přirozeně postupná a každý krok lze popsat samostatně. Díky tomu lze jednotlivé filtry testovat odděleně, měnit pořadí kroků nebo některé části zpracování znovu použít v jiné pipeline.

### 14.2 Příklady

- Unix shell pipeline
- ETL processing
- image processing
- audio processing
- compiler pipeline
- data import pipeline

Příklad:

- read file → parse CSV → validate rows → transform data → save to database

### 14.3 Výhody

- dobrá modularita
- snadné testování jednotlivých filtrů
- reuse filtrů v různých pipelines
- možnost paralelizace některých kroků
- jasný data flow

Výhody vznikají hlavně z toho, že filtr má úzký účel a dobře definovaný vstup i výstup. Pokud filtr začne řešit příliš mnoho věcí najednou, styl rychle ztrácí svoji přehlednost.

### 14.4 Nevýhody

- overhead předávání dat
- latence celé pipeline
- složitější error handling
- stavové filtry mohou zkomplikovat návrh

### 16.1 Princip

**Space-based architecture** používá distribuovaný in-memory data grid. Každý server drží část dat přímo v RAM a může rychle obsluhovat požadavky bez neustálého přístupu do centrální databáze.

Cílem je odstranit databázi jako bottleneck.

Typické prvky:

- processing units - uzly, které obsahují aplikační logiku a zpracovávají požadavky.
- virtualized middleware - vrstva, která propojuje všechny části systému a skrývá složitost distribuované infrastruktury.
- data grid - distribuované úložiště dat v paměti mezi více uzly.
- messaging grid - mechanismus pro posílání zpráv mezi uzly a službami.
- processing grid - mechanismus pro rozdělování výpočetních úloh mezi více uzlů.
- deployment manager - komponenta, která spravuje nasazení, spouštění, zastavování a škálování processing units.

Data i processing jsou distribuované mezi více nodes.

### 16.2 Kdy se hodí

- velmi vysoká škálovatelnost
- nízká latence
- real-time analytics
- high-performance systems
- systémy s extrémním zatížením

### 16.3 Výhody

- vysoká škálovatelnost
- nízká latence
- fault tolerance
- rychlý přístup k datům v paměti
- snížení databázového bottlenecku

### 16.4 Nevýhody

- vysoká komplexita
- náročná správa dat
- obtížné consistency management
- vyšší nároky na infrastrukturu

Toto je důležité hlavně u distribuovaných systémů a microservices.

### 18.1 Orchestration

Jeden centrální orchestrator řídí celý proces.

Příklad:

- Order Orchestrator:
  1. call Payment Service
  2. call Inventory Service
  3. call Shipping Service
  4. send confirmation

Výhody:

- proces je na jednom místě
- snazší pochopení flow
- jednodušší řízení business procesu

Nevýhody:

- orchestrator může být bottleneck
- vyšší coupling na centrální komponentu
- riziko distributed monolith

### 18.2 Choreography

Služby reagují na události bez centrálního řídicího prvku.

Příklad:

- Order Service publishes OrderCreated.
- Payment Service reacts and publishes PaymentCompleted.
- Inventory Service reacts and reserves items.
- Notification Service sends email.

Výhody:

- looser coupling
- lepší škálovatelnost
- lepší autonomie služeb

Nevýhody:

- složitější pochopení celého flow
- složitější debugging
- eventual consistency

### 18.3 Zkoušková formulace

> Orchestration uses a central controller to coordinate services. Choreography uses events, where each service reacts independently. Orchestration is easier to understand, but can create coupling. Choreography improves autonomy and loose coupling, but makes the global process harder to trace.

## 19. Jak vybrat architektonický styl

Neexistuje univerzálně nejlepší styl.

Výběr závisí na:

- functional requirements
- quality attributes
- team size
- team skills
- business domain
- deployment environment
- expected load
- security requirements
- maintainability needs
- time to market
- budget
- operational maturity

### 19.1 Malá aplikace / MVP

Vhodné:

- simple monolith
- layered architecture
- modular monolith

Nevhodné bez silného důvodu:

- microservices
- complex event-driven architecture
- service mesh
- Kubernetes-heavy architecture

### 19.2 Enterprise CRUD aplikace

Vhodné:

- layered architecture
- modular monolith
- hexagonal architecture
- client-server
- REST API

### 19.3 Velký systém s více týmy

Vhodné:

- modular monolith
- microservices
- service-oriented architecture
- event-driven architecture

Podmínky:

- dobré DevOps
- CI/CD
- monitoring
- logging
- API contracts
- test automation
- clear ownership

### 19.4 High-volume event processing

Vhodné:

- event-driven architecture
- pipes and filters
- stream processing
- message queues

### 19.5 Plugin platform

Vhodné:

- microkernel architecture
- plugin-based architecture

## 20. Comparison table

| Style | Main idea | Strengths | Weaknesses | Good for |
|---|---|---|---|---|
| Monolith | One deployable application | Simple deployment, debugging, transactions | Can become large and coupled | Small/medium systems, MVP |
| Layered | Horizontal technical layers | Simple, understandable, testable | Layer coupling, performance overhead | CRUD, enterprise apps |
| Modular monolith | Monolith with clear modules | Good boundaries, low ops complexity | One deployment, discipline needed | Growing systems |
| Hexagonal | Core isolated from external adapters | Testability, low framework coupling | More abstractions | Domain-focused systems |
| Microkernel | Core + plugins | Extensibility | Plugin API complexity | IDEs, extensible platforms |
| Client-server | Clients request services from server | Clear split, centralized data | Server bottleneck/failure | Web/mobile systems |
| SOA | Enterprise services with contracts | Reuse, integration | ESB/management complexity | Enterprise integration |
| Event-driven | Components communicate by events | Loose coupling, scalability | Debugging, eventual consistency | Real-time, async workflows |
| Microservices | Independent business services | Independent deploy/scale, team autonomy | Distributed complexity | Large systems, many teams |
| Pipes and filters | Data processing pipeline | Reuse, modular data flow | Latency, error handling | ETL, processing pipelines |
| Blackboard | Shared knowledge space | Complex problem solving | Hard testing, complexity | AI, diagnosis |
| Space-based | Distributed in-memory processing | High scalability, low latency | Very complex | High-load systems |
| Peer-to-peer | Nodes act as client and server | Decentralization, resilience | Security/control issues | Blockchain, file sharing |
