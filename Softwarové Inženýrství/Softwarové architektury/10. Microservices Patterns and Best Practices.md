# Microservices Patterns and Best Practices

> **Zkouškový fokus:** umět popsat decomposition, database per service, Saga, Outbox, Event Sourcing, CQRS, API Composition, resiliency patterns, API Gateway a observability.

## 1. Proč microservices potřebují patterns

Microservices nejsou jen rozdělení aplikace na více malých služeb.

Jakmile systém rozdělíme přes síť, vzniknou nové problémy:

```text
jak správně rozdělit služby
jak zajistit data ownership
jak řešit konzistenci dat
jak implementovat queries přes více služeb
jak zabránit cascading failures
jak verzovat API
jak monitorovat request přes mnoho služeb
jak nasazovat služby nezávisle
```

Proto se u microservices používá sada architektonických patternů a best practices.

Důležitá zkoušková věta:

> Microservices require patterns because they replace local in-process complexity with distributed system complexity.

---

## 2. Základní principy dobré microservice architecture

Dobrá microservice architecture má typicky tyto vlastnosti:

```text
services are organized around business capabilities
each service has clear responsibility
each service owns its data
services communicate through explicit contracts
services are independently deployable
services are loosely coupled
services are observable
services are designed for failure
```

Špatná microservice architecture často vypadá takto:

```text
too many tiny services
shared database
synchronous chains everywhere
unclear service ownership
no monitoring
no CI/CD
breaking API changes
manual deployment
```

---

# Service decomposition

## 3. Decomposition by business capability

## 3.1 Princip

Nejdůležitější microservice pattern je správné rozdělení systému.

**Decompose by business capability** znamená, že služby odpovídají business funkcím systému.

Dobré příklady:

```text
Order Service
Payment Service
Inventory Service
Shipping Service
Customer Service
Notification Service
```

Špatné příklady:

```text
Controller Service
Repository Service
Database Service
Validation Service
```

To je technické rozdělení, ne business rozdělení.

---

## 3.2 Proč business capability

Business capability je relativně stabilní.

Například v e-shopu budou skoro vždy existovat:

```text
orders
payments
customers
inventory
shipping
```

Implementace se může měnit, ale business oblasti zůstávají.

Výhody:

```text
lepší ownership
lepší team autonomy
menší coupling
služby odpovídají business jazyku
snazší komunikace s doménovými experty
```

---

## 3.3 Příklad

E-shop:

```text
Product Catalog Service
- manages product information
- owns product metadata

Order Service
- creates and manages orders
- owns order lifecycle

Payment Service
- processes payments
- owns payment transactions

Inventory Service
- manages stock
- owns stock reservations

Shipping Service
- manages delivery
- owns shipment tracking
```

Každá služba má jasnou business odpovědnost.

---

## 4. Decomposition by DDD subdomain

## 4.1 Princip

DDD znamená **Domain-Driven Design**.

DDD pomáhá rozdělit systém podle domény.

Důležité pojmy:

```text
domain
subdomain
bounded context
ubiquitous language
aggregate
domain event
```

---

## 4.2 Bounded Context

**Bounded Context** je hranice, uvnitř které má model přesný význam.

Příklad:

```text
Customer in Sales context
Customer in Support context
Customer in Billing context
```

Slovo “Customer” může znamenat něco trochu jiného v každém kontextu.

Proto je lepší mít jasné hranice.

---

## 4.3 Bounded context and microservices

Často platí:

```text
one bounded context can become one microservice
```

Ne vždy přesně, ale je to dobré vodítko.

Příklad:

```text
Ordering Context → Order Service
Payment Context → Payment Service
Shipping Context → Shipping Service
Inventory Context → Inventory Service
```

---

## 4.4 Ubiquitous Language

**Ubiquitous language** je společný jazyk mezi vývojáři a doménovými experty.

Příklad v ordering context:

```text
Order
OrderItem
Checkout
Reservation
Cancellation
Refund
```

Výhoda:

```text
kód odpovídá business jazyku
méně nedorozumění
lepší modelování domény
```

---

## 5. Single Responsibility Principle at service level

Služba by měla mít malou, ale smysluplnou odpovědnost.

Ne příliš velká:

```text
ECommerceService handles users, orders, payments, shipping and inventory.
```

Ne příliš malá:

```text
CreateOrderService
CancelOrderService
UpdateOrderStatusService
```

Lepší:

```text
Order Service owns order lifecycle.
```

Zkoušková formulace:

> A microservice should be small enough to be owned and understood by one team, but large enough to represent a meaningful business capability.

---

## 6. Wrong cuts

Špatné rozdělení služeb je jeden z největších problémů microservices.

Typické wrong cuts:

```text
services by technical layer
services by database table
service per CRUD entity
service per small feature
service boundaries crossing business transactions too often
```

Důsledky:

```text
chatty communication
distributed monolith
data consistency problems
hard deployment
hard testing
```

# Data ownership and consistency

## 7. Database per service

## 7.1 Princip

Každá služba vlastní svoje data.

```text
Order Service owns order database/tables.
Payment Service owns payment database/tables.
Inventory Service owns inventory database/tables.
```

Jiná služba nesmí přímo číst nebo zapisovat interní tabulky jiné služby.

---

## 7.2 Proč je to důležité

Pokud služby sdílí databázi:

```text
schema changes can break other services
ownership is unclear
services are tightly coupled
independent deployment becomes harder
```

Správně:

```text
services communicate through APIs or events
```

Špatně:

```text
Payment Service directly updates orders table
```

---

## 7.3 Fyzická vs logická databáze

Database per service nemusí vždy znamenat fyzicky oddělený DB server.

Možnosti:

```text
separate database server per service
separate database schema per service
separate tables with strict ownership
```

Nejdůležitější je:

```text
logical ownership
```

Tedy že pouze vlastník dat je smí měnit.

---

## 8. Shared persistence antipattern

**Shared persistence** znamená, že více služeb přímo používá stejné databázové tabulky.

Problém:

```text
hidden coupling
schema cannot evolve independently
services are not autonomous
testing is harder
data ownership is unclear
```

Lepší alternativy:

```text
API access
domain events
data replication through events
CQRS read model
API composition
```

---

## 9. Distributed transactions problem

V monolitu:

```text
begin transaction
create order
reserve inventory
create payment
commit transaction
```

V microservices:

```text
Order Service has own database
Payment Service has own database
Inventory Service has own database
```

Nelze jednoduše použít jednu ACID transakci přes všechny služby.

Proto se často používají:

```text
Saga
eventual consistency
compensating transactions
Outbox Pattern
Event Sourcing
```

---

## 10. Saga Pattern

## 10.1 Princip

**Saga** je business transakce rozdělená na sekvenci lokálních transakcí.

Každý krok:

```text
updates local database
publishes event or sends command
triggers next step
```

Pokud některý krok selže, spustí se kompenzační akce.

---

## 10.2 Příklad order saga

```text
1. Order Service creates order with status PENDING
2. Payment Service authorizes payment
3. Inventory Service reserves items
4. Shipping Service creates shipment
5. Order Service marks order as CONFIRMED
```

Pokud Inventory Service selže:

```text
Payment Service refunds or cancels payment authorization
Order Service marks order as REJECTED
```

---

## 10.3 Compensating transaction

Kompenzace není technický rollback.

Je to business operace, která opraví předchozí krok.

Příklad:

```text
payment was captured → issue refund
inventory was reserved → release reservation
shipment was created → cancel shipment
```

Důležité:

```text
not everything can be perfectly undone
```

Proto musí být saga navržena podle business pravidel.

---

## 10.4 Choreography-based saga

Služby reagují na eventy.

Příklad:

```text
Order Service publishes OrderCreated.
Payment Service reacts and publishes PaymentAuthorized.
Inventory Service reacts and publishes InventoryReserved.
Shipping Service reacts and publishes ShipmentCreated.
Order Service reacts and confirms order.
```

Výhody:

```text
loose coupling
no central orchestrator
services are autonomous
```

Nevýhody:

```text
workflow is harder to see
debugging is harder
cyclic event dependencies can appear
```

---

## 10.5 Orchestration-based saga

Centrální orchestrator řídí kroky.

Příklad:

```text
OrderSagaOrchestrator:
1. command Payment Service
2. command Inventory Service
3. command Shipping Service
4. command Order Service to confirm
```

Výhody:

```text
workflow is explicit
easier to monitor
easier to reason about business process
```

Nevýhody:

```text
orchestrator can become too central
higher coupling to process controller
risk of distributed monolith
```

---

## 10.6 Kdy použít Saga

Saga se hodí, když:

```text
business transaction spans multiple services
strong ACID transaction is not available
eventual consistency is acceptable
compensating actions exist
```

Nehodí se, pokud:

```text
business cannot tolerate temporary inconsistency
operations cannot be compensated
domain boundaries are probably wrong
```

---

## 11. Outbox Pattern

## 11.1 Problém

Služba často potřebuje atomicky:

```text
update database
publish event
```

Špatný scénář:

```text
database update succeeds
event publishing fails
```

Výsledek:

```text
data changed, but other services do not know
```

Druhý špatný scénář:

```text
event published
database update fails
```

Výsledek:

```text
other services react to event about change that did not happen
```

---

## 11.2 Řešení

Služba zapíše business změnu i event do stejné databázové transakce.

```text
orders table
outbox_events table
```

Flow:

```text
1. update order
2. insert event into outbox table
3. commit transaction
4. background publisher reads outbox
5. publisher sends event to broker
6. event is marked as published
```

---

## 11.3 Výhody

```text
atomic database update and event creation
higher reliability
prevents lost events
works well with event-driven systems
```

## 11.4 Nevýhody

```text
more infrastructure
publisher process needed
duplicate event delivery possible
consumers must be idempotent
```

---

## 12. Event Sourcing

## 12.1 Princip

**Event Sourcing** ukládá stav systému jako sekvenci eventů, ne jen jako aktuální stav.

Místo:

```text
Order(id=1, status=PAID)
```

uložíme:

```text
OrderCreated
PaymentAuthorized
PaymentCaptured
OrderConfirmed
```

Aktuální stav se získá přehráním eventů.

---

## 12.2 Výhody

```text
complete audit log
can reconstruct past state
events can drive integration
good fit for complex domain events
reliable event publishing
```

---

## 12.3 Nevýhody

```text
higher complexity
learning curve
event versioning
harder querying
eventual consistency with read models
debugging requires event understanding
```

---

## 12.4 Kdy použít Event Sourcing

Vhodné pro:

```text
audit-critical systems
financial systems
complex domain workflows
systems where history matters
event-driven domains
```

Nevhodné pro:

```text
simple CRUD
small applications
teams without experience
domains where only current state matters
```

---

## 13. CQRS

## 13.1 Princip

**CQRS** znamená **Command Query Responsibility Segregation**.

Odděluje:

```text
commands = write operations
queries = read operations
```

Write model řeší změny stavu.

Read model řeší rychlé čtení.

---

## 13.2 Příklad

Command side:

```text
CreateOrder
CancelOrder
PayOrder
ShipOrder
```

Query side:

```text
GetOrderDetail
ListCustomerOrders
GetDashboardStatistics
```

Read model může být denormalizovaný.

Příklad:

```text
order_summary_view
customer_order_history_view
dashboard_stats_view
```

---

## 13.3 Výhody CQRS

```text
read and write models can be optimized separately
supports complex queries
works well with Event Sourcing
supports scalable denormalized views
improves separation of concerns
```

---

## 13.4 Nevýhody CQRS

```text
higher complexity
eventual consistency between write and read model
possible code duplication
more infrastructure
harder debugging
```

---

## 13.5 Kdy použít CQRS

Vhodné:

```text
read and write workloads are very different
complex queries across service data
high read scalability needed
event sourcing is used
many denormalized views needed
```

Nevhodné:

```text
simple CRUD application
small system
low complexity domain
```

---

## 14. API Composition

## 14.1 Problém

V microservices jsou data rozdělena mezi služby.

Příklad:

```text
Order Service owns orders
Customer Service owns customers
Payment Service owns payments
```

Klient chce obrazovku:

```text
order detail with customer name and payment status
```

Nelze jednoduše použít SQL join.

---

## 14.2 Řešení

API Composer zavolá více služeb a složí response.

Příklad:

```text
Client → API Composer
API Composer → Order Service
API Composer → Customer Service
API Composer → Payment Service
API Composer → Client
```

---

## 14.3 Výhody

```text
simple concept
no data duplication needed
good for simple aggregation
can be implemented in API Gateway or backend-for-frontend
```

---

## 14.4 Nevýhody

```text
latency from multiple calls
availability depends on multiple services
risk of chatty communication
composer can become too smart
not good for complex high-volume queries
```

---

## 14.5 Kdy použít API Composition

Vhodné:

```text
simple UI aggregation
low to medium traffic
small number of service calls
fresh data required
```

Nevhodné:

```text
heavy analytics
large joins
high-latency chains
complex dashboard queries
```

Pro složitější queries je často lepší CQRS read model.

---

# Communication patterns

## 15. Synchronous communication

Služba zavolá jinou službu a čeká na odpověď.

Příklad:

```text
Order Service → Payment Service
```

Technologie:

```text
REST
gRPC
GraphQL
```

Výhody:

```text
simple mental model
immediate response
easy for request-response use cases
```

Nevýhody:

```text
temporal coupling
latency
caller depends on callee availability
risk of cascading failure
```

Best practices:

```text
timeouts
retries with backoff
circuit breaker
bulkhead
idempotency
avoid long call chains
```

---

## 16. Asynchronous communication

Služba publikuje message/event a nečeká přímo na okamžitou odpověď.

Technologie:

```text
Kafka
RabbitMQ
ActiveMQ
NATS
SNS/SQS
Pub/Sub
```

Výhody:

```text
loose coupling
better resilience
better scalability
good for long-running workflows
good for integration
```

Nevýhody:

```text
eventual consistency
harder debugging
harder user feedback
duplicate messages
ordering problems
```

Best practices:

```text
idempotent consumers
message keys / partitions
dead-letter queue
correlation id
monitoring of queues/topics
outbox pattern
```

---

## 17. Command vs Event

### Command

Command říká:

```text
do something
```

Příklady:

```text
CreateOrder
ReserveInventory
CapturePayment
SendEmail
```

Vlastnosti:

```text
usually one intended receiver
can be accepted or rejected
imperative name
```

### Event

Event říká:

```text
something happened
```

Příklady:

```text
OrderCreated
InventoryReserved
PaymentCaptured
EmailSent
```

Vlastnosti:

```text
can have many consumers
represents fact from the past
producer does not know all consumers
```

---

## 18. Idempotent Consumer

## 18.1 Problém

Message broker může doručit stejnou zprávu vícekrát.

Consumer musí zvládnout duplicate messages.

---

## 18.2 Řešení

Consumer zpracuje stejnou zprávu opakovaně bez změny výsledku.

Techniky:

```text
message id
processed_messages table
idempotency key
unique constraints
deduplication cache
business idempotency
```

Příklad:

```text
PaymentCaptured event arrives twice.
Order is marked as paid only once.
```

---

## 19. Correlation ID

**Correlation ID** propojuje requesty, logy a eventy napříč službami.

Příklad:

```text
correlation_id = abc-123
```

Stejné ID se předává přes:

```text
HTTP headers
message headers
logs
traces
metrics labels where appropriate
```

Výhoda:

```text
can trace one business operation across many services
```

# Resilience patterns

## 20. Timeout

Každé síťové volání musí mít timeout.

Špatně:

```text
Order Service waits forever for Payment Service.
```

Dobře:

```text
Payment call timeout = 3 seconds.
After timeout, order remains PENDING_PAYMENT.
```

Bez timeoutu může jeden pomalý dependency vyčerpat všechny resources calleru.

---

## 21. Retry with backoff

Retry pomáhá při dočasných chybách.

Ale retry bez omezení je nebezpečný.

Špatně:

```text
retry immediately forever
```

Dobře:

```text
retry 3 times
with exponential backoff
with jitter
only for retryable errors
only for idempotent operations
```

Riziko:

```text
retry storm can overload already failing service
```

---

## 22. Circuit Breaker

**Circuit Breaker** chrání před opakovaným voláním selhávající služby.

Stavy:

```text
closed
open
half-open
```

Princip:

```text
closed: calls go through
open: calls fail fast or use fallback
half-open: limited test calls check recovery
```

Výhody:

```text
prevents cascading failures
reduces load on failing service
improves system stability
```

Příklad:

```text
Recommendation Service is down.
Circuit breaker opens.
E-shop hides recommendations instead of blocking checkout.
```

---

## 23. Bulkhead

**Bulkhead** izoluje resources, aby chyba jedné části neohrozila celý systém.

Techniky:

```text
separate thread pools
separate connection pools
separate service instances
separate queues
resource limits
```

Příklad:

```text
Reporting requests have separate thread pool.
If reports are slow, checkout still works.
```

---

## 24. Rate Limiting

Rate limiting omezuje počet requestů.

Použití:

```text
protect API from abuse
protect downstream services
handle traffic spikes
enforce fair usage
```

Příklad:

```text
max 100 requests per minute per user
```

Může být implementováno v:

```text
API Gateway
service mesh
application middleware
load balancer
```

---

## 25. Fallback

Fallback poskytne alternativní odpověď při chybě.

Příklad:

```text
Recommendation Service unavailable
→ return popular products instead
```

Nebo:

```text
Currency rate service unavailable
→ use last known exchange rate
```

Pozor:

```text
fallback must be safe and visible enough
not every operation has safe fallback
```

---

## 26. Graceful Degradation

Systém při chybě zůstane částečně funkční.

Příklad:

```text
Search works.
Checkout works.
Recommendations are temporarily disabled.
```

Cíl:

```text
avoid total outage when non-critical service fails
```

---

# Edge and integration patterns

## 27.1 Princip

API Gateway je jednotný vstupní bod do systému.

```text
Client → API Gateway → internal services
```

Může řešit:

```text
routing
authentication
authorization
rate limiting
request validation
TLS termination
logging
monitoring
protocol translation
response aggregation
```

---

## 27.2 Výhody

```text
clients do not know internal topology
central place for edge concerns
simplifies clients
can hide service decomposition
```

---

## 27.3 Nevýhody

```text

can become too complex
risk of business logic in gateway
single entry point must be highly available
```

Best practice:

```text

not become a central business logic component.
```

---

## 28.2 Výhody

```text
UI-specific aggregation
less frontend complexity

```

---

## 28.3 Nevýhody

```text
more services to maintain
possible duplication
BFF can become too smart
```

```text

traffic routing
load balancing
retries
timeouts
circuit breaking
observability
distributed tracing

access policies
```

Příklady:

```text
Istio

Consul Connect
```

---

## 31.2 Výhody

```text

better observability
```

```text
high operational complexity
learning curve
more moving parts
not needed for small systems
```

> Service mesh does not magically fix bad microservice design. It only helps manage service communication concerns.

# Deployment and cloud-native practices

## 32. Twelve-Factor App

Twelve-Factor App je sada principů pro cloud-native aplikace.

Důležité body:

* **One codebase, many deploys** — jedna codebase v repozitáři, ale může mít více deploymentů, například dev, staging a production.
* **Explicit dependencies** — všechny dependencies musí být jasně deklarované, například v `pom.xml`, `package.json` nebo `requirements.txt`.
* **Config in environment** — konfigurace se neukládá do kódu, ale do environment variables, například DB URL nebo API keys.
* **Backing services as attached resources** — databáze, message broker nebo cache se berou jako připojené externí služby.
* **Strict separation of build, release, run** — build, release a běh aplikace jsou oddělené fáze.
* **Stateless processes** — aplikace neukládá stav lokálně v procesu; stav má být v databázi, cache nebo jiném externím úložišti.
* **Port binding** — aplikace sama poslouchá na portu a poskytuje službu přes HTTP nebo jiný protokol.
* **Scale out via process model** — škálování probíhá spuštěním více instancí procesu.
* **Fast startup and graceful shutdown** — aplikace má rychle startovat a korektně se ukončovat, aby šla snadno restartovat nebo škálovat.
* **Dev/prod parity** — vývojové, testovací a produkční prostředí by si měla být co nejpodobnější.
* **Logs as event streams** — aplikace zapisuje logy jako proud událostí, typicky na `stdout`, a neřeší sama jejich ukládání.
* **Admin tasks as one-off processes** — administrační úlohy, například migrace databáze, se spouštějí jako jednorázové procesy.

# Exam answers

## 63. Zkoušková odpověď: microservices best practices

Microservices should be designed around business capabilities or Domain-Driven Design bounded contexts. Each service should have a clear responsibility, clear owner and explicit API contract. A service should own its data and other services should not access its database directly.

Because microservices are distributed systems, they must be designed for failure. This means using timeouts, retries with backoff, circuit breakers, bulkheads, health checks, monitoring, centralized logging and distributed tracing. Communication should be explicit and stable, using REST, gRPC or asynchronous messaging. For long-running business transactions, patterns such as Saga and eventual consistency are often used.

Microservices also require strong DevOps practices: automated CI/CD, containerization, configuration outside the code, observability, rollback strategy and safe deployment. Without these practices, microservices can easily become more complex and less reliable than a monolith.

---

## 64. Zkoušková odpověď: Saga pattern

The Saga pattern is used to manage a business transaction that spans multiple microservices. Instead of one distributed ACID transaction, a saga is a sequence of local transactions. Each service updates its own database and then triggers the next step, usually by publishing an event or receiving a command.

If one step fails, the saga executes compensating transactions to undo or compensate the previous successful steps. For example, if payment was captured but inventory reservation fails, the compensation can be a refund.

Saga can be implemented using choreography, where services react to events, or orchestration, where a central orchestrator controls the workflow. Choreography gives looser coupling, but the process is harder to trace. Orchestration makes the workflow explicit, but can introduce a central dependency.

---

## 65. Zkoušková odpověď: CQRS and Event Sourcing

CQRS means Command Query Responsibility Segregation. It separates the write model, which handles commands and changes state, from the read model, which handles queries. This allows read and write models to be optimized independently. CQRS is useful when queries are complex, read load is high, or the system needs multiple denormalized views.

Event Sourcing stores the state of a system as a sequence of events instead of only storing the current state. The current state can be reconstructed by replaying events. It provides a complete audit log and works well with event-driven systems, but it increases complexity and makes querying harder. Event Sourcing is often combined with CQRS, where events update read models asynchronously.

---

## 66. Zkoušková odpověď: API Gateway and Service Mesh

An API Gateway is the entry point for clients into a microservice system. It can handle routing, authentication, authorization, rate limiting, TLS termination, logging and request aggregation. It hides the internal service topology from clients. However, it can become a bottleneck or a place where too much business logic is accumulated.

A service mesh manages service-to-service communication inside the system. It often uses sidecar proxies and provides features such as service discovery, load balancing, retries, timeouts, mTLS, traffic routing, observability and tracing. A service mesh helps with operational concerns, but it also increases complexity and does not fix bad service design.

---

## 67. Zkoušková odpověď: database per service

Database per service means that each microservice owns its data. Other services must not directly access or modify its database. They should use the service API or consume events.

This improves loose coupling, independent deployment and clear data ownership. However, it makes cross-service queries and transactions harder. Since one ACID transaction across multiple services is usually avoided, systems often use Saga, eventual consistency, API Composition, CQRS or event-driven read models.

Shared database between services is an antipattern because it creates hidden coupling and makes schema changes dangerous.
