# Microservices vs Monolith

> **Zkouškový fokus:** umět porovnat monolith a microservices podle vývoje, deploymentu, škálování, transakcí, testování, týmů a provozní komplexity.

## 1. Proč je toto důležité

Otázka **monolith vs microservices** je jedna z nejčastějších zkouškových otázek v SWA.

Není správné říct:

```text
microservices are good
monolith is bad
```

Správná odpověď:

```text
záleží na kontextu
záleží na požadavcích
záleží na týmu
záleží na provozní zralosti
záleží na očekávaném růstu systému
záleží na quality attributes
```

Hlavní zkoušková myšlenka:

> Microservices are not a universal replacement for monoliths. They solve some problems of large monoliths, but introduce distributed system complexity.

---

## 2. Monolithic architecture

## 2.1 Definice

**Monolithic architecture** je architektura, kde je aplikace nasazena jako jeden celek.

Typicky:

```text
one codebase
one deployable artifact
one runtime process or closely connected processes
one primary database
all main business capabilities inside one application
```

Příklad:

```text
E-shop as one Spring Boot application:

- user management
- product catalog
- shopping cart
- orders
- payments
- admin
- notifications
```

Všechno je součástí jedné aplikace.

---

## 2.2 Monolith neznamená automaticky chaos

Monolith může být:

```text
well-structured
layered
modular
testable
maintainable
```

Špatný monolith je často:

```text
Big Ball of Mud
```

To znamená:

```text
žádné jasné hranice
všechno závisí na všem
business logic je rozptýlená všude
změny jsou rizikové
```

Důležitá věta:

> The problem is not monolith itself. The problem is an unstructured monolith.

---

## 3. Typická struktura monolitu

Monolit může být například layered:

```text
Controller layer
Service layer
Repository layer
Database
```

Nebo modular monolith:

```text
User module
Order module
Payment module
Inventory module
Notification module
```

Rozdíl:

```text
ordinary monolith can have weak boundaries
modular monolith intentionally defines strong internal boundaries
```

---

## 4. Výhody monolitu

## 4.1 Simpler development

Vývoj je jednodušší, protože:

```text
všechno je v jedné codebase
není potřeba řešit síťovou komunikaci mezi částmi
lokální spuštění je jednodušší
vývojář vidí celý systém na jednom místě
```

Příklad:

```text
OrderService může přímo zavolat PaymentService jako lokální metodu.
```

V microservices by to bylo síťové volání nebo event.

---

## 4.2 Simpler deployment

Monolith se typicky nasazuje jako jeden artifact.

Příklad:

```text
one .jar file
one Docker image
one deployment
```

Výhoda:

```text
méně deployment pipelines
méně konfigurace
méně verzovacích problémů mezi službami
```

---

## 4.3 Easier debugging

Debugging je jednodušší, protože request často běží v jednom procesu.

```text
breakpoint in controller
breakpoint in service
breakpoint in repository
```

Není potřeba sledovat request přes mnoho služeb.

---

## 4.4 Easier testing

End-to-end nebo integration testy mohou být jednodušší.

```text
start application
start database
run tests
```

U microservices může být potřeba spustit:

```text
several services
message broker
service discovery
API gateway
multiple databases
```

---

## 4.5 Easier transactions

V monolitu je často jedna databáze.

To umožňuje klasické ACID transakce.

Příklad:

```text
create order
reserve inventory
create payment record
```

může být v jedné databázové transakci.

V microservices jsou tyto operace často v různých databázích a je potřeba Saga nebo eventual consistency.

---

## 4.6 Lower operational complexity

Monolith obvykle nepotřebuje tolik infrastruktury.

Může stačit:

```text
application server
database
reverse proxy
monitoring
```

Microservices často potřebují:

```text
API gateway
service discovery
message broker
centralized logging
distributed tracing
container orchestration
configuration management
secrets management
service mesh sometimes
```

---

## 5. Nevýhody monolitu

## 5.1 Growing complexity

Jak aplikace roste, monolith může být těžší pochopit.

Symptomy:

```text
large codebase
many modules without clear boundaries
hard onboarding
developers afraid of changes
slow builds
slow tests
```

---

## 5.2 Tight coupling

Pokud nejsou hranice dobře nastavené, části systému se silně provážou.

Příklad:

```text
Payment logic directly reads and modifies order tables.
Order logic directly depends on notification internals.
Admin logic directly calls repository of every module.
```

Problém:

```text
změna jedné části rozbije jinou část
refactoring je riskantní
moduly nejsou samostatné
```

---

## 5.3 Slower development in large teams

Více týmů pracuje ve stejné codebase.

Problémy:

```text
merge conflicts
unclear ownership
longer code reviews
coordination overhead
shared release cycle
```

---

## 5.4 One deployment unit

I malá změna vyžaduje deployment celé aplikace.

Příklad:

```text
change in notification logic
→ deploy whole monolith
```

Riziko:

```text
větší release
větší regression risk
pomalejší release cycle
```

---

## 5.5 Limited independent scaling

Monolith se škáluje jako celek.

Příklad:

```text
Only product search is under heavy load.
But we must scale the whole application.
```

To může být dražší než škálovat pouze jednu část.

---

## 5.6 Technology lock-in

Celý systém typicky používá jeden hlavní technology stack.

Příklad:

```text
Java + Spring + PostgreSQL
```

Pokud chceme jednu část přepsat do Go nebo použít jinou databázi, je to obtížnější než u samostatné služby.

---

## 6. Kdy zvolit monolith

Monolith je dobrá volba, pokud:

```text
small team
simple or medium business domain
early project / MVP
need fast delivery
limited DevOps maturity
unclear domain boundaries
low or moderate scale
one team owns whole system
```

Příklad:

```text
startup building first version of product
school information system for limited users
internal admin tool
simple e-commerce MVP
```

Bezpečná věta:

> For many systems, a well-structured modular monolith is the best starting point.

---

## 7. Microservices architecture

## 7.1 Definice

**Microservices architecture** strukturuje aplikaci jako kolekci malých služeb.

Každá služba je:

```text
loosely coupled
independently deployable
independently scalable
organized around business capability
owned by a small team
```

Příklad:

```text
User Service
Product Service
Order Service
Payment Service
Inventory Service
Notification Service
```

---

## 7.2 Hlavní rozdíl oproti monolitu

V monolitu:

```text
components communicate by local method calls
one deployment unit
often one database
```

V microservices:

```text
services communicate over network
each service can be deployed independently
each service should own its data
```

---

## 8. Business capability orientation

Microservices by měly být rozdělené podle business capabilities.

Dobře:

```text
Order Service
Payment Service
Shipping Service
Customer Service
Inventory Service
```

Špatně:

```text
Controller Service
Business Logic Service
Repository Service
Database Service
```

To by bylo technické rozdělení vrstev přes síť a často vede k distributed monolith.

---

## 9. Service ownership

Každá microservice by měla mít jasného vlastníka.

Typicky:

```text
one small team owns one or more services
```

Team owns:

```text
code
tests
deployment
monitoring
incidents
API contract
data model
documentation
```

To podporuje team autonomy.

---

## 10. Výhody microservices

## 10.1 Independent deployment

Každá služba může být nasazena samostatně.

Příklad:

```text
Payment Service can be deployed without deploying Order Service.
```

Výhoda:

```text
rychlejší release
menší deployment risk
týmy se méně blokují
```

Podmínka:

```text
stable and backward-compatible API contracts
good CI/CD
automated tests
monitoring
```

---

## 10.2 Independent scalability

Každou službu lze škálovat podle její zátěže.

Příklad:

```text
Product Search Service needs 20 replicas.
User Profile Service needs 2 replicas.
```

Výhoda:

```text
lepší využití infrastruktury
nižší náklady
lepší performance pro zatížené části
```

---

## 10.3 Fault isolation

Chyba v jedné službě nemusí shodit celý systém.

Příklad:

```text
Recommendation Service is down.
E-shop still allows browsing and checkout.
```

Podmínka:

```text
graceful degradation
timeouts
circuit breakers
fallbacks
```

Bez těchto mechanismů může chyba jedné služby způsobit cascading failure.

---

## 10.4 Team autonomy

Microservices podporují autonomní týmy.

Tým může rozhodovat o:

```text
implementation details
release schedule
internal data model
service-specific technology choices
```

Ale musí respektovat:

```text
API contracts
security rules
observability standards
deployment standards
organization-wide governance
```

---

## 10.5 Technology flexibility

Každá služba může teoreticky používat jiný technology stack.

Příklad:

```text
Order Service: Java + PostgreSQL
Recommendation Service: Python + ML stack
Notification Service: Node.js
```

Výhoda:

```text
lepší volba technologie pro konkrétní problém
```

Riziko:

```text
too many technologies
vyšší provozní komplexita
těžší hiring
těžší support
```

---

## 10.6 Smaller codebases

Každá služba má menší codebase než celý monolith.

Výhody:

```text
rychlejší pochopení služby
rychlejší build
rychlejší testy služby
menší scope změn
```

Pozor:

```text
celková komplexita systému může být vyšší,
i když jednotlivé služby jsou menší.
```

---

## 11. Nevýhody microservices

## 11.1 Distributed complexity

Microservices jsou distribuovaný systém.

To znamená:

```text
network calls can fail
latency is not zero
services can be temporarily unavailable
data is distributed
debugging requires observability
```

Lokální method call v monolitu se mění na:

```text
HTTP/gRPC call
message publishing
event consumption
timeout
retry
authentication
serialization
versioning
```

---

## 11.2 Harder testing

Testování je těžší kvůli mnoha službám.

Typy testů:

```text
unit tests
service tests
contract tests
integration tests
end-to-end tests
consumer-driven contract tests
resilience tests
```

Problém:

```text
end-to-end test environment is expensive and fragile
```

Proto se často používá:

```text
contract testing
test doubles
local containers
staging environments
```

---

## 11.3 Harder debugging

Request může projít mnoha službami.

Příklad:

```text
API Gateway
→ Order Service
→ Payment Service
→ Fraud Service
→ Inventory Service
→ Notification Service
```

K debugování potřebujeme:

```text
correlation id
centralized logs
distributed tracing
metrics
service dashboards
```

---

## 11.4 Data consistency

Každá služba by měla vlastnit svá data.

To znamená:

```text
no single database transaction across all services
```

Příklad:

```text
Order created in Order Service
Payment processed in Payment Service
Inventory reserved in Inventory Service
```

Mezi těmito kroky může být systém dočasně nekonzistentní.

Řešení:

```text
Saga
eventual consistency
compensating transactions
outbox pattern
idempotency
```

---

## 11.5 API versioning and compatibility

Služby komunikují přes API.

Breaking change může rozbít consumer services.

Příklad breaking changes:

```text
remove endpoint
remove field from response
change field type
make optional field required
change semantics of operation
```

Proto jsou důležité:

```text
API versioning
backward-compatible changes
consumer-driven contracts
OpenAPI / Protobuf contracts
deprecation policy
```

---

## 11.6 Deployment complexity

Microservices vyžadují zralejší deployment proces.

Potřebujeme:

```text
CI/CD
containerization
service discovery
configuration management
secrets management
rolling deployment
rollback strategy
monitoring
logging
alerting
```

Bez toho je microservices architecture velmi riziková.

---

## 11.7 Operational overhead

Každá služba potřebuje:

```text
build pipeline
deployment
monitoring
logs
alerts
documentation
security configuration
runtime resources
```

Pokud je služeb mnoho, provozní náklady výrazně rostou.

---

## 12. Kdy zvolit microservices

Microservices dávají smysl, pokud:

```text
system is large and complex
multiple teams work independently
business capabilities evolve independently
independent deployment is valuable
different parts need different scaling
organization has DevOps maturity
team understands distributed systems
strong observability exists
domain boundaries are clear
```

Příklad:

```text
large e-commerce platform
streaming platform
banking ecosystem
large SaaS platform
IoT backend
marketplace platform
```

---

## 13. Kdy microservices nezvolit

Microservices jsou špatná volba, pokud:

```text
small team
simple application
early MVP
unclear domain boundaries
no DevOps experience
no CI/CD
no monitoring
no need for independent scaling
deployment of monolith is not a problem
```

Důležitá věta:

> Do not start with microservices only because they are modern. Start with them only when their benefits justify their complexity.

---

## 14. Microservice premium

Microservices mají “premium”, tedy dodatečnou cenu.

Tato cena zahrnuje:

```text
infrastructure complexity
deployment complexity
monitoring and tracing
network reliability
data consistency
service contracts
team coordination
security between services
```

Proto:

```text
benefits must be greater than this premium
```

Pokud nejsou, microservices zhorší produktivitu.

---

## 15. Modular monolith as a middle ground

Mezi špatným monolitem a microservices existuje dobrá střední cesta:

```text
modular monolith
```

Vlastnosti:

```text
one deployment
clear modules
business capability boundaries
controlled dependencies
simple transactions
lower operational complexity
```

Příklad:

```text
Order module
Payment module
User module
Inventory module
```

Důležitá věta:

> A modular monolith can preserve simplicity while preparing the system for possible future extraction into microservices.

---

## 16. Monolith to microservices migration

Migrace by neměla být “big bang”.

Lepší je postupný přístup.

Typický proces:

```text
1. stabilize monolith
2. identify domain boundaries
3. modularize internally
4. extract one service at a time
5. define API contracts
6. move data ownership carefully
7. add observability and CI/CD
```

---

## 17. Strangler Fig Pattern

**Strangler Fig Pattern** znamená postupné nahrazování monolitu novými službami.

Princip:

```text
new functionality is built outside monolith
old functionality remains in monolith
traffic is gradually routed to new services
monolith is slowly reduced
```

Příklad:

```text
API Gateway routes:
- /old/* to monolith
- /payments/* to new Payment Service
- /orders/* still to monolith
```

Výhoda:

```text
nižší riziko než kompletní rewrite
```

Nevýhoda:

```text
dočasně vyšší komplexita, protože běží starý i nový systém
```

---

## 18. Database migration problem

Nejtěžší část migrace na microservices bývá data ownership.

Špatně:

```text
new Payment Service still directly uses monolith database tables
```

To není skutečná service autonomy.

Lépe:

```text
Payment Service owns payment data.
Monolith communicates through API or events.
```

Ale migrace dat vyžaduje:

```text
data synchronization
backward compatibility
dual writes risk
outbox pattern
event-driven synchronization
careful cutover
```

---

## 19. Development differences

## 19.1 Monolith development

Typicky:

```text
one repository
one build
one deployment pipeline
one database schema
local development easier
```

Výhody:

```text
rychlejší start
méně infrastruktury
snazší refactoring across modules
```

Nevýhody:

```text
velký build
velké test suite
shared release cycle
```

---

## 19.2 Microservices development

Typicky:

```text
multiple repositories or monorepo with many services
many deployment pipelines
many databases
many API contracts
service-specific ownership
```

Výhody:

```text
team autonomy
independent deployment
independent scaling
```

Nevýhody:

```text
těžší lokální development
nutnost mockovat nebo spouštět dependent services
contract compatibility problems
integration complexity
```

---

## 20. Repository strategy

### Monorepo

Všechny služby v jednom repository.

Výhody:

```text
jednodušší koordinované změny
jedno místo pro code search
sdílená tooling konfigurace
```

Nevýhody:

```text
velký repository
nutnost dobré CI selekce
možné slabší ownership boundaries
```

### Polyrepo

Každá služba má vlastní repository.

Výhody:

```text
jasné ownership
nezávislý release
menší repository
```

Nevýhody:

```text
těžší koordinované změny
více repository managementu
složitější dependency tracking
```

---

## 21. Communication differences

## 21.1 Monolith

Komunikace je lokální.

```text
method calls
in-memory objects
same transaction
same process
```

Výhoda:

```text
rychlé
jednoduché
snadnější refactoring
```

---

## 21.2 Microservices

Komunikace je síťová nebo messaging.

```text
REST
gRPC
message broker
events
queues
streams
```

Nutno řešit:

```text
serialization
timeouts
retries
idempotency
versioning
authentication
authorization
observability
```

---

## 22. Synchronous vs asynchronous communication

### Synchronous

Příklad:

```text
Order Service calls Payment Service and waits for response.
```

Výhody:

```text
jednoduchý mental model
okamžitá odpověď
snadnější error handling v jednoduchých případech
```

Nevýhody:

```text
vyšší coupling
latence
downstream service failure affects caller
riziko cascading failures
```

---

### Asynchronous

Příklad:

```text
Order Service publishes OrderCreated event.
Payment Service processes event later.
```

Výhody:

```text
looser coupling
lepší resilience
lepší scalability
vhodné pro long-running workflows
```

Nevýhody:

```text
eventual consistency
těžší debugging
těžší user feedback
nutnost idempotency
```

---

## 23. Data management comparison

| Aspect | Monolith | Microservices |
|---|---|---|
| Database | often one database | database per service preferred |
| Transactions | simpler ACID transactions | distributed transactions avoided |
| Consistency | strong consistency easier | eventual consistency common |
| Schema change | one schema, coordinated | each service owns schema |
| Reporting | easier joins | harder cross-service queries |
| Data ownership | can be unclear | should be explicit |

---

## 24. Query problem in microservices

V monolitu:

```text
SELECT orders + customers + payments with SQL join
```

V microservices:

```text
Order data in Order Service
Customer data in Customer Service
Payment data in Payment Service
```

Nelze jednoduše udělat join přes databáze služeb.

Možná řešení:

```text
API Composition
CQRS read model
materialized views
event-driven replication
data warehouse for analytics
```

---

## 25. Testing comparison

| Test type         | Monolith           | Microservices          |
| ----------------- | ------------------ | ---------------------- |
| Unit tests        | simple             | simple inside service  |
| Integration tests | app + db           | service + dependencies |
| E2E tests         | easier environment | complex and fragile    |
| Contract tests    | useful             | critical               |
| Performance tests | app-level          | service + system-level |
| Resilience tests  | less needed        | very important         |

---

## 26. Deployment comparison

| Aspect | Monolith | Microservices |
|---|---|---|
| Deployment unit | whole app | individual services |
| Release coordination | centralized | decentralized |
| Rollback | one artifact | per service, but dependencies matter |
| Infrastructure | simpler | more complex |
| CI/CD | one/few pipelines | many pipelines |
| Compatibility | internal code compatibility | API contract compatibility |

---

## 27. Scalability comparison

## 27.1 Monolith scaling

Monolith lze škálovat horizontálně:

```text
run multiple instances behind load balancer
```

Toto se někdy označuje jako X-axis scaling.

Výhoda:

```text
jednoduché
zvyšuje kapacitu a dostupnost
```

Nevýhoda:

```text
škáluje se celý systém
```

---

## 27.2 Microservices scaling

Microservices umožňují škálovat jednotlivé služby.

Příklad:

```text
Search Service: 20 replicas
Order Service: 5 replicas
Admin Service: 1 replica
```

Výhoda:

```text
lepší využití zdrojů
škálování podle reálné zátěže
```

Nevýhoda:

```text
složitější orchestrace a monitoring
```

---

## 28. Fault isolation comparison

Monolith:

```text
bug can affect whole application
shared memory/process/resources
```

Microservices:

```text
bug can be isolated to one service
```

Ale pouze pokud existuje:

```text
timeouts
circuit breakers
fallbacks
bulkheads
graceful degradation
```

Jinak může microservice failure způsobit cascading failure.

---

## 29. Security comparison

Monolith:

```text
security mostly inside one application boundary
fewer network boundaries
centralized authorization easier
```

Microservices:

```text
more network communication
service-to-service authentication needed
distributed authorization
secrets management for many services
larger attack surface
```

Microservices potřebují:

```text
mTLS (**mutual TLS**) or service identity
API gateway security
centralized identity provider
consistent authorization model
secure secret storage
```

---

## 30. Observability comparison

Monolith:

```text
logs from one application
simpler stack traces
simpler metrics
```

Microservices:

```text
logs from many services
need correlation id
need distributed tracing
need service dashboards
need centralized logging
```

Without observability:

```text
microservices are almost impossible to operate reliably
```

## 32. Conway’s Law

Conway’s Law říká:

```text
Organizations design systems that mirror their communication structures.
```

Dopad:

```text
Pokud má firma týmy podle business capabilities,
microservices mohou přirozeně odpovídat organizaci.
```

Příklad:

```text
Payments team → Payment Service
Orders team → Order Service
Shipping team → Shipping Service
```

Pokud je organizace špatně nastavena, microservices mohou kopírovat špatnou strukturu.

## 33. Common microservices antipatterns

## 33.1 Microservices as the goal

Špatně:

```text
Our goal is to have 100 microservices.
```

Správně:

```text
Our goal is faster delivery, scalability or better team autonomy.
Microservices are only a means, not the goal.
```

---

## 33.2 Magic pixie dust

Představa, že microservices automaticky vyřeší problémy.

Realita:

```text
špatný design v monolitu se často jen změní na špatný distributed design
```

---

## 33.3 Distributed monolith

Služby jsou oddělené deploymentem, ale silně závislé.

Symptomy:

```text
must deploy services together
long synchronous call chains
shared database

```

## 35. Twelve-Factor App relevance

Twelve-Factor App principy jsou užitečné pro cloud-native a microservices aplikace.

Důležité body:

* **One codebase, many deploys** — jedna codebase v repozitáři, ale může mít více deploymentů, například dev, staging a production.
* **Explicit dependencies** — všechny dependencies musí být jasně deklarované, například v `pom.xml`, `package.json` nebo `requirements.txt`.
* **Config in environment** — konfigurace se neukládá do kódu, ale do environment variables, například DB URL nebo API keys.
* **Backing services as attached resources** — databáze, message broker nebo cache se berou jako připojené externí služby.
* **Strict separation of build, release, run** — build, release a běh aplikace jsou oddělené fáze.
* **Stateless processes** — aplikace neukládá stav lokálně v procesu; stav má být v databázi, cache nebo jiném externím úložišti.
* **Port binding** — aplikace sama poslouchá na portu a poskytuje službu přes HTTP nebo jiný protokol.
* **Scale out via process model** — škálování probíhá spuštěním více instancí procesu.
* **Fast startup and graceful shutdown** — aplikace má rychle startovat a korektně se ukončovat, aby šla snadno restartovat nebo škálovat.
* **Dev/prod parity** — vývojové, testovací a produkční prostředí by si měla být co nejpodobnější.
* **Logs as event streams** — aplikace zapisuje logy jako proud událostí, typicky na `stdout`, a neřeší sama jejich ukládání.
* **Admin tasks as one-off processes** — administrační úlohy, například migrace databáze, se spouštějí jako jednorázové procesy.

Nejde o microservices-only pravidla, ale pro microservices jsou velmi relevantní.

## 36. Design for failure

V microservices architektuře musíme počítat s tím, že některé části systému mohou kdykoliv selhat nebo být pomalé.

Může selhat například:

- **Service** — služba může spadnout nebo být dočasně nedostupná.
- **Network** — síť může mít výpadky, vysokou latenci nebo ztrácet requesty.
- **Database** — databáze může být přetížená nebo nedostupná.
- **Message broker** — Kafka, RabbitMQ nebo jiný broker nemusí dočasně přijímat zprávy.
- **External API** — externí služba může odpovídat pomalu nebo vůbec.

Proto se systém navrhuje tak, aby s chybami počítal.

- **Timeouts** — request nesmí čekat nekonečně dlouho.
- **Retries with backoff** — opakování requestu s postupně delší prodlevou.
- **Circuit breakers** — dočasné zastavení volání služby, která opakovaně selhává.
- **Bulkheads**  (способ или техника изоляции при ошибке) — oddělení částí systému, aby chyba jedné části neshodila celý systém. (Recommendation Service использует отдельный thread pool / connection pool.
Если он завис, он не забирает ресурсы у Product Service, Cart Service и Checkout.) (graceful shutdown - стратегия системы чтобы работала в ограниченном режиме если что то не работает и не падала полностью система, поведение системы при отказе)
- **Fallbacks** — náhradní odpověď nebo zjednodušené chování při selhání.
- **Health checks** — kontrola, jestli služba běží a je připravená přijímat requesty.
- **Graceful shutdown** — služba se při vypnutí ukončí korektně a dokončí rozpracované requesty.
- **Idempotency** — opakované zpracování stejného requestu nezpůsobí duplicitní změny.
- **Dead-letter queues** — zprávy, které nejdou zpracovat, se uloží zvlášť pro pozdější analýzu.

## 41. Zkoušková odpověď: monolith vs microservices

A monolithic architecture deploys the application as one unit. It usually has one codebase, one main deployment artifact and often one database. Its advantages are simple development, simple deployment, easier debugging, easier testing and simpler transactions. Its disadvantages appear when the system grows: the codebase can become hard to understand, changes become risky, teams can block each other and the whole application must be deployed and scaled together.

Microservices architecture structures an application as a set of small, loosely coupled and independently deployable services organized around business capabilities. Its advantages are independent deployment, independent scaling, team autonomy, better fault isolation and technology flexibility. Its disadvantages are distributed system complexity, harder testing and debugging, network failures, data consistency problems, API versioning and higher operational requirements.

Neither architecture is universally better. A well-structured modular monolith can be the best choice for small or medium systems. Microservices are useful for large and complex systems where independent delivery, scalability and team autonomy justify the additional complexity.
