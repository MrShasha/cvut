# Software Architecture Basics

> **Zkouškový fokus:** pochopit definici software architecture, rozdíl architecture/design, stakeholdery, quality attributes, architecture decisions a základní design principles.

## 1. Co je software architecture

**Software architecture** popisuje základní strukturu softwarového systému na nejvyšší úrovni.

Neřeší každý detail implementace, ale hlavně:

```text
jaké hlavní části systém má
jaké jsou jejich odpovědnosti
jak spolu komunikují
jak jsou nasazeny
jak systém splňuje funkční a nefunkční požadavky
```

Zjednodušeně:

> Software architecture is the big picture of the system.

Architektura ukazuje, **kde se co děje**, ale nemusí detailně ukazovat, **jak přesně je to naprogramované**.

Například u e-shopu architektura může říkat:

```text
Frontend komunikuje s backendem přes REST API.
Backend je rozdělen na vrstvy controller-service-repository.
Data jsou uložena v relační databázi.
Autentizace je řešena pomocí JWT.
Systém běží v kontejnerech za reverse proxy.
```

Ale architektura už nemusí popisovat každý konkrétní řádek kódu nebo každou pomocnou metodu.

## 2. Architecture vs Design

Architektura a design spolu souvisí, ale nejsou totéž.

### Architecture

Architektura:

```text
mění se pomalu
mluví o komponentách, službách, vrstvách a uzlech
řeší komunikaci mezi částmi systému
řeší nejdůležitější technická rozhodnutí
má velký dopad na kvalitu systému
```

Příklad architektonického rozhodnutí:

```text
Systém bude monolit.
Systém bude rozdělen na microservices.
Služby budou komunikovat asynchronně přes message broker.
Backend bude rozdělen do layered architecture.
```

### Design

Design:

```text
mění se rychleji
mluví spíš o třídách, rozhraních a metodách
řeší opakující se implementační problémy
často se mění refactoringem
```

Příklad designového rozhodnutí:

```text
Použijeme Strategy pattern pro výběr platební metody.
Repository bude implementováno přes DAO.
Service dostane závislosti přes dependency injection.
```

### Bezpečná formulace ke zkoušce

> Architecture řeší hrubou strukturu systému, hlavní komponenty, jejich odpovědnosti, komunikaci a nasazení. Design je detailnější úroveň, která řeší konkrétní třídy, rozhraní, metody a implementační vzory. Hranice mezi nimi nemusí být vždy ostrá, ale architektura má obvykle větší dopad na dlouhodobou kvalitu systému.

## 3. Proč je software architecture důležitá

Dobrá architektura je důležitá hlavně u větších systémů, protože pomáhá řídit složitost.

Ovlivňuje například:

```text
consistency of design
development costs
maintenance costs
technical debt
number of defects
team organization
integration with other systems
extendability
scalability
performance
deployment
security
testability
```

### 3.1 Development

Dobře navržený systém se lépe rozšiřuje.

Když je systém chaotický:

```text
nové feature se přidávají pomalu
každá změna může rozbít jinou část systému
debugging je těžší
testování je těžší
technický dluh roste
```

Dobrá architektura dává vývojářům jasné hranice:

```text
kam patří business logic
kam patří persistence
jak komunikovat s externími systémy
kde řešit validaci
kde řešit bezpečnost
```

### 3.2 Maintenance

V praxi se často více času utratí za údržbu než za prvotní vývoj.

Proto architektura musí počítat s tím, že systém se bude měnit:

```text
nové požadavky
nové integrace
změna databáze
větší provoz
bezpečnostní požadavky
změna týmu
```

Architektura by tedy neměla být navržena jen pro aktuální stav, ale i pro rozumnou evoluci systému.

### 3.3 Communication

Architektura je také komunikační nástroj.

Pomáhá komunikovat mezi:

```text
vývojáři
architekty
manažery
zákazníkem
testery
DevOps týmem
security týmem
```

Například diagram komponent může rychle ukázat, jak spolu části systému komunikují, aniž by člověk musel číst celý kód.

### 3.4 Risk management

Architektura pomáhá odhalit rizika ještě před implementací.

Příklad:

```text
Požadavek: systém musí zvládnout 10 000 requestů za sekundu.

Špatný přístup:
nejdřív vše naprogramujeme a pak zjistíme, že databáze nestíhá.

Lepší přístup:
už při návrhu řešíme caching, load balancing, horizontální škálování,
databázové indexy, fronty nebo read modely.
```

## 4. Architecture as a bridge between requirements and code

Architektura je mezivrstva mezi požadavky a implementací.

```text
requirements → architecture → design → code
```

Požadavky říkají, **co systém má dělat**.

Architektura říká, **jak bude systém na vysoké úrovni uspořádán**, aby tyto požadavky splnil.

Kód je konkrétní implementace těchto rozhodnutí.

Příklad:

```text
Requirement:
Users must be able to upload and download large files.

Architectural decision:
Files will not be stored directly in the database.
They will be stored in object storage.
Database will store only metadata and object keys.

Code:
Implementation of storage service, repository, upload handler, etc.
```

## 5. Stakeholders

**Stakeholders** jsou lidé nebo skupiny, které mají zájem na výsledném systému.

Každý stakeholder má jiné priority.

### 5.1 End users

Uživatelé často neřeší vnitřní architekturu.

Zajímá je:

```text
systém funguje
je rychlý
je dostupný
je jednoduchý na použití
nedělá chyby
```

### 5.2 Clients / customers

Zákazníci řeší:

```text
jestli systém splňuje business cíle
jestli se dá rozšiřovat
kolik stojí vývoj
kolik stojí provoz
jestli je systém bezpečný
```

### 5.3 Project managers

Project manager potřebuje architekturu hlavně kvůli:

```text
odhadu rizik
plánování práce
rozdělení týmu
kontrole rozsahu
sledování technického dluhu
```

### 5.4 Developers

Vývojáři potřebují architekturu jako vodítko:

```text
kam psát nový kód
jaké vrstvy nebo moduly existují
jaké závislosti jsou povolené
jak komunikovat mezi komponentami
jaké technologie se mají používat
```

### 5.5 Operations / DevOps

DevOps tým řeší:

```text
deployment
monitoring
logging
scaling
configuration
fault recovery
infrastructure
```

## 6. Architecture characteristics / quality attributes

Architektura se neposuzuje jen podle toho, jestli systém “funguje”.

Důležité jsou také **quality attributes**, tedy kvalitativní vlastnosti systému.

Typické quality attributes:

```text
availability
reliability
performance
scalability
elasticity
security
maintainability
modifiability
testability
usability
interoperability
portability
recoverability
```

### 6.1 Functional vs non-functional requirements

Functional requirements říkají, co systém dělá.

Příklad:

```text
User can register.
User can create an order.
Admin can manage products.
```

Non-functional requirements říkají, jak dobře to systém dělá.

Příklad:

```text
System must respond within 200 ms.
System must be available 99.9 % of the time.
System must support 500 concurrent users.
System must encrypt sensitive data.
```

Architektura má často větší dopad právě na nefunkční požadavky.

---

## 7. Architecture is about trade-offs

Neexistuje jedna nejlepší architektura pro všechny systémy.

Architektura je vždy kompromis mezi různými požadavky.

Příklad:

```text
Microservices:
+ independent deployment
+ better scalability of individual services
+ team autonomy

- higher operational complexity
- harder testing
- distributed communication problems
- data consistency problems
```

Monolith:

```text
+ simpler development
+ easier debugging
+ simpler deployment
+ easier transactions

- harder independent scaling
- harder team separation
- can become too large
```

Proto je bezpečné říct:

> Software architecture is not about finding the perfect solution. It is about finding the least bad solution for a specific context.

## 8. Architecture decisions

**Architecture decision** je důležité technické rozhodnutí, které ovlivňuje strukturu systému.

Architecture decisions jsou spíš pravidla, která vývojáři musí dodržovat.

Příklady:

```text
Business layer must not access the database directly.
All database access must go through repositories.
Services communicate only through public APIs.
Sensitive data must be encrypted at rest.
All external APIs must be documented using OpenAPI.
```

Dobré architecture decisions by měly být:

```text
explicitní
zdokumentované
odůvodněné
kontrolovatelné
srozumitelné pro tým
```

### ADR

Často se používá forma **ADR — Architecture Decision Record**.

Jednoduchá struktura ADR:

```text
Title
Context
Decision
Consequences
Alternatives
Status
```

Příklad:

```text
Title:
Use PostgreSQL as primary database

Context:
The system needs relational consistency and complex queries.

Decision:
We will use PostgreSQL as the main database.

Consequences:
+ strong SQL support
+ mature transactions
- horizontal scaling is harder than with some NoSQL databases
```

## 9. Design principles

Design principles jsou obecnější doporučení, ne vždy tvrdá pravidla.

Typické principy:

```text
KISS
YAGNI
DRY
Separation of Concerns
High Cohesion
Loose Coupling
Encapsulation
Dependency Inversion
Don’t talk to strangers / Law of Demeter
```

### 9.1 KISS

**Keep It Simple, Stupid**

Systém by měl být co nejjednodušší, ale stále musí splnit požadavky.

Špatně:

```text
Použijeme Kubernetes, microservices, Kafka a service mesh pro malou školní aplikaci.
```

Lépe:

```text
Začneme jednoduchým monolitem s jasnými moduly.
```

### 9.2 YAGNI

**You Aren’t Gonna Need It**

Nemáme implementovat funkcionalitu nebo architektonickou složitost jen proto, že by se možná někdy hodila.

Příklad:

```text
Nepřidávat plugin systém, pokud zatím není jasný požadavek na pluginy.
```

### 9.3 DRY

**Don’t Repeat Yourself**

Duplicitní logika zvyšuje riziko chyb.

Příklad:

```text
Validace stejného business pravidla by neměla být zkopírovaná ve třech různých services.
```

Pozor: v microservices může být určitá duplicita lepší než silné sdílení knihoven, které services příliš sváže.

### 9.4 Separation of Concerns

Každá část systému má mít jasnou odpovědnost.

Příklad ve vrstvené architektuře:

```text
Controller řeší HTTP request/response.
Service řeší business logic.
Repository řeší persistence.
```

### 9.5 High cohesion, loose coupling

**High cohesion** znamená, že věci, které patří k sobě, jsou pohromadě.

**Loose coupling** znamená, že části systému nejsou zbytečně silně závislé jedna na druhé.

Dobře:

```text
OrderService pracuje s objednávkami.
PaymentService pracuje s platbami.
Komunikují přes jasné rozhraní.
```

Špatně:

```text
OrderService přímo mění interní databázové tabulky PaymentService.
```

## 10. System structure

Dobrá architektura musí mít jasnou strukturu.

Struktura může obsahovat:

```text
components
connectors
interfaces
layers
services
databases
deployment nodes
external systems
communication protocols
```

Systém může kombinovat více stylů.

Příklad:

```text
Aplikace může být monolit,
uvnitř používat layered architecture,
pro import dat používat pipes and filters,
a s externími systémy komunikovat přes REST API.
```

Architektura by měla být dokumentovaná:

```text
component diagrams
deployment diagrams
sequence diagrams
API documentation
architecture decision records
README files
UML diagrams
OpenAPI specifications
```

## 11. Standards and models used in SWA

Standardy a modely pomáhají architekturu popsat, vyhodnotit a komunikovat.

### 11.1 UML

**UML** je běžný modelovací jazyk pro popis systému.

Užitečné diagramy:

```text
class diagram
component diagram
sequence diagram
activity diagram
state diagram
deployment diagram
use-case diagram
```

Příklad použití:

```text
Class diagram:
ukazuje hlavní doménové třídy a vztahy.

Sequence diagram:
ukazuje komunikaci objektů nebo komponent v čase.

Deployment diagram:
ukazuje, kde systém běží fyzicky nebo logicky.
```

### 11.2 ISO/IEC 25010

**ISO/IEC 25010** je quality model pro hodnocení softwarového produktu.

Obsahuje například:

```text
functional suitability
performance efficiency
compatibility
usability
reliability
security
maintainability
portability
```

Pro SWA je důležitý hlavně proto, že připomíná, že kvalita systému není jen “funguje/nefunguje”.

### 11.3 OpenAPI / Swagger

**OpenAPI** slouží k popisu REST API.

Pomáhá:

```text
dokumentovat endpointy
popsat requesty a response
generovat klienty nebo servery
testovat API
kontrolovat kompatibilitu API
```

Příklad:

```text
GET /users/{id}
POST /orders
DELETE /products/{id}
```

### 11.4 REST constraints

REST je architektonický styl pro webové API.

Základní constraints:

```text
client-server
stateless
cacheable
uniform interface
layered system
code on demand optional
```

REST není jen “JSON over HTTP”. REST znamená dodržování architektonických omezení, která podporují škálovatelnost, jednoduchost a interoperabilitu.

## 12. Design guidelines for software architecture

Při návrhu architektury je dobré postupovat systematicky.

### 12.1 Start from requirements

Nejdřív je potřeba pochopit:

```text
functional requirements
quality attributes
business constraints
technical constraints
team skills
budget
deployment environment
security requirements
integration requirements
```

### 12.2 Identify architecturally significant requirements

Ne každý požadavek je architektonicky významný.

Architecturally significant requirement je požadavek, který má velký dopad na strukturu systému.

Příklad:

```text
System must support 10 users.
```

To nemusí změnit architekturu.

Ale:

```text
System must support 1 million users.
System must be available 99.99 %.
System must process payments securely.
System must integrate with many external systems.
```

To už architekturu silně ovlivňuje.

### 12.3 Prioritize quality attributes

Nelze maximalizovat všechno.

Příklad konfliktu:

```text
maximum security vs usability
maximum consistency vs availability
maximum performance vs maintainability
maximum flexibility vs simplicity
```

Proto je potřeba určit priority.

### 12.4 Prefer simplicity

Architektura by neměla být zbytečně složitá.

Bezpečná věta:

> If a simpler architecture satisfies the requirements and quality attributes, it is usually better than a more complex one.

### 12.5 Document decisions

Architektonická rozhodnutí musí být zdokumentovaná, jinak se ztratí jejich důvod.

Důležité je dokumentovat nejen co bylo rozhodnuto, ale i proč.

### 12.6 Validate architecture

Architektura by se měla ověřovat:

```text
review
prototype
load test
security review
quality attribute scenarios
ATAM
proof of concept
```

## 13. Example: architecture decision and quality attributes

Představme si systém pro online objednávky.

### Requirement

```text
Customers can create orders.
System must handle traffic peaks.
System must be easy to maintain.
System must be secure.
```

### Possible architecture

```text
Layered modular monolith
PostgreSQL database
REST API
JWT authentication
Redis cache for selected read operations
Docker-based deployment
```

### Why this can be good

```text
Layered structure improves maintainability.
PostgreSQL supports transactions.
REST API improves interoperability.
JWT supports stateless authentication.
Redis can improve read performance.
Docker improves deployment repeatability.
```

### Trade-off

```text
This architecture is simpler than microservices,
but it does not allow independent deployment of every business capability.
```

## 14. Časté chyby v architektuře

### 14.1 Overengineering

Příliš složitá architektura pro jednoduchý problém.

Příklad:

```text
Malá CRUD aplikace je rozdělena na 20 microservices.
```

Problém:

```text
více deploymentu
více konfigurace
více síťové komunikace
těžší debugging
vyšší náklady
```

### 14.2 Big Ball of Mud

Systém nemá jasnou strukturu.

Typické symptomy:

```text
všechno závisí na všem
není jasné, kam psát nový kód
business logic je v controllerech, repository i UI
změna v jedné části rozbije jinou část
```

### 14.3 Golden Hammer

Tým používá jednu oblíbenou technologii nebo styl na všechno.

Příklad:

```text
Použijeme microservices pro každý projekt, protože microservices jsou moderní.
```

### 14.4 God Object

Jedna třída nebo komponenta ví příliš mnoho a dělá příliš mnoho.

Příklad:

```text
ApplicationManager řeší uživatele, objednávky, platby, logování i databázi.
```

Problém:

```text
těžké testování
těžké změny
vysoká coupling
nízká cohesion
```

### 14.5 Spaghetti Code

Kód nemá jasnou strukturu a řízení toku je chaotické.

Typické symptomy:

```text
mnoho skrytých závislostí
nejasné side effects
obtížné ladění
změny vytvářejí nové chyby
```

### 14.6 Lava Flow

V systému zůstává starý, mrtvý nebo nepochopený kód, který se nikdo nebojí odstranit.

Problém:

```text
vyšší složitost
nejasná odpovědnost
horší údržba
riziko chyb při změnách
```

### 14.7 Copy-Paste Programming

Logika se kopíruje místo toho, aby byla vhodně abstrahována.

Problém:

```text
chyba se musí opravit na více místech
kopie se časem začnou lišit
systém je hůř udržovatelný
```

### 14.8 Ignoring quality attributes

Tým řeší jen funkcionalitu, ale ignoruje:

```text
performance
security
availability
maintainability
testability
```

Výsledkem je systém, který sice něco dělá, ale nejde ho provozovat, měnit nebo bezpečně používat.

## 15. Zkoušková odpověď: What is software architecture?

Software architecture is the high-level structure of a software system. It defines the main elements of the system, their responsibilities, externally visible properties, interfaces, relationships, communication and deployment. It does not describe every implementation detail, but it gives the big picture of how the system works.

Architecture is important because it influences development costs, maintenance, technical debt, scalability, security, reliability, testability and the ability of the system to evolve. It also supports communication between stakeholders and helps developers understand where new functionality should be implemented.

A good architecture is not universally good in every context. It must be evaluated against functional requirements, quality attributes and business constraints. Therefore architecture is mainly about trade-offs. The best architecture is usually the simplest architecture that satisfies the important requirements and quality attributes of the given system.
