## Úvod

Problém: ze 3D scény s N objekty a P pixely najdi pro každý pixel nejbližší objekt.

Dva základní pohledy:

- **Image space:** rozhoduje se pro pixely nebo oblasti obrazu → z-buffer, ray casting, Warnock, scanline.
- **Object space:** pracuje s pořadím a vzájemnými vztahy geometrie → depth-sort malířova algoritmu, BSP. Výsledná geometrie se nakonec stejně rasterizuje.

Konkrétní složitost závisí na algoritmu a akceleračních strukturách; nelze ji pro celou skupinu obecně shrnout jediným `O(P·N)` nebo `O(N²)`.

## Z-buffer [Catmull 1975]

**Princip:** dvě pole – `z_buffer[x,y]` + `color_buffer[x,y]`. Objekty v libovolném pořadí.

```
pro každý fragment (x, y, z):
  if z < z_buffer[x][y]:
    z_buffer[x][y] = z
    color_buffer[x][y] = shade(fragment)
```

### Hloubka a přesnost

Po perspektivní projekci: `z'' ~ 1/z` (proporcionální převrácené hodnotě, ne lineární).  
Důvod: perspektivní dělení homogenní souřadnicí `w ~ z`.

Důsledek: blízké objekty mají velké rozlišení hloubky, vzdálené jsou nacpány do úzkého pruhu.

```
near=0.01, far=10 → 90 % hodnot z-bufferu mezi 0.01–0.1
near=1,    far=10 → 50 % hodnot mezi 1.0–1.8  ← lepší
```

Pravidlo: `far/near` co nejmenší. `near` co nejdál od nuly.  
Median rozlišení = `2·near·far / (near + far)`

### Problémy

- **Z-fighting:** dva koplanární povrchy daleko od kamery → stejná `z''` hodnota → flickering
- **Overdraw:** rasterizuje i zakryté fragmenty, zahazuje až po z-testu
- **Průhlednost:** zapíše jen nejbližší fragment → průhledné objekty nelze přímo kompozitovat

### Řešení z-fightingu

1. Správné nastavení `near` (nejčastější chyba: `near=0.001`)
2. `glPolygonOffset(factor, units)` – mírný posun `z''` koplanárních povrchů
3. **Reverse-Z:** mapování `z → [1,0]` místo `[0,1]` → lepší přesnost pro vzdálené objekty
4. 32-bit float depth buffer místo 24-bit int

### GPU optimalizace

- **Early z-test:** z-test před fragment shaderem (výchozí na moderních GPU, vypnuté pokud shader modifikuje `gl_FragDepth`)
- **Z-cull:** zmin/zmax pro 8×8 bloky pixelů → zahod celý blok

### Perspektivně korektní interpolace atributů

Hloubka i ostatní atributy po perspektivní projekci nejsou ve screen space obecně lineární. Pro atribut `a` se přes trojúhelník interpolují hodnoty `a/w` a `1/w`, poté se provede rekonstrukce:

```text
a = interpolované(a/w) / interpolované(1/w)
```

Stejný princip se používá pro UV souřadnice v texture mappingu.

### Průhledné objekty

Neprůhlednou část scény vykreslíme běžně se zápisem do z-bufferu. Průhledné povrchy se poté typicky řadí odzadu dopředu, používají depth test, ale nezapisují novou hloubku. Obecné vzájemně se protínající průhledné plochy vyžadují order-independent transparency, například A-buffer.

> [!note] 🧠 Matějův příprdek
Renderování **odzadu dopředu stačí**, pokud lze průhledné plochy jednoznačně seřadit pro celý obraz. To platí například pro několik oddělených skleněných tabulí.
>
>Problém nastane, když se plochy:
>- protínají,
>- cyklicky překrývají,
>- nebo se jejich pořadí mění pixel od pixelu.

### A-buffer [Carpenter 1984]

Řeší průhlednost: místo jedné hloubky na pixel ukládá **seznam všech fragmentů**, který se při výsledné kompozici seřadí podle hloubky.  
Ukládá: hloubku, barvu, průhlednost, masku pokrytí 4×4, ID objektu, normálu.  
Renderovací průchod: kompozice odpředu dozadu. Základ RenderMan (Pixar).

## Malířův algoritmus [Newell 1972]

Renderuj **odzadu dopředu** – vzdálenější přepsáno bližším. Nevyžaduje z-buffer.

### Depth sort

1. Seřaď polygony podle `zmax`
2. Nejvzdálenější = kandidát P1, testuj vůči ostatním P2:

|Test|Podmínka|Výsledek|
|---|---|---|
|1. Depth overlap|z-rozsahy se nepřekrývají (`z1max < z2min`)|vykresli P1|
|2. XY-projection overlap|průměty v XY se nepřekrývají|přejdi na další patch|
|3. P2 before P1|P2 celý na přivrácené straně roviny P1|přejdi na další patch|
|4. P1 behind P2|P1 celý na odvrácené straně roviny P2|přejdi na další patch|

Všechny 4 testy selhaly → **prohození** (P2 = nový kandidát).  
Detekován cyklický překryv → **řezání polygonů** rovinou.

**Problémy:** overdraw, cyklické překryvy, vlastní průsečíky.  
**Použití dnes:** 2D vrstvy (Photoshop, CSS z-index).

## BSP strom (Binary Space Partitioning)

Rekurzivní dělení prostoru rovinami polygonů scény.

**Dvě fáze:**

1. **Konstrukce** (1× předzpracování) – polygony se při potřebě rozřežou → eliminace cyklických překryvů
2. **Průchod každý frame** – automatické pořadí odzadu dopředu

**Průchod:** v každém uzlu otestuj kameru vůči dělící rovině:

```
dot(kamera - bod_na_rovině, normála) > 0  → kamera před rovinou
                                    < 0  → kamera za rovinou
```

Nejdřív vzdálenější větev, pak bližší → korektní pořadí bez dalších testů.

**Výhoda oproti malířovu:** rozdělení geometrie odstraní cyklické překryvy a při vykreslení nejsou potřeba opakované párové testy polygonů; zůstává jen průchod stromem a test kamery vůči dělícím rovinám.  
**Nevýhoda:** předzpracování, statická scéna (pohyb = rebuild).  
**Použití:** Quake engine, portálové systémy.

## Warnockův algoritmus [Warnock 1969]

Divide-and-conquer na obrazovém prostoru. Rekurzivně dělí oblast na čtvrtiny.

Pro každou oblast jeden ze 4 případů:

1. Žádný objekt → barva pozadí
2. Jeden objekt → vykresli
3. Více objektů, jeden jednoznačně blíž (zakrývá celou oblast) → vykresli jen bližší
4. Nejasné → rekurzivně rozděl na 4

Rekurze zastaví na úrovni **jednoho pixelu**.

**Problém:** pro komplexní scény degeneruje až na pixel level → rekurze velmi hluboká, režie navíc oproti z-bufferu.

## Scanline algoritmus [Watkins 1970]

Řeší viditelnost řádek po řádku.

```
pro každý scan line Y:
  najdi průsečíky primitiv s řádkem → spans
  rozděl na elementární spans (průsečíky spans)
  pro každé elementární span najdi nejbližší Z
  obarvi
```

**Klíčová optimalizace – koherence:** průsečíky polygonu se scan linem se inkrementálně updatují mezi sousedními řádky → žádný přepočet od nuly.

Předchůdce z-bufferu. Z-buffer zjednodušil: místo řazení spans jen porovnáváš hloubku fragmentu.

## Ray casting [Appel 1968]

Pro každý pixel vyšli paprsek, najdi nejbližší průsečík.

```
ray_origin = o
ray_dir = Normalize(a + x/width·s + y/height·t - o)
```

Bez akcelerační struktury: `O(R·N)`. S dobře vyváženou BVH/kd-strukturou bývá typická cena výrazně nižší a často se aproximuje jako `O(R·log N)`, nejhorší případ však může zůstat lineární.

**Akcelerační struktury:** BVH, kd-strom, octree, 3D mřížka.  
**Dynamické scény:** kd-strom obvykle vyžaduje nákladnou aktualizaci nebo rebuild. BVH lze často levně **refitovat** změnou bounding boxů a teprve při výrazném zhoršení struktury znovu postavit.

## Z-buffer vs. Ray casting

||Z-buffer|Ray casting|
|---|---|---|
|Iteruje přes|objekty → pixely|pixely → objekty|
|Typická koherence|dobrá prostorová a paměťová koherence rasterizace|nepravidelné přístupy paprsků, lze zlepšit tříděním|
|Potřeba předzpracování|✗|✓ BVH/kd-strom|
|Zahazování zakrytých obj.|✗ až po rasterizaci|✓ BVH přeskočí větve|
|Dynamické scény|✓ velmi vhodný|BVH refit/rebuild, záleží na míře změn|
|Mnoho překryvů|správný výsledek, ale možný vysoký overdraw|nejbližší zásah se hledá při průchodu strukturou|

Z-buffer je přirozenou volbou pro interaktivní rasterizaci dynamických scén. Ray casting je výhodný tam, kde lze dobře využít prostorovou akceleraci a potřebujeme přirozeně pracovat s paprsky, například u složité viditelnosti nebo ray tracingu.
